**难度**：简单 ｜ **状态**：✅ 已重写并 AC（2026-08-29） ｜ **目录**：[0121-BestTimeToBuyAndSellStock](../LeetCode/0121-BestTimeToBuyAndSellStock/)

### 我的错误思路

从右往左遍历，分别记录**全局最高价日**（max）和**全局最低价日**（min），最后用 `prices[max] - prices[min]` 算利润；发现 max 在 min 前面（时间倒流）就返回 0。

### 为什么错

- **模型错误**：最优交易不一定用全局最高/最低价。全局高低点配对后只能验证「这一对」行不行，会错过其他合法组合里更赚钱的交易。
- **补丁救不了**：尝试「只在发现新低时重算利润」「max 更新时也重算」都失败——前者漏算，后者又造出时光倒流。**模型错了，修补无意义，必须换思路。**

### 打脸反例

| 输入 | 期望 | 我的代码输出 | 原因 |
|---|---|---|---|
| `{5, 6, 1, 2}` | 1 | 0 | 最高(6)在最低(1)前面 → 误判无解，但买 1 卖 2 能赚 1 |
| `{3, 2, 6, 5, 0, 3}` | 4 | 0 或 6 | 全局对是「第2天6、第4天0」：直接算=时光倒流；返回0=漏掉 2→6 的合法交易 |

### 正确思路（一句话模型）

**一次从左到右遍历，维护两个变量**：
- `minPrice`：走到今天为止见过的最低价（历史最低买点）
- `result`：走到今天为止的最大利润（每天尝试「今天卖」）

为什么对：算 `prices[i] - minPrice` 时买点保证在卖点之前（合法）；而任何一笔合法交易的买点都不低于历史最低，所以最优解一定被覆盖。

### 教训

1. **「先配对再验证」≠「边走边维护」**：枚举每个卖出日、让买点自动取历史最低，合法性天然成立。
2. **示例通过 ≠ 正确**：LeetCode 示例太温柔，必须自己造边界反例。
3. **模型错了要果断换，别打补丁**：判断标准——修补两次还错，说明是思路问题不是实现问题。
4. **「遍历时维护历史极值」是通用模式**：485 的计数器、283 的零计数器、121 的历史最低价，全是这个套路。

## ⚠️ 错误 02：283. 移动零——边界条件漏测（2026-08-29）

**难度**：简单 ｜ **状态**：✅ 已修复 AC ｜ **目录**：[0283-MoveZeroes](../LeetCode/0283-MoveZeroes/)

### 我的错误

覆盖写法第一版：`nums[i - zero] = nums[i]; nums[i] = 0;` 无条件执行 else 分支。当 `zero == 0`（前面没有 0）时，`i - zero == i`，自己拷给自己再抹成 0，`{1,2,3}` 直接变 `{0,0,0}`。

我造的测试用例开头全是 0（`{0,1,0,3,12}`、`{0,0,1}`），走 else 时 zero 必然 ≥ 1，bug 被掩盖。

给「清零当前位」加条件：只在 `zero != 0` 时执行。

### 教训

- **测试用例必须覆盖边界**：有 / 无 / 全有（全 0、全非 0、零在中间、零在两头）。
- 示例通过就急着交，等于把 bug 留给 LeetCode 的隐藏用例帮我发现。

## ❌ 重点错误 03：53. 最大子数组和（2026-08-30，复盘日）

**难度**：中等 ｜ **状态**：✅ 已重写并 AC（2026-08-30） ｜ **目录**：[0053-MaximumSubarray](../LeetCode/0053-MaximumSubarray/)

### 📦 错误版本存档：commit `5263b6e`

### 我的错误思路

「贪心吸收」：先跳过开头的负数，遇到正数就累加；遇到负数就用内层 while 往后吞，直到累计和变正，把「桥梁段」整个加进 result。

### 为什么错

1. **全负数返回 0**：开头 while 把所有元素跳光，for 不执行，返回初始值 0。但题目要求子数组**至少含一个元素**，全负时必须返回最大的那个（如 `{-3,-1,-2}` → `-1`）。
2. **吸收负数前没和「重新开始」比较**：`{1,-3,4}` 吸收后总和是 2，不如扔掉前缀从 4 重新开始。贪心吸收只看「桥能不能搭成正的」，不看「搭桥值不值」。
3. **内层 while 修改外层 i + 中途 return**：控制流绕，正确性难分析——这本身就是危险信号。

### 打脸反例

| 输入 | 期望 | 我的输出 | 原因 |
|---|---|---|---|
| `{-2,1,-3,4,-1,2,1,-5,4}` | 6 | 5 | 桥接段吸收亏了没重来 |
| `{5,4,-1,7,8}` | 23 | 15 | 同上，-1 桥接把连续大段拆散 |
| `{-3,-1,-2}` | -1 | 0 | 全负数边界，跳光后返回 0 |

### 正确思路（提示，重写时用）

还是「遍历时维护历史信息」，但这次维护的量变了——
- 变量 A：**以今天结尾**的最大子数组和。每天二选一：延续昨天（A_prev + nums[i]）还是从今天重新开始（nums[i]）？**谁大选谁**。
- 变量 B：历史所有 A 的最大值。
- 这样「要不要为负数搭桥」的决策被简化成了每天一次的取大，且天然处理全负数。

### 教训

1. **「至少选一个」类的边界（全负/全零/空）必须在第一版就想到**——我在骨架注释里专门标了全负数测试，结果还是错了它。
2. **贪心策略要证明「局部最优=全局最优」才能用**：吸收负数是局部看似合理，全局可能亏。
3. **内层循环改外层变量 + 中途 return 是坏味道**：写出来控制流就已经在报警了。

## ❌ 重点错误 04：88. 合并两个有序数组（2026-09-01，机动日）

**难度**：简单 ｜ **状态**：✅ 已重写并 AC（2026-09-01） ｜ **目录**：[0088-MergeSortedArray](../LeetCode/0088-MergeSortedArray/)

### 📦 错误版本存档：commit `10b6fe0`

### 我的错误思路

双层循环从后往前：外层倒序遍历 nums2（取一个待插入数），内层倒序扫 nums1 有效位——nums1 的元素更大就右移腾位；否则把 nums2[i] 放下并 break。

### 为什么错

**漏了第三条路**：当 nums1 的有效元素全部比 nums2[i] 大时，内层 j 一路右移直到走完，**没有任何分支把 nums2[i] 放进去**——这个数凭空消失。

结构性缺陷：整个循环不保证「每步恰好放置一个元素」。原地合并/填充类题目的正确姿势是：每个指针每走一步，必须有一个值落到最终位置。

### 打脸反例

| 输入 | 期望 | 我的输出 | 原因 |
|---|---|---|---|
| `nums1={3,0,0}` m=1，`nums2={1,2}` | 1,2,3 | 3,3,0 | 3 比两个数都大，1 和 2 没人放 |
| `nums1={1,2,7,0,0}` m=3，`nums2={0,8}` | 0,1,2,7,8 | 1,1,2,7,8 | 7 右移两次后 j 走完，0 丢失 |

### 正确思路（提示，重写时用）

三个指针各管一头，**每步必放一个值**：
- `i = m-1`（nums1 有效尾）、`j = n-1`（nums2 尾）、`k = m+n-1`（填充位）
- 每步只比较：`nums1[i]` 和 `nums2[j]` 谁大？大的放进 `nums1[k]`，k 和对应指针一起左移
- 收尾：谁先走完，就把另一方剩下的整体搬过去（此时 k 位置正好对齐，不用想复杂）
- 副产品：`m=0` 的特判不再需要——想想为什么（答案：i 从 -1 开始时第一个 while 天然跳过，收尾 while 会把 nums2 全搬进去）

### 教训

1. **原地填充类题目的自检清单：每个指针每一步，必须恰好落一个值**——多放、少放、跳过都是结构性 bug。
2. **第三次靠自造反例救场**（283 的 `{1,2,3}`、121 的两组、这次 t4）：题目给的测试永远不够，写完先自己当测试员。
3. **好的结构能消掉特判**：需要 `if (m==0)` 之类的补丁时，先想想换结构能不能让它自然消失。

## ❌ 重点错误 05：顶层方法重载报错（2026-09-03，方法进阶练习）

**难度**：练习 1 ｜ **状态**：✅ 已修复 ｜ **目录**：[2026/09/03/AdvancedMethods](../CSharpPractice/2026/09/03/AdvancedMethods/)

### 我的错误

在顶层文件直接写了三个同名 `static int Max(int,int)` / `static double Max(double,double)` / `static int Max(int,int,int)` 想做重载 → 编译错误 **CS0128：已在此范围定义了名为 Max 的局部变量或函数**。

### 为什么错（连环三坑）

1. **CS0128**：顶层方法其实是**本地函数（local function）**，而本地函数**不支持重载**——重载是「类成员」的特权。之前的方法都不同名所以没暴露。
2. **CS8803**：把 `static class Tools` 放到了文件开头——顶层程序的规则：**可执行语句必须全部在类型声明之前**。
3. **CS0122**：类成员不写访问修饰符默认 `private`，外面的顶层语句访问不到——工具方法必须加 `public`。

### 正确结构

```csharp
// ① 顶级语句区（最上面）：调用示例
Console.WriteLine(Tools.Max(3, 5));

// ② 类型声明区（文件底部）
static class Tools
{
    public static int Max(int a, int b) { ... }
    public static double Max(double a, double b) { ... }
    public static int Max(int a, int b, int c) { ... }
}
```

连带修复的逻辑 bug：`Factorial` 基准情况 `else return 0` → `0! = 1`，终止条件的返回值错 = 全链全错；返回值改 `long`（int 在 13! 溢出）。

### 教训

1. **重载 = 类成员特权，本地函数做不到**——想把一组同名方法组织起来，包个类（这就是 `Math.Max` 的真身：类里的 public static 重载群）。
2. **顶层程序文件结构铁律**：语句在前，类型声明在后。
3. **类成员默认 private**——「外部要调」就必须显式 `public`（LeetCode 模板的 public 谜底揭晓）。
4. **递归基准情况的返回值和条件同样重要**：`0! = 1` 不是 `0`。

## ⚠️ 错误 06：82 删除重复元素 II——盲写漏跨接行 + 测试形状盲区（2026-09-13 复盘日）

**难度**：中等 ｜ **状态**：✅ 已修复并补测试 ｜ **目录**：[0082-RemoveDuplicatesFromSortedListII](../LeetCode/0082-RemoveDuplicatesFromSortedListII/)

### 盲写时的错

漏掉 `prev.next = cur;`（跳过整族重复后的**跨接**）——但**4 组测试全部通过**。

### 为什么全绿（假象推演）

- 重复族后面若还有非重复节点 → 下一轮 `else` 分支的 `prev.next = cur` 会**碰巧补接**
- `{1,1}` 全重复 → cur 跳到 null 循环结束，`dummy.next` 从没赋值恰好是 null → 输出空 ✓（碰巧对）
- **所有用例的重复族都在中间，从没测过“重复族在末尾”**

### 打脸反例（复盘日新增 t5/t6/t7 后现形）

| 输入 | 期望 | 漏行版输出 | 原因 |
|---|---|---|---|
| `{1, 2, 2}` | `1` | `1→2` | 末尾整族跳过后 cur = null，再无人补接 → 悬尾 |
| `{1, 1, 2, 2}` | （空） | 全重复，恰好对 | 碰巧 |
| `{1, 2, 3, 3, 4, 4}` | `1→2` | `1→2→3→4` | 末尾连续两个族都留了尾巴 |

### 正确做法

`if` 分支跳过整族后**立即** `prev.next = cur`（链任何时刻都完整）；`else` 分支再赋一次同值是**幂等冗余**，无害。

> 等价优化版（只在 else 接 + 循环后 `prev.next = null` 断悬尾）已作为注释写在题目文件里，供复习对照——但**不推荐启用**：把“冗余赋值”换成“必须记得收尾”不划算。

### 教训

1. **“碰巧对”≠“保证对”**：靠别处的分支恰好补接，是隐式依赖，不是正确性证明
2. **测试要穷举“形状”，不只是“值”**：重复族在开头/中间/**末尾**/全是/没有——形状覆盖不全，隐藏 bug 就永远测不出来（第三次栽在同一坑：283 的“开头无 0”、88 的“nums1 全大”）
3. **幂等的冗余是廉价的，被遗忘的收尾是昂贵的**

## ⚠️ 错误 07：232 用栈实现队列——盲写守卫条件写反（2026-09-13 复盘日）

**难度**：简单 ｜ **状态**：✅ 已修复 ｜ **目录**：[0232-ImplementQueueUsingStacks](../LeetCode/0232-ImplementQueueUsingStacks/)

### 盲写时的错

```csharp
public int Pop() {
    if (outStack.Count != 0) return 0;   // ❌ 有货反而返回 0
    while (inStack.Count != 0) outStack.Push(inStack.Pop());
    return outStack.Pop();
}
```

输出全变 `0`（期望 1/1/False/2/2/3/True…，实际 1/0/False/0/0/0/False…）。

### 为什么错

| outStack 状态 | 应该做什么 | 我写的 |
|---|---|---|
| **有货** | 栈顶就是队头，**直接用**，继续往下走 → `outStack.Pop()` | `return 0` **把正常情况当成了终止** |
| 空 | 才需要倒手 | while 倒手 ✓ |

`return` 在这里语义错位：**两种情况的终点都是 `outStack.Pop()`**，不存在“提前结束”的分支。

### 正确做法（二选一）

```csharp
// A：正着写条件，去掉提前 return
if (outStack.Count == 0) { while (inStack.Count != 0) outStack.Push(inStack.Pop()); }
return outStack.Pop();

// B：抽辅助方法（DRY——Pop/Peek 共用，规则只写一处）
private void EnsureOutHasItems() {
    if (outStack.Count != 0) return;   // "有货→什么都不用干"，这才是 return 的正确语义
    while (inStack.Count != 0) outStack.Push(inStack.Pop());
}
```

### 教训

1. **提前 return（卫语句）只用于“异常/终止”分支**——当所有分支最终都要走到同一句代码时，不该用 return
2. **判断守卫条件时先问“两个分支各自要干什么”**，再决定用 if / if-else / 提前 return
3. 盲写重现 + 抽辅助方法（DRY）——`Pop`/`Peek` 抄两遍倒手逻辑，将来改一处漏一处

## ⚠️ 错误 08：202 快乐数——三坑连踩（2026-09-16）

**难度**：简单 ｜ **状态**：✅ 已修复 + 网页 AC ｜ **目录**：[0202-HappyNumber](../LeetCode/0202-HappyNumber/)

### 我的错误版本

```csharp
while (true) {
    int temp = 0;
    while (n > 10) {              // ❌ 坑 2：丢个位
        temp += (n % 10) ^ 2;     // ❌ 坑 1：^ 是异或，不是乘方
        n /= 10;
    }
    n = temp;
    if (!judge.Add(n)) return false;   // 判环思路 ✓（`Add` 返回值一步查+登记）
    if (n == 1) return true;
}
```

**症状**：7 组测试**全部输出 False** —— 连 `19`、`1` 这种必然为真的都错。

### 三个坑

| # | 坑 | 为什么错 | 正解 |
|---|---|---|---|
| 1 | `(n % 10) ^ 2` | **C# 里 `^` 是位异或**：`9 ^ 2 = 11`（`1001 XOR 0010`）。Python 的 `**` 在 C# **不存在**（唯一的幂是 `Math.Pow`，返回 `double`，慢） | `int d = n % 10; temp += d * d;` |
| 2 | `while (n > 10)` | `n = 10` 时循环体不执行 → 十位丢了；`n = 7` 时**整个数字没参与计算** | `while (n > 0)` |
| 3 | 入口的 `n` 从未登记 | 结构是"先变换再登记"，`n = 1` 被算成 `0` 再登记 → 判错；判环也漏了起点 | 经典写法：`while (n != 1) { if (!seen.Add(n)) return false; n = 平方和(n); } return true;` |

> 坑 3 的细节：改完后"先变换再登记"在**值域有界**的本题**侥幸能跑对**（第 1 步之后的每个数都会进集合，环一定会被后续值撞上）——但这是**隐式依赖**，不是正确性证明。**"先登记当前值、再变换"才是防守型写法**，被检查的对象永远同一个、不漏起点。

### 教训

1. **C# 没有幂运算符**：`^ & | << >>` 全是**位运算符**，逻辑运算必须写 `&&` `||`。`^` 当乘方用是 **Python → C# 迁移的第一大坑**。
2. **取数位的循环终止条件是 `> 0`**：写 `> 10` 的潜台词是"只剩一位就不处理"，但每一位都要算。
3. **全 False ≠ 边界问题**：连"必然为真"的用例都错 → 说明是**核心逻辑**坏了。先分诊，别急着打补丁。
4. **"结果全错但能跑"的题，用单步打印**：`Console.WriteLine($"n={n}, temp={temp}")` → 一眼看到 `19` 走成 `11 → 3 → 0` 的死路，比盯代码快十倍（Unity 里同款手段是 `Debug.Log`）。
5. **`Add` 返回值一步完成"查 + 登记"**（217 学的）在本题迁移成功 ✓ —— 好模式会重复出现。

## ⚠️ 错误 09：205 同构字符串——单字典只守了一个方向的门（2026-09-17）

**难度**：简单 ｜ **状态**：✅ 已修复 + 网页 AC ｜ **目录**：[0205-IsomorphicStrings](../LeetCode/0205-IsomorphicStrings/)

### 我的错误版本（第一版）

只建了一个 `Dictionary<char,char>` 记录 `s→t`，每条 mapping "没见过就登记、见过就比对"。

**症状**：8 条测试里最后两条（`"ab"/"aa"` 之外的那类）**漏判为 True**。

### 为什么错

题目的两条规则**分属两个方向**，被我（和大多数人）当成了"同一件事的两个说法"：

| 规则 | 实际检查的 | 需要哪个方向的数据 |
|---|---|---|
| ① 同一字符始终映射到同一字符 | "s 里同一个 a 不能变心" | **s → t** |
| ② **不同**字符不能映射到同一字符 | "t 里同一个 x 不能被两个人抢" | **t → s** ← **反面！** |

**一个 Dictionary 只能守一个方向的门。**

### 打脸反例

`"badc"` / `"baba"`：

```
b → b（首次，登记）
a → a（首次，登记）
d → b（d 首次，登记）   ← 单方向认为没问题
c → a（c 首次，登记）   ← 依然没问题 → 误判 True
```
实际：`b` 和 `d` 两个不同字符都映射到 `b` → 违反规则② → 应为 **False**。
（前两条 `"ab"/"aa"`、`"foo"/"bar"` 能测出来，是因为它们**同一个 s 字符变了心**，属于规则①。）

### 正确做法

**两个 `Dictionary` 双向守门**（或一个 Dictionary + 一个 HashSet，分别管"谁映射过/谁被映射过"）：

```csharp
dict1[s[i]] = t[i];   // s → t 方向，管规则①
dict2[t[i]] = s[i];   // t → s 方向，管规则②
// 两边都是"先检查、不通过就 return false；通过才登记"
```

### 教训

1. **"同一个东西一致" 和 "不能撞车" 是两个方向的约束** —— 遇到"映射/对应"类问题先问：**要保证的是"函数"还是"双射"？**
2. **单字典 = 单向函数；双射必须两张表**（或一张表 + 一个集合）
3. **"首次出现就登记"的写法天然只检查一个方向** —— 因为"没见过的"永远没冲突可言，撞车只能从**另一个方向的视角**看出来
4. **推广**：数据库外键、缓存 key→value 的反查、`Dictionary<K,V>` 想按 value 反查 key——**全是同一个坑**

## ⚠️ 错误 10：219 存在重复元素 II——多写的"保险丝"剪掉了真答案（2026-09-21）

**难度**：简单 ｜ **状态**：✅ 已修复 + 网页 AC ｜ **目录**：[0219-ContainsDuplicateII](../LeetCode/0219-ContainsDuplicateII/)

### 我的错误版本

```csharp
public bool ContainsNearbyDuplicate(int[] nums, int k) {
    if (nums.Length < k) return false;   // ❌ 把"数组短"当成"没答案"
    Dictionary<int,int> dict = new Dictionary<int, int>();
    for (int i = 0; i < nums.Length; i++) {
        if (dict.TryGetValue(nums[i], out int n)) if (i - n <= k) return true;
        dict[nums[i]] = i;               // ✅ 无条件覆盖——这步是对的
    }
    return false;
}
```

**症状**：7 组用例**全部通过**（本地 9/9 是补了用例之后的事）。

### 为什么错

把"数组长度"和"距离上限 `k`"两个**不相干的量**硬扯在一起：长度短 **不代表**没有答案。

| 输入 | k | 正确输出 | 这行代码给出 | 说明 |
|---|---|---|---|---|
| `[1, 1]` | 5 | **true** | false | 两个 1 相距 1 ≤ 5 → 合法答案被**提前返回剪掉** |
| `[5, 5, 5]` | 100 | **true** | false | 同上 |

这类错误只在"合法的真答案"上触发 → **不报错、不崩、不越界**，安静地返回错值（**假失败 / false negative**）。

### 为什么 7 组用例全绿（假象推演）

我原本的短数组用例是 `[1], k=1` 和 `[], k=5` —— **它们的期望值本来就是 `false`**，所以那行错误代码**"因为错误的原因给出了正确答案"**，等于根本没过测试。这和错误 06（82 的测试形状盲区）是同一个病：**用例只覆盖了"值"，没覆盖"形状"**。

### 修复（二选一）

```csharp
if (nums.Length < 2) return false;   // A：对着【真不变量】—— "一对"至少需要两个元素
// B：直接删掉——循环从 i = 0 起，空数组天然不进循环，本就没有越界风险
```

### 教训

1. **保险丝要对准"不变量"，不对准"我觉得更安全"** —— 对比 09-19 `BrickSpawner` 里的 `cols * rows > 200`：那道防的是"手滑填 1000×1000 把编辑器搞假死"，是真实存在的不变量，该留；今天这行纯属凭感觉。
2. **测试用例要成对配**：既要有"**期望 false 的边界**"，也要有"**参数极端但期望 true 的反向用例**"（`[1,1], k=5`）。只测前者时，**所有多余的前置 `return` 都永远不会露头** —— 这是测试形状盲区的第三次复发（283 的"开头无 0"、82 的"重复族在末尾"、219 的"长度 < k 但为真"）。
3. **"假绿"有两副面孔**：**假 AC**（错值被当成对，如 219 的假 AC 陷阱）与**假失败**（真答案被剪掉，今天这种）。后者更隐蔽，因为它在"正常路径"上工作得好好的。
4. **冗余的防御代码是有成本的**：每一个提前 `return` 都是一次额外决策，都得能被证明是必要的。**写不写它，先问"这条不变量真的成立吗"。**

## ❌ 错误 13：169 多数元素——把"净票数"当成"出现次数"（2026-09-24）

**难度**：简单 ｜ **状态**：✅ 已修复 + 网页 AC ｜ **目录**：[0169-MajorityElement](../LeetCode/0169-MajorityElement/)

### 我的错误版本

```csharp
public int MajorityElement(int[] nums) {
    int times = 1;
    int result = nums[0];
    for (int i = 1; i < nums.Length; i++) {
        if (nums[i] == result) times += 1;
        else times -= 1;
        if (times == 0) result = nums[i + 1];      // ⚠️ 偷看下一个：末尾会越界
        if (times >= nums.Length / 2) return result;   // ❌ 把净票数当成出现次数
    }
    return result;
}
```

**症状**：给的 10 组用例**全部通过**（假 AC）——错误分支一次都没被踩到。

### 打脸反例

| 输入 | 期望 | 我的输出 | n/2 | 出错帧 |
|---|---|---|---|---|
| `[1,1,2,2,2]` | **2** | 1 | 2 | i=1 时 `times=2 >= 2` → 只读了 2 个元素就 return |
| `[1,1,1,2,2,2,2]` | **2** | 1 | 3 | i=2 时 `times=3 >= 3` |
| `[3,3,4,4,4]` | **4** | 3 | 2 | 同上 |

穷举验证（脚本模拟原算法）：**n = 2~11、取值 `{0,1,2}` 的全部合法输入**中，n≤8 就有 12 组反例，**全部同一类**——都由那行剪枝造成。

### 为什么错（最关键的一步推理）

`times` 是**净票数**（同阵营 +1 / 异阵营 −1，**随时会被抵消**），不是"`result` 出现了几次"。设当前 epoch 起点为 `s`，`c` = `result` 在 `nums[s..i]` 里的**出现次数**、`o` = 其余数字的次数，则**每一刻恒有**：

```
times = c − o
```

- 拆开看：`times` 只告诉你**"净胜多少票"**，`c` 才是"出现次数"。**未跑完时这两个量不是一回事。**
- `[1,1,2,2,2]` 那一帧的真相：`c − o = 2`（1 比杂兵净多 2 票），而 `c` 其实只有 2 —— **但真正的答案 2 还没上场**。

**为什么 Boyer–Moore 必须跑完全程**：正确性来自"抵消到底之后，多数元素必然还有剩"（每次同归于尽都要拿一个非 M 去换，而 m > n − m）。**这个结论是关于终点的**，中途的 `times` 不携带"谁最终会赢"的信息。

### 修复（`>=` → `>` 就对了，而且可证明）

剪枝写成 **严格 `>`** 后合法，证明只需一行：

```
times > n/2  ⟹  c = times + o > n/2 + 0 > n/2
（o ≥ 0）
```

而 `c` 只是**整个数组里 `result` 出现次数的下界** → `result` 出现超过 n/2 次 → 它就是多数元素。∎

**隔壁 `>=` 为什么塌**：`times >= n/2` 只能推出 `c >= n/2`——**"大于等于"不是"超过"**，`c = n/2` 时答案完全可以另有其人，而那一刻还没跑完、无从分辨。**所以是"严格大于"这半边在支撑 `o ≥ 0` 这个不等式。**

> 附带修掉的第二处：`result = nums[i + 1]` 的"偷看下一个"改成 `if (times == 0) result = nums[i];`——换人动作落回**当前下标**，两个下标的信息不再搅在一起（原写法让 n=1 之外的边界要靠"保证有众数"这条前提兜底，去掉前提后 `[1,2]` 直接越界）。

### 教训

1. **净票数 ≠ 出现次数**：`times = c − o`，它可增可减、随时被抵消；名字叫 `times` 会把人带偏——**变量名要写它的语义**（`netVotes` / `candidate` 比 `times` / `result` 安全得多）。
2. **剪枝必须能证明**：能证明的是 `>`，不能证明的是 `>=`——一字之差，一个对一个是 WA。**没有正确性证明的优化，就是主动埋雷。** 而且本题剪枝的收益是 **0**（还是 O(n)），属于"只在最好情况下有用、却让最坏情况也变复杂"。
3. **边界即证明**：`>=` 与 `>` 的区别不是"抠细节"，而是背后有没有一个能写出来的不等式。**能被证明的边界，才算写对了。**
4. **这是"多一个出口"的第三次复发**（错误 07 的提前 return 写反 → 错误 10 的前置 return 剪掉真答案 → 本次剪枝）。**出口越多，越容易有一条路径你没想到**——写之前先问："这个出口的不变量是什么？"
5. **测试形状盲区（第四次）**：给的 10 组用例里，多数元素在 `times` 摸到 `n/2` 那一刻**恰好总是领先**，所以错误分支永远不被触发。缺的形状是「**前半段票数虚高、后半段被反超**」——**代码里有几个分支，用例就该有几种形状**。

```csharp
}
```

### ⚠️ 顺带的陷阱：别用副作用掩盖逻辑漏洞

把 `Time.timeScale = 0` 恢复回来后，这个 bug **"看不见"了**（物理停了，球再也进不了 `FailZone`）。
**但那是"碰巧对"，不是修复** —— 用一个副作用掩盖了一个逻辑漏洞。哪天想做"结算慢动作"（`timeScale = 0.3`）或"庆祝动画"，bug 立刻复活。

**正确顺序**：先在 `End()` 上锁（**逻辑修复**），再恢复 `timeScale = 0`（**视觉表现**）。两件事分开做、分开验证。

### 教训

1. **入口上锁 ≠ 全局上锁**：守卫要放在**唯一出口**，以后加多少入口都只维护一处
2. **守卫的顺序**：`if (已结束) return;` 必须在 `标记结束 = true;` **之前**（写反了第一次都进不来 —— 错误 07 同款考点）
3. **"看起来管住了"是危险信号**：想清楚**有哪几条路径能到达这个状态**，比逐行读代码更重要

## ❌ 错误 16：一个空动画事件，让整个项目"保存不下去"（2026-09-25，Unity 工程）

**状态**：✅ 已修复 ｜ **文件**：`Projects/Unity/Breakout/Assets/Animation/OverlayFade.anim`

### 现象（它伪装成"崩溃"）

按 `Ctrl+S` **保存不了**；播放模式里黑幕不出现；整个游戏像"卡住"。
第一直觉是"动画做错了"或"Unity 崩了"。

### 真相链条（一层套一层，值得整条记住）

```
手滑点了动画窗口的「添加事件」按钮
  → Clip 里多了一个【空的 functionName】的动画事件（一共 6 个，全在 time:0【叠成一个点，界面上看不见】）
  → Clip 变成【坏数据】→ 控制台报 AnimationEvent has no function name
  → Unity【拒绝保存】这个 Clip
  → 连带【场景也存不下去】（磁盘上还是昨天 22:15 的版本）
  → 连带【Controller 也存不下去】（m_AnimatorLayers 还是 []）
  → 运行时自然什么都不发生
```

### 证据（两条，都是扒文件拿到的）

```yaml
# ① OverlayFade.anim 里的坏数据
  m_Events:
  - time: 0
    functionName:          # ← 空！

# ② Overlay.controller 是空壳
  m_AnimatorParameters: []
  m_AnimatorLayers: []     # ← 连一个图层都没有
```

### 为什么"预览能播、运行时不动"

| 场景 | 谁在干活 | 结果 |
|---|---|---|
| **动画窗口预览** | 编辑器**直接把 Clip 的属性值怼到物体上** | ✅ 不需要 Controller |
| **运行时** | `Animator` 组件**读 Controller 的状态机** | ❌ Controller 空 → 什么都不发生 |

> **"预览能播"从来没有证明过"运行时会播"** —— 它们是两条完全不同的链路。

### 抢救手法

`.anim` 是**文本 YAML** → **记事本打开，把 `m_Events:` 那一段删掉**（或改成 `m_Events: []`）→ 保存 → Unity 自动重新导入 ✓
（`m_Events` 正好是文件最后一个字段，所以就是"删到结尾"。）

### 教训

1. **「添加事件」按钮不要随手点** —— 它有正当用途，但**空事件 = 坏数据 = 整个资产报废**
2. **"保存"必须验证，不能假定成功** —— 这次是**连续第四天**栽在落盘上（09-22 场景 / 09-23 项目设置 / 09-24 UI + 场景 / 09-25 Clip + 场景 + Controller）
   → **判据**：**改完资产/场景后，用 `git status` 或"扒文件"确认磁盘真的变了**，别靠"我按了 Ctrl+S"
3. **"三层保存"之外还有第四层：资产（`.anim` / `.controller` / Prefab）** —— 它们也**不是自动写盘**的
4. **一个坏资产能连坐一整片**：Clip 坏 → 保存被拒 → 场景和 Controller 一起存不下去。**排错要顺着"谁依赖谁"往上找**
5. **窗口预览 ≠ 运行结果**：任何"编辑器里看着对、跑起来不对"的现象，先去问"这两条链路是不是同一条"

## ❌ 错误 18：通关音变成"电流声"——锁在入口，副作用留在外面（2026-09-26，Unity 工程）

**状态**：✅ 已修复 ｜ **文件**：`Projects/Unity/Breakout/Assets/Scripts/GameManager.cs`

### 现象（两条症状，指向两个不同的根因）

打光砖块后：**通关音刺耳**，而且**一直不结束**，像持续的电流声 / 嗡嗡声。

### 证据链（三行代码拼起来）

```csharp
// ① Update：没有 _isGameOver 守门 → 通关后每一帧都在调 Win()
void Update() { ...  if (brickSpawner.RemainingBricks == 0) Win(); }

// ② Win：副作用写在 End() 的【锁外面】
private void Win() { audioSource.PlayOneShot(Sfx.GameWin()); End("YOU WIN"); }

// ③ End：锁在这儿，但已经拦不住上面那句了
private void End(string message) { if (_isGameOver) return; _isGameOver = true; ... }
```

→ 通关那一帧之后，**每帧 `PlayOneShot` 一次 0.36 秒的音** → **每秒 60 次叠加**。

### 为什么听起来是"电流声"（两件事叠在一起）

| 症状 | 机理 |
|---|---|
| **永不结束** | 每帧都有新的一发补进来 → 声音被无限"续命" |
| **刺耳** | 0.3 振幅 × 几十条叠加 → 波形远超 `[-1, 1]` → **削波 → 方波化 → 大量高次谐波** |
| **像嗡嗡/电流** | 这是 09-25「同相位叠加」的**极端版**：2 声 = "更响"；**60 声/秒** = 融合成**持续音**（颗粒合成原理） |

### 为什么**只有通关**炸、失败没事

| 出口 | 调用源 | 触发次数 |
|---|---|---|
| `Lose()` ← `FailZone.OnTriggerEnter2D` | **事件** | 天然**只一次** ✅ |
| `Win()` ← `Update()` | **每帧轮询** | **每帧一次** ❌ |

> **同一个写法，换了个调用源，就从安全变爆炸。**

### 修法（两步都要做）

```csharp
// ① 补回守门员
void Update() { if (_isGameOver) return;  ... }

// ② 让锁罩住副作用：音效当参数传进 End，播放由 End 自己保证只发生一次
private void Win()  { End("YOU WIN",   Sfx.GameWin()); }
private void End(string message, AudioClip sound)
{
    if (_isGameOver) return;          // 先上锁
    _isGameOver = true;               // 再改状态
    ...
    audioSource.PlayOneShot(sound);   // 最后才是副作用
}
```

> **修 ① 只堵住"这一个调用点"；修 ② 让"任何调用者重复喊 `Win()` 都安全"** —— 后者才是治本。

### 教训

1. **⭐ 锁必须把副作用整个罩住，否则等于没锁** —— 判据：**"这个副作用会不会因为调用者重复调用而叠加？"**
2. **区分调用源**：**事件**（天然一次）vs **每帧轮询**（每次都来）—— 同一个方法，两种命运
3. **"刺耳"和"响个不停"是两个信号**：前者是**削波**（振幅问题），后者是**重复触发**（时序问题）—— 分开追，定位更快
4. 这是 09-24 错误 15（**入口上锁 ≠ 全局上锁**）的**升级版**：上次是"只锁了入口"，这次是"**锁在入口，副作用在外面**"
5. **又一条"难走的路径"**：通关要打光 32 块砖，是全场最难触达的分支 —— 所以**用"临时调小砖块数"把它变成最好走的路**，是补测试盲区的通用手法（今天正是靠这个在 30 秒内验证修好了）

## ❌ 错误 19：`dict[key].Add(s)` → `KeyNotFoundException`——索引器"读"不创建（2026-09-26，49 题）

**状态**：✅ 已修复 ｜ **文件**：`LeetCode/0049-GroupAnagrams/Program.cs`

### 现象

```
Unhandled exception. System.Collections.Generic.KeyNotFoundException:
The given key '10001000000000000001000000' was not present in the dictionary.
   at Solution.GroupAnagrams(String[] strs) ... Program.cs:line 166
```

### 我的错误

```csharp
foreach (string s in strs)
{
    if (s.Length == 0) { dict["nothing"].Add(s); }      // ← 同一个错，还漏了 continue
    int[] judge = new int[26];
    foreach (char c in s) judge[c - 'a']++;
    dict[string.Join("", judge)].Add(s);                // ← 先【读】dict[key]，key 不存在 → 抛异常
}
```

### 为什么错：同一个索引器，读和写行为不同

| 操作 | key 不存在时 |
|---|---|
| `dict[key]`（**读** / getter） | ❌ 抛 `KeyNotFoundException` |
| `dict[key] = value;`（**写** / setter） | ✅ **自动创建**这条记录 |

> **我自己在 383 题里用对过这一条**：`dict[magazine[i]] = times + 1;` —— 那是**写**，所以不需要先判断存在性。
> 这次写成了**读**，把"写才会创建"的便利当成了索引器的通用性质。

### 顺带踩到的第二个坑：`judge.ToString()`

`int[]` **没有重写 `ToString()`** → 继承自 `object` 的那个 → 返回**类型全名** `"System.Int32[]"`：

```csharp
dict[judge.ToString()].Add(s);   // 所有词算出【同一个 key】→ 全挤一组，还一个异常都不抛
```

**根因**：`Dictionary` 比 key 用的是 `Equals`，而 `int[]` 是**引用类型、默认比地址** → 内容相同的两个数组也判不相等。

### 打脸反例（判题工具里的 4 组，专抓"有损编码"）

| 反例 | 抓的是 |
|---|---|
| `["ad","bc"]`（和都是 197） | ASCII **和**当 key |
| `["ac","bb"]`（和都是 196） | 同上（换一对） |
| `["aa","bb"]`（异或都是 0） | **异或**当 key（成对字母自相抵消） |
| `["abbbbbbbbbbb","aaaaaaaaaaab"]`（都拼成 `"111000…"`） | 计数表**无分隔符**拼接（编码有歧义） |

### 修复

```csharp
string key = string.Join(",", judge);                    // ① 无损 + 无歧义
if (dict.TryGetValue(key, out List<string> group))       // ② 建筐三步
    group.Add(s);
else
{
    group = new List<string>();
    dict[key] = group;                                   // ⚠️ 写进字典（漏这句 = 每组只剩最后一个词）
    group.Add(s);
}
// ③ 空串特判整段删除 —— 空串的计数表是全 0，本身就是一把稳定唯一的 key
```

### 教训

1. **⭐ 同一语法的"读"和"写"语义可以完全不同** —— 索引器就是典型；**"取不到"和"写进去"是两件事**
2. **建筐三步**：造空筐 → **把筐写进字典** → 再装词。漏了哪一步，失败形态完全不同：
   - 漏"先建筐" → **当场抛 `KeyNotFoundException`**（响亮，好抓）
   - 漏"写进字典" → **每组只剩最后一个词**（静默，更可怕）
3. **规范形式（key）必须同时满足**：**同类同键 + 异类异键**。加 / 异或 / 无分隔符拼接都只满足前半条
4. **两层"碰撞"要分清**：**语义层**（我的 key，绝不能撞）vs **哈希层**（`Dictionary` 内部，允许撞，靠 `Equals` 兜底）
5. **判据**：**规范形式对了，任何合法输入都不需要特判** —— 需要特判（比如"空串怎么办"）往往说明 key 在某个形状上失效了
6. **异常消息就是最好的证据**：它把 key 原样打出来（`10001000000000000001000000` = `"eat"` 的计数表），一眼能反推出"key 怎么造的"
