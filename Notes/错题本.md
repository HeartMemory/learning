**难度**：简单 ｜ **状态**：✅ 已重写并 AC（2026-08-29） ｜ **目录**：[0121-BestTimeToBuyAndSellStock](../LeetCode/0121-BestTimeToBuyAndSellStock/)

### 我的错误思路

从右往左遍历，分别记录**全局最高价日**（max）和**全局最低价日**（min），最后用 `prices[max] - prices[min]` 算利润；发现 max 在 min 前面（时间倒流）就返回 0。

### 为什么错

- **模型错误**：最优交易不一定用全局最高/最低价。全局高低点配对后只能验证「这一对」行不行，会错过其他合法组合里更赚钱的交易。
- **补丁救不了**：尝试「只在发现新低时重算利润」「max 更新时也重算」都失败——前者漏算，后者又造出时光倒流。**模型错了，修补无意义，必须换思路。**

### 打脸反例

| 输入 | 期望 | 我的代码输出 | 原因 |
|---|---|---|---|
| `{5, 6, 1, 2}` | 1 | 0 | 最高(6)在最低(1)前面 → 误判无解，但买 1 卖 2 能赚 1 |
| `{3, 2, 6, 5, 0, 3}` | 4 | 0 或 6 | 全局对是「第2天6、第4天0」：直接算=时光倒流；返回0=漏掉 2→6 的合法交易 |

### 正确思路（一句话模型）

**一次从左到右遍历，维护两个变量**：
- `minPrice`：走到今天为止见过的最低价（历史最低买点）
- `result`：走到今天为止的最大利润（每天尝试「今天卖」）

为什么对：算 `prices[i] - minPrice` 时买点保证在卖点之前（合法）；而任何一笔合法交易的买点都不低于历史最低，所以最优解一定被覆盖。

### 教训

1. **「先配对再验证」≠「边走边维护」**：枚举每个卖出日、让买点自动取历史最低，合法性天然成立。
2. **示例通过 ≠ 正确**：LeetCode 示例太温柔，必须自己造边界反例。
3. **模型错了要果断换，别打补丁**：判断标准——修补两次还错，说明是思路问题不是实现问题。
4. **「遍历时维护历史极值」是通用模式**：485 的计数器、283 的零计数器、121 的历史最低价，全是这个套路。

## ⚠️ 错误 02：283. 移动零——边界条件漏测（2026-08-29）

**难度**：简单 ｜ **状态**：✅ 已修复 AC ｜ **目录**：[0283-MoveZeroes](../LeetCode/0283-MoveZeroes/)

### 我的错误

覆盖写法第一版：`nums[i - zero] = nums[i]; nums[i] = 0;` 无条件执行 else 分支。当 `zero == 0`（前面没有 0）时，`i - zero == i`，自己拷给自己再抹成 0，`{1,2,3}` 直接变 `{0,0,0}`。

### 为什么一开始没发现

我造的测试用例开头全是 0（`{0,1,0,3,12}`、`{0,0,1}`），走 else 时 zero 必然 ≥ 1，bug 被掩盖。

### 修复

给「清零当前位」加条件：只在 `zero != 0` 时执行。

### 教训

- **测试用例必须覆盖边界**：有 / 无 / 全有（全 0、全非 0、零在中间、零在两头）。
- 示例通过就急着交，等于把 bug 留给 LeetCode 的隐藏用例帮我发现。

## ❌ 重点错误 03：53. 最大子数组和（2026-08-30，复盘日）

**难度**：中等 ｜ **状态**：✅ 已重写并 AC（2026-08-30） ｜ **目录**：[0053-MaximumSubarray](../LeetCode/0053-MaximumSubarray/)

### 📦 错误版本存档：commit `5263b6e`

### 我的错误思路

「贪心吸收」：先跳过开头的负数，遇到正数就累加；遇到负数就用内层 while 往后吞，直到累计和变正，把「桥梁段」整个加进 result。

### 为什么错

1. **全负数返回 0**：开头 while 把所有元素跳光，for 不执行，返回初始值 0。但题目要求子数组**至少含一个元素**，全负时必须返回最大的那个（如 `{-3,-1,-2}` → `-1`）。
2. **吸收负数前没和「重新开始」比较**：`{1,-3,4}` 吸收后总和是 2，不如扔掉前缀从 4 重新开始。贪心吸收只看「桥能不能搭成正的」，不看「搭桥值不值」。
3. **内层 while 修改外层 i + 中途 return**：控制流绕，正确性难分析——这本身就是危险信号。

### 打脸反例

| 输入 | 期望 | 我的输出 | 原因 |
|---|---|---|---|
| `{-2,1,-3,4,-1,2,1,-5,4}` | 6 | 5 | 桥接段吸收亏了没重来 |
| `{5,4,-1,7,8}` | 23 | 15 | 同上，-1 桥接把连续大段拆散 |
| `{-3,-1,-2}` | -1 | 0 | 全负数边界，跳光后返回 0 |

### 正确思路（提示，重写时用）

还是「遍历时维护历史信息」，但这次维护的量变了——
- 变量 A：**以今天结尾**的最大子数组和。每天二选一：延续昨天（A_prev + nums[i]）还是从今天重新开始（nums[i]）？**谁大选谁**。
- 变量 B：历史所有 A 的最大值。
- 这样「要不要为负数搭桥」的决策被简化成了每天一次的取大，且天然处理全负数。

### 教训

1. **「至少选一个」类的边界（全负/全零/空）必须在第一版就想到**——我在骨架注释里专门标了全负数测试，结果还是错了它。
2. **贪心策略要证明「局部最优=全局最优」才能用**：吸收负数是局部看似合理，全局可能亏。
3. **内层循环改外层变量 + 中途 return 是坏味道**：写出来控制流就已经在报警了。

## ❌ 重点错误 04：88. 合并两个有序数组（2026-09-01，机动日）

**难度**：简单 ｜ **状态**：✅ 已重写并 AC（2026-09-01） ｜ **目录**：[0088-MergeSortedArray](../LeetCode/0088-MergeSortedArray/)

### 📦 错误版本存档：commit `10b6fe0`

### 我的错误思路

双层循环从后往前：外层倒序遍历 nums2（取一个待插入数），内层倒序扫 nums1 有效位——nums1 的元素更大就右移腾位；否则把 nums2[i] 放下并 break。

### 为什么错

**漏了第三条路**：当 nums1 的有效元素全部比 nums2[i] 大时，内层 j 一路右移直到走完，**没有任何分支把 nums2[i] 放进去**——这个数凭空消失。

结构性缺陷：整个循环不保证「每步恰好放置一个元素」。原地合并/填充类题目的正确姿势是：每个指针每走一步，必须有一个值落到最终位置。

### 打脸反例

| 输入 | 期望 | 我的输出 | 原因 |
|---|---|---|---|
| `nums1={3,0,0}` m=1，`nums2={1,2}` | 1,2,3 | 3,3,0 | 3 比两个数都大，1 和 2 没人放 |
| `nums1={1,2,7,0,0}` m=3，`nums2={0,8}` | 0,1,2,7,8 | 1,1,2,7,8 | 7 右移两次后 j 走完，0 丢失 |

### 正确思路（提示，重写时用）

三个指针各管一头，**每步必放一个值**：
- `i = m-1`（nums1 有效尾）、`j = n-1`（nums2 尾）、`k = m+n-1`（填充位）
- 每步只比较：`nums1[i]` 和 `nums2[j]` 谁大？大的放进 `nums1[k]`，k 和对应指针一起左移
- 收尾：谁先走完，就把另一方剩下的整体搬过去（此时 k 位置正好对齐，不用想复杂）
- 副产品：`m=0` 的特判不再需要——想想为什么（答案：i 从 -1 开始时第一个 while 天然跳过，收尾 while 会把 nums2 全搬进去）

### 教训

1. **原地填充类题目的自检清单：每个指针每一步，必须恰好落一个值**——多放、少放、跳过都是结构性 bug。
2. **第三次靠自造反例救场**（283 的 `{1,2,3}`、121 的两组、这次 t4）：题目给的测试永远不够，写完先自己当测试员。
3. **好的结构能消掉特判**：需要 `if (m==0)` 之类的补丁时，先想想换结构能不能让它自然消失。

## ❌ 重点错误 05：顶层方法重载报错（2026-09-03，方法进阶练习）

**难度**：练习 1 ｜ **状态**：✅ 已修复 ｜ **目录**：[2026/09/03/AdvancedMethods](../CSharpPractice/2026/09/03/AdvancedMethods/)

### 我的错误

在顶层文件直接写了三个同名 `static int Max(int,int)` / `static double Max(double,double)` / `static int Max(int,int,int)` 想做重载 → 编译错误 **CS0128：已在此范围定义了名为 Max 的局部变量或函数**。

### 为什么错（连环三坑）

1. **CS0128**：顶层方法其实是**本地函数（local function）**，而本地函数**不支持重载**——重载是「类成员」的特权。之前的方法都不同名所以没暴露。
2. **CS8803**：把 `static class Tools` 放到了文件开头——顶层程序的规则：**可执行语句必须全部在类型声明之前**。
3. **CS0122**：类成员不写访问修饰符默认 `private`，外面的顶层语句访问不到——工具方法必须加 `public`。

### 正确结构

```csharp
// ① 顶级语句区（最上面）：调用示例
Console.WriteLine(Tools.Max(3, 5));

// ② 类型声明区（文件底部）
static class Tools
{
    public static int Max(int a, int b) { ... }
    public static double Max(double a, double b) { ... }
    public static int Max(int a, int b, int c) { ... }
}
```

连带修复的逻辑 bug：`Factorial` 基准情况 `else return 0` → `0! = 1`，终止条件的返回值错 = 全链全错；返回值改 `long`（int 在 13! 溢出）。

### 教训

1. **重载 = 类成员特权，本地函数做不到**——想把一组同名方法组织起来，包个类（这就是 `Math.Max` 的真身：类里的 public static 重载群）。
2. **顶层程序文件结构铁律**：语句在前，类型声明在后。
3. **类成员默认 private**——「外部要调」就必须显式 `public`（LeetCode 模板的 public 谜底揭晓）。
4. **递归基准情况的返回值和条件同样重要**：`0! = 1` 不是 `0`。

## ⚠️ 错误 06：82 删除重复元素 II——盲写漏跨接行 + 测试形状盲区（2026-09-13 复盘日）

**难度**：中等 ｜ **状态**：✅ 已修复并补测试 ｜ **目录**：[0082-RemoveDuplicatesFromSortedListII](../LeetCode/0082-RemoveDuplicatesFromSortedListII/)

### 盲写时的错

漏掉 `prev.next = cur;`（跳过整族重复后的**跨接**）——但**4 组测试全部通过**。

### 为什么全绿（假象推演）

- 重复族后面若还有非重复节点 → 下一轮 `else` 分支的 `prev.next = cur` 会**碰巧补接**
- `{1,1}` 全重复 → cur 跳到 null 循环结束，`dummy.next` 从没赋值恰好是 null → 输出空 ✓（碰巧对）
- **所有用例的重复族都在中间，从没测过“重复族在末尾”**

### 打脸反例（复盘日新增 t5/t6/t7 后现形）

| 输入 | 期望 | 漏行版输出 | 原因 |
|---|---|---|---|
| `{1, 2, 2}` | `1` | `1→2` | 末尾整族跳过后 cur = null，再无人补接 → 悬尾 |
| `{1, 1, 2, 2}` | （空） | 全重复，恰好对 | 碰巧 |
| `{1, 2, 3, 3, 4, 4}` | `1→2` | `1→2→3→4` | 末尾连续两个族都留了尾巴 |

### 正确做法

`if` 分支跳过整族后**立即** `prev.next = cur`（链任何时刻都完整）；`else` 分支再赋一次同值是**幂等冗余**，无害。

> 等价优化版（只在 else 接 + 循环后 `prev.next = null` 断悬尾）已作为注释写在题目文件里，供复习对照——但**不推荐启用**：把“冗余赋值”换成“必须记得收尾”不划算。

### 教训

1. **“碰巧对”≠“保证对”**：靠别处的分支恰好补接，是隐式依赖，不是正确性证明
2. **测试要穷举“形状”，不只是“值”**：重复族在开头/中间/**末尾**/全是/没有——形状覆盖不全，隐藏 bug 就永远测不出来（第三次栽在同一坑：283 的“开头无 0”、88 的“nums1 全大”）
3. **幂等的冗余是廉价的，被遗忘的收尾是昂贵的**

## ⚠️ 错误 07：232 用栈实现队列——盲写守卫条件写反（2026-09-13 复盘日）

**难度**：简单 ｜ **状态**：✅ 已修复 ｜ **目录**：[0232-ImplementQueueUsingStacks](../LeetCode/0232-ImplementQueueUsingStacks/)

### 盲写时的错

```csharp
public int Pop() {
    if (outStack.Count != 0) return 0;   // ❌ 有货反而返回 0
    while (inStack.Count != 0) outStack.Push(inStack.Pop());
    return outStack.Pop();
}
```

输出全变 `0`（期望 1/1/False/2/2/3/True…，实际 1/0/False/0/0/0/False…）。

### 为什么错

| outStack 状态 | 应该做什么 | 我写的 |
|---|---|---|
| **有货** | 栈顶就是队头，**直接用**，继续往下走 → `outStack.Pop()` | `return 0` **把正常情况当成了终止** |
| 空 | 才需要倒手 | while 倒手 ✓ |

`return` 在这里语义错位：**两种情况的终点都是 `outStack.Pop()`**，不存在“提前结束”的分支。

### 正确做法（二选一）

```csharp
// A：正着写条件，去掉提前 return
if (outStack.Count == 0) { while (inStack.Count != 0) outStack.Push(inStack.Pop()); }
return outStack.Pop();

// B：抽辅助方法（DRY——Pop/Peek 共用，规则只写一处）
private void EnsureOutHasItems() {
    if (outStack.Count != 0) return;   // "有货→什么都不用干"，这才是 return 的正确语义
    while (inStack.Count != 0) outStack.Push(inStack.Pop());
}
```

### 教训

1. **提前 return（卫语句）只用于“异常/终止”分支**——当所有分支最终都要走到同一句代码时，不该用 return
2. **判断守卫条件时先问“两个分支各自要干什么”**，再决定用 if / if-else / 提前 return
3. 盲写重现 + 抽辅助方法（DRY）——`Pop`/`Peek` 抄两遍倒手逻辑，将来改一处漏一处

## ⚠️ 错误 08：202 快乐数——三坑连踩（2026-09-16）

**难度**：简单 ｜ **状态**：✅ 已修复 + 网页 AC ｜ **目录**：[0202-HappyNumber](../LeetCode/0202-HappyNumber/)

### 我的错误版本

```csharp
while (true) {
    int temp = 0;
    while (n > 10) {              // ❌ 坑 2：丢个位
        temp += (n % 10) ^ 2;     // ❌ 坑 1：^ 是异或，不是乘方
        n /= 10;
    }
    n = temp;
    if (!judge.Add(n)) return false;   // 判环思路 ✓（`Add` 返回值一步查+登记）
    if (n == 1) return true;
}
```

**症状**：7 组测试**全部输出 False** —— 连 `19`、`1` 这种必然为真的都错。

### 三个坑

| # | 坑 | 为什么错 | 正解 |
|---|---|---|---|
| 1 | `(n % 10) ^ 2` | **C# 里 `^` 是位异或**：`9 ^ 2 = 11`（`1001 XOR 0010`）。Python 的 `**` 在 C# **不存在**（唯一的幂是 `Math.Pow`，返回 `double`，慢） | `int d = n % 10; temp += d * d;` |
| 2 | `while (n > 10)` | `n = 10` 时循环体不执行 → 十位丢了；`n = 7` 时**整个数字没参与计算** | `while (n > 0)` |
| 3 | 入口的 `n` 从未登记 | 结构是"先变换再登记"，`n = 1` 被算成 `0` 再登记 → 判错；判环也漏了起点 | 经典写法：`while (n != 1) { if (!seen.Add(n)) return false; n = 平方和(n); } return true;` |

> 坑 3 的细节：改完后"先变换再登记"在**值域有界**的本题**侥幸能跑对**（第 1 步之后的每个数都会进集合，环一定会被后续值撞上）——但这是**隐式依赖**，不是正确性证明。**"先登记当前值、再变换"才是防守型写法**，被检查的对象永远同一个、不漏起点。

### 教训

1. **C# 没有幂运算符**：`^ & | << >>` 全是**位运算符**，逻辑运算必须写 `&&` `||`。`^` 当乘方用是 **Python → C# 迁移的第一大坑**。
2. **取数位的循环终止条件是 `> 0`**：写 `> 10` 的潜台词是"只剩一位就不处理"，但每一位都要算。
3. **全 False ≠ 边界问题**：连"必然为真"的用例都错 → 说明是**核心逻辑**坏了。先分诊，别急着打补丁。
4. **"结果全错但能跑"的题，用单步打印**：`Console.WriteLine($"n={n}, temp={temp}")` → 一眼看到 `19` 走成 `11 → 3 → 0` 的死路，比盯代码快十倍（Unity 里同款手段是 `Debug.Log`）。
5. **`Add` 返回值一步完成"查 + 登记"**（217 学的）在本题迁移成功 ✓ —— 好模式会重复出现。
