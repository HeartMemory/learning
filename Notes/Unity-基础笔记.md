## 1. Unity 脚本基础与生命周期（09-16）

### 一、从 .NET 控制台到 Unity：4 个环境差异（同一份 C# 代码会"炸"的原因）

| # | 差异 | 控制台项目（dotnet） | Unity 脚本程序集 |
|---|---|---|---|
| 1 | **入口点** | 支持**顶级语句**（文件顶层直接写代码） | ❌ 报 **CS8805**（程序集是 DLL，没有入口）→ 代码必须进方法 |
| 2 | **隐式 using** | `.csproj` 有 `<ImplicitUsings>enable</ImplicitUsings>`，`List<>`/`Console` 自动可用 | ❌ 老式 csproj，**必须手写** `using System.Collections.Generic;` → 否则 **CS0246** |
| 3 | **输出目标** | `Console.WriteLine` → 终端 | ⚠️ 能编译，但只写进 `Editor.log`，**不显示在控制台窗口** → 必须用 `Debug.Log` |
| 4 | **可空上下文** | 可开 `<Nullable>enable</Nullable>` | ❌ 默认关闭，`Character?` 报 **CS8632**（警告）→ 去掉 `?`（原理见 `CSharp-基础笔记.md` 第 18 章） |

> 🔑 **迁移检查清单**（任何 C# 代码搬进 Unity，先过这四项）：顶级语句？using 齐吗？`Console` 换 `Debug.Log` 了吗？可空问号？

### 二、MonoBehaviour = "能被挂到 GameObject 上的组件"

```csharp
public class LifecycleDemo : MonoBehaviour   // 继承 MonoBehaviour = "我是一个组件"
```

- **写类 ≠ 有对象**：脚本文件建好了但**没挂到任何 GameObject 上 → 一行都不会执行**（引擎只对场景中的**组件实例**点名）。这就是"播放后控制台一片空白"的头号原因
- 硬约束：**一个 `.cs` 文件最多一个 `MonoBehaviour`，且文件名必须 = 类名**；**普通类 / 接口不受此限**（一个文件可装任意多个，文件名随便叫）
- 同一个 GameObject 可以挂**多个相同组件**（要禁止得在类上加 `[DisallowMultipleComponent]`）——排查"改了脚本没反应"时先看一眼是不是挂了两个

### 三、生命周期回调（引擎按名字点名）

```
Awake → OnEnable → Start → (每帧: Update → LateUpdate) → OnDisable → OnDestroy
```

| 回调 | 触发时机 | 次数 |
|---|---|---|
| `Awake` | 实例被加载（物体激活时） | **一生一次** |
| `OnEnable` | 物体**且**组件都启用时 | **每次进出都触发** |
| `Start` | 第一次启用后、第一帧 `Update` 前 | **一生一次** |
| `Update` | 每帧 | 每帧 |
| `LateUpdate` | 本帧所有 `Update` 跑完后 | 每帧 |
| `OnDisable` | 物体**或**组件被禁用 / 销毁前 | **每次进出都触发** |
| `OnDestroy` | 实例被销毁 | 一生一次 |

**三条关键结论**：
1. `Awake` → `OnEnable` → `Start`；**`Awake`/`Start` 的"一次"指"这个实例的一生"**，重新启用**不会**重跑
2. **`Update` 频率不是固定 60**：编辑器空场景可跑上千帧/秒（没开垂直同步）→ **任何速度/时间逻辑必须乘 `Time.deltaTime`**（帧率无关性铁律）
3. **`LateUpdate` 存在的理由**：多个组件之间 `Update` 的**执行顺序不保证** → 相机跟随必须放 `LateUpdate`，才能拿到所有物体本帧的**最终位置**（否则画面抖动）

### 四、⭐ 按名字点名 vs vtable（两种调用机制对照）

| | `virtual` / `override` | Unity 生命周期（消息机制） |
|---|---|---|
| 谁决定被调用 | **编译器**（编译期焊进 vtable） | **引擎**（运行时扫描方法名，结果缓存成"消息表"） |
| 定位方式 | 类型指针 → 虚方法表 → 跳转 | 按**名字**匹配 |
| 写错了 | **编译报错** | **不报错，静默失效**（`void update()` 永远不跑） |
| 访问修饰符 | 只能 `public`/`protected` | **随便**（`private` 也能被调） |
| 类比 | 填表格（格子印好了，每格都要处理） | 喊名字（答应哪个干哪个，没人应也没人管） |

**Unity 为什么选"点名"**：① **`private` 也能被调用**（`void Start()` 就是隐式私有，这在 virtual 体系里做不到）；② **不依赖继承体系**（ScriptableObject、编辑器脚本也能接回调）；③ 多语言兼容（早期支持 JS/Boo）；④ 想用哪个写哪个，新增回调不用改基类。
**代价**：没有编译期保护 → **生命周期方法永远用 IDE 补全，绝不手打**。

> 注意：`virtual` 只是"**可以**改写"，不是"必须"（必须的是 `abstract`）。`Monster` 没 override 就用父类默认实现 ✓

### 五、组件禁用 vs 物体禁用（两个长得几乎一样的 checkbox）

| | 组件勾选框（`enabled`） | 物体勾选框（`activeSelf` / `SetActive`） |
|---|---|---|
| 影响范围 | **只有这一个组件** | **物体上所有组件** |
| 子物体 | 不受影响 | **全部一起失活** |
| 层级窗口 | 物体**不变灰** | 物体名**变灰** |

**关键洞察（实测得出）**：**从脚本自身看，两种情况收到的回调一模一样（`OnDisable` / `OnEnable`）**——脚本根本分不清"我被禁用了"还是"我所在的物体被禁用了"。唯一区别在**影响范围**。
（实锤实验：一个物体挂两个相同组件，勾选的跑完整流程，未勾选的一条日志都没有。）

### 六、场景心智模型

- **你运行的不是"某个脚本"，而是"整个场景"**：播放时场景里**所有物体同时活着、同时运行**（所以会莫名多出别的脚本的日志）
- 场景会"记住"你放进去的一切（`Ctrl+S` 保存 `.unity` 文件）；**代码保存（VS 的 `Ctrl+S`）和场景保存是两件独立的事**

### 七、两个必踩的工程坑

| 坑 | 现象 | 原因 / 修法 |
|---|---|---|
| **编码** | VS 弹"某些 Unicode 字符未能保存到当前代码页" | 脚本里有中文/emoji，VS 默认 ANSI/GBK 存不下 → **存 UTF-8**（Unity 按 UTF-8 解析 `.cs`）；VS2022 里用 `文件 → 高级保存选项 → Unicode (UTF-8 带签名)`（详见第 3 章第十一节） |
| **粘贴括号层级** | `CS1513: } expected` + `CS1022: Type or namespace definition...` | 粘贴时**忘闭合方法体** → 后面的类型声明被"吸"进方法里。**看见括号类报错先数括号**（VS 光标放 `{` 上可高亮配对，`Ctrl+]` 跳转），别盯代码内容 |

### 八、接口回收：`IEnumerable<T>` / `IList<T>` / `IDictionary<K,V>` / `KeyValuePair<K,V>`

**和自写的 `IAttackable` 是同一种东西**，区别只在"谁写的 + **消费者是谁**"：

| 接口 | 契约内容 | **消费者（谁在认它）** | 使用痕迹 |
|---|---|---|---|
| `IAttackable` | `Name` / `IsAlive` / `TakeDamage` | 自写的 `Character.Attack()` | 09-14 |
| `IEnumerable<T>` | "我能被逐个遍历" | **`foreach` 关键字本身** | 从第一天起每条 `foreach` |
| `IList<T>` | "能按下标访问 + Add + Count" | `[]` 索引器、`Add` | 118 杨辉三角（`IList<IList<int>>`） |
| `IReadOnlyList<T>` | "能下标、不能改" | 只读访问 | 09-08 Encapsulation |
| `IDictionary<K,V>` | "能用 key 查 value" | `dict[key]`、`TryGetValue` | 09-14 起 |
| `KeyValuePair<K,V>` | "一对 (key, value)" | 遍历 Dictionary 时 | ❌ 还没用过 |

**继承层次（越往下能力越多）**：

```
IEnumerable<T>            ← 能被 foreach（最底层能力）
├── ICollection<T>        ← 能 Count / Add / Remove
│   ├── IList<T>          ← 能按下标 list[0]
│   └── IDictionary<K,V>  ← 能用 key 查 value
└── IReadOnlyList<T>      ← 只读版：能下标、不能改
```

- **铁律：接口必须有"另一端"（消费者）才有意义** —— 没有消费者的接口是废纸。判断任何接口先问：**谁在认这份契约？**
- 预告：`IComparable<T>`（消费者 `List.Sort()`）、`IDisposable`（消费者 `using`）、`IEquatable<T>`（消费者 `Dictionary`/`HashSet` 判重）—— 全是同一套逻辑
- **选用原则：自己内部用 → 选实现（`List<T>`）；给别人用 → 选接口（`IReadOnlyList<T>` / `IEnumerable<T>`）**

### 九、`using` 的机制（易误解点）

- `using X;` **不是"引入"什么**，它只是把 X 命名空间里的类型名加进**检索范围**（短名 → 全名的查找表）
- 类型的**全名**永远是 `命名空间.类型名`（如 `UnityEngine.Debug`）；`using` 只让你能写短名。联想：`using` ≈ 把目录加进 `PATH`
- `System.Collections.Generic` 读作**路径**：`System` → `Collections`（老式非泛型 `ArrayList`/`Hashtable`，存 `object` 要装箱）→ `Generic`（泛型版，类型安全 + 免装箱）
- 两个 `Debug` 会打架：`UnityEngine.Debug`（控制台输出）vs `System.Diagnostics.Debug`（诊断）—— 同时 using 会报 **CS0104 不明确的引用**，届时只能写全名
- **万能判定法：删掉这个 `using`，编译一次，看哪儿报红。** 不报红 = 没用（VS 也会显示成灰色）

## 2. Unity 空间与运动（09-17）

### 三件套的关系

```
GameObject  = 空容器（本身什么都不会）
Component   = 装在容器里的功能件（行为 / 数据 / 外观）
Transform   = 唯一【强制】自带的组件（删不掉）
```

- **Unity 里没有"物体的行为"，只有"组件的行为"**：想移动 → 挂脚本组件；想碰撞 → Collider；想被看见 → 渲染组件
- **`transform` 不是全局变量**，是**继承自 `Component` 的属性**（≡ `this.transform`）
  - `: MonoBehaviour` 的真正价值 = 白送一批快捷访问（`transform`/`gameObject`/`name`/`enabled`）+ 生命周期方法的"报名资格"
- **Scene 窗口 = 上帝视角**（右键环视、右键+WASD 飞行、滚轮缩放、选中按 `F` 聚焦）｜**Game 窗口 = 相机视角**

### ⭐ 运动母公式

```csharp
transform.position += new Vector3(speed * Time.deltaTime, 0f, 0f);
//                              └──── 这一帧应该走的距离 ────┘
```

- **`Update` 是"每帧一次"，不是"每秒一次"** → 必须 `× Time.deltaTime` 换算成"每秒"
- **去掉 `deltaTime`** → "每秒移动"变"每帧移动" → 实测一秒上千帧 → **速度放大 ~1000 倍**
- **铁律**：凡是"每秒多少"的（移动/旋转/冷却/计时）一律 `× Time.deltaTime`；"每帧一次"的（读输入）不乘
- 数学本质 = **数值积分（欧拉法）**：时间切片，每片当匀速累加
- "10 秒后 ≈ 10 而非精确 10"的两个原因：①**`deltaTime` 每帧在波动**（主因）②浮点累加误差（次因）
- **两条互斥的移动路线**：直接改 `transform.position`（运动学，自己算，会穿墙）｜ 操作 `Rigidbody`（物理引擎算，有碰撞重力）
  - ⚠️ **千万别混用**（加了 `Rigidbody` 还在 `Update` 里手改 `position` → 抖动/穿模/弹飞）；两套的正确姿势见第 3 章第六节

### ⚠️ 世界坐标 vs 本地坐标（**最容易搞反的一处**）

| | 代码 API | **Inspector 的字段** |
|---|---|---|
| 世界坐标 | **`transform.position`** ✅ | ❌ **看不到** |
| 本地坐标 | `transform.localPosition` | ✅ **「位置」显示的就是它** |

**Unity 官方手册原文**（Unity 6.0 与 4.3 两版一致）：

> *"The Transform values for any child GameObject are displayed **relative to the parent GameObject's Transform values**. These values are called **local coordinates**."*
> *"Unity measures the Position, Rotation and Scale values of a Transform **relative to the Transform's parent**. If the Transform has no parent, Unity measures the properties in world space."*

**结论**：
- **Inspector 的「位置 / 旋转 / 缩放」全部是本地坐标**（有父物体时）；Normal 和 Debug **两个模式显示的都是本地值**，Debug 只是把序列化字段名（`局部位置`）直接暴露出来
- **世界坐标没有任何面板字段** → **只能在代码里取**
- 在面板里改「位置」等价于 `transform.localPosition = ...`（**不是** `transform.position = ...`）——**两套量搞混是父子结构下最经典的 bug 来源**
- **为什么这样设计**：调子物体时关心的是"相对父物体的偏移"（父动子动是常态）
- **父子关系**：`世界坐标 = 父的世界坐标 + 自己的本地坐标`（无旋转缩放时）；拖拽成子物体时 Unity **保持世界位置不变**，自动改本地坐标
- **父子关系的价值**：角色跑动时手里的剑**不需要写任何跟随代码** —— 剑的 `localPosition` 一直是 `(0.5, 0, 0)`，世界坐标被"继承"着算出来

### CS1612：属性返回 struct → 只能"整体读写"

```csharp
transform.position += v;        // ✅ 展开成 transform.position = transform.position + v（整体赋值）
transform.position.x = 5f;      // ❌ CS1612：无法修改"Transform.position"的返回值，因为它不是变量
```

**根因链**：`position` 是**属性**（执行代码，**返回一份拷贝**）→ `Vector3` 是 **struct** → 属性返回 struct = 返回拷贝 → 拷贝没有名字、没有存储位置 → **不是变量** → 不能出现在赋值号左边

| 写法 | 流程 | 合法 |
|---|---|---|
| `transform.position += v;` | 读 → 算新的 → **整体写回** | ✅ |
| `transform.position.x = 5f;` | 读 → 改拷贝 → **丢掉** | ❌ |

**三种正解**：
1. `Vector3 p = transform.position; p.x = 5f; transform.position = p;`（局部变量是变量，合法）
2. `transform.position = new Vector3(5f, p.y, p.z);`（整体赋值）
3. **优先用 Unity 封装的方法**：`transform.Translate(...)` / `transform.Rotate(...)` —— **这类方法存在的意义就是帮你做"读-改-写回"**

**类推**：
| 写法 | 合法 | 原因 |
|---|---|---|
| `list[0].x = 5f`（`List<Vector3>`） | ❌ | 索引器是**属性**（返回拷贝） |
| `arr[0].x = 5f`（`Vector3[]`） | ✅ | **数组下标是语言内建的"变量"** |

**为什么编译器要拦**：它能确定这个操作毫无意义。**宁可编译报错，也不要静默 bug。**

> 与 Unity 生命周期对照：**编译器能管的错 → 报错**（`virtual`/CS1612）；**编译器管不了的（引擎反射）→ 静默失效**（`void update()`）。**凡是能靠编译器抓的，绝不留到运行时。**

### 字段 vs 属性（判定三步法）

| 长相 | 是什么 |
|---|---|
| 类型 + 名字 + `;` | **字段** |
| `{ get; set; }` / `{ get {…} set {…} }` / `=> 表达式` | **属性** |
| `this[int] { get; set; }` | **索引器**（本质是属性） |

1. **看写法**（有花括号 → 属性）
2. **看命名惯例**（字段 `_camelCase`、属性 `PascalCase`）——⚠️ **只能猜，不能定**
3. **悬停 / `F12` 转到定义** —— ⭐ **唯一权威判定**

**四个实际后果**：
| # | 差异 | 字段 | 属性 |
|---|---|---|---|
| 1 | 能否"只改一个分量" | ✅（是变量） | ❌ CS1612 |
| 2 | 能否当 `out`/`ref` 参数 | ✅ | ❌ CS0206 |
| 3 | 读取代价 | 近乎零 | **要执行代码**（`transform.position` 要跨到引擎内部取数 → **读一次缓存到局部变量**） |
| 4 | 结果是否稳定 | 一定稳定 | 可能每次不同（计算属性） |

**记忆锚点**：**字段 = 抽屉**（直接拿/放）｜**属性 = 前台**（跑一套流程再给你；**没法隔着前台动抽屉里的某一格**）

## 3. Unity 输入与物理（09-18）

### 一、读输入：轮询（拉），不是消息（推）
```csharp
Input.GetKey(KeyCode.A)        // 按住期间每帧为真（状态）
Input.GetKeyDown(KeyCode.A)    // 按下那一帧为真（事件）
Input.GetKeyUp(KeyCode.A)      // 松开那一帧为真（事件）
Input.GetAxisRaw("Horizontal") // -1 / 0 / +1，瞬时
Input.GetAxis("Horizontal")    // -1 ~ +1，平滑过渡
```
- 与生命周期对照：生命周期是**引擎按名字点名（推）**，输入是**你每帧主动去问（拉）**

### 二、⭐ GetAxis vs GetAxisRaw（"松手后滑行"的根因）
| API | 松手瞬间 | 适合 |
|---|---|---|
| `GetAxis` | **平滑回落**：按该轴 `Gravity` 参数衰减（默认 3 → 约 0.33 秒归零） | 要缓动手感（赛车/转向） |
| `GetAxisRaw` | **立刻归零** | 要"指哪打哪"（挡板） |

- **滑行 ≠ 物理惯性**：Kinematic 刚体没有质量/摩擦/惯性，位置完全由代码指定 → 滑行只来自**输入值的平滑**
- 手感可调：`项目设置 → 输入管理器 → 轴` 里改 `Gravity`（回落速度）/ `Sensitivity`（上升速度）→ **参数化而不是写死**
- 排查心法：先分清"**输入平滑**"和"**刚体阻尼**"两个完全不同的成因，方向错了会白调半天

### 三、轴名表 = 数据驱动的输入配置
- `"Horizontal"` 是**名字**，Unity 拿它去 `ProjectSettings/InputManager.asset` 这张表里查（拼错/大小写错 → `Input Axis xxx is not setup` 异常）
- 默认 `Horizontal` = 主键 `left`/`right` + 备用键 `a`/`d`（`Alt Negative/Positive Button`）
- 意义：**代码只说"我要水平轴"，具体是哪些键由表决定** → 换键位不改代码，还能同时吃键盘与手柄
- 表属于 `ProjectSettings/` → **会进 git**，换机器克隆下来键位设置跟着走

### 四、⭐ 双时钟：Update vs FixedUpdate
| | `Update` | `FixedUpdate` |
|---|---|---|
| 频率 | 每帧一次（跟帧率，几十 ~ 上千次/秒） | 固定物理步长，默认 0.02s = **50Hz** |
| 谁驱动 | 渲染循环 | 物理引擎 |
| 一帧内跑几次 | 必然 1 次 | **0 / 1 / 多次** |
| 放什么 | 读输入、相机（`LateUpdate`）、纯逻辑/UI | **所有物理操作**（力、速度、`MovePosition`） |
| 配套时间量 | `Time.deltaTime` | `Time.fixedDeltaTime` |

- 为什么输入在 `Update` 读：`GetKeyDown` 只在"按下那一帧"为真，而 `FixedUpdate` 一帧可能 0 次或多次 → **会漏按键 / 重复触发**
- 代价：`Update` 写的值最快要到下一次 `FixedUpdate` 才被用掉（最多一帧延迟，对挡板无感）
- "50Hz"是**目标频率/长期平均值**，不是"每秒恰好 50 次"：卡顿时会**连跑多次追赶**，超时（`最大允许时间步长` 默认 0.3333s）则**主动丢步**防"死亡螺旋"
- ⚠️ `FixedUpdate` 拼错 = 永不执行且不报错（生命周期"按名字点名"同款坑）

### 五、Rigidbody2D：三种主体类型（Body Type）
| 类型 | 谁控制位置 | 典型用途 |
|---|---|---|
| **Dynamic** 动态 | 物理引擎（重力/受力/被撞飞） | 球 |
| **Kinematic** 运动学 | **代码**（`MovePosition`），但仍参与碰撞、能顶飞别人 | 挡板 |
| **Static** 静态 | 谁都不动 | 地板、墙 |

- 改成 Kinematic 后，`质量 / 线性阻尼 / 重力大小` 这些参数失效（谁在管位置，一目了然）
- **`Collider2D` 决定"能不能被撞"，`Rigidbody2D` 决定"位置归不归物理引擎管"** —— 两件事分开的。砖块只要前者（没刚体的碰撞体 = 静态碰撞体，最省）

### 六、⭐ 移动的两种语义（09-18 的分水岭）
```csharp
transform.position += v;    // 直接改坐标（瞬移）：绕过物理引擎 → 两套账打架（抖动/穿墙/碰撞失真）
_rb.MovePosition(next);     // 申请："这一步请把我搬到 next" → 引擎执行 + 同步 Transform + 顺便做碰撞检测
```
- `MovePosition` 要的是**目标位置**，不是增量 → 得自己算 `当前位置 + 位移`
- 基准用 `_rb.position`（**物理引擎账本里的位置**，Vector2），比 `transform.position` 更可靠

### 七、为什么 `_rb.position += v` 编译不过
- `Rigidbody2D.position` 是**只读属性**（只有 get）→ **CS0200**（不能赋值）
- 对照：`transform.position` 有 setter → `+=` 能过（编译器展开成"整体读-加-整体写回"）；`transform.position.x = 5f` 是 **CS1612**（改的是返回的拷贝）→ 同属本册第 2 章"字段 vs 属性"

### 八、取组件与暴露字段
- `_rb = GetComponent<Rigidbody2D>();`：去**自己所在的 GameObject** 上找组件（找不到返回 `null`）；`transform` 本质就是白送的 `GetComponent<Transform>()`
- 放 `Awake`：生命周期最早、只跑一次，保证后续方法用时已接好
- `[SerializeField] private float speed = 8f;` = **对检查器开窗、对代码关门**（`public` 会拆掉封装墙）；运行时才赋值的引用（`_rb`）**不要**加
- **检查器里拖进去的字段值，在 `Awake` 时已经可用**（Unity 在反序列化阶段就填好了）→ 所以 `speed` 读到的一直是你设的值

### 九、⚠️ 2D / 3D 是两套物理引擎
| | 3D | 2D |
|---|---|---|
| 刚体 | `Rigidbody` | `Rigidbody2D` |
| 碰撞体 | `BoxCollider` | `BoxCollider2D` / `CircleCollider2D` |
| 渲染 | `MeshRenderer` | `SpriteRenderer` |

- 混用**不报错、静默失效**（2D 物体挂 3D `Rigidbody` = 完全不参与 2D 物理）

### 十、活动输入处理（旧 / 新 / 两者）
- `项目设置 → 玩家 → 其他设置 → 活动输入处理`：Unity 6 新项目模板默认「**输入系统包（新）**」→ 旧的 `Input.*` 会**直接抛异常**
- 学习期选「**两者**」（改完需**重启编辑器**）：两套 API 都能用；新输入系统（Input Actions + 按键重映射）留到需要多平台/自定义键位时专门学
- 心法：**API 不生效 → 先查项目设置，再怀疑代码**

### 十一、编码坑：VS2022 存 GB2312 → CodeBuddy 乱码
- 症状：同一文件 VS2022 中文正常，CodeBuddy（VS Code 系，默认按 UTF-8 解码）全是乱码
- 根因：VS2022 按中文 Windows 的**系统代码页（GB2312 / 936）**保存，没存成 UTF-8
- 修法：VS2022 `文件 → 高级保存选项` → **`Unicode (UTF-8 带签名) - 代码页 65001`**
- 为什么"带签名"（BOM）：文件头写死"我是 UTF-8"（`EF BB BF`），任何编辑器都不用猜
- Unity 要求 `.cs` 用 UTF-8（GBK 字节被按 UTF-8 解码 → 注释乱码，甚至编译报错）
- 校验技巧：`UTF8Encoding($false, $true)` 严格解码能过 = 合法 UTF-8；再看头 3 字节有没有 BOM
- 编辑器日志：CodeBuddy 输出面板的 `[info]` 只是正常心跳（识别工作区/仓库），**只有 `[error]` 才要管**

### 十二、Unity 项目进 git（首次入库实测）
- 待跟踪文件 39 个（`Assets/` + `Packages/` + `ProjectSettings/`），`Library/ Temp/ Logs/ *.csproj *.sln` 全被 `.gitignore` 拦住
- 验证手段：`git status --short --untracked-files=all` + `Select-String 'Library/'`（应为空）；`git check-ignore -v <路径>`（能看到是哪一条规则拦下的）

## 4. Prefab、实例化与场景装配（09-19）

### 一、Prefab = 模具，场景里的对象 = 副本

- **Prefab 源文件**住在 `Assets/Prefabs/`（拖进去后，层级窗口里那个对象的名字**变蓝** + 右侧出现「覆盖 / Overrides」按钮）
- 改**模具**（双击 Prefab 进编辑）→ 所有副本里**未被覆盖**的字段一起变；改**某个副本** → 只在它身上生效（会记一笔"覆盖"）
- 为什么要 Prefab：一次配好（外观/碰撞体/脚本参数），后面靠代码批量复制 —— 手摆 32 块是不可维护的

### 二、`Instantiate` 在做什么

```csharp
Instantiate(prefab);                          // 用模板自己的位置
Instantiate(prefab, 位置, 旋转);                // 常用
Instantiate(prefab, 位置, 旋转, 父物体);        // + 顺手挂父物体（坐标按世界空间解释）
```

| 步骤 | 内部干了什么 |
|---|---|
| ① 反序列化 | 把 `Assets/` 里那个 Prefab 文件（YAML/二进制）读出来 |
| ② 装配 | 按数据建出 GameObject + 各组件，把 `[SerializeField]` 的值填好，修好引用 |
| ③ 入场景 | 加进当前场景，触发 `Awake`/`OnEnable`（`Start` 等下一帧） |

**与 C# `new` 的分水岭**：

| | `new GameObject()` | `Instantiate(prefab)` |
|---|---|---|
| 造出什么 | **空壳**，一个组件都没有 | **一整套**（渲染/碰撞/脚本 + 数值全在） |
| 数据来源 | 从零构造 | 从磁盘上的模板**拷贝** |
| 成本 | 便宜 | **贵**（读文件 + 堆分配）→ 别放 `Update`，这就是对象池（09-22）的动机 |

**三条实操铁律**：
1. **返回值必须接住**（`GameObject b = Instantiate(...)`）—— 不接住对象照样存在，但你**再也拿不到它的引用**，以后想回收只能满世界 `Find`
2. **`Quaternion.identity` = 不旋转**（identity ≈ 数字里的 1）；注意第三格是**覆盖**：传 `identity` 会抹掉模板自带旋转 —— 想跟模板一致就传 `prefab.transform.rotation`
3. 副本名字带 **`(Clone)`** 后缀 —— 播放后看到一堆 `Brick(Clone)` 就说明复制成功

### 三、生成器（Spawner）该挂谁 + 容器要"干净变换"

| 候选 | 评价 |
|---|---|
| **场景级空物体**（`Board` / `GameManager`） | ✅ 职责匹配：管整局游戏，不参与画面 |
| 相机 | ⚠️ 能跑，但语义混乱（相机是"眼睛"） |
| 挡板 / 砖块自己 | ❌ 会移动、会连累逻辑；**挂在自己生成的东西上 = 指数爆炸**（见第六节事故 2） |

**容器（Board）保持 `位置(0,0,0)` + `旋转(0,0,0)` + `缩放(1,1,1)`** —— 这样子的**本地坐标 = 世界坐标**，所有算坐标的代码都不会错。要整体挪动只改它的**位置**。

### 四、`SetParent`：父子变换对子物体的三个影响

```csharp
brick.transform.SetParent(transform);   // 把生成的砖块挂到 Board 底下（默认保持世界位置不变）
```

| 改父物体的… | 子物体（砖块）会怎样 |
|---|---|
| **位置** | 整体**平移**，形状与间距比例不变 ✅ 安全 |
| **旋转** | 整片砖墙**跟着转** |
| **缩放** | 位置与尺寸**一起被乘** ⚠️ 形状可能变形 |

缩放的具体后果（`Board` 的 `scale.x` 改成 2）：砖块世界尺寸 `1.6×0.6 → 3.2×0.6`（**变宽变扁**）、相邻间距 `1.7 → 3.4`（阵列以父的本地原点为中心撑开）、`BoxCollider2D` 跟着放大。而**检查器里显示的是本地值**（还是 1.6/0.6）→ 从数据上看不出，只在 Scene 视图里看得出来。

**隐藏的连带坑**：`transform.localScale.x * 0.5f` 这种算"半宽"的写法只在**没有父物体 / 父缩放为 1** 时成立；一旦被缩放的父物体包住，要改用 `lossyScale`（世界缩放）或更稳的 `SpriteRenderer.bounds.extents`。

**挂成子物体后的坐标语义**：子物体的检查器「位置」变成**相对父的本地坐标**；`transform.position` 仍是世界坐标 —— 父在原点且无缩放旋转时两者数值相同，父一动就分家（第 2 章那个坑的现场版）。

### 五、正交相机的世界单位换算 + `Mathf` 速查

```
屏幕【全高】= orthographicSize × 2
屏幕【全宽】= 全高 × aspect
屏幕【半宽】= orthographicSize × aspect      ← 布局/边界最常用
```

- `Camera.main` = 标签为 `MainCamera` 的相机（**可能为 null**：场景里没有主相机时）；内部是按标签查找，**建议 `Awake` 里取一次存字段**，别每帧调
- 相机是**透视**时 `orthographicSize` 无意义（2D 模板默认正交）

| `Mathf` API | 作用 |
|---|---|
| `Clamp(v, min, max)` | 夹进区间 |
| `Clamp01(v)` | 夹到 0~1（进度条、插值 t） |
| `Abs / Max / Min` | 绝对值 / 取大 / 取小 |
| `Lerp(a, b, t)` | 线性插值 |
| `Approximately(a, b)` | 浮点近似相等（"别用 `==` 比浮点"的正解） |

### 六、⭐ 两起事故复盘（09-19）

**事故 1：字段初始化器里访问 `transform` → 报错**

```csharp
// ❌ 写在类成员位置（字段初始化器）
float halfPaddle = transform.localScale.x * 0.5f;
```
> 报错大意：`get_transform is not allowed to be called from a MonoBehaviour constructor (or instance field initializer), call it in Awake or Start instead.`

**生命周期顺序（关键）**：
```
C# 构造函数（字段初始化器在这里跑）  ← Unity 的"原生物体"还没和 C# 对象绑定
      ↓
    Awake  ← 从这里开始 transform / gameObject / GetComponent / Camera.main 才能用
      ↓
  OnEnable → Start → Update…
```
**修法**：需要引擎信息的计算全部搬进 `Awake`；只把**要跨方法用的结果**升成字段（如 `_limit`），中间量用局部变量。

**事故 2：生成器自引用 → 指数爆炸 → 编辑器假死**

- 症状：一进播放就卡死，任务管理器里 Unity 无响应
- 根因（从场景文件里挖出的证据）：`BrickSpawner` 挂在**场景里的 Brick** 上，而它的 `brickPrefab` 又指向**它自己**
  ```yaml
  # 场景文件里的证据
  --- !u!114 &1906376736                  # BrickSpawner 组件
    m_GameObject: {fileID: 1906376735}    # 挂在 Brick 上
    brickPrefab: {fileID: 1906376735}     # ← 指向自己！
  ```
  → `Instantiate(self)` 出来的每个副本**也带着生成器** → 32 → 32² → 32³ … 几秒几十万个物体 💥
- **正确姿势**：生成器挂**场景级空物体**；槽位拖的是 **Project 窗口里的 Prefab 资产**（引用里带 `guid`），**不是层级窗口里的对象**（引用里只有 `fileID`）—— 这是"我拖对了吗"的硬核判别法
- **救场流程**：① 任务管理器强杀 `Unity.exe`（播放模式的改动不会保存，场景不会坏）② 重启后若弹 **Recovering Scene Backups** 选「是」→ 备份进 `Assets/_Recovery/`（强杀前未保存的编辑只在这里）③ 打开恢复场景检查、修好、**`Ctrl+S` 存场景** ④ 确认无用后删掉 `_Recovery/`（别提交进 git）

### 七、防御性编程：给自己装保险丝

```csharp
if (cols <= 0 || rows <= 0) return;
if (cols * rows > 200)
{
    Debug.LogError($"砖块数量异常：{cols} × {rows}，已拒绝生成");
    return;
}
Debug.Log($"准备生成 {cols * rows} 块砖");   // 先打印"打算做多少"，出问题时日志能说明意图
```
原则：**对"外部输入"（检查器里手输的值、别人拖进来的引用）永远先做合法性检查，再动手**。

## 5. 碰撞、物理材质与反弹（09-21）

### 一、三件套的分工（一张表定死）

| | Collider2D | Rigidbody2D | PhysicsMaterial2D |
|---|---|---|---|
| 回答什么 | 我占多大空间、和谁接触 | 多少惯性、什么速度、谁在推动我 | 表面多滑、多能弹 |
| 数量 | 一个物体可以**多个**（头/身/脚） | 一个物体**只有一个** | 挂在 **Collider** 上（刚体级槽是 Unity 6 的便捷入口） |
| 没有它会怎样 | 撞不到任何东西 | 是静态几何体：不动、推不动、不产生回调 | 用默认值（摩擦≈0.4 / 弹性 0） |

**两条最容易反的**：
- **"检测"只要碰撞体，"响应"要刚体**：双方都没刚体 = 静态×静态 → **零回调**（所以静态墙之间没有事件）
- **子物体的 Collider 会挂到最近的父级刚体上**（复合碰撞体）→ 别给 `Walls` 这种容器随手加刚体

### 二、物理材质：混合规则（Combine Mode）—— 弹性是"成对算"的

一次碰撞要把双方的摩擦/弹性**压成一个数**才能算冲量，规则就是那两个下拉框：

| 规则 | 公式 | 现实模型 |
|---|---|---|
| 最小值 Min | `min(a,b)` | 最滑 / 最不弹的那方说了算 |
| Mean | `(a+b)/2` | 取中（Unity 默认） |
| 最大 Maximum | `max(a,b)` | 乒乓球撞水泥地（**弹性推荐**） |
| 乘积 Multiply | `a×b` | Box2D 经典摩擦默认 |

**本项目取值与理由**：

| 属性 | 值 | 理由 |
|---|---|---|
| 摩擦力 | 0 | 只想要"纯反射"；有摩擦会削横向速度、把轨迹带歪 |
| 弹性 | 1 | 满弹 |
| **反弹合并** | **最大** | 墙/挡板**即使不挂材质**（默认弹性 0）球也能弹满 |
| **摩擦组合** | 平均（默认） | ⚠️ **隐患**：墙默认摩擦≈0.4 → `(0+0.4)/2 = 0.2` → 贴墙轻微掉速 → **球与墙/挡板都挂同一材质**（0 与 0 混出来还是 0），或把摩擦组合改成"最小值" |

> 🧪 **对照实验（1 分钟，别跳过）**：把「反弹合并」从"最大"切成"平均" → 播放，球**越弹越矮**；切回"最大" → 恢复满弹。**混合规则不是纸面概念，它就写在球的高度上。**

### 三、Collider2D 家族：形状决定手感

| 碰撞体 | 形状 | 说明 |
|---|---|---|
| **Box Collider 2D** | 矩形（半宽 × 半高，可加"边缘半径"做圆角） | **最快**；墙 / 砖 / 挡板都该用它 |
| **Circle Collider 2D** | 圆（半径） | 第二快；**没有"角"**，反弹最干净 |
| Capsule / Polygon | 胶囊 / 凸多边形 | 更贴合、更贵，角色常用 |
| Edge / Composite | 线段 / 组合 | 地形、单向平台 |

- **外观与碰撞解耦**：Sprite 是给眼睛看的，物理只看 Collider → "图明明对上了却撞不到"通常就是这儿
- ⚠️ **球必须用 Circle**：套 Box 的话撞墙是**角**先接触 → 抖动、乱转向、卡墙角
- ⚠️ 勾了 **Is Trigger** 后**材质完全失效**（触发器不参与物理解算，只发 `OnTriggerEnter2D`）→ 09-22 做撞砖要在"物理碰撞"与"触发器"两条路线里选一条
- 技巧：**按住 Shift 拖手柄**只改 Collider 大小、**不改 Transform 缩放**（避免污染 `localScale` —— 挡板"半宽"就是靠它算的）

### 四、Rigidbody2D 面板逐项（按功能分四组）

| 组 | 项 | 说明 |
|---|---|---|
| **身份** | 身体类型 | Dynamic / Kinematic / Static（见本册第 3 章第五节；**Kinematic × Static 不产生回调**） |
| | 材质 | Unity 6 新增的"刚体级"入口；**权威仍在各 Collider 上**，本项目留空 |
| | 模拟的 | 物理总开关；关掉 = 位置冻结、不参与碰撞，但对象还在（暂停 / 尸体场景） |
| | 使用自动质量 / 质量 | 自动 = 面积 × 密度；质量只在"撞会动的物体"时才起作用（撞墙/挡板=无限质量，白设） |
| **耗散** | 线性阻尼 | 空气阻力，速度按指数衰减；0 = 永远不停 |
| | 角阻尼 | 自旋阻力，**默认 0.05 → 球建议改 0** |
| **环境与时间** | 重力大小 | 受重力倍数；**俯视图必须 0**（否则球直接掉出屏幕） |
| | 碰撞检测 | 离散 / 持续；持续 = 扫掠求交防高速穿墙（**只对 Dynamic 有效**） |
| | 休眠模式 | 速度低于阈值一段时间会"睡着" → 现象是"球莫名卡住"；球建议 **从不休眠** |
| | 插值 | 物理跑 50Hz、渲染帧率浮动 → 插值补帧防抖（外推会过冲） |
| **约束** | 冻结位置 / 旋转 | 物理层面的方向锁；挡板可勾"冻结位置 Y + 旋转 Z"做**双保险**（与代码 `Clamp` 互补：一个数学锁、一个引擎锁） |

### 五、球的配置 + 三面墙的数值来源

**球（Dynamic）**：重力缩放 **0** / 碰撞检测 **持续** / 线性·角阻尼 **0** / 休眠 **从不休眠** / 插值 → `CircleCollider2D`（材质 `BallMaterial`）。

> ✅ **自检法（推荐固化）**：**先不写任何代码，播放一次 → 球应悬在原地不动**。一步就能验证"重力缩放确实生效"，比事后靠现象倒推强。

```
屏幕半宽 = orthographicSize × aspect = 5 × 1.777 ≈ 8.89  → 墙中心 x = 8.89 + 半厚 0.25 = 9.14
屏幕半高 = orthographicSize           = 5               → 上墙中心 y = 5 + 0.25   = 5.25
```

|---|---|---|
| LeftWall / RightWall | x = ∓9.14 | `0.5 / 11` |
| TopWall | y = 5.25 | `19 / 0.5` |

- 容器 `Walls` **保持 (0,0,0) 且不缩放** → 子物体**本地坐标 = 世界坐标**，上表数值可直接填（本册第 2 章坐标坑的实战应用）
- **墙不加刚体**（默认即静态）；**下边界不封** —— 那是以后的"失败判定"位置

### 六、发球：`linearVelocity` 与 `normalized`

```csharp
_rb.linearVelocity = new Vector2(1f, 1f).normalized * speed;   // 只发一次 → 放 Start，不放 Update
```

- **Unity 6 里 `velocity` 已废弃** → 用 **`linearVelocity`**（写旧名会有过时警告）
- **必须 `normalized`**：`(1,1)` 长度为 `√2 ≈ 1.414`，不归一化就等于速度乘了 1.414 → 斜着发比直着发快，轨迹会怪
- 按键发球：读项目级 Input Actions 的动作（如 `Player/Fire`），或自建 `Gameplay` 地图（见本册回访清单）

### 七、`OnCollisionEnter2D(Collision2D other)` 拆解

```csharp
void OnCollisionEnter2D(Collision2D other)
{
    Debug.Log($"撞到 {other.gameObject.name}，撞后速度 {_rb.linearVelocity}，相对速度 {other.relativeVelocity}");
}
```

| 要点 | 说明 |
|---|---|
| 谁调用 | **引擎按名字点名**（与生命周期同机制）→ **拼错 = 静默失效**（写成 `OnCollisionEnter2d` / 漏掉 `2D` 都不报错） |
| Enter / Stay / Exit | 只在**开始接触那一帧**一次 / 持续接触每个物理步 / 分开那一帧 |
| `other` 是什么 | **碰撞报告**：`collider`（对方碰撞体）/ `gameObject`（对方物体）/ `rigidbody`（撞静态墙时为 `null`）/ `relativeVelocity` / `contacts`（接触点数组） |
| 为什么认 `other.gameObject` | 判断"撞的是砖还是挡板"要认**物体本身**（Tag / 组件），改名不影响 Tag |
| 速度是"撞后"的 | 回调在物理**求解完成之后**调用；想看撞击强度用 `other.relativeVelocity` |
| 触发前提 | 至少一方是**动态刚体** + 双方都没勾 Is Trigger |
| 对照 | `OnTriggerEnter2D(Collider2D other)` —— 只有碰撞体，**没有接触数据、没有冲量**（参数类型本身就是"信息量"的提示） |

**用途演进**：今天 = 让物理过程可见（X 光片）→ 09-22 = 识别 + 处理（撞砖消失）→ 收尾 = 用 `contacts[0].point` 算"打在挡板哪一侧"来改反弹角度（**打砖块手感的一半在这个偏移量上**）。

### 八、排查清单（今日结论）

| 现象 | 先查什么 |
|---|---|
| 球不弹 | 材质是不是挂到了**刚体**上（该挂 Collider）；重力缩放是否没归零；「反弹合并」是不是被改成了"平均" |
| 球穿墙 / 穿挡板 | 碰撞检测是否为"离散"；墙是不是太薄；主体类型是不是被误设成 Kinematic（**Kinematic 与静态墙根本不碰撞**） |
| 球莫名停住 | 休眠模式（改"从不休眠"）；线性/角阻尼被调大 |
| 球越弹越矮 | **不是错觉**：即使弹性 1，求解器仍有微小能量损失（穿透修正 + 容差）→ 收尾用"每帧锁速度"打磨 |

### 九、性能小结（为 09-22 对象池埋伏笔）

## 6. 对象池与 GC（09-22）

### 一、为什么需要对象池

| 操作 | 真实代价 |
|---|---|
| `Instantiate` | 读模板（反序列化）→ 建 GameObject + 各组件 → 装配 `[SerializeField]` 值 → 入场景 → **堆分配** |
| `Destroy` | **不是立刻回收**：Unity 先标记，真正的清理排在**帧末**；C# 那侧要等 **GC** |

- GC 的杀手不是"慢"，是**停顿**（stop-the-world：回收时主线程被按住）→ 分配越频繁/堆越大，越容易周期性掉帧（GC spike）
- **对象池 = 把运行中的分配次数变成常数**：开场一次性分配，之后只在 `SetActive` 之间切换 → 运行中零分配
- 附加知识：`Destroy(obj)` 之后**那个 C# 引用不等于 `null`（C# 意义上）**，但 `obj == null` 却为 `true`——Unity **重载了 `==`**，会去问引擎"还活着吗"；所以"销毁后访问"报的是 `MissingReferenceException`，不是空引用

### 二、池的四个设计决策

| 决策 | 结论 | 理由 |
|---|---|---|
| **容器** | `Queue`（或 `Stack`） | 语义是"只在一端进出"→ 用窄接口把约束焊进类型。`List` 也能 O(1)（取出与归还**都用尾部**），但它允许 `RemoveAt(0)` → **O(n)**，编译器不拦。**接口越窄，误用越不可能**（同 `IReadOnlyList` 思想） |
| **池空** | `LogError` + `return null` | 预分配数 = 总需求 → 池空只可能是**逻辑 bug** → 响亮地失败；调用方仍要判空 |
| **归还时重置** | 位置/旋转**不重置**（借出时统一设置）；父子关系用"归属检查"兜住 | 单一保证点：**谁发出去谁负责初始状态**；将来有血量/颜色等可变状态时，必须在归还处清（否则"带着上次的伤复活"） |
| **⚠️ 双重归还防线** | `if (!brick.activeSelf) return;` | 池里的物体**一定失活** → 免费 O(1) 的标志。没它 = 同一对象入池两次 → 借出同一个对象两次 → **分身幽灵 bug** |

### 三、骨架（结构，不是实现）

```
预分配（Start）：循环创建 → SetActive(false) → Init(注入) → 入池 → _instantiateCount++
借出（Rent）  ：池空? LogError+null : Dequeue → SetActive(true) → _rentCount++
归还（Return）：判空 → 判归属 → 判是否已在池中(!activeSelf) → SetActive(false) → 入池
```

- **保险丝要在"动手之前"**：`cols <= 0 || cols*rows > 200` 这类检查必须挡在 `Instantiate` **之前**，放进 `FillBoard` 就晚了（生成已经发生）
- `SetActive(false)` **不会打断当前方法**：它只是把物体标记失活，**正在执行的方法会继续跑完**（与 `return` 是两码事）

### 四、依赖注入：Prefab 不能引用场景对象

- **现象**：给 Prefab 上的脚本加 `[SerializeField] BrickSpawner _pool` → **拖不进去**
- **原因**：Prefab 是**资产**（可被多个场景共用），场景对象是**实例** → 资产不能绑定某个场景实例
- **解法（运行期装配）**：池在预分配时 `brick.Init(this)` —— 普通方法，**不是引擎回调**，由你自己调用；**"这块砖属于这个池"是永久关系 → 建立一次就够**
- **对照**：`[SerializeField]` = 编辑器期装配（反序列化阶段就填好）；`Init(this)` = 运行期装配（依赖注入雏形，Block 3 委托/事件的前身）

### 五、怎么证明池真的在跑（验收三件套）

1. **预分配次数恒定**（`_instantiateCount` 开场 32 之后不再增长）
2. **借出计数 = 场上物体数**（`_rentCount`）
3. **归还后池水量回升**（`池中剩余` 从 0 往上涨 → 这是"有借有还"的唯一硬证据）
4. 层级窗口里物体总数**恒定**（灰掉的还在）

> **教训**：机制类改动必须用"能证明它在跑的数据"验收，而不是"看起来对"——砖块消失这件事，**"自己 SetActive"和"归还给池"两种实现产生的现象完全一样**。

### 六、易踩点清单

| 现象 | 原因 |
|---|---|
| 复用出来的物体带着上次的位置/状态 | 借出时没设初始状态 / 归还时没清可变状态 |
| 一块砖同时出现在两个位置 | **双重归还**（池里两份相同引用） |
| 池空后空引用崩溃 | `Rent()` 静默返回 `null`，调用方没判空 |
| 下次借出拿到 `null` | 归还时用了 `Destroy` 而不是 `SetActive(false)` |
| 开场编辑器假死 | 保险丝放在了生成**之后**，或数量上限没设 |

## 7. 碰撞进阶与手感（09-22）

### 一、`contacts` 数组：什么时候真的会空

- **理论上**：`OnCollisionEnter2D` 时接触流形刚刚建立 → **至少 1 个点**（引擎语义保证）
- **但这是"通常成立"，不是"契约保证"**（所以判空是**对准真实脆弱点**的廉价保险，和 219 那种凭感觉的保险丝不同）：
  1. `Collision2D` 是**复用包装对象**——只在回调期间有效，**存起来下次读就是空的**（"**存值不存包裹**"）
  2. 同一物理步内更早的回调把碰撞体禁用 → 后续数据可能不完整
  3. 版本/后端实现差异、位置修正（slop）
- **0 个 / 多个的根源是几何**：圆↔圆 1 点、圆↔面 1 点、**方↔方 面贴面最多 2 点**；顺序**无保证**，不要做位置假设；读数用 `other.contactCount` / `other.GetContact(i)`
- `ContactPoint2D` 是 **struct**（值类型）→ 先取到局部变量**不产生堆分配**，可放心为可读性多写一行

### 二、卡顿与"漏事件"全景（易混，值得单独记）

| 现象 | 事件会漏吗 | 根因 | 解法 |
|---|---|---|---|
| 物体太快，一步跨过对方 | ✅ 会（接触从未发生） | 离散检测 | 碰撞检测 = **连续** |
| **极端卡顿** | ✅ 会 | 超过 `最大允许时间步长`（默认 0.333s）→ **丢步**，被丢的物理步不执行 | 优化性能（对象池就是在干这个） |
| 回调之后再读 `contacts` | ✅ 数据没了 | 包装对象复用 | 当场读、**存值不存包裹** |
| 接触中被 `SetActive(false)` | ✅ 可能收不到 `Exit` | 接触对被移除 | 别把关键逻辑只挂在 `Exit` |
| 卡顿 → 一帧跑多个物理步 | 反向问题：`Stay` 一帧被调多次 | 固定步长追赶 | `Stay` 里累加要乘 `fixedDeltaTime` 或做幂等保护 |

**架构结论**：**事件为主 + 状态兜底** —— 事件负责"精确一次"的动作（撞砖→消失/加分），**状态查询**负责"持久正确"的信息（分数应能从"剩余砖块数"重算，漏一次事件也不会永久跑偏）。

### 三、静默失效四连（不报错 ≠ 执行了）

| # | 写法 | 后果 |
|---|---|---|
| 1 | 生命周期方法拼错（`OnCollisionEnter2d`） | 永不执行 |
| 2 | `CompareTag("paddle")` 大小写/拼写错 | 恒 `false` |
| 3 | 忘把脚本挂到 Prefab 上 | `GetComponent` 返回 `null` |
| 4 | **标签只加在编辑器内存里、没"保存项目"，或场景对象没贴标签** | 恒 `false` |

**通用判据：改完逻辑必须留一个"它在跑"的证据**（`Debug.Log` / 计数 / 数据变化）。**没有证据的"手感变化"，都是安慰剂。**

### 四、手感接管：击打点改角度（Pong / Breakout 的灵魂）

**为什么必须自己接管**：球撞**水平挡板**时接触法线竖直 → 反射角与击打位置**无关**。物理给的是"几何正确"，玩法要的是"好玩"——这就是**"物理给结果、玩法给手感"**的分界线。

**四步**：① 门卫判定是不是挡板 → ② 取击打点偏移 → ③ 归一化成 `t ∈ [-1, 1]` → ④ 用 `t` 造方向并**锁速率**覆盖速度。

| 数据源 | 范围 | 代价 |
|---|---|---|
| **球心**：`transform.position.x - other.transform.position.x` | ±(半宽 + 球半径) = ±1.8 | 简单、不会空；含球半径，边缘提前饱和 |
| **接触点**：`GetContact(0).point.x - other.transform.position.x` | ±半宽 = ±1.5 | 精确；**必须先判 `contactCount > 0`** |

**覆盖速度的三条纪律**：
1. `dir.normalized` **之后再乘速率**（方向管"往哪飞"、长度管"多快"，两件事分开）
2. **保证 y 分量 > 0**（否则球水平平推、在两侧墙间横跳、永远不再落到挡板 → 卡死）
3. 在**碰撞回调里改**（物理求解已完成，改下一步生效）；**不要每帧覆盖**，那会把物理结果全抹掉

**角度映射的两代写法**：

```csharp
// 第一代：(t, 1).normalized —— 角度 = atan(t)，t 越大越平，边缘区分度变差
Vector2 dir = new Vector2(t, 1f).normalized;

// 第二代：按角度线性映射 —— 每 1% 偏移 = 相同度数的转向，边缘不再"发死"
[SerializeField] private float maxBounceAngle = 60f;   // 边缘最大偏角（度）
float angle = t * maxBounceAngle * Mathf.Deg2Rad;
Vector2 dir = new Vector2(Mathf.Sin(angle), Mathf.Cos(angle));
```

> 代价：换写法后**已调好的手感要重调一遍**（`t=1` 时 63° → 60°）。取舍自己定。

**抽象时机**（今天特意**没有**抽）：

```
内联算式 → private 方法（现在） → 静态工具类（第二个真实调用方出现时）
```

- 只有一个调用方 → **留在原类内 + `private`**（`public` 要能点出"谁在调"）
- 真要共享 → **静态工具类**（`public static class HitUtil`），**不是 MonoBehaviour**：纯计算没有生命周期/状态，做成组件只会多一个"忘挂就静默失效"的坑，还进不了编辑器工具/单元测试
- 抽出去的**真实成本**：静态方法没有 `this`，"谁的目标"必须**显式传参**（上下文显式化）

### 五、补充：材质是"成对计算"的（今日实战）

- 一次碰撞的摩擦/弹性 = **两个碰撞体材质的混合值** → 谁漏挂，都按"默认材质（摩擦≈0.4 / 弹性 0）"参与混合
- 本项目实战：**球自己的碰撞体没挂材质** → `Mean(0.4, 对方 0) = 0.2` → 撞谁都被"搓"：掉速 + 变向；弹性走"最大" `max(0,1)=1` 所以**照弹**——现象是"弹得挺好但越来越歪"
- **认知纠偏**：**"现象最明显的地方"≠"根因所在"**（撞挡板变化最大，但根因在**球**——它是**每一对碰撞里共用的那一方**）
- 排查手段：**缓存"撞前"速度**（`FixedUpdate` 里存 `linearVelocity.magnitude`，它在物理模拟**之前**执行），在 `OnCollisionEnter2D` 里打印"撞前 → 撞后"

## 8. UGUI 与 TextMeshPro（09-23）

### 一、Canvas = UI 的"另一个世界"

| 渲染模式 | UI 活在哪儿 | 用途 |
|---|---|---|
| **屏幕空间 - 叠加**（默认） | 直接贴屏幕，永远盖在画面上 | **HUD / 计分 / 血条** ← 本项目 |
| 屏幕空间 - 摄像机 | 挂在某台相机前，跟着相机走 | 需要被 3D 物体遮挡 / 后处理 |
| 世界空间 | 变成世界里的一块平面，有位置有朝向 | 游戏内面板 / 告示牌 / VR UI |

- **UI 元素不活在游戏世界里**：它们用 **`RectTransform`**（不是 `Transform`），坐标属于 Canvas 这个独立坐标系
- **UI 用像素、世界用单位**，两套尺度互不相干（`50` 在 UI 里是 50 像素，在世界里是 50 单位 = 整个屏幕还大）
- ⚠️ 叠加模式下 Canvas 的 RectTransform 里 `LocalScale = (0,0,0)`、`sizeDelta = (0,0)` 是**引擎驱动的占位值**，**别去动它**（不是问题）

### 二、RectTransform 四件套（面板 ↔ 代码对照）

| 面板项 | 代码 | 含义 |
|---|---|---|
| **位置 X / Y** | `anchoredPosition` | **相对锚点的偏移（像素）**——不是世界坐标，也不是本地坐标 |
| **锚点 Min/Max** | `anchorMin` / `anchorMax` | 归一化 0~1，相对**父 RectTransform** 的矩形 |
| **轴心** | `pivot` | 归一化 0~1，**自身矩形内的参考点** |
| **宽度 / 高度** | `sizeDelta` | 点锚点下 = 实际宽高；拉伸锚点下 = 与父矩形的差值 |

**关键区分（今天踩的坑）**：
> **锚点**决定"相对父容器的哪个点定位"，**轴心**决定"自身哪一点对准那个位置"。

- 想"左上角贴边 40/30" → **锚点 (0,1) + 轴心 (0,1)** + 位置 (40,−30)
- 若轴心留在默认 `(0.5,0.5)`，同一个位置数值会让元素**中心**落在那里 → 400 宽的框会有一半伸到画布外 → **被切**

**定位公式**：
```
世界位置 = Canvas 位置 + 锚点在父矩形中的位置 + anchoredPosition − 轴心影响
```

### 三、Canvas Scaler 三件套

| 字段 | 说明 |
|---|---|
| **UI 缩放模式** | `常量像素大小`（画布 = 屏幕像素数，小窗口会挤爆）／**`按屏幕大小缩放`**（推荐）／`常量物理大小`（按 DPI） |
| **参考分辨率** | **= 美术设计稿尺寸**（1920×1080 是主流基准）⚠️ **不是"我屏幕多大就填多大"**：基准放大 → 同一字号显得越小（800×600 → 1920×1080 后，36 号字的观感直接砍半） |
| **屏幕匹配模式** | `Match Width Or Height`（推荐，配合下面的匹配滑条）／ `展开`（取较小缩放系数 → **绝不裁切**，会多留白）／ `Shrink`（取较大者 → **可能裁掉**超出画布的内容） |
| **匹配（Match）** | 0 = 完全跟宽度（保左右）｜ 1 = 完全跟高度（保上下）｜ **0.5 = 折中**（对数插值） |
| **每单位像素参考** | 只管**精灵/图片**的原生尺寸换算（Sprite PPU ↔ 画布 PPU），**与文字无关**；**默认 100 不要动** |

**UI 会不会被"压缩变形"？不会。** 缩放系数是**单一标量**（等比）→ UI 只会整体放大缩小。**只有"超出画布矩形"的部分才不渲染**（= 被切）。

### 四、TextMeshPro（TMP）

- **来源**：包 `com.unity.ugui`（`Packages/manifest.json`），代码程序集 `Unity.TextMeshPro`，命名空间 **`TMPro`**

  → 字段用 `TMP_Text`（基类）更通用（09-15 抽象类的实战价值）

### 五、UI 的性能纪律（与对象池同源）

1. **重建由"数据变化"决定，不由"代码每帧执行"决定**：`Text.text` 的 setter 会先比较——**值相同就提前 return，不标记 dirty、不重建**（脏检查）
2. **但"每帧执行"仍有代价**：`_score.ToString()` **每次都在堆上新建字符串** → GC 垃圾（对象池解决的是同一类问题）
3. **`Auto Size` 不要开**：每次改文字都重新算字号 → 放大重建
4. **自动布局组件（Layout Group / Content Size Fitter）会把"改文字"升级为"重新排布"** → 顶点重建 + Canvas 重新合批，最贵
5. **纪律**：**写 UI 由"数据变化"触发，而不是由 `Update` 触发**

```csharp
// ❌ 每帧制造垃圾（值不变虽不重建，但字符串照分配）
void Update() { _text.text = _score.ToString(); }

// ✅ 只在变化时写（无垃圾、无重建）
public void AddScore(int delta) { _score += delta; _text.text = _score.ToString(); }
```

6. **验证工具**：Profiler 看 `GC Alloc`（有没有垃圾）+ `Canvas.SendWillRenderCanvases`（重建耗时）

## 9. 架构决策、状态与配置陷阱（09-24）

> 今天从"加三个功能（胜负判定 / 场景重载 / 重开按钮）"起手，实际练的全是**结构题**：
> 依赖该往哪个方向走、数据该从哪来、守卫该放哪、UI 该靠什么跟世界分开。
> 成品：打砖块 **通关 / 失败 / 重开** 闭环跑通。

### 一、⭐ 依赖方向：裁判模式（方案甲 vs 方案乙）

**背景**：`BrickSpawner` 原本"加分"→ 认识 `ScoreManager`；现在又要判"通关"→ 需要"剩余砖块数"。若让 `ScoreManager` 反向去问 `BrickSpawner`，就成环。

| 方案 | 依赖图（箭头 = "知道"） | 代价 |
|---|---|---|
| 乙 · 事件通知 | `BrickSpawner → GameManager` **且** `GameManager → BrickSpawner` | ⚠️ **成环**（除非把数据塞进通知参数里绕开） |
| **甲 · 状态派生（采用）** | `GameManager → BrickSpawner`（只读状态）＋ `GameManager → ScoreManager`（只写显示） | 每帧一次减法（可忽略）；**全图无环** |

**结论**：**上层知道下层，下层谁都不认识。** 以后加"关卡 / 暂停 / 复活"，改动只落在 `GameManager` 一个文件里。

> 环为什么是坏味道（不是情绪，是工程代价）：
> ① 两个类**谁也不能单独测试**（想测 A 得先造一个真的 B）
> ② `Awake` 初始化顺序**靠运气**
> ③ 改一处要同时担心另一处

### 二、⭐ 状态派生 vs 事件累加（幂等从哪来）

| | 事件累加（旧 `AddScore`） | 状态派生（新 `SetDestroyedCount`） |
|---|---|---|
| 写法 | `_score += delta` | `显示 = f(打掉几块)` |
| 正确性靠 | **调用方只喊一次的纪律** | **结构本身**（喊一次和喊一百次一样） |
| 所以 | 09-23 得把加分塞进池的"三道防线之后"才敢用 | 09-23 那条伏笔直接销账 |

**判据**：**能"从状态重算"的量，就不要用"事件累加"去维护。**

⚠️ 一个容易忽略的顺序：`SetDestroyedCount(...)` 必须在"判通关"**之前**。反过来的话，最后一块砖被打掉那一帧会直接 `Win()` 返回，**分数停在 310**。

### 三、⭐ 存量 vs 流量（同一个数字，两种身份）

`RemainingBricks` 该用 `_instantiateCount` 还是 `_rentCount`？两者今天**数值相等**，但：

| 量 | 语义 | 由什么驱动 | 身份 |
|---|---|---|---|
| `_instantiateCount` | 世界里**一共有多少块砖** | `Instantiate`（创造） | 📦 **存量** |
| `_rentCount` | **"借出"这个动作发生过几次** | `Rent()` 被调用 | 🌊 **流量** |

**严格判据 —— 哪个是恒等式**（`N` = 砖总数、`B` = 累计借出、`R` = 累计归还、`P` = 池中数）：

```
每块砖在任意时刻只有两态（在池 / 在场）→ 这是一个"划分"
      场上 = N − P               ← 恒等式，永远成立 ✅
而    P = N − B + R
      B − P = 2B − N − R         ← 只有 B = N 时才等于"场上"
```

**`B ≠ N` 会发生吗？会。** 同一块砖 `Return` 回池后**可以再次被借出**。今天恰好 `B == N`，只因为 `Rent()` 只在 `FillBoard()` 里调、而 `FillBoard()` 只在 `Start()` 里跑**一次** —— **这是当前调用图的巧合，不是两个量之间的关系。**

未来会翻车的场景：加"补砖"机制后某列打光再借 4 块 → `N=32, B=36, R=5, P=1` → `B − P = 35`，而真实场上只有 **31**。

**判据（通用，拿去用一辈子）**：

| 名字里带 | 是 | 例 |
|---|---|---|
| **次数 / 累计 / 计数** | 🌊 **流量**（记录"发生过什么"） | `_rentCount`、`_hitCount` |
| **总数 / 当前 / 剩余 / 数量** | 📦 **存量**（描述"现在是什么状态"） | `_instantiateCount`、`_pool.Count` |

**问"现在"→ 用存量；问"一共几次"→ 用流量。** 诊断日志问的是"借出过几次"，用 `_rentCount` 完全正确 —— **各归各位**。

> 🔁 这是错误 06「**碰巧对 ≠ 保证对**」的又一次现身：靠隐式前提成立的正确性，改一个调用点就静默失效。

### 四、⚠️ 序列化字段：编译器看不见的输入

`[SerializeField] private GameManager gameManager;` 的赋值**不在代码里** —— 由 Unity 加载场景时填入。

- 编译器看到的是"一个从未被赋值的引用字段" → **完全合法**（默认 `null`）
- 所以 **编译器 / `ReadLints` / IDE 全都抓不到这个 bug**，**只有真跑 + 看控制台才会暴露**

**场景 YAML 里的判据**：

```yaml
gameManager: {fileID: 0}           # ❌ {fileID: 0} = null（槽位没连）
gameManager: {fileID: 400841083}   # ✅ 已连
```

**排查命令**（照抄可用）：

```powershell
Select-String -Path Assets\Scenes\SampleScene.unity -Pattern 'gameManager:|m_MethodName|m_IsTrigger'
```

> **"编译通过" ≠ "能跑对"** —— 编译只覆盖"代码层面"，配置是另一个战场。
> **按钮绑定的自查**：搜 `m_MethodName` —— 有输出 = 绑上了**且已落盘**；空输出 = 没绑上 **或场景没保存**。
> ⚠️ 反过来也别被日志骗：`Editor.log` 里"最后一条错误"可能是**历史残留**（编译成功时不会再写新的错误行）→ 判据是 **`Library/ScriptAssemblies/Assembly-CSharp.dll` 的时间戳 vs 源码时间戳**。

### 五、⭐ 入口上锁 ≠ 全局上锁（守卫要放在唯一出口）

今天最漂亮的一个 bug —— **静态看代码看不出来**，只有真跑才会暴露：

```csharp
void Update() {
    if (_isGameOver) return;                        // ← 锁在【入口】
    if (brickSpawner.RemainingBricks == 0) Win();
}
public void OnBallLost() { Lose(); }                // ← 这条侧门【绕开】了 Update
```

**复现路径**：打光最后一块砖 → `Win()` 显示 `YOU WIN` → 球还在飞 → 漏进 `FailZone` → `OnBallLost → Lose → End` → **结果被覆盖成 `GAME OVER`**。**你赢了，屏幕上写着"你输了"。**

**修法**：守卫搬到**唯一出口**。

```csharp
private void End(string message) {
    if (_isGameOver) return;   // ★ 守卫必须在"标记结束"的【前面】
    _isGameOver = true;        // 先上锁，再干别的
    ...                        // 副作用
}
```

**判据**：
- 数一数：入口有几个、出口有几个？→ **守卫放在最窄的那道门**（出口通常只有一个）
- ⚠️ 顺序：`if (已结束) return;` 必须在 `标记结束 = true;` **之前**（写反了第一次都进不来 —— 错误 07"守卫条件写反"同款）

### 六、⚠️ "空值"与"未初始化"是两件事

```csharp
if (brickSpawner == null || scoreManager == null) return;   // 防的是"引用没连"
```

它防不住**"这一局还不成立"**：

```
Board 的 Cols 改成 0 → 保险丝 LogError + return
  → _instantiateCount = 0、_pool.Count = 0
  → RemainingBricks 算出 0 → 开场第一帧 YOU WIN（毫无提示）
```

**修法**：再补一道用"能表达『这一局还不成立』"的量做的守门条件：

```csharp
if (brickSpawner.TotalBricks == 0) return;   // 还没摆砖 / 保险丝拦下了
```

**同一个病在字段层面**：`ScoreManager._lastDestroyed` 初始值给 `-1` 而不是 `0` —— 因为 `0` 是一个**合法的**"打掉 0 块"，用 `0` 当哨兵就分不清"还没画过"和"画了 0"。

> **手筋**：**给一个业务上不可能出现的值当哨兵。**

### 七、`Debug.Log` 的位置，决定它能证明什么

```csharp
gameManager.OnBallLost();          // ← gameManager 是 null，这里抛 NRE
Debug.Log("球掉进了 FailZone");     // ← 异常把它截断了，永远不打印
```

**现象 = "日志没打印" → 得出错误结论"回调没被调用"**。真相是：**回调调用了，炸在半路。**

| 日志放哪 | 它证明什么 |
|---|---|
| **第一行** | ✅ 「**我到达了这里**」——后面炸没炸是下一件事 |
| **最后一行** | ❌ 「前面全都成功了」——一旦前面有问题，它什么都证明不了，还给你错误结论 |

**规则**：**验证性日志放在你怀疑的那一段的最前面** —— 让它证明"到过"，而不是"走完"。

> 与错误 12「改完逻辑必须留一个**它在跑**的证据」、09-23「**磁盘才是事实**」同族。这一族的总名：**「证据要放在能证伪的位置」**。

### 八、⚠️ UI 与世界是两套坐标系（不是层级问题，是位置问题）

**反直觉事实**：`屏幕空间 - 叠加` 的 Canvas **永远画在世界画面之上** —— 世界里的精灵**不可能**遮挡 UI。
所以"文字被砖块挡住"的真相是**位置撞车**：

```
相机 orthographicSize = 5 → 视野高 10 世界单位 = 1080px → 1 世界单位 = 108px
砖块行 y = 3.5 / 2.7 / 1.9 / 1.1  →  屏幕中心往上 +378 / +292 / +205 / +119 px
∴ 砖块区 ≈ +90 ~ +420 px；挡板 ≈ −475 px；空区 ≈ −400 ~ +80 px
```

**但"挪位置"是隐式耦合**：把 `origin.y` 从 3.5 改成 2.0，砖块整体下移 162px → **又压上了**。

**正解：用结构，不用数值。**
① 给结束画面加**全屏半透明底板**（UI → 图像；黑 + `A≈150`）
② 把 `ResultText` / `RestartButton` **拖成底板（`Overlay`）的子物体**

两条引擎规则让代码**变短**：

| 规则 | 收益 |
|---|---|
| **子物体永远画在父物体之上** | 底板自动在文字/按钮**下面**，**不用手动排序** |
| **`SetActive` 有传染性** | 父物体失活 → 子物体全失活 → **一句 `overlay.SetActive(...)` 管住三样**，还省掉一个字段 |

> **判据**：**凡是靠"当前数值恰好不冲突"成立的东西都是脆弱的；用层级/结构把约定变成显式关系。**

### 九、场景重载：什么被清掉，什么不会（今日底层原理）

| | 会不会随重载复位 |
|---|---|
| 场景里的 GameObject / 组件 / **实例字段**（分数、池、球的位置…） | ✅ **会**（它们的"生命"属于**场景**） |
| **`static` 字段、`Time.timeScale` 等全局设置** | ❌ **不会**（挂在**类型/进程**上，程序集不卸载） |

```csharp
// End()：借出这笔账
Time.timeScale = 0;   // ⚠️ 全局静态设置
// Restart()：必须还回来
Time.timeScale = 1;   // 忘了 → 重开后的新一局是【冻结的】
```

**这就是"重开不用写一行『分数清零 / 池重填 / 球归位』"的原因** —— 那些东西本来就会随场景重载复位。

**顺手实测的三个答案**（`Time.timeScale = 0` 之后）：
- `Update()` **还跑**（不依赖时间步进）
- `FixedUpdate()` **不跑**（物理时钟停摆 → 球和挡板一起冻结）
- **UI 按钮还能点**（EventSystem 用 `unscaledDeltaTime`，**UI 不受 `timeScale` 影响**）

**`LoadScene` 的前提**：当前场景必须在「文件 → 生成配置文件」的**场景列表**里，否则会静默失败。

## 10. Animator、CanvasGroup 与音频（09-25）

> 今天给打砖块装上"**结局的表现**"：黑幕淡入 + 三个音效。
> 真正花时间的不是代码，而是**三条"看不见的线"**：`timeScale` 的影响力半径、**保存链路**、**同相位叠加**。

### 一、四个"Anim"先分清（混了就寸步难行）

| 东西 | 一句话 | 文件 | 谁引用谁 |
|---|---|---|---|
| **AnimationClip**（动画剪辑） | "**哪个属性**，在**第几秒**，是**什么值**" —— 一堆关键帧 | `.anim` | — |
| **AnimatorController**（动画控制器） | 一台**状态机**：状态 + 箭头 + 参数 | `.controller` | 每个 State 指向一个 Clip |
| **Animator 组件** | 挂在物体上的**播放器**：读 Controller，把值写回物体 | 层级/Prefab 上 | 读 Controller |
| **Animation 窗口** | **编辑器**（录制/编辑 Clip），**运行时不存在** | — | — |

> ⚠️ 另有一个曾经的 **`Animation` 组件**（只能播单个 Clip、没有状态机）—— **那个才是旧版/遗留**，只作了解。**`Animator` 是当前主流**。
> ⚠️ **「动画」窗口做 Clip，「动画器」窗口做状态机** —— 两个不同的窗口，别混。

### 二、`AnimationClip` 里到底存了什么

**关键帧 = "某个组件的某个属性，在第几秒，等于什么"。**
所以做动画有三步：① 选物体 ② `添加属性` 选**要动哪个属性** ③ 在时间轴上打关键帧。

**创建 Clip 的完整动作链**（Unity 会自动补后面几步）：

```
选中物体 → 打开「动画」窗口 → 点【创建】→ 存 xxx.anim
   → Unity 自动生成 xxx.controller，并给物体挂上 Animator 组件
```

### 三、⭐ 做 UI 淡入：为什么用 `CanvasGroup` 而不是动画 `Image.color`

| 候选 | 后果 |
|---|---|
| 动画 `Image.color` 的 alpha | ❌ 只有**那一块板子**淡入；文字和按钮会**"啪"地满不透明地跳出来**；而且颜色值被动画**写死** |
| **`CanvasGroup.alpha`** ⭐ | ✅ **整组一起淡入**（`alpha` **乘法传播**给所有子物体，除非子物体勾了 `Ignore Parent Group`）；颜色/内容仍归你管 |

**`CanvasGroup` 三件套**：

| 字段 | 管什么 |
|---|---|
| `Alpha` | 整组透明度（传播给子物体） |
| **`Interactable`** | 整组**要不要响应交互**（按钮还能不能被点；会显示成 disabled 外观） |
| **`Blocks Raycasts`** | 整组**参不参与射线检测**（不参与 = 点击**穿透**到它背后的 UI） |

> **两个开关的判据**：**`Blocks Raycasts` = 碰不碰得到 ｜ `Interactable` = 碰到了管不管。**
> **"看不见" ≠ "点不到"** —— `SetActive(false)` 是"物体不存在"（天然点不到）；`alpha = 0` 是"还在，只是透明"（**看不见但照样接点击**）。
> **所以配置三件套时，先问一句："我的隐藏机制是哪一种？"**

### 四、⭐ `Update Mode`：`Time.timeScale` 的"影响力半径"

**打砖块里 `End()` 会设 `Time.timeScale = 0`（冻住球和挡板），结果黑幕永远淡不进来。**

原因：`Animator` 组件的 **`Update Mode` 默认是 `Normal`，它跟着 `Time` 走 → 被 `timeScale = 0` 冻死**。

| `Update Mode` | 跟谁走 | 受 `timeScale` 影响 |
|---|---|---|
| **`Normal`（默认）** | `Update` | ✅ 受 → **暂停时冻住** |
| `Animate Physics` | `FixedUpdate` | ✅ 受 |
| **`Unscaled Time`** | 真实时间 | ❌ **不受** ← UI 表现层要选它 |

**这是 `Time.timeScale` 的第二笔账**（第一笔：**它不随场景重载复位** → `Restart()` 里要还）：

> **判据**：写下 `Time.timeScale = 0` 之前先问：**"我到底想冻住什么？"**
> - 只想冻**玩法** → `timeScale = 0`，但把 **UI 表现层的时钟换成 Unscaled**
> - **对照表**（`timeScale = 0` 之后）：
>   | 东西 | 受影响吗 |
>   |---|---|
>   | `Update()` | ❌ 照跑 |
>   | `FixedUpdate()` / 物理 | ✅ 停 |
>   | `Animator`（`Normal`） | ✅ 停 |
>   | **`AudioSource`** | ❌ **完全不受影响**（音频走独立时钟） |
>
> **"游戏世界停下来，表现层继续走"** —— 这才是一个暂停该有的样子。

### 五、⚠️ 动画窗口的「添加事件」陷阱：一个空事件能让整个 Clip 变成坏数据

**现象**：控制台报 `'Overlay' AnimationEvent has no function name specified!` → **Unity 拒绝保存** → 连带**场景、Controller 全都存不下去**。

**病因**（扒 `.anim` 文件看到的）：

```yaml
  m_Events:
  - time: 0
    functionName:          # ← 空！
```

**6 个空的 `functionName`，全部 `time: 0`** —— 在时间轴上叠成一个点，界面上**根本看不见**。

**这一条链条值得整个记住**：

```
手滑点了「添加事件」
  → Clip 里多一个空事件 → Clip 变成【坏数据】
  → 控制台报错 → 【保存被拒】
  → 场景没存（磁盘还停在昨天）
  → Controller 没存（m_AnimatorLayers 还是 []）
  → 运行时自然什么都不发生
```

> ⚠️ **「添加事件」按钮不要随手点**（它有正当用途，但不是今天）。
> 💡 **抢救手法**：`.anim` 是文本 YAML → **记事本打开，把 `m_Events:` 那一段删掉**（或改成 `m_Events: []`）→ 保存 → Unity 自动重新导入 ✓

### 六、Animator 组件上两个名字很像的下拉

| 下拉 | 管什么 | 三个选项 |
|---|---|---|
| **更新模式**（`Update Mode`） | **用哪个时钟驱动动画** | 普通 / 动画物理 / **非缩放时间** |
| **剔除模式**（`Culling Mode`） | **看不见时要不要省着跑** | 总是动画化 / 剔除更新变换 / 完全剔除 |

**记法**：**「更新模式」= 时钟（什么时间） ｜ 「剔除模式」= 开关（要不要省）**

### 七、音频三件套

| 东西 | 是什么 | 在哪 |
|---|---|---|
| **`AudioClip`** | **一段声音数据**（`.wav`/`.mp3`/`.ogg`）；对象层面带 `length` / `frequency` / `channels` / `samples`；**数据层面就是那一串 `float` 采样点** | 资产 / 运行时内存 |
| **`AudioSource`** | **喇叭**：Clip + 音量 + 循环 + 空间混合 | 挂在物体上（可多个） |
| **`AudioListener`** | **耳朵**：场景里**只能有一个**（多个会警告）；默认在 `Main Camera` 上 | 已有 |

**类比**：`AudioClip` = **唱片**（一张可被多个唱机同时放） ｜ `AudioSource` = **唱机** ｜ `AudioListener` = **耳朵**

| API | 行为 | 用在哪 |
|---|---|---|
| `Play()` | 播 `clip` **字段**里那一个，**打断上一个** | BGM、循环音 |
| **`PlayOneShot(clip)`** | 把 clip 当**参数**传入，**叠加**播放、互不打断 → **字段可以空着** | **音效** ✓ |

**`Spatial Blend`（空间混合）**：`0` = **2D**（不随距离/方位变化）← 街机/全屏玩法用；`1` = 3D（有衰减和方位感）。

### 八、⭐ 数字音频是什么（**了解级**，但模型很值钱）

> **数字音频 = 一串采样点。** 采样率 = 每秒记多少个点；每个点的值 = 那一瞬间的振幅（-1 ~ +1）。

**`SampleRate`（采样率）**：

| 值 | 用在哪 |
|---|---|
| 8000 Hz | 老式电话（人声够，发闷） |
| **44100 Hz** | **CD 音质** ← 我们用这个 |
| 48000 Hz | 视频/影视标准 |

**⭐ 为什么是 44100？—— 奈奎斯特采样定理**：**要还原频率 `f`，采样率必须 > `2f`。**
```
人耳上限 ≈ 20000 Hz → 采样率必须 > 40000 → CD 选 44100（留余量）
∴ 频率上限 = 采样率 / 2（奈奎斯特频率）= 22050 Hz
```
**采样率不足 → 混叠（aliasing）：高频被误认成低频。**
> 直观例子：**电影里高速转动的车轮会"倒转"**（马车轮效应）—— 24 帧/秒跟不上轮速，你"看到"了一个不存在的反向慢转。**那不是轮子倒转，是采样率不够。**

**`envelope`（包络）= 套在波形外面的"响度轮廓"**（吉他拨弦：`freq` 管音高，包络管"越来越小"）：

```csharp
data[i] = Mathf.Sin(2π · freq · t) * envelope * 0.3f;
//              ↑ 音高              ↑ 响度轮廓
```

**不乘包络会怎样**：振幅在结尾**瞬间跳到 0** → **"咔"的一声爆音（click）**。
> 🔗 **任何物理量突然突变，都会产生额外的频率成分** —— 音频里是爆音，视觉里是"闪一下"。
> **这和"动画要淡入淡出"是同一个道理**（你昨天给 `Overlay` 做的淡入，本质就是给视觉加了个包络）。

**配参口诀**：**`decay × duration ≥ 3`**（`e⁻³ ≈ 5%`）→ 结尾已衰减到听不见 → **无爆音**。

**ADSR（专业叫法，了解即可）**：`A` 起音 / `D` 衰减 / `S` 延音 / `R` 释音。
**打击类音效 = A 极短 + D 很快 + 无 S**（一击即走）。

**三要素**：采样率（水平多密，决定最高频率）/ **位深**（垂直多细，决定动态范围与底噪）/ 声道数。

### 九、程序化音效：用代码"算"出一张唱片

```csharp
int count = (int)(SampleRate * duration);                     // 采样点个数
AudioClip clip = AudioClip.Create(name, count, 1, SampleRate, false);  // 造【空白唱片】
clip.SetData(data, 0);                                        // 把算好的采样点【灌进去】
```

**两种存在方式**：磁盘资产（`.wav` 导入，**能进 git**）｜ **运行时内存**（`AudioClip.Create` 造的，**关掉就没**）。

### 十、⭐ 两个"生成一次、用很多次"：缓存 + 变体

**① 必须缓存**：每次撞砖都新建 clip = 每次分配 `3528` 个 `float`（**14KB**）→ 打 32 块砖 = **450KB GC 垃圾**。

```csharp
private static AudioClip _brickHit;
public static AudioClip BrickHit()
{
    if (_brickHit == null) _brickHit = Tone(...);   // 只有第一次真的算
    return _brickHit;
}
```
> 🔑 **"生成"是昂贵的，"复用"是廉价的 —— 任何"生成一次、用很多次"的东西都该缓存。**
> `BrickSpawner._pool` 缓存的是**对象**，`Sfx._brickHit` 缓存的是**资产**，**同一个思想的两种形态**。

**② 变体（variation）**：同时撞两块砖 → `PlayOneShot` **确实响了两声**，但**两段完全相同的波形起点对齐 → 同相位叠加 → `sin + sin = 2sin`，听起来只是"更响的一声"**。

| 两声之间的时间差 | 听感 |
|---|---|
| > 30~50 ms | 清楚的两声 |
| **< 20 ms** | 融成一声、音色变厚（**哈斯效应 / 优先效应**） |
| **0（同一帧同采样）** | **就是一声，只是更响** |

**解法的核心是"让第二声不同相"** —— 准备 **3 个音高微差（±6%）的变体，随机挑一个**：

```csharp
_brickHits[i] = Tone($"BrickHit{i}", 880f * (1f + (i - 1) * 0.06f), 0.08f, 40f);
return _brickHits[Random.Range(0, _brickHits.Length)];
```

> ⚠️ **别用改 `AudioSource.pitch` 的办法** —— `pitch` 是**整台唱机**的属性，会把**正在播的第一声也一起变调**。
> 💡 **为什么真实游戏都要做变体**：不加变体，连打 10 块砖 = **完全相同的 10 声** → 听感像"机枪"，机械、假。专业叫 **音效变体（variation / round-robin）**，枪声/脚步/命中音全都要做。
> ⚠️ **`Random.Range` 两个重载行为不同**（经典坑）：`Random.Range(0, 3)`（int 版）返回 `0/1/2`**不含 3**；`Random.Range(0f, 3f)`（float 版）返回 `[0, 3]`**含 3**。
