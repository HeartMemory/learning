## 1. Unity 脚本基础与生命周期（09-16）

### 一、从 .NET 控制台到 Unity：4 个环境差异（同一份 C# 代码会"炸"的原因）

| # | 差异 | 控制台项目（dotnet） | Unity 脚本程序集 |
|---|---|---|---|
| 1 | **入口点** | 支持**顶级语句**（文件顶层直接写代码） | ❌ 报 **CS8805**（程序集是 DLL，没有入口）→ 代码必须进方法 |
| 2 | **隐式 using** | `.csproj` 有 `<ImplicitUsings>enable</ImplicitUsings>`，`List<>`/`Console` 自动可用 | ❌ 老式 csproj，**必须手写** `using System.Collections.Generic;` → 否则 **CS0246** |
| 3 | **输出目标** | `Console.WriteLine` → 终端 | ⚠️ 能编译，但只写进 `Editor.log`，**不显示在控制台窗口** → 必须用 `Debug.Log` |
| 4 | **可空上下文** | 可开 `<Nullable>enable</Nullable>` | ❌ 默认关闭，`Character?` 报 **CS8632**（警告）→ 去掉 `?`（原理见 `CSharp-基础笔记.md` 第 18 章） |

> 🔑 **迁移检查清单**（任何 C# 代码搬进 Unity，先过这四项）：顶级语句？using 齐吗？`Console` 换 `Debug.Log` 了吗？可空问号？

### 二、MonoBehaviour = "能被挂到 GameObject 上的组件"

```csharp
public class LifecycleDemo : MonoBehaviour   // 继承 MonoBehaviour = "我是一个组件"
```

- **写类 ≠ 有对象**：脚本文件建好了但**没挂到任何 GameObject 上 → 一行都不会执行**（引擎只对场景中的**组件实例**点名）。这就是"播放后控制台一片空白"的头号原因
- 硬约束：**一个 `.cs` 文件最多一个 `MonoBehaviour`，且文件名必须 = 类名**；**普通类 / 接口不受此限**（一个文件可装任意多个，文件名随便叫）
- 同一个 GameObject 可以挂**多个相同组件**（要禁止得在类上加 `[DisallowMultipleComponent]`）——排查"改了脚本没反应"时先看一眼是不是挂了两个

### 三、生命周期回调（引擎按名字点名）

```
Awake → OnEnable → Start → (每帧: Update → LateUpdate) → OnDisable → OnDestroy
```

| 回调 | 触发时机 | 次数 |
|---|---|---|
| `Awake` | 实例被加载（物体激活时） | **一生一次** |
| `OnEnable` | 物体**且**组件都启用时 | **每次进出都触发** |
| `Start` | 第一次启用后、第一帧 `Update` 前 | **一生一次** |
| `Update` | 每帧 | 每帧 |
| `LateUpdate` | 本帧所有 `Update` 跑完后 | 每帧 |
| `OnDisable` | 物体**或**组件被禁用 / 销毁前 | **每次进出都触发** |
| `OnDestroy` | 实例被销毁 | 一生一次 |

**三条关键结论**：
1. `Awake` → `OnEnable` → `Start`；**`Awake`/`Start` 的"一次"指"这个实例的一生"**，重新启用**不会**重跑
2. **`Update` 频率不是固定 60**：编辑器空场景可跑上千帧/秒（没开垂直同步）→ **任何速度/时间逻辑必须乘 `Time.deltaTime`**（帧率无关性铁律）
3. **`LateUpdate` 存在的理由**：多个组件之间 `Update` 的**执行顺序不保证** → 相机跟随必须放 `LateUpdate`，才能拿到所有物体本帧的**最终位置**（否则画面抖动）

### 四、⭐ 按名字点名 vs vtable（两种调用机制对照）

| | `virtual` / `override` | Unity 生命周期（消息机制） |
|---|---|---|
| 谁决定被调用 | **编译器**（编译期焊进 vtable） | **引擎**（运行时扫描方法名，结果缓存成"消息表"） |
| 定位方式 | 类型指针 → 虚方法表 → 跳转 | 按**名字**匹配 |
| 写错了 | **编译报错** | **不报错，静默失效**（`void update()` 永远不跑） |
| 访问修饰符 | 只能 `public`/`protected` | **随便**（`private` 也能被调） |
| 类比 | 填表格（格子印好了，每格都要处理） | 喊名字（答应哪个干哪个，没人应也没人管） |

**Unity 为什么选"点名"**：① **`private` 也能被调用**（`void Start()` 就是隐式私有，这在 virtual 体系里做不到）；② **不依赖继承体系**（ScriptableObject、编辑器脚本也能接回调）；③ 多语言兼容（早期支持 JS/Boo）；④ 想用哪个写哪个，新增回调不用改基类。
**代价**：没有编译期保护 → **生命周期方法永远用 IDE 补全，绝不手打**。

> 注意：`virtual` 只是"**可以**改写"，不是"必须"（必须的是 `abstract`）。`Monster` 没 override 就用父类默认实现 ✓

### 五、组件禁用 vs 物体禁用（两个长得几乎一样的 checkbox）

| | 组件勾选框（`enabled`） | 物体勾选框（`activeSelf` / `SetActive`） |
|---|---|---|
| 影响范围 | **只有这一个组件** | **物体上所有组件** |
| 子物体 | 不受影响 | **全部一起失活** |
| 层级窗口 | 物体**不变灰** | 物体名**变灰** |

**关键洞察（实测得出）**：**从脚本自身看，两种情况收到的回调一模一样（`OnDisable` / `OnEnable`）**——脚本根本分不清"我被禁用了"还是"我所在的物体被禁用了"。唯一区别在**影响范围**。
（实锤实验：一个物体挂两个相同组件，勾选的跑完整流程，未勾选的一条日志都没有。）

### 六、场景心智模型

- **你运行的不是"某个脚本"，而是"整个场景"**：播放时场景里**所有物体同时活着、同时运行**（所以会莫名多出别的脚本的日志）
- 场景会"记住"你放进去的一切（`Ctrl+S` 保存 `.unity` 文件）；**代码保存（VS 的 `Ctrl+S`）和场景保存是两件独立的事**

### 七、两个必踩的工程坑

| 坑 | 现象 | 原因 / 修法 |
|---|---|---|
| **编码** | VS 弹"某些 Unicode 字符未能保存到当前代码页" | 脚本里有中文/emoji，VS 默认 ANSI/GBK 存不下 → **存 UTF-8**（Unity 按 UTF-8 解析 `.cs`）；VS2022 里用 `文件 → 高级保存选项 → Unicode (UTF-8 带签名)`（详见第 3 章第十一节） |
| **粘贴括号层级** | `CS1513: } expected` + `CS1022: Type or namespace definition...` | 粘贴时**忘闭合方法体** → 后面的类型声明被"吸"进方法里。**看见括号类报错先数括号**（VS 光标放 `{` 上可高亮配对，`Ctrl+]` 跳转），别盯代码内容 |

### 八、接口回收：`IEnumerable<T>` / `IList<T>` / `IDictionary<K,V>` / `KeyValuePair<K,V>`

**和自写的 `IAttackable` 是同一种东西**，区别只在"谁写的 + **消费者是谁**"：

| 接口 | 契约内容 | **消费者（谁在认它）** | 使用痕迹 |
|---|---|---|---|
| `IAttackable` | `Name` / `IsAlive` / `TakeDamage` | 自写的 `Character.Attack()` | 09-14 |
| `IEnumerable<T>` | "我能被逐个遍历" | **`foreach` 关键字本身** | 从第一天起每条 `foreach` |
| `IList<T>` | "能按下标访问 + Add + Count" | `[]` 索引器、`Add` | 118 杨辉三角（`IList<IList<int>>`） |
| `IReadOnlyList<T>` | "能下标、不能改" | 只读访问 | 09-08 Encapsulation |
| `IDictionary<K,V>` | "能用 key 查 value" | `dict[key]`、`TryGetValue` | 09-14 起 |
| `KeyValuePair<K,V>` | "一对 (key, value)" | 遍历 Dictionary 时 | ❌ 还没用过 |

**继承层次（越往下能力越多）**：

```
IEnumerable<T>            ← 能被 foreach（最底层能力）
├── ICollection<T>        ← 能 Count / Add / Remove
│   ├── IList<T>          ← 能按下标 list[0]
│   └── IDictionary<K,V>  ← 能用 key 查 value
└── IReadOnlyList<T>      ← 只读版：能下标、不能改
```

- **铁律：接口必须有"另一端"（消费者）才有意义** —— 没有消费者的接口是废纸。判断任何接口先问：**谁在认这份契约？**
- 预告：`IComparable<T>`（消费者 `List.Sort()`）、`IDisposable`（消费者 `using`）、`IEquatable<T>`（消费者 `Dictionary`/`HashSet` 判重）—— 全是同一套逻辑
- **选用原则：自己内部用 → 选实现（`List<T>`）；给别人用 → 选接口（`IReadOnlyList<T>` / `IEnumerable<T>`）**

### 九、`using` 的机制（易误解点）

- `using X;` **不是"引入"什么**，它只是把 X 命名空间里的类型名加进**检索范围**（短名 → 全名的查找表）
- 类型的**全名**永远是 `命名空间.类型名`（如 `UnityEngine.Debug`）；`using` 只让你能写短名。联想：`using` ≈ 把目录加进 `PATH`
- `System.Collections.Generic` 读作**路径**：`System` → `Collections`（老式非泛型 `ArrayList`/`Hashtable`，存 `object` 要装箱）→ `Generic`（泛型版，类型安全 + 免装箱）
- 两个 `Debug` 会打架：`UnityEngine.Debug`（控制台输出）vs `System.Diagnostics.Debug`（诊断）—— 同时 using 会报 **CS0104 不明确的引用**，届时只能写全名
- **万能判定法：删掉这个 `using`，编译一次，看哪儿报红。** 不报红 = 没用（VS 也会显示成灰色）

## 2. Unity 空间与运动（09-17）

### 三件套的关系

```
GameObject  = 空容器（本身什么都不会）
Component   = 装在容器里的功能件（行为 / 数据 / 外观）
Transform   = 唯一【强制】自带的组件（删不掉）
```

- **Unity 里没有"物体的行为"，只有"组件的行为"**：想移动 → 挂脚本组件；想碰撞 → Collider；想被看见 → 渲染组件
- **`transform` 不是全局变量**，是**继承自 `Component` 的属性**（≡ `this.transform`）
  - `: MonoBehaviour` 的真正价值 = 白送一批快捷访问（`transform`/`gameObject`/`name`/`enabled`）+ 生命周期方法的"报名资格"
- **Scene 窗口 = 上帝视角**（右键环视、右键+WASD 飞行、滚轮缩放、选中按 `F` 聚焦）｜**Game 窗口 = 相机视角**

### ⭐ 运动母公式

```csharp
transform.position += new Vector3(speed * Time.deltaTime, 0f, 0f);
//                              └──── 这一帧应该走的距离 ────┘
```

- **`Update` 是"每帧一次"，不是"每秒一次"** → 必须 `× Time.deltaTime` 换算成"每秒"
- **去掉 `deltaTime`** → "每秒移动"变"每帧移动" → 实测一秒上千帧 → **速度放大 ~1000 倍**
- **铁律**：凡是"每秒多少"的（移动/旋转/冷却/计时）一律 `× Time.deltaTime`；"每帧一次"的（读输入）不乘
- 数学本质 = **数值积分（欧拉法）**：时间切片，每片当匀速累加
- "10 秒后 ≈ 10 而非精确 10"的两个原因：①**`deltaTime` 每帧在波动**（主因）②浮点累加误差（次因）
- **两条互斥的移动路线**：直接改 `transform.position`（运动学，自己算，会穿墙）｜ 操作 `Rigidbody`（物理引擎算，有碰撞重力）
  - ⚠️ **千万别混用**（加了 `Rigidbody` 还在 `Update` 里手改 `position` → 抖动/穿模/弹飞）；两套的正确姿势见第 3 章第六节

### ⚠️ 世界坐标 vs 本地坐标（**最容易搞反的一处**）

| | 代码 API | **Inspector 的字段** |
|---|---|---|
| 世界坐标 | **`transform.position`** ✅ | ❌ **看不到** |
| 本地坐标 | `transform.localPosition` | ✅ **「位置」显示的就是它** |

**Unity 官方手册原文**（Unity 6.0 与 4.3 两版一致）：

> *"The Transform values for any child GameObject are displayed **relative to the parent GameObject's Transform values**. These values are called **local coordinates**."*
> *"Unity measures the Position, Rotation and Scale values of a Transform **relative to the Transform's parent**. If the Transform has no parent, Unity measures the properties in world space."*

**结论**：
- **Inspector 的「位置 / 旋转 / 缩放」全部是本地坐标**（有父物体时）；Normal 和 Debug **两个模式显示的都是本地值**，Debug 只是把序列化字段名（`局部位置`）直接暴露出来
- **世界坐标没有任何面板字段** → **只能在代码里取**
- 在面板里改「位置」等价于 `transform.localPosition = ...`（**不是** `transform.position = ...`）——**两套量搞混是父子结构下最经典的 bug 来源**
- **为什么这样设计**：调子物体时关心的是"相对父物体的偏移"（父动子动是常态）
- **父子关系**：`世界坐标 = 父的世界坐标 + 自己的本地坐标`（无旋转缩放时）；拖拽成子物体时 Unity **保持世界位置不变**，自动改本地坐标
- **父子关系的价值**：角色跑动时手里的剑**不需要写任何跟随代码** —— 剑的 `localPosition` 一直是 `(0.5, 0, 0)`，世界坐标被"继承"着算出来

### CS1612：属性返回 struct → 只能"整体读写"

```csharp
transform.position += v;        // ✅ 展开成 transform.position = transform.position + v（整体赋值）
transform.position.x = 5f;      // ❌ CS1612：无法修改"Transform.position"的返回值，因为它不是变量
```

**根因链**：`position` 是**属性**（执行代码，**返回一份拷贝**）→ `Vector3` 是 **struct** → 属性返回 struct = 返回拷贝 → 拷贝没有名字、没有存储位置 → **不是变量** → 不能出现在赋值号左边

| 写法 | 流程 | 合法 |
|---|---|---|
| `transform.position += v;` | 读 → 算新的 → **整体写回** | ✅ |
| `transform.position.x = 5f;` | 读 → 改拷贝 → **丢掉** | ❌ |

**三种正解**：
1. `Vector3 p = transform.position; p.x = 5f; transform.position = p;`（局部变量是变量，合法）
2. `transform.position = new Vector3(5f, p.y, p.z);`（整体赋值）
3. **优先用 Unity 封装的方法**：`transform.Translate(...)` / `transform.Rotate(...)` —— **这类方法存在的意义就是帮你做"读-改-写回"**

**类推**：
| 写法 | 合法 | 原因 |
|---|---|---|
| `list[0].x = 5f`（`List<Vector3>`） | ❌ | 索引器是**属性**（返回拷贝） |
| `arr[0].x = 5f`（`Vector3[]`） | ✅ | **数组下标是语言内建的"变量"** |

**为什么编译器要拦**：它能确定这个操作毫无意义。**宁可编译报错，也不要静默 bug。**

> 与 Unity 生命周期对照：**编译器能管的错 → 报错**（`virtual`/CS1612）；**编译器管不了的（引擎反射）→ 静默失效**（`void update()`）。**凡是能靠编译器抓的，绝不留到运行时。**

### 字段 vs 属性（判定三步法）

| 长相 | 是什么 |
|---|---|
| 类型 + 名字 + `;` | **字段** |
| `{ get; set; }` / `{ get {…} set {…} }` / `=> 表达式` | **属性** |
| `this[int] { get; set; }` | **索引器**（本质是属性） |

1. **看写法**（有花括号 → 属性）
2. **看命名惯例**（字段 `_camelCase`、属性 `PascalCase`）——⚠️ **只能猜，不能定**
3. **悬停 / `F12` 转到定义** —— ⭐ **唯一权威判定**

**四个实际后果**：
| # | 差异 | 字段 | 属性 |
|---|---|---|---|
| 1 | 能否"只改一个分量" | ✅（是变量） | ❌ CS1612 |
| 2 | 能否当 `out`/`ref` 参数 | ✅ | ❌ CS0206 |
| 3 | 读取代价 | 近乎零 | **要执行代码**（`transform.position` 要跨到引擎内部取数 → **读一次缓存到局部变量**） |
| 4 | 结果是否稳定 | 一定稳定 | 可能每次不同（计算属性） |

**记忆锚点**：**字段 = 抽屉**（直接拿/放）｜**属性 = 前台**（跑一套流程再给你；**没法隔着前台动抽屉里的某一格**）

## 3. Unity 输入与物理（09-18）

### 一、读输入：轮询（拉），不是消息（推）
```csharp
Input.GetKey(KeyCode.A)        // 按住期间每帧为真（状态）
Input.GetKeyDown(KeyCode.A)    // 按下那一帧为真（事件）
Input.GetKeyUp(KeyCode.A)      // 松开那一帧为真（事件）
Input.GetAxisRaw("Horizontal") // -1 / 0 / +1，瞬时
Input.GetAxis("Horizontal")    // -1 ~ +1，平滑过渡
```
- 与生命周期对照：生命周期是**引擎按名字点名（推）**，输入是**你每帧主动去问（拉）**

### 二、⭐ GetAxis vs GetAxisRaw（"松手后滑行"的根因）
| API | 松手瞬间 | 适合 |
|---|---|---|
| `GetAxis` | **平滑回落**：按该轴 `Gravity` 参数衰减（默认 3 → 约 0.33 秒归零） | 要缓动手感（赛车/转向） |
| `GetAxisRaw` | **立刻归零** | 要"指哪打哪"（挡板） |

- **滑行 ≠ 物理惯性**：Kinematic 刚体没有质量/摩擦/惯性，位置完全由代码指定 → 滑行只来自**输入值的平滑**
- 手感可调：`项目设置 → 输入管理器 → 轴` 里改 `Gravity`（回落速度）/ `Sensitivity`（上升速度）→ **参数化而不是写死**
- 排查心法：先分清"**输入平滑**"和"**刚体阻尼**"两个完全不同的成因，方向错了会白调半天

### 三、轴名表 = 数据驱动的输入配置
- `"Horizontal"` 是**名字**，Unity 拿它去 `ProjectSettings/InputManager.asset` 这张表里查（拼错/大小写错 → `Input Axis xxx is not setup` 异常）
- 默认 `Horizontal` = 主键 `left`/`right` + 备用键 `a`/`d`（`Alt Negative/Positive Button`）
- 意义：**代码只说"我要水平轴"，具体是哪些键由表决定** → 换键位不改代码，还能同时吃键盘与手柄
- 表属于 `ProjectSettings/` → **会进 git**，换机器克隆下来键位设置跟着走

### 四、⭐ 双时钟：Update vs FixedUpdate
| | `Update` | `FixedUpdate` |
|---|---|---|
| 频率 | 每帧一次（跟帧率，几十 ~ 上千次/秒） | 固定物理步长，默认 0.02s = **50Hz** |
| 谁驱动 | 渲染循环 | 物理引擎 |
| 一帧内跑几次 | 必然 1 次 | **0 / 1 / 多次** |
| 放什么 | 读输入、相机（`LateUpdate`）、纯逻辑/UI | **所有物理操作**（力、速度、`MovePosition`） |
| 配套时间量 | `Time.deltaTime` | `Time.fixedDeltaTime` |

- 为什么输入在 `Update` 读：`GetKeyDown` 只在"按下那一帧"为真，而 `FixedUpdate` 一帧可能 0 次或多次 → **会漏按键 / 重复触发**
- 代价：`Update` 写的值最快要到下一次 `FixedUpdate` 才被用掉（最多一帧延迟，对挡板无感）
- "50Hz"是**目标频率/长期平均值**，不是"每秒恰好 50 次"：卡顿时会**连跑多次追赶**，超时（`最大允许时间步长` 默认 0.3333s）则**主动丢步**防"死亡螺旋"
- ⚠️ `FixedUpdate` 拼错 = 永不执行且不报错（生命周期"按名字点名"同款坑）

### 五、Rigidbody2D：三种主体类型（Body Type）
| 类型 | 谁控制位置 | 典型用途 |
|---|---|---|
| **Dynamic** 动态 | 物理引擎（重力/受力/被撞飞） | 球 |
| **Kinematic** 运动学 | **代码**（`MovePosition`），但仍参与碰撞、能顶飞别人 | 挡板 |
| **Static** 静态 | 谁都不动 | 地板、墙 |

- 改成 Kinematic 后，`质量 / 线性阻尼 / 重力大小` 这些参数失效（谁在管位置，一目了然）
- **`Collider2D` 决定"能不能被撞"，`Rigidbody2D` 决定"位置归不归物理引擎管"** —— 两件事分开的。砖块只要前者（没刚体的碰撞体 = 静态碰撞体，最省）

### 六、⭐ 移动的两种语义（09-18 的分水岭）
```csharp
transform.position += v;    // 直接改坐标（瞬移）：绕过物理引擎 → 两套账打架（抖动/穿墙/碰撞失真）
_rb.MovePosition(next);     // 申请："这一步请把我搬到 next" → 引擎执行 + 同步 Transform + 顺便做碰撞检测
```
- `MovePosition` 要的是**目标位置**，不是增量 → 得自己算 `当前位置 + 位移`
- 基准用 `_rb.position`（**物理引擎账本里的位置**，Vector2），比 `transform.position` 更可靠

### 七、为什么 `_rb.position += v` 编译不过
- `Rigidbody2D.position` 是**只读属性**（只有 get）→ **CS0200**（不能赋值）
- 对照：`transform.position` 有 setter → `+=` 能过（编译器展开成"整体读-加-整体写回"）；`transform.position.x = 5f` 是 **CS1612**（改的是返回的拷贝）→ 同属本册第 2 章"字段 vs 属性"

### 八、取组件与暴露字段
- `_rb = GetComponent<Rigidbody2D>();`：去**自己所在的 GameObject** 上找组件（找不到返回 `null`）；`transform` 本质就是白送的 `GetComponent<Transform>()`
- 放 `Awake`：生命周期最早、只跑一次，保证后续方法用时已接好
- `[SerializeField] private float speed = 8f;` = **对检查器开窗、对代码关门**（`public` 会拆掉封装墙）；运行时才赋值的引用（`_rb`）**不要**加
- **检查器里拖进去的字段值，在 `Awake` 时已经可用**（Unity 在反序列化阶段就填好了）→ 所以 `speed` 读到的一直是你设的值

### 九、⚠️ 2D / 3D 是两套物理引擎
| | 3D | 2D |
|---|---|---|
| 刚体 | `Rigidbody` | `Rigidbody2D` |
| 碰撞体 | `BoxCollider` | `BoxCollider2D` / `CircleCollider2D` |
| 渲染 | `MeshRenderer` | `SpriteRenderer` |

- 混用**不报错、静默失效**（2D 物体挂 3D `Rigidbody` = 完全不参与 2D 物理）

### 十、活动输入处理（旧 / 新 / 两者）
- `项目设置 → 玩家 → 其他设置 → 活动输入处理`：Unity 6 新项目模板默认「**输入系统包（新）**」→ 旧的 `Input.*` 会**直接抛异常**
- 学习期选「**两者**」（改完需**重启编辑器**）：两套 API 都能用；新输入系统（Input Actions + 按键重映射）留到需要多平台/自定义键位时专门学
- 心法：**API 不生效 → 先查项目设置，再怀疑代码**

### 十一、编码坑：VS2022 存 GB2312 → CodeBuddy 乱码
- 症状：同一文件 VS2022 中文正常，CodeBuddy（VS Code 系，默认按 UTF-8 解码）全是乱码
- 根因：VS2022 按中文 Windows 的**系统代码页（GB2312 / 936）**保存，没存成 UTF-8
- 修法：VS2022 `文件 → 高级保存选项` → **`Unicode (UTF-8 带签名) - 代码页 65001`**
- 为什么"带签名"（BOM）：文件头写死"我是 UTF-8"（`EF BB BF`），任何编辑器都不用猜
- Unity 要求 `.cs` 用 UTF-8（GBK 字节被按 UTF-8 解码 → 注释乱码，甚至编译报错）
- 校验技巧：`UTF8Encoding($false, $true)` 严格解码能过 = 合法 UTF-8；再看头 3 字节有没有 BOM
- 编辑器日志：CodeBuddy 输出面板的 `[info]` 只是正常心跳（识别工作区/仓库），**只有 `[error]` 才要管**

### 十二、Unity 项目进 git（首次入库实测）
- 待跟踪文件 39 个（`Assets/` + `Packages/` + `ProjectSettings/`），`Library/ Temp/ Logs/ *.csproj *.sln` 全被 `.gitignore` 拦住
- 验证手段：`git status --short --untracked-files=all` + `Select-String 'Library/'`（应为空）；`git check-ignore -v <路径>`（能看到是哪一条规则拦下的）

## 4. Prefab、实例化与场景装配（09-19）

### 一、Prefab = 模具，场景里的对象 = 副本

- **Prefab 源文件**住在 `Assets/Prefabs/`（拖进去后，层级窗口里那个对象的名字**变蓝** + 右侧出现「覆盖 / Overrides」按钮）
- 改**模具**（双击 Prefab 进编辑）→ 所有副本里**未被覆盖**的字段一起变；改**某个副本** → 只在它身上生效（会记一笔"覆盖"）
- 为什么要 Prefab：一次配好（外观/碰撞体/脚本参数），后面靠代码批量复制 —— 手摆 32 块是不可维护的

### 二、`Instantiate` 在做什么

```csharp
Instantiate(prefab);                          // 用模板自己的位置
Instantiate(prefab, 位置, 旋转);                // 常用
Instantiate(prefab, 位置, 旋转, 父物体);        // + 顺手挂父物体（坐标按世界空间解释）
```

| 步骤 | 内部干了什么 |
|---|---|
| ① 反序列化 | 把 `Assets/` 里那个 Prefab 文件（YAML/二进制）读出来 |
| ② 装配 | 按数据建出 GameObject + 各组件，把 `[SerializeField]` 的值填好，修好引用 |
| ③ 入场景 | 加进当前场景，触发 `Awake`/`OnEnable`（`Start` 等下一帧） |

**与 C# `new` 的分水岭**：

| | `new GameObject()` | `Instantiate(prefab)` |
|---|---|---|
| 造出什么 | **空壳**，一个组件都没有 | **一整套**（渲染/碰撞/脚本 + 数值全在） |
| 数据来源 | 从零构造 | 从磁盘上的模板**拷贝** |
| 成本 | 便宜 | **贵**（读文件 + 堆分配）→ 别放 `Update`，这就是对象池（09-22）的动机 |

**三条实操铁律**：
1. **返回值必须接住**（`GameObject b = Instantiate(...)`）—— 不接住对象照样存在，但你**再也拿不到它的引用**，以后想回收只能满世界 `Find`
2. **`Quaternion.identity` = 不旋转**（identity ≈ 数字里的 1）；注意第三格是**覆盖**：传 `identity` 会抹掉模板自带旋转 —— 想跟模板一致就传 `prefab.transform.rotation`
3. 副本名字带 **`(Clone)`** 后缀 —— 播放后看到一堆 `Brick(Clone)` 就说明复制成功

### 三、生成器（Spawner）该挂谁 + 容器要"干净变换"

| 候选 | 评价 |
|---|---|
| **场景级空物体**（`Board` / `GameManager`） | ✅ 职责匹配：管整局游戏，不参与画面 |
| 相机 | ⚠️ 能跑，但语义混乱（相机是"眼睛"） |
| 挡板 / 砖块自己 | ❌ 会移动、会连累逻辑；**挂在自己生成的东西上 = 指数爆炸**（见第六节事故 2） |

**容器（Board）保持 `位置(0,0,0)` + `旋转(0,0,0)` + `缩放(1,1,1)`** —— 这样子的**本地坐标 = 世界坐标**，所有算坐标的代码都不会错。要整体挪动只改它的**位置**。

### 四、`SetParent`：父子变换对子物体的三个影响

```csharp
brick.transform.SetParent(transform);   // 把生成的砖块挂到 Board 底下（默认保持世界位置不变）
```

| 改父物体的… | 子物体（砖块）会怎样 |
|---|---|
| **位置** | 整体**平移**，形状与间距比例不变 ✅ 安全 |
| **旋转** | 整片砖墙**跟着转** |
| **缩放** | 位置与尺寸**一起被乘** ⚠️ 形状可能变形 |

缩放的具体后果（`Board` 的 `scale.x` 改成 2）：砖块世界尺寸 `1.6×0.6 → 3.2×0.6`（**变宽变扁**）、相邻间距 `1.7 → 3.4`（阵列以父的本地原点为中心撑开）、`BoxCollider2D` 跟着放大。而**检查器里显示的是本地值**（还是 1.6/0.6）→ 从数据上看不出，只在 Scene 视图里看得出来。

**隐藏的连带坑**：`transform.localScale.x * 0.5f` 这种算"半宽"的写法只在**没有父物体 / 父缩放为 1** 时成立；一旦被缩放的父物体包住，要改用 `lossyScale`（世界缩放）或更稳的 `SpriteRenderer.bounds.extents`。

**挂成子物体后的坐标语义**：子物体的检查器「位置」变成**相对父的本地坐标**；`transform.position` 仍是世界坐标 —— 父在原点且无缩放旋转时两者数值相同，父一动就分家（第 2 章那个坑的现场版）。

### 五、正交相机的世界单位换算 + `Mathf` 速查

```
屏幕【全高】= orthographicSize × 2
屏幕【全宽】= 全高 × aspect
屏幕【半宽】= orthographicSize × aspect      ← 布局/边界最常用
```

- `Camera.main` = 标签为 `MainCamera` 的相机（**可能为 null**：场景里没有主相机时）；内部是按标签查找，**建议 `Awake` 里取一次存字段**，别每帧调
- 相机是**透视**时 `orthographicSize` 无意义（2D 模板默认正交）

| `Mathf` API | 作用 |
|---|---|
| `Clamp(v, min, max)` | 夹进区间 |
| `Clamp01(v)` | 夹到 0~1（进度条、插值 t） |
| `Abs / Max / Min` | 绝对值 / 取大 / 取小 |
| `Lerp(a, b, t)` | 线性插值 |
| `Approximately(a, b)` | 浮点近似相等（"别用 `==` 比浮点"的正解） |

### 六、⭐ 两起事故复盘（09-19）

**事故 1：字段初始化器里访问 `transform` → 报错**

```csharp
// ❌ 写在类成员位置（字段初始化器）
float halfPaddle = transform.localScale.x * 0.5f;
```
> 报错大意：`get_transform is not allowed to be called from a MonoBehaviour constructor (or instance field initializer), call it in Awake or Start instead.`

**生命周期顺序（关键）**：
```
C# 构造函数（字段初始化器在这里跑）  ← Unity 的"原生物体"还没和 C# 对象绑定
      ↓
    Awake  ← 从这里开始 transform / gameObject / GetComponent / Camera.main 才能用
      ↓
  OnEnable → Start → Update…
```
**修法**：需要引擎信息的计算全部搬进 `Awake`；只把**要跨方法用的结果**升成字段（如 `_limit`），中间量用局部变量。

**事故 2：生成器自引用 → 指数爆炸 → 编辑器假死**

- 症状：一进播放就卡死，任务管理器里 Unity 无响应
- 根因（从场景文件里挖出的证据）：`BrickSpawner` 挂在**场景里的 Brick** 上，而它的 `brickPrefab` 又指向**它自己**
  ```yaml
  # 场景文件里的证据
  --- !u!114 &1906376736                  # BrickSpawner 组件
    m_GameObject: {fileID: 1906376735}    # 挂在 Brick 上
    brickPrefab: {fileID: 1906376735}     # ← 指向自己！
  ```
  → `Instantiate(self)` 出来的每个副本**也带着生成器** → 32 → 32² → 32³ … 几秒几十万个物体 💥
- **正确姿势**：生成器挂**场景级空物体**；槽位拖的是 **Project 窗口里的 Prefab 资产**（引用里带 `guid`），**不是层级窗口里的对象**（引用里只有 `fileID`）—— 这是"我拖对了吗"的硬核判别法
- **救场流程**：① 任务管理器强杀 `Unity.exe`（播放模式的改动不会保存，场景不会坏）② 重启后若弹 **Recovering Scene Backups** 选「是」→ 备份进 `Assets/_Recovery/`（强杀前未保存的编辑只在这里）③ 打开恢复场景检查、修好、**`Ctrl+S` 存场景** ④ 确认无用后删掉 `_Recovery/`（别提交进 git）

### 七、防御性编程：给自己装保险丝

```csharp
if (cols <= 0 || rows <= 0) return;
if (cols * rows > 200)
{
    Debug.LogError($"砖块数量异常：{cols} × {rows}，已拒绝生成");
    return;
}
Debug.Log($"准备生成 {cols * rows} 块砖");   // 先打印"打算做多少"，出问题时日志能说明意图
```
原则：**对"外部输入"（检查器里手输的值、别人拖进来的引用）永远先做合法性检查，再动手**。

## 5. 碰撞、物理材质与反弹（09-21）

### 一、三件套的分工（一张表定死）

| | Collider2D | Rigidbody2D | PhysicsMaterial2D |
|---|---|---|---|
| 回答什么 | 我占多大空间、和谁接触 | 多少惯性、什么速度、谁在推动我 | 表面多滑、多能弹 |
| 数量 | 一个物体可以**多个**（头/身/脚） | 一个物体**只有一个** | 挂在 **Collider** 上（刚体级槽是 Unity 6 的便捷入口） |
| 没有它会怎样 | 撞不到任何东西 | 是静态几何体：不动、推不动、不产生回调 | 用默认值（摩擦≈0.4 / 弹性 0） |

**两条最容易反的**：
- **"检测"只要碰撞体，"响应"要刚体**：双方都没刚体 = 静态×静态 → **零回调**（所以静态墙之间没有事件）
- **子物体的 Collider 会挂到最近的父级刚体上**（复合碰撞体）→ 别给 `Walls` 这种容器随手加刚体

### 二、物理材质：混合规则（Combine Mode）—— 弹性是"成对算"的

一次碰撞要把双方的摩擦/弹性**压成一个数**才能算冲量，规则就是那两个下拉框：

| 规则 | 公式 | 现实模型 |
|---|---|---|
| 最小值 Min | `min(a,b)` | 最滑 / 最不弹的那方说了算 |
| Mean | `(a+b)/2` | 取中（Unity 默认） |
| 最大 Maximum | `max(a,b)` | 乒乓球撞水泥地（**弹性推荐**） |
| 乘积 Multiply | `a×b` | Box2D 经典摩擦默认 |

**本项目取值与理由**：

| 属性 | 值 | 理由 |
|---|---|---|
| 摩擦力 | 0 | 只想要"纯反射"；有摩擦会削横向速度、把轨迹带歪 |
| 弹性 | 1 | 满弹 |
| **反弹合并** | **最大** | 墙/挡板**即使不挂材质**（默认弹性 0）球也能弹满 |
| **摩擦组合** | 平均（默认） | ⚠️ **隐患**：墙默认摩擦≈0.4 → `(0+0.4)/2 = 0.2` → 贴墙轻微掉速 → **球与墙/挡板都挂同一材质**（0 与 0 混出来还是 0），或把摩擦组合改成"最小值" |

> 🧪 **对照实验（1 分钟，别跳过）**：把「反弹合并」从"最大"切成"平均" → 播放，球**越弹越矮**；切回"最大" → 恢复满弹。**混合规则不是纸面概念，它就写在球的高度上。**

### 三、Collider2D 家族：形状决定手感

| 碰撞体 | 形状 | 说明 |
|---|---|---|
| **Box Collider 2D** | 矩形（半宽 × 半高，可加"边缘半径"做圆角） | **最快**；墙 / 砖 / 挡板都该用它 |
| **Circle Collider 2D** | 圆（半径） | 第二快；**没有"角"**，反弹最干净 |
| Capsule / Polygon | 胶囊 / 凸多边形 | 更贴合、更贵，角色常用 |
| Edge / Composite | 线段 / 组合 | 地形、单向平台 |

- **外观与碰撞解耦**：Sprite 是给眼睛看的，物理只看 Collider → "图明明对上了却撞不到"通常就是这儿
- ⚠️ **球必须用 Circle**：套 Box 的话撞墙是**角**先接触 → 抖动、乱转向、卡墙角
- ⚠️ 勾了 **Is Trigger** 后**材质完全失效**（触发器不参与物理解算，只发 `OnTriggerEnter2D`）→ 09-22 做撞砖要在"物理碰撞"与"触发器"两条路线里选一条
- 技巧：**按住 Shift 拖手柄**只改 Collider 大小、**不改 Transform 缩放**（避免污染 `localScale` —— 挡板"半宽"就是靠它算的）

### 四、Rigidbody2D 面板逐项（按功能分四组）

| 组 | 项 | 说明 |
|---|---|---|
| **身份** | 身体类型 | Dynamic / Kinematic / Static（见本册第 3 章第五节；**Kinematic × Static 不产生回调**） |
| | 材质 | Unity 6 新增的"刚体级"入口；**权威仍在各 Collider 上**，本项目留空 |
| | 模拟的 | 物理总开关；关掉 = 位置冻结、不参与碰撞，但对象还在（暂停 / 尸体场景） |
| | 使用自动质量 / 质量 | 自动 = 面积 × 密度；质量只在"撞会动的物体"时才起作用（撞墙/挡板=无限质量，白设） |
| **耗散** | 线性阻尼 | 空气阻力，速度按指数衰减；0 = 永远不停 |
| | 角阻尼 | 自旋阻力，**默认 0.05 → 球建议改 0** |
| **环境与时间** | 重力大小 | 受重力倍数；**俯视图必须 0**（否则球直接掉出屏幕） |
| | 碰撞检测 | 离散 / 持续；持续 = 扫掠求交防高速穿墙（**只对 Dynamic 有效**） |
| | 休眠模式 | 速度低于阈值一段时间会"睡着" → 现象是"球莫名卡住"；球建议 **从不休眠** |
| | 插值 | 物理跑 50Hz、渲染帧率浮动 → 插值补帧防抖（外推会过冲） |
| **约束** | 冻结位置 / 旋转 | 物理层面的方向锁；挡板可勾"冻结位置 Y + 旋转 Z"做**双保险**（与代码 `Clamp` 互补：一个数学锁、一个引擎锁） |

### 五、球的配置 + 三面墙的数值来源

**球（Dynamic）**：重力缩放 **0** / 碰撞检测 **持续** / 线性·角阻尼 **0** / 休眠 **从不休眠** / 插值 → `CircleCollider2D`（材质 `BallMaterial`）。

> ✅ **自检法（推荐固化）**：**先不写任何代码，播放一次 → 球应悬在原地不动**。一步就能验证"重力缩放确实生效"，比事后靠现象倒推强。

```
屏幕半宽 = orthographicSize × aspect = 5 × 1.777 ≈ 8.89  → 墙中心 x = 8.89 + 半厚 0.25 = 9.14
屏幕半高 = orthographicSize           = 5               → 上墙中心 y = 5 + 0.25   = 5.25
```

|---|---|---|
| LeftWall / RightWall | x = ∓9.14 | `0.5 / 11` |
| TopWall | y = 5.25 | `19 / 0.5` |

- 容器 `Walls` **保持 (0,0,0) 且不缩放** → 子物体**本地坐标 = 世界坐标**，上表数值可直接填（本册第 2 章坐标坑的实战应用）
- **墙不加刚体**（默认即静态）；**下边界不封** —— 那是以后的"失败判定"位置

### 六、发球：`linearVelocity` 与 `normalized`

```csharp
_rb.linearVelocity = new Vector2(1f, 1f).normalized * speed;   // 只发一次 → 放 Start，不放 Update
```

- **Unity 6 里 `velocity` 已废弃** → 用 **`linearVelocity`**（写旧名会有过时警告）
- **必须 `normalized`**：`(1,1)` 长度为 `√2 ≈ 1.414`，不归一化就等于速度乘了 1.414 → 斜着发比直着发快，轨迹会怪
- 按键发球：读项目级 Input Actions 的动作（如 `Player/Fire`），或自建 `Gameplay` 地图（见本册回访清单）

### 七、`OnCollisionEnter2D(Collision2D other)` 拆解

```csharp
void OnCollisionEnter2D(Collision2D other)
{
    Debug.Log($"撞到 {other.gameObject.name}，撞后速度 {_rb.linearVelocity}，相对速度 {other.relativeVelocity}");
}
```

| 要点 | 说明 |
|---|---|
| 谁调用 | **引擎按名字点名**（与生命周期同机制）→ **拼错 = 静默失效**（写成 `OnCollisionEnter2d` / 漏掉 `2D` 都不报错） |
| Enter / Stay / Exit | 只在**开始接触那一帧**一次 / 持续接触每个物理步 / 分开那一帧 |
| `other` 是什么 | **碰撞报告**：`collider`（对方碰撞体）/ `gameObject`（对方物体）/ `rigidbody`（撞静态墙时为 `null`）/ `relativeVelocity` / `contacts`（接触点数组） |
| 为什么认 `other.gameObject` | 判断"撞的是砖还是挡板"要认**物体本身**（Tag / 组件），改名不影响 Tag |
| 速度是"撞后"的 | 回调在物理**求解完成之后**调用；想看撞击强度用 `other.relativeVelocity` |
| 触发前提 | 至少一方是**动态刚体** + 双方都没勾 Is Trigger |
| 对照 | `OnTriggerEnter2D(Collider2D other)` —— 只有碰撞体，**没有接触数据、没有冲量**（参数类型本身就是"信息量"的提示） |

**用途演进**：今天 = 让物理过程可见（X 光片）→ 09-22 = 识别 + 处理（撞砖消失）→ 收尾 = 用 `contacts[0].point` 算"打在挡板哪一侧"来改反弹角度（**打砖块手感的一半在这个偏移量上**）。

### 八、排查清单（今日结论）

| 现象 | 先查什么 |
|---|---|
| 球不弹 | 材质是不是挂到了**刚体**上（该挂 Collider）；重力缩放是否没归零；「反弹合并」是不是被改成了"平均" |
| 球穿墙 / 穿挡板 | 碰撞检测是否为"离散"；墙是不是太薄；主体类型是不是被误设成 Kinematic（**Kinematic 与静态墙根本不碰撞**） |
| 球莫名停住 | 休眠模式（改"从不休眠"）；线性/角阻尼被调大 |
| 球越弹越矮 | **不是错觉**：即使弹性 1，求解器仍有微小能量损失（穿透修正 + 容差）→ 收尾用"每帧锁速度"打磨 |

### 九、性能小结（为 09-22 对象池埋伏笔）

## 6. 对象池与 GC（09-22）

### 一、为什么需要对象池

| 操作 | 真实代价 |
|---|---|
| `Instantiate` | 读模板（反序列化）→ 建 GameObject + 各组件 → 装配 `[SerializeField]` 值 → 入场景 → **堆分配** |
| `Destroy` | **不是立刻回收**：Unity 先标记，真正的清理排在**帧末**；C# 那侧要等 **GC** |

- GC 的杀手不是"慢"，是**停顿**（stop-the-world：回收时主线程被按住）→ 分配越频繁/堆越大，越容易周期性掉帧（GC spike）
- **对象池 = 把运行中的分配次数变成常数**：开场一次性分配，之后只在 `SetActive` 之间切换 → 运行中零分配
- 附加知识：`Destroy(obj)` 之后**那个 C# 引用不等于 `null`（C# 意义上）**，但 `obj == null` 却为 `true`——Unity **重载了 `==`**，会去问引擎"还活着吗"；所以"销毁后访问"报的是 `MissingReferenceException`，不是空引用

### 二、池的四个设计决策

| 决策 | 结论 | 理由 |
|---|---|---|
| **容器** | `Queue`（或 `Stack`） | 语义是"只在一端进出"→ 用窄接口把约束焊进类型。`List` 也能 O(1)（取出与归还**都用尾部**），但它允许 `RemoveAt(0)` → **O(n)**，编译器不拦。**接口越窄，误用越不可能**（同 `IReadOnlyList` 思想） |
| **池空** | `LogError` + `return null` | 预分配数 = 总需求 → 池空只可能是**逻辑 bug** → 响亮地失败；调用方仍要判空 |
| **归还时重置** | 位置/旋转**不重置**（借出时统一设置）；父子关系用"归属检查"兜住 | 单一保证点：**谁发出去谁负责初始状态**；将来有血量/颜色等可变状态时，必须在归还处清（否则"带着上次的伤复活"） |
| **⚠️ 双重归还防线** | `if (!brick.activeSelf) return;` | 池里的物体**一定失活** → 免费 O(1) 的标志。没它 = 同一对象入池两次 → 借出同一个对象两次 → **分身幽灵 bug** |

### 三、骨架（结构，不是实现）

```
预分配（Start）：循环创建 → SetActive(false) → Init(注入) → 入池 → _instantiateCount++
借出（Rent）  ：池空? LogError+null : Dequeue → SetActive(true) → _rentCount++
归还（Return）：判空 → 判归属 → 判是否已在池中(!activeSelf) → SetActive(false) → 入池
```

- **保险丝要在"动手之前"**：`cols <= 0 || cols*rows > 200` 这类检查必须挡在 `Instantiate` **之前**，放进 `FillBoard` 就晚了（生成已经发生）
- `SetActive(false)` **不会打断当前方法**：它只是把物体标记失活，**正在执行的方法会继续跑完**（与 `return` 是两码事）

### 四、依赖注入：Prefab 不能引用场景对象

- **现象**：给 Prefab 上的脚本加 `[SerializeField] BrickSpawner _pool` → **拖不进去**
- **原因**：Prefab 是**资产**（可被多个场景共用），场景对象是**实例** → 资产不能绑定某个场景实例
- **解法（运行期装配）**：池在预分配时 `brick.Init(this)` —— 普通方法，**不是引擎回调**，由你自己调用；**"这块砖属于这个池"是永久关系 → 建立一次就够**
- **对照**：`[SerializeField]` = 编辑器期装配（反序列化阶段就填好）；`Init(this)` = 运行期装配（依赖注入雏形，Block 3 委托/事件的前身）

### 五、怎么证明池真的在跑（验收三件套）

1. **预分配次数恒定**（`_instantiateCount` 开场 32 之后不再增长）
2. **借出计数 = 场上物体数**（`_rentCount`）
3. **归还后池水量回升**（`池中剩余` 从 0 往上涨 → 这是"有借有还"的唯一硬证据）
4. 层级窗口里物体总数**恒定**（灰掉的还在）

> **教训**：机制类改动必须用"能证明它在跑的数据"验收，而不是"看起来对"——砖块消失这件事，**"自己 SetActive"和"归还给池"两种实现产生的现象完全一样**。

### 六、易踩点清单

| 现象 | 原因 |
|---|---|
| 复用出来的物体带着上次的位置/状态 | 借出时没设初始状态 / 归还时没清可变状态 |
| 一块砖同时出现在两个位置 | **双重归还**（池里两份相同引用） |
| 池空后空引用崩溃 | `Rent()` 静默返回 `null`，调用方没判空 |
| 下次借出拿到 `null` | 归还时用了 `Destroy` 而不是 `SetActive(false)` |
| 开场编辑器假死 | 保险丝放在了生成**之后**，或数量上限没设 |

## 7. 碰撞进阶与手感（09-22）

### 一、`contacts` 数组：什么时候真的会空

- **理论上**：`OnCollisionEnter2D` 时接触流形刚刚建立 → **至少 1 个点**（引擎语义保证）
- **但这是"通常成立"，不是"契约保证"**（所以判空是**对准真实脆弱点**的廉价保险，和 219 那种凭感觉的保险丝不同）：
  1. `Collision2D` 是**复用包装对象**——只在回调期间有效，**存起来下次读就是空的**（"**存值不存包裹**"）
  2. 同一物理步内更早的回调把碰撞体禁用 → 后续数据可能不完整
  3. 版本/后端实现差异、位置修正（slop）
- **0 个 / 多个的根源是几何**：圆↔圆 1 点、圆↔面 1 点、**方↔方 面贴面最多 2 点**；顺序**无保证**，不要做位置假设；读数用 `other.contactCount` / `other.GetContact(i)`
- `ContactPoint2D` 是 **struct**（值类型）→ 先取到局部变量**不产生堆分配**，可放心为可读性多写一行

### 二、卡顿与"漏事件"全景（易混，值得单独记）

| 现象 | 事件会漏吗 | 根因 | 解法 |
|---|---|---|---|
| 物体太快，一步跨过对方 | ✅ 会（接触从未发生） | 离散检测 | 碰撞检测 = **连续** |
| **极端卡顿** | ✅ 会 | 超过 `最大允许时间步长`（默认 0.333s）→ **丢步**，被丢的物理步不执行 | 优化性能（对象池就是在干这个） |
| 回调之后再读 `contacts` | ✅ 数据没了 | 包装对象复用 | 当场读、**存值不存包裹** |
| 接触中被 `SetActive(false)` | ✅ 可能收不到 `Exit` | 接触对被移除 | 别把关键逻辑只挂在 `Exit` |
| 卡顿 → 一帧跑多个物理步 | 反向问题：`Stay` 一帧被调多次 | 固定步长追赶 | `Stay` 里累加要乘 `fixedDeltaTime` 或做幂等保护 |

**架构结论**：**事件为主 + 状态兜底** —— 事件负责"精确一次"的动作（撞砖→消失/加分），**状态查询**负责"持久正确"的信息（分数应能从"剩余砖块数"重算，漏一次事件也不会永久跑偏）。

### 三、静默失效四连（不报错 ≠ 执行了）

| # | 写法 | 后果 |
|---|---|---|
| 1 | 生命周期方法拼错（`OnCollisionEnter2d`） | 永不执行 |
| 2 | `CompareTag("paddle")` 大小写/拼写错 | 恒 `false` |
| 3 | 忘把脚本挂到 Prefab 上 | `GetComponent` 返回 `null` |
| 4 | **标签只加在编辑器内存里、没"保存项目"，或场景对象没贴标签** | 恒 `false` |

**通用判据：改完逻辑必须留一个"它在跑"的证据**（`Debug.Log` / 计数 / 数据变化）。**没有证据的"手感变化"，都是安慰剂。**

### 四、手感接管：击打点改角度（Pong / Breakout 的灵魂）

**为什么必须自己接管**：球撞**水平挡板**时接触法线竖直 → 反射角与击打位置**无关**。物理给的是"几何正确"，玩法要的是"好玩"——这就是**"物理给结果、玩法给手感"**的分界线。

**四步**：① 门卫判定是不是挡板 → ② 取击打点偏移 → ③ 归一化成 `t ∈ [-1, 1]` → ④ 用 `t` 造方向并**锁速率**覆盖速度。

| 数据源 | 范围 | 代价 |
|---|---|---|
| **球心**：`transform.position.x - other.transform.position.x` | ±(半宽 + 球半径) = ±1.8 | 简单、不会空；含球半径，边缘提前饱和 |
| **接触点**：`GetContact(0).point.x - other.transform.position.x` | ±半宽 = ±1.5 | 精确；**必须先判 `contactCount > 0`** |

**覆盖速度的三条纪律**：
1. `dir.normalized` **之后再乘速率**（方向管"往哪飞"、长度管"多快"，两件事分开）
2. **保证 y 分量 > 0**（否则球水平平推、在两侧墙间横跳、永远不再落到挡板 → 卡死）
3. 在**碰撞回调里改**（物理求解已完成，改下一步生效）；**不要每帧覆盖**，那会把物理结果全抹掉

**角度映射的两代写法**：

```csharp
// 第一代：(t, 1).normalized —— 角度 = atan(t)，t 越大越平，边缘区分度变差
Vector2 dir = new Vector2(t, 1f).normalized;

// 第二代：按角度线性映射 —— 每 1% 偏移 = 相同度数的转向，边缘不再"发死"
[SerializeField] private float maxBounceAngle = 60f;   // 边缘最大偏角（度）
float angle = t * maxBounceAngle * Mathf.Deg2Rad;
Vector2 dir = new Vector2(Mathf.Sin(angle), Mathf.Cos(angle));
```

> 代价：换写法后**已调好的手感要重调一遍**（`t=1` 时 63° → 60°）。取舍自己定。

**抽象时机**（今天特意**没有**抽）：

```
内联算式 → private 方法（现在） → 静态工具类（第二个真实调用方出现时）
```

- 只有一个调用方 → **留在原类内 + `private`**（`public` 要能点出"谁在调"）
- 真要共享 → **静态工具类**（`public static class HitUtil`），**不是 MonoBehaviour**：纯计算没有生命周期/状态，做成组件只会多一个"忘挂就静默失效"的坑，还进不了编辑器工具/单元测试
- 抽出去的**真实成本**：静态方法没有 `this`，"谁的目标"必须**显式传参**（上下文显式化）

### 五、补充：材质是"成对计算"的（今日实战）

- 一次碰撞的摩擦/弹性 = **两个碰撞体材质的混合值** → 谁漏挂，都按"默认材质（摩擦≈0.4 / 弹性 0）"参与混合
- 本项目实战：**球自己的碰撞体没挂材质** → `Mean(0.4, 对方 0) = 0.2` → 撞谁都被"搓"：掉速 + 变向；弹性走"最大" `max(0,1)=1` 所以**照弹**——现象是"弹得挺好但越来越歪"
- **认知纠偏**：**"现象最明显的地方"≠"根因所在"**（撞挡板变化最大，但根因在**球**——它是**每一对碰撞里共用的那一方**）
- 排查手段：**缓存"撞前"速度**（`FixedUpdate` 里存 `linearVelocity.magnitude`，它在物理模拟**之前**执行），在 `OnCollisionEnter2D` 里打印"撞前 → 撞后"

## 8. UGUI 与 TextMeshPro（09-23）

### 一、Canvas = UI 的"另一个世界"

| 渲染模式 | UI 活在哪儿 | 用途 |
|---|---|---|
| **屏幕空间 - 叠加**（默认） | 直接贴屏幕，永远盖在画面上 | **HUD / 计分 / 血条** ← 本项目 |
| 屏幕空间 - 摄像机 | 挂在某台相机前，跟着相机走 | 需要被 3D 物体遮挡 / 后处理 |
| 世界空间 | 变成世界里的一块平面，有位置有朝向 | 游戏内面板 / 告示牌 / VR UI |

- **UI 元素不活在游戏世界里**：它们用 **`RectTransform`**（不是 `Transform`），坐标属于 Canvas 这个独立坐标系
- **UI 用像素、世界用单位**，两套尺度互不相干（`50` 在 UI 里是 50 像素，在世界里是 50 单位 = 整个屏幕还大）
- ⚠️ 叠加模式下 Canvas 的 RectTransform 里 `LocalScale = (0,0,0)`、`sizeDelta = (0,0)` 是**引擎驱动的占位值**，**别去动它**（不是问题）

### 二、RectTransform 四件套（面板 ↔ 代码对照）

| 面板项 | 代码 | 含义 |
|---|---|---|
| **位置 X / Y** | `anchoredPosition` | **相对锚点的偏移（像素）**——不是世界坐标，也不是本地坐标 |
| **锚点 Min/Max** | `anchorMin` / `anchorMax` | 归一化 0~1，相对**父 RectTransform** 的矩形 |
| **轴心** | `pivot` | 归一化 0~1，**自身矩形内的参考点** |
| **宽度 / 高度** | `sizeDelta` | 点锚点下 = 实际宽高；拉伸锚点下 = 与父矩形的差值 |

**关键区分（今天踩的坑）**：
> **锚点**决定"相对父容器的哪个点定位"，**轴心**决定"自身哪一点对准那个位置"。

- 想"左上角贴边 40/30" → **锚点 (0,1) + 轴心 (0,1)** + 位置 (40,−30)
- 若轴心留在默认 `(0.5,0.5)`，同一个位置数值会让元素**中心**落在那里 → 400 宽的框会有一半伸到画布外 → **被切**

**定位公式**：
```
世界位置 = Canvas 位置 + 锚点在父矩形中的位置 + anchoredPosition − 轴心影响
```

### 三、Canvas Scaler 三件套

| 字段 | 说明 |
|---|---|
| **UI 缩放模式** | `常量像素大小`（画布 = 屏幕像素数，小窗口会挤爆）／**`按屏幕大小缩放`**（推荐）／`常量物理大小`（按 DPI） |
| **参考分辨率** | **= 美术设计稿尺寸**（1920×1080 是主流基准）⚠️ **不是"我屏幕多大就填多大"**：基准放大 → 同一字号显得越小（800×600 → 1920×1080 后，36 号字的观感直接砍半） |
| **屏幕匹配模式** | `Match Width Or Height`（推荐，配合下面的匹配滑条）／ `展开`（取较小缩放系数 → **绝不裁切**，会多留白）／ `Shrink`（取较大者 → **可能裁掉**超出画布的内容） |
| **匹配（Match）** | 0 = 完全跟宽度（保左右）｜ 1 = 完全跟高度（保上下）｜ **0.5 = 折中**（对数插值） |
| **每单位像素参考** | 只管**精灵/图片**的原生尺寸换算（Sprite PPU ↔ 画布 PPU），**与文字无关**；**默认 100 不要动** |

**UI 会不会被"压缩变形"？不会。** 缩放系数是**单一标量**（等比）→ UI 只会整体放大缩小。**只有"超出画布矩形"的部分才不渲染**（= 被切）。

### 四、TextMeshPro（TMP）

- **来源**：包 `com.unity.ugui`（`Packages/manifest.json`），代码程序集 `Unity.TextMeshPro`，命名空间 **`TMPro`**

  → 字段用 `TMP_Text`（基类）更通用（09-15 抽象类的实战价值）

### 五、UI 的性能纪律（与对象池同源）

1. **重建由"数据变化"决定，不由"代码每帧执行"决定**：`Text.text` 的 setter 会先比较——**值相同就提前 return，不标记 dirty、不重建**（脏检查）
2. **但"每帧执行"仍有代价**：`_score.ToString()` **每次都在堆上新建字符串** → GC 垃圾（对象池解决的是同一类问题）
3. **`Auto Size` 不要开**：每次改文字都重新算字号 → 放大重建
4. **自动布局组件（Layout Group / Content Size Fitter）会把"改文字"升级为"重新排布"** → 顶点重建 + Canvas 重新合批，最贵
5. **纪律**：**写 UI 由"数据变化"触发，而不是由 `Update` 触发**

```csharp
// ❌ 每帧制造垃圾（值不变虽不重建，但字符串照分配）
void Update() { _text.text = _score.ToString(); }

// ✅ 只在变化时写（无垃圾、无重建）
public void AddScore(int delta) { _score += delta; _text.text = _score.ToString(); }
```

6. **验证工具**：Profiler 看 `GC Alloc`（有没有垃圾）+ `Canvas.SendWillRenderCanvases`（重建耗时）

## 9. 架构决策、状态与配置陷阱（09-24）

> 今天从"加三个功能（胜负判定 / 场景重载 / 重开按钮）"起手，实际练的全是**结构题**：
> 依赖该往哪个方向走、数据该从哪来、守卫该放哪、UI 该靠什么跟世界分开。
> 成品：打砖块 **通关 / 失败 / 重开** 闭环跑通。

### 一、⭐ 依赖方向：裁判模式（方案甲 vs 方案乙）

**背景**：`BrickSpawner` 原本"加分"→ 认识 `ScoreManager`；现在又要判"通关"→ 需要"剩余砖块数"。若让 `ScoreManager` 反向去问 `BrickSpawner`，就成环。

| 方案 | 依赖图（箭头 = "知道"） | 代价 |
|---|---|---|
| 乙 · 事件通知 | `BrickSpawner → GameManager` **且** `GameManager → BrickSpawner` | ⚠️ **成环**（除非把数据塞进通知参数里绕开） |
| **甲 · 状态派生（采用）** | `GameManager → BrickSpawner`（只读状态）＋ `GameManager → ScoreManager`（只写显示） | 每帧一次减法（可忽略）；**全图无环** |

**结论**：**上层知道下层，下层谁都不认识。** 以后加"关卡 / 暂停 / 复活"，改动只落在 `GameManager` 一个文件里。

> 环为什么是坏味道（不是情绪，是工程代价）：
> ① 两个类**谁也不能单独测试**（想测 A 得先造一个真的 B）
> ② `Awake` 初始化顺序**靠运气**
> ③ 改一处要同时担心另一处

### 二、⭐ 状态派生 vs 事件累加（幂等从哪来）

| | 事件累加（旧 `AddScore`） | 状态派生（新 `SetDestroyedCount`） |
|---|---|---|
| 写法 | `_score += delta` | `显示 = f(打掉几块)` |
| 正确性靠 | **调用方只喊一次的纪律** | **结构本身**（喊一次和喊一百次一样） |
| 所以 | 09-23 得把加分塞进池的"三道防线之后"才敢用 | 09-23 那条伏笔直接销账 |

**判据**：**能"从状态重算"的量，就不要用"事件累加"去维护。**

⚠️ 一个容易忽略的顺序：`SetDestroyedCount(...)` 必须在"判通关"**之前**。反过来的话，最后一块砖被打掉那一帧会直接 `Win()` 返回，**分数停在 310**。

### 三、⭐ 存量 vs 流量（同一个数字，两种身份）

`RemainingBricks` 该用 `_instantiateCount` 还是 `_rentCount`？两者今天**数值相等**，但：

| 量 | 语义 | 由什么驱动 | 身份 |
|---|---|---|---|
| `_instantiateCount` | 世界里**一共有多少块砖** | `Instantiate`（创造） | 📦 **存量** |
| `_rentCount` | **"借出"这个动作发生过几次** | `Rent()` 被调用 | 🌊 **流量** |

**严格判据 —— 哪个是恒等式**（`N` = 砖总数、`B` = 累计借出、`R` = 累计归还、`P` = 池中数）：

```
每块砖在任意时刻只有两态（在池 / 在场）→ 这是一个"划分"
      场上 = N − P               ← 恒等式，永远成立 ✅
而    P = N − B + R
      B − P = 2B − N − R         ← 只有 B = N 时才等于"场上"
```

**`B ≠ N` 会发生吗？会。** 同一块砖 `Return` 回池后**可以再次被借出**。今天恰好 `B == N`，只因为 `Rent()` 只在 `FillBoard()` 里调、而 `FillBoard()` 只在 `Start()` 里跑**一次** —— **这是当前调用图的巧合，不是两个量之间的关系。**

未来会翻车的场景：加"补砖"机制后某列打光再借 4 块 → `N=32, B=36, R=5, P=1` → `B − P = 35`，而真实场上只有 **31**。

**判据（通用，拿去用一辈子）**：

| 名字里带 | 是 | 例 |
|---|---|---|
| **次数 / 累计 / 计数** | 🌊 **流量**（记录"发生过什么"） | `_rentCount`、`_hitCount` |
| **总数 / 当前 / 剩余 / 数量** | 📦 **存量**（描述"现在是什么状态"） | `_instantiateCount`、`_pool.Count` |

**问"现在"→ 用存量；问"一共几次"→ 用流量。** 诊断日志问的是"借出过几次"，用 `_rentCount` 完全正确 —— **各归各位**。

> 🔁 这是错误 06「**碰巧对 ≠ 保证对**」的又一次现身：靠隐式前提成立的正确性，改一个调用点就静默失效。

### 四、⚠️ 序列化字段：编译器看不见的输入

`[SerializeField] private GameManager gameManager;` 的赋值**不在代码里** —— 由 Unity 加载场景时填入。

- 编译器看到的是"一个从未被赋值的引用字段" → **完全合法**（默认 `null`）
- 所以 **编译器 / `ReadLints` / IDE 全都抓不到这个 bug**，**只有真跑 + 看控制台才会暴露**

**场景 YAML 里的判据**：

```yaml
gameManager: {fileID: 0}           # ❌ {fileID: 0} = null（槽位没连）
gameManager: {fileID: 400841083}   # ✅ 已连
```

**排查命令**（照抄可用）：

```powershell
Select-String -Path Assets\Scenes\SampleScene.unity -Pattern 'gameManager:|m_MethodName|m_IsTrigger'
```

> **"编译通过" ≠ "能跑对"** —— 编译只覆盖"代码层面"，配置是另一个战场。
> **按钮绑定的自查**：搜 `m_MethodName` —— 有输出 = 绑上了**且已落盘**；空输出 = 没绑上 **或场景没保存**。
> ⚠️ 反过来也别被日志骗：`Editor.log` 里"最后一条错误"可能是**历史残留**（编译成功时不会再写新的错误行）→ 判据是 **`Library/ScriptAssemblies/Assembly-CSharp.dll` 的时间戳 vs 源码时间戳**。

### 五、⭐ 入口上锁 ≠ 全局上锁（守卫要放在唯一出口）

今天最漂亮的一个 bug —— **静态看代码看不出来**，只有真跑才会暴露：

```csharp
void Update() {
    if (_isGameOver) return;                        // ← 锁在【入口】
    if (brickSpawner.RemainingBricks == 0) Win();
}
public void OnBallLost() { Lose(); }                // ← 这条侧门【绕开】了 Update
```

**复现路径**：打光最后一块砖 → `Win()` 显示 `YOU WIN` → 球还在飞 → 漏进 `FailZone` → `OnBallLost → Lose → End` → **结果被覆盖成 `GAME OVER`**。**你赢了，屏幕上写着"你输了"。**

**修法**：守卫搬到**唯一出口**。

```csharp
private void End(string message) {
    if (_isGameOver) return;   // ★ 守卫必须在"标记结束"的【前面】
    _isGameOver = true;        // 先上锁，再干别的
    ...                        // 副作用
}
```

**判据**：
- 数一数：入口有几个、出口有几个？→ **守卫放在最窄的那道门**（出口通常只有一个）
- ⚠️ 顺序：`if (已结束) return;` 必须在 `标记结束 = true;` **之前**（写反了第一次都进不来 —— 错误 07"守卫条件写反"同款）

### 六、⚠️ "空值"与"未初始化"是两件事

```csharp
if (brickSpawner == null || scoreManager == null) return;   // 防的是"引用没连"
```

它防不住**"这一局还不成立"**：

```
Board 的 Cols 改成 0 → 保险丝 LogError + return
  → _instantiateCount = 0、_pool.Count = 0
  → RemainingBricks 算出 0 → 开场第一帧 YOU WIN（毫无提示）
```

**修法**：再补一道用"能表达『这一局还不成立』"的量做的守门条件：

```csharp
if (brickSpawner.TotalBricks == 0) return;   // 还没摆砖 / 保险丝拦下了
```

**同一个病在字段层面**：`ScoreManager._lastDestroyed` 初始值给 `-1` 而不是 `0` —— 因为 `0` 是一个**合法的**"打掉 0 块"，用 `0` 当哨兵就分不清"还没画过"和"画了 0"。

> **手筋**：**给一个业务上不可能出现的值当哨兵。**

### 七、`Debug.Log` 的位置，决定它能证明什么

```csharp
gameManager.OnBallLost();          // ← gameManager 是 null，这里抛 NRE
Debug.Log("球掉进了 FailZone");     // ← 异常把它截断了，永远不打印
```

**现象 = "日志没打印" → 得出错误结论"回调没被调用"**。真相是：**回调调用了，炸在半路。**

| 日志放哪 | 它证明什么 |
|---|---|
| **第一行** | ✅ 「**我到达了这里**」——后面炸没炸是下一件事 |
| **最后一行** | ❌ 「前面全都成功了」——一旦前面有问题，它什么都证明不了，还给你错误结论 |

**规则**：**验证性日志放在你怀疑的那一段的最前面** —— 让它证明"到过"，而不是"走完"。

> 与错误 12「改完逻辑必须留一个**它在跑**的证据」、09-23「**磁盘才是事实**」同族。这一族的总名：**「证据要放在能证伪的位置」**。

### 八、⚠️ UI 与世界是两套坐标系（不是层级问题，是位置问题）

**反直觉事实**：`屏幕空间 - 叠加` 的 Canvas **永远画在世界画面之上** —— 世界里的精灵**不可能**遮挡 UI。
所以"文字被砖块挡住"的真相是**位置撞车**：

```
相机 orthographicSize = 5 → 视野高 10 世界单位 = 1080px → 1 世界单位 = 108px
砖块行 y = 3.5 / 2.7 / 1.9 / 1.1  →  屏幕中心往上 +378 / +292 / +205 / +119 px
∴ 砖块区 ≈ +90 ~ +420 px；挡板 ≈ −475 px；空区 ≈ −400 ~ +80 px
```

**但"挪位置"是隐式耦合**：把 `origin.y` 从 3.5 改成 2.0，砖块整体下移 162px → **又压上了**。

**正解：用结构，不用数值。**
① 给结束画面加**全屏半透明底板**（UI → 图像；黑 + `A≈150`）
② 把 `ResultText` / `RestartButton` **拖成底板（`Overlay`）的子物体**

两条引擎规则让代码**变短**：

| 规则 | 收益 |
|---|---|
| **子物体永远画在父物体之上** | 底板自动在文字/按钮**下面**，**不用手动排序** |
| **`SetActive` 有传染性** | 父物体失活 → 子物体全失活 → **一句 `overlay.SetActive(...)` 管住三样**，还省掉一个字段 |

> **判据**：**凡是靠"当前数值恰好不冲突"成立的东西都是脆弱的；用层级/结构把约定变成显式关系。**

### 九、场景重载：什么被清掉，什么不会（今日底层原理）

| | 会不会随重载复位 |
|---|---|
| 场景里的 GameObject / 组件 / **实例字段**（分数、池、球的位置…） | ✅ **会**（它们的"生命"属于**场景**） |
| **`static` 字段、`Time.timeScale` 等全局设置** | ❌ **不会**（挂在**类型/进程**上，程序集不卸载） |

```csharp
// End()：借出这笔账
Time.timeScale = 0;   // ⚠️ 全局静态设置
// Restart()：必须还回来
Time.timeScale = 1;   // 忘了 → 重开后的新一局是【冻结的】
```

**这就是"重开不用写一行『分数清零 / 池重填 / 球归位』"的原因** —— 那些东西本来就会随场景重载复位。

**顺手实测的三个答案**（`Time.timeScale = 0` 之后）：
- `Update()` **还跑**（不依赖时间步进）
- `FixedUpdate()` **不跑**（物理时钟停摆 → 球和挡板一起冻结）
- **UI 按钮还能点**（EventSystem 用 `unscaledDeltaTime`，**UI 不受 `timeScale` 影响**）

**`LoadScene` 的前提**：当前场景必须在「文件 → 生成配置文件」的**场景列表**里，否则会静默失败。

| 面板改了但行为没变 | 编译有红字时，**编辑器里的一切都是"上一个世界"的** | 先看控制台有没有红字 |

## 10. Animator、CanvasGroup 与音频（09-25）

> 今天给打砖块装上"**结局的表现**"：黑幕淡入 + 三个音效。
> 真正花时间的不是代码，而是**三条"看不见的线"**：`timeScale` 的影响力半径、**保存链路**、**同相位叠加**。

### 一、四个"Anim"先分清（混了就寸步难行）

| 东西 | 一句话 | 文件 | 谁引用谁 |
|---|---|---|---|
| **AnimationClip**（动画剪辑） | "**哪个属性**，在**第几秒**，是**什么值**" —— 一堆关键帧 | `.anim` | — |
| **AnimatorController**（动画控制器） | 一台**状态机**：状态 + 箭头 + 参数 | `.controller` | 每个 State 指向一个 Clip |
| **Animator 组件** | 挂在物体上的**播放器**：读 Controller，把值写回物体 | 层级/Prefab 上 | 读 Controller |
| **Animation 窗口** | **编辑器**（录制/编辑 Clip），**运行时不存在** | — | — |

> ⚠️ 另有一个曾经的 **`Animation` 组件**（只能播单个 Clip、没有状态机）—— **那个才是旧版/遗留**，只作了解。**`Animator` 是当前主流**。
> ⚠️ **「动画」窗口做 Clip，「动画器」窗口做状态机** —— 两个不同的窗口，别混。

### 二、`AnimationClip` 里到底存了什么

**关键帧 = "某个组件的某个属性，在第几秒，等于什么"。**
所以做动画有三步：① 选物体 ② `添加属性` 选**要动哪个属性** ③ 在时间轴上打关键帧。

**创建 Clip 的完整动作链**（Unity 会自动补后面几步）：

```
选中物体 → 打开「动画」窗口 → 点【创建】→ 存 xxx.anim
   → Unity 自动生成 xxx.controller，并给物体挂上 Animator 组件
```

### 三、⭐ 做 UI 淡入：为什么用 `CanvasGroup` 而不是动画 `Image.color`

| 候选 | 后果 |
|---|---|
| 动画 `Image.color` 的 alpha | ❌ 只有**那一块板子**淡入；文字和按钮会**"啪"地满不透明地跳出来**；而且颜色值被动画**写死** |
| **`CanvasGroup.alpha`** ⭐ | ✅ **整组一起淡入**（`alpha` **乘法传播**给所有子物体，除非子物体勾了 `Ignore Parent Group`）；颜色/内容仍归你管 |

**`CanvasGroup` 三件套**：

| 字段 | 管什么 |
|---|---|
| `Alpha` | 整组透明度（传播给子物体） |
| **`Interactable`** | 整组**要不要响应交互**（按钮还能不能被点；会显示成 disabled 外观） |
| **`Blocks Raycasts`** | 整组**参不参与射线检测**（不参与 = 点击**穿透**到它背后的 UI） |

> **两个开关的判据**：**`Blocks Raycasts` = 碰不碰得到 ｜ `Interactable` = 碰到了管不管。**
> **"看不见" ≠ "点不到"** —— `SetActive(false)` 是"物体不存在"（天然点不到）；`alpha = 0` 是"还在，只是透明"（**看不见但照样接点击**）。
> **所以配置三件套时，先问一句："我的隐藏机制是哪一种？"**

### 四、⭐ `Update Mode`：`Time.timeScale` 的"影响力半径"

**打砖块里 `End()` 会设 `Time.timeScale = 0`（冻住球和挡板），结果黑幕永远淡不进来。**

原因：`Animator` 组件的 **`Update Mode` 默认是 `Normal`，它跟着 `Time` 走 → 被 `timeScale = 0` 冻死**。

| `Update Mode` | 跟谁走 | 受 `timeScale` 影响 |
|---|---|---|
| **`Normal`（默认）** | `Update` | ✅ 受 → **暂停时冻住** |
| `Animate Physics` | `FixedUpdate` | ✅ 受 |
| **`Unscaled Time`** | 真实时间 | ❌ **不受** ← UI 表现层要选它 |

**这是 `Time.timeScale` 的第二笔账**（第一笔：**它不随场景重载复位** → `Restart()` 里要还）：

> **判据**：写下 `Time.timeScale = 0` 之前先问：**"我到底想冻住什么？"**
> - 只想冻**玩法** → `timeScale = 0`，但把 **UI 表现层的时钟换成 Unscaled**
> - **对照表**（`timeScale = 0` 之后）：
>   | 东西 | 受影响吗 |
>   |---|---|
>   | `Update()` | ❌ 照跑 |
>   | `FixedUpdate()` / 物理 | ✅ 停 |
>   | `Animator`（`Normal`） | ✅ 停 |
>   | **`AudioSource`** | ❌ **完全不受影响**（音频走独立时钟） |
>
> **"游戏世界停下来，表现层继续走"** —— 这才是一个暂停该有的样子。

### 五、⚠️ 动画窗口的「添加事件」陷阱：一个空事件能让整个 Clip 变成坏数据

**现象**：控制台报 `'Overlay' AnimationEvent has no function name specified!` → **Unity 拒绝保存** → 连带**场景、Controller 全都存不下去**。

**病因**（扒 `.anim` 文件看到的）：

```yaml
  m_Events:
  - time: 0
    functionName:          # ← 空！
```

**6 个空的 `functionName`，全部 `time: 0`** —— 在时间轴上叠成一个点，界面上**根本看不见**。

**这一条链条值得整个记住**：

```
手滑点了「添加事件」
  → Clip 里多一个空事件 → Clip 变成【坏数据】
  → 控制台报错 → 【保存被拒】
  → 场景没存（磁盘还停在昨天）
  → Controller 没存（m_AnimatorLayers 还是 []）
  → 运行时自然什么都不发生
```

> ⚠️ **「添加事件」按钮不要随手点**（它有正当用途，但不是今天）。
> 💡 **抢救手法**：`.anim` 是文本 YAML → **记事本打开，把 `m_Events:` 那一段删掉**（或改成 `m_Events: []`）→ 保存 → Unity 自动重新导入 ✓

### 六、Animator 组件上两个名字很像的下拉

| 下拉 | 管什么 | 三个选项 |
|---|---|---|
| **更新模式**（`Update Mode`） | **用哪个时钟驱动动画** | 普通 / 动画物理 / **非缩放时间** |
| **剔除模式**（`Culling Mode`） | **看不见时要不要省着跑** | 总是动画化 / 剔除更新变换 / 完全剔除 |

**记法**：**「更新模式」= 时钟（什么时间） ｜ 「剔除模式」= 开关（要不要省）**

### 七、音频三件套

| 东西 | 是什么 | 在哪 |
|---|---|---|
| **`AudioClip`** | **一段声音数据**（`.wav`/`.mp3`/`.ogg`）；对象层面带 `length` / `frequency` / `channels` / `samples`；**数据层面就是那一串 `float` 采样点** | 资产 / 运行时内存 |
| **`AudioSource`** | **喇叭**：Clip + 音量 + 循环 + 空间混合 | 挂在物体上（可多个） |
| **`AudioListener`** | **耳朵**：场景里**只能有一个**（多个会警告）；默认在 `Main Camera` 上 | 已有 |

**类比**：`AudioClip` = **唱片**（一张可被多个唱机同时放） ｜ `AudioSource` = **唱机** ｜ `AudioListener` = **耳朵**

| API | 行为 | 用在哪 |
|---|---|---|
| `Play()` | 播 `clip` **字段**里那一个，**打断上一个** | BGM、循环音 |
| **`PlayOneShot(clip)`** | 把 clip 当**参数**传入，**叠加**播放、互不打断 → **字段可以空着** | **音效** ✓ |

**`Spatial Blend`（空间混合）**：`0` = **2D**（不随距离/方位变化）← 街机/全屏玩法用；`1` = 3D（有衰减和方位感）。

### 八、⭐ 数字音频是什么（**了解级**，但模型很值钱）

> **数字音频 = 一串采样点。** 采样率 = 每秒记多少个点；每个点的值 = 那一瞬间的振幅（-1 ~ +1）。

**`SampleRate`（采样率）**：

| 值 | 用在哪 |
|---|---|
| 8000 Hz | 老式电话（人声够，发闷） |
| **44100 Hz** | **CD 音质** ← 我们用这个 |
| 48000 Hz | 视频/影视标准 |

**⭐ 为什么是 44100？—— 奈奎斯特采样定理**：**要还原频率 `f`，采样率必须 > `2f`。**
```
人耳上限 ≈ 20000 Hz → 采样率必须 > 40000 → CD 选 44100（留余量）
∴ 频率上限 = 采样率 / 2（奈奎斯特频率）= 22050 Hz
```
**采样率不足 → 混叠（aliasing）：高频被误认成低频。**
> 直观例子：**电影里高速转动的车轮会"倒转"**（马车轮效应）—— 24 帧/秒跟不上轮速，你"看到"了一个不存在的反向慢转。**那不是轮子倒转，是采样率不够。**

**`envelope`（包络）= 套在波形外面的"响度轮廓"**（吉他拨弦：`freq` 管音高，包络管"越来越小"）：

```csharp
data[i] = Mathf.Sin(2π · freq · t) * envelope * 0.3f;
//              ↑ 音高              ↑ 响度轮廓
```

**不乘包络会怎样**：振幅在结尾**瞬间跳到 0** → **"咔"的一声爆音（click）**。
> 🔗 **任何物理量突然突变，都会产生额外的频率成分** —— 音频里是爆音，视觉里是"闪一下"。
> **这和"动画要淡入淡出"是同一个道理**（你昨天给 `Overlay` 做的淡入，本质就是给视觉加了个包络）。

**配参口诀**：**`decay × duration ≥ 3`**（`e⁻³ ≈ 5%`）→ 结尾已衰减到听不见 → **无爆音**。

**ADSR（专业叫法，了解即可）**：`A` 起音 / `D` 衰减 / `S` 延音 / `R` 释音。
**打击类音效 = A 极短 + D 很快 + 无 S**（一击即走）。

**三要素**：采样率（水平多密，决定最高频率）/ **位深**（垂直多细，决定动态范围与底噪）/ 声道数。

### 九、程序化音效：用代码"算"出一张唱片

```csharp
int count = (int)(SampleRate * duration);                     // 采样点个数
AudioClip clip = AudioClip.Create(name, count, 1, SampleRate, false);  // 造【空白唱片】
clip.SetData(data, 0);                                        // 把算好的采样点【灌进去】
```

**两种存在方式**：磁盘资产（`.wav` 导入，**能进 git**）｜ **运行时内存**（`AudioClip.Create` 造的，**关掉就没**）。

### 十、⭐ 两个"生成一次、用很多次"：缓存 + 变体

**① 必须缓存**：每次撞砖都新建 clip = 每次分配 `3528` 个 `float`（**14KB**）→ 打 32 块砖 = **450KB GC 垃圾**。

```csharp
private static AudioClip _brickHit;
public static AudioClip BrickHit()
{
    if (_brickHit == null) _brickHit = Tone(...);   // 只有第一次真的算
    return _brickHit;
}
```
> 🔑 **"生成"是昂贵的，"复用"是廉价的 —— 任何"生成一次、用很多次"的东西都该缓存。**
> `BrickSpawner._pool` 缓存的是**对象**，`Sfx._brickHit` 缓存的是**资产**，**同一个思想的两种形态**。

**② 变体（variation）**：同时撞两块砖 → `PlayOneShot` **确实响了两声**，但**两段完全相同的波形起点对齐 → 同相位叠加 → `sin + sin = 2sin`，听起来只是"更响的一声"**。

| 两声之间的时间差 | 听感 |
|---|---|
| > 30~50 ms | 清楚的两声 |
| **< 20 ms** | 融成一声、音色变厚（**哈斯效应 / 优先效应**） |
| **0（同一帧同采样）** | **就是一声，只是更响** |

**解法的核心是"让第二声不同相"** —— 准备 **3 个音高微差（±6%）的变体，随机挑一个**：

```csharp
_brickHits[i] = Tone($"BrickHit{i}", 880f * (1f + (i - 1) * 0.06f), 0.08f, 40f);
return _brickHits[Random.Range(0, _brickHits.Length)];
```

> ⚠️ **别用改 `AudioSource.pitch` 的办法** —— `pitch` 是**整台唱机**的属性，会把**正在播的第一声也一起变调**。
> 💡 **为什么真实游戏都要做变体**：不加变体，连打 10 块砖 = **完全相同的 10 声** → 听感像"机枪"，机械、假。专业叫 **音效变体（variation / round-robin）**，枪声/脚步/命中音全都要做。
> ⚠️ **`Random.Range` 两个重载行为不同**（经典坑）：`Random.Range(0, 3)`（int 版）返回 `0/1/2`**不含 3**；`Random.Range(0f, 3f)`（float 版）返回 `[0, 3]`**含 3**。

| 现象 | 根因 | 一眼判据 |
|---|---|---|
| 控制台报 `AnimationEvent has no function name` + **不让保存** | Clip 里被塞了**空的动画事件** | 记事本打开 `.anim` 搜 `functionName:` 是否为空 |
| "动画预览能播，运行时不动" | **动画窗口预览直接改属性**（不需要 Controller）；运行时走的是 **Controller 状态机**，而它是空的 | 看 `.controller` 的 `m_AnimatorLayers` 是不是 `[]` |
| 黑幕淡不进来 + **整个游戏卡住** | `Time.timeScale = 0` 把 `Animator`（默认 `Normal`）一起冻了 | 算一算"谁在管时钟" |
| 按钮**点不了** | `CanvasGroup` 的 `Interactable` / `Blocks Raycasts` 被关了，而隐藏其实靠 `SetActive` | **先问"隐藏机制是哪一种"** |

## 11. 结算音效、锁与副作用、面板值的归属（09-26）

**本章是打砖块收官日（09-26）的沉淀** —— 打磨 5 项 + 抓掉一个"电流声"bug + 录屏存档。
主角仍是**"看不见的线"**：锁的位置、拼接处的突变、面板值的归属。

### 一、胜负音设计：**上行 = 胜利，下滑 = 失落**

| 音 | 波形 | 听感 |
|---|---|---|
| `Sfx.GameOver()` | `Sweep(440 → 110Hz)` 下滑 0.7s | "失落感" |
| `Sfx.GameWin()` | 三个音 **上行** `C5(523.25) → E5(659.25) → G5(783.99)` | "胜利感" |

> ⭐ 一个可复用的直觉：**音高往上走 = 正向 / 获得，往下走 = 负向 / 失去**。
> 音乐里的"终止式"就是往上收尾，所以上行音阶天然听起来像"完成"。

**"放什么音"属于"哪个结局"的知识，不属于"收尾"的知识** —— 所以音效**当参数传进 `End()`**：

```csharp
private void Win()  { End("YOU WIN",   Sfx.GameWin()); }
private void Lose() { End("GAME OVER", Sfx.GameOver()); }
private void End(string message, AudioClip sound) { ... audioSource.PlayOneShot(sound); }
```

（这就是 09-24「职责归属」那把尺子：`ScoreManager` 管分值、`GameManager` 只管流程、**调用方决定"用什么音"**。）

### 二、⭐ 段尾淡出：**拼接处的突变 = 爆音**（和 `decay × duration` 不是一回事）

把三个音**拼进同一个 `AudioClip`** 时，多了一道新工序：

```csharp
float envelope = Mathf.Exp(-8f * t);                     // 段内衰减（老配方）
float tail = Mathf.Min(1f, (perNote - i) / tailLen);     // ★ 段尾 20ms 线性收到 0
data[...] = Mathf.Sin(2π·f·t) * envelope * tail * 0.3f;
```

| 口诀 | 管的是什么 |
|---|---|
| `decay × duration ≥ 3`（09-25 学的） | **一个音自己收干净**（结尾振幅 < 5%） |
| **段尾淡出**（今天学的） | **两段音拼接处不突变** |

- 拼接处"前一段末尾振幅**突然归零**、后一段从 0 **重新起跳**" = **突变 → 额外频率成分 → "咔"声**
- ⚠️ **别用"把 envelope 拉到很低"代替它** —— 那会连音色一起改掉；淡出只处理**最后 20ms**

> 🔗 **"任何物理量的突然突变，都会产生额外的频率成分"** —— 音频里是"咔/爆音"，视觉里是"闪一下"。
> **和"动画要淡入淡出"是同一条物理规律**（09-25 第 10 章也记过这条线）。

### 三、⭐⭐ 锁必须罩住副作用（本章最重要的一条）

**事故**：通关音刺耳 + 一直响（像电流声）。**根因三行代码**：

```csharp
void Update() { ... if (brickSpawner.RemainingBricks == 0) Win(); }        // ① 每帧都调，无守门员
private void Win() { audioSource.PlayOneShot(Sfx.GameWin()); End("YOU WIN"); }  // ② 副作用在锁外
private void End(string message) { if (_isGameOver) return; ... }           // ③ 锁在这儿，拦不住②
```

→ **每帧播一次 0.36 秒的音 = 每秒 60 次叠加**。

| 症状 | 机理 |
|---|---|
| 永不结束 | 每帧都补一发新的 → 声音被无限"续命" |
| **刺耳** | 0.3 × 几十条叠加 → 波形超 `[-1,1]` → **削波（clipping）→ 方波化 → 大量高次谐波** |
| 像嗡嗡/电流 | 09-25「同相位叠加」的**极端版**：2 声="更响"；**60 声/秒 = 融合成持续音**（颗粒合成原理：**密度够高时叠加会变成一种全新声音**） |

**为什么只有通关炸、失败没事？—— 看调用源：**

| 出口 | 调用源 | 触发次数 |
|---|---|---|
| `Lose()` ← `FailZone.OnTriggerEnter2D` | **事件** | 天然**只一次** ✅ |
| `Win()` ← `Update()` | **每帧轮询** | **每帧一次** ❌ |

> **同一个写法，换个调用源，从安全变爆炸。**

**修法（两步，缺一不可）**：

1. **补守门员**：`void Update() { if (_isGameOver) return; ... }`
2. **让锁罩住副作用**：音效当参数进 `End()`，`End()` 内部**先上锁 → 再改状态 → 最后播**

> **判据**：**锁必须把副作用整个罩住，否则等于没锁。**
> 修 ① 只堵住"这一个调用点"；**修 ② 让"任何调用者重复调用都安全"—— 这才是治本**。
> ⚠️ 顺带一个测试手法：通关要打光 32 块砖，是**全场最难走的分支** → **临时把砖块数调小**，把它变成最好走的路，30 秒就能验证。**补测试盲区的通用招式。**

### 四、`Debug.LogError(msg, context)` —— 让日志"可点可定位"

```csharp
Debug.LogError("GameManager 引用缺失：请在检查器里挂上 brickSpawner / scoreManager", this);
// 真实签名：public static void LogError(object message, Object context);
```

- **`context` 的作用**：双击控制台里的这条日志，**在「层级」里选中这个物体 + 检查器高亮这个组件**

- ⚠️ **它只影响"日志怎么被定位/展示"，不影响内容与行为**
- **消息告诉你"发生了什么"，`context` 告诉你"在哪儿"**

## 12. 委托做回调：装配期 vs 运行期（09-28）

### 一、这次改了什么（**纯内部重构，观感零变化**）

- **改前**：`GameManager.Update()` 里直接 `scoreManager.SetDestroyedCount(...)` —— 裁判**认识** `ScoreManager` 这个类
- **改后**：裁判只持有 `private Action<int> _notifyScore;`，在 `Start()` 里用**方法组**装配，`Update()` 里只喊委托
  ```csharp
  private Action<int> _notifyScore;                       // 只认"一个能吃 int 的签名合同"
  void Start()   { _notifyScore = scoreManager.SetDestroyedCount; }   // 方法组 → 委托实例
  void Update()  { _notifyScore?.Invoke(brickSpawner.TotalBricks - brickSpawner.RemainingBricks); }
  ```
- **依赖方向变成了**：`GameManager ─→ BrickSpawner（读状态）` ＋ `GameManager ─→ Action<int>（一个合同，不知道背后是谁）`
- ⚠️ **不是"事件总线"**：分数仍然是 `f(剩余砖块)` 的**派生量**（第 9 章第二节的方案甲没动），委托只是把"通知这一跳"从"认类"换成"认签名"

### 二、⭐ 装配期检查 vs 运行期检查（今天最值得带走的一条）

| 何时查 | 查什么 | 查不到怎么办 |
|---|---|---|
| **`Start`（装配期，一次）** | "**必须有人接**"的接线（`scoreManager == null` → 装配根本不成立） | **响亮地失败**：`Debug.LogError(..., this)` + **`enabled = false`**（不关掉自己就会每帧刷同一行红字，把真正的错误淹掉） |
| **`Update`（运行期，每帧）** | 每帧真的要读的**状态源**（`brickSpawner == null`） | 同上 |

- 两边都查不算错，但会让你分不清"**接线坏了**"还是"**运行中数据坏了**"
- `_notifyScore?.Invoke(...)` 里的 **`?.`** 防的是"**没人订阅**"（字段为 null）：
  - **通知类**（可选旁路）→ 允许安静跳过
  - **接线类**（必须有人接）→ 必须响亮失败（所以 `Start` 那道防线不能省）
- ⚠️ **委托可以为 null 的根源**：`+=`/`-=` 底层是 `Delegate.Combine/Remove` **造新对象再赋回** → 减空之后变量就是 null（编译器给 `CS8602` 警告正是这件事）

### 三、⚠️ 委托**不能**序列化 —— 所以永远拖不进检查器

- Unity 的序列化只认它认识的类型（`UnityEngine.Object` 引用 / 基元类型 / 标了 `[Serializable]` 的类或结构…）→ **`Action<int>` / 自定义委托都不在其中** → 委托字段**只能在代码里装配**
- 想在**面板上拖** → 就得换成 **`UnityEvent`**：它是 **Unity 自己的类型**、可序列化、能存进场景文件；代价是更重（反射调用 + 手动配置）
- 因此 `[SerializeField] private ScoreManager scoreManager;` **要保留**：它是**装配用的插头**，只是不再出现在每帧路径上

## 13. 漏球改事件广播：方向反转、退订与编译上下文（09-29）

### 一、这次改了什么（**纯内部重构，观感零变化**）

|  | 改前 | 改后 |
|---|---|---|
| 广播方式 | `FailZone` 直接调 `gameManager.OnBallLost()` | `FailZone` 声明 `public event Action BallLost;` → `BallLost?.Invoke();` |
| 依赖方向 | `FailZone ─→ GameManager` | **`GameManager ─→ FailZone`（订阅）**；`FailZone ─→ 谁都不认识` |
| 事件声明在谁身上 | —— | **发布者**（`event` 只能由声明它的类内部 raise → **发布者 = 声明者**） |

`GameManager` 侧三处：新增 `[SerializeField] FailZone failZone;` → `Start()` 里防线 + `failZone.BallLost += OnBallLost;` → `OnDestroy()` 里 `if (failZone != null) failZone.BallLost -= OnBallLost;`

### 二、⭐ 防线该属于哪一侧（今天最容易错的地方）

| 角色 | 引用别人吗 | 需要防线吗 | 形态 |
|---|---|---|---|
| **发布者** | 谁都不引用 | **不需要** | `?.Invoke()` 兜"没人订阅"（通知是可选旁路，安静跳过合法） |
| **订阅者** | 引用了发布者 | **需要** | `if (x == null) { Debug.LogError(…, this); enabled = false; return; }` |

**今天的现场**：改造时把 `gameManager` 字段删了，却把那 5 行空引用检查留着、只把变量名改成 `failZone` → **CS0103**（`failZone` 是 GameManager 的字段名）→ 见 `错题本` 错误 20。

> 判据：**"我必须认识谁"的那一侧才需要防线**；改方向时，**旧防线连同旧注释一起删**。

### 三、⭐ 订阅 / 退订的配对判据

| 订阅写在哪 | 退订就该写在哪 | 为什么 |
|---|---|---|
| `Start()` | `OnDestroy()` | 两者**都只执行一次** → 天生配对（当前工程就是这条） |
| `OnEnable()` | `OnDisable()` | 两者会**反复成对触发**（物体被反复启停），必须成对 |
| ❌ 错配（如 `OnEnable` + `OnDestroy`） | —— | **重复订阅 → 回调被调多次**（分数加两遍、音效响两声） |

- **对象被销毁后重建**（含场景重载 = 按 `RESTART`）**不需要手写"重新订阅"**：新对象有自己的 `Start`，会自己订阅一次；旧对象走 `OnDestroy` 退订一次
- ⚠️ **退订不能用 `?.` 简写**（`a?.B -= x` 语法不合法）→ 必须写 `if (a != null) a.B -= x;`
- ⚠️ 而这个 `if (a != null)` 恰好也是 Unity"假 null"（对象已销毁）的正解 —— `?.` 只管字段本身是不是 null

### 四、⚠️ Unity 的编译上下文与 nullable

|  | 控制台练习项目 | Unity 生成的 `Assembly-CSharp.csproj` |
|---|---|---|
| `<Nullable>` | `enable`（我们手写的 csproj） | **未设置 = 关闭** |
| 写 `Action?` | 合法，且**真的参与空分析**（09-28 那条 CS8602 就是它给的） | **CS8632 警告**："只能在 `#nullable` 注释上下文内使用" |
| 结论 | —— | **注解能省就省；`?.` 该写还得写** |

⭐ 记住这句：**注解（`?`）是给编译器的提示，`?.` 是运行时检查** —— 两件事，别混。

### 二、⭐ 核心：刚体类型决定"谁有权威"

| | 挡板 `PaddleController` | 玩家 `PlayerController` |
|---|---|---|
| 刚体类型 | **Kinematic** | **Dynamic** |
| 交出去的东西 | **目标位置**（`MovePosition`） | **速度**（`linearVelocity`） |
| 位移谁算 | **自己算**（`速度 × Time.fixedDeltaTime`） | **物理引擎积分** |
| 竖直方向 | 写死 `0f`（挡板永远水平） | **保留 `y`**（归重力管） |
| 限位 | `Mathf.Clamp` | 不需要（地形来挡） |

**判据**：`Kinematic = 位置权威` → 只能 `MovePosition` / 改 `position`；`Dynamic = 速度权威` → `linearVelocity` / `AddForce`，位置交给引擎积分。

**两种错配的症状**（记症状，别记结论）：

| 错配 | 症状 |
|---|---|
| Kinematic 设 `linearVelocity` | **完全不动**（速度被忽略） |
| Dynamic 用 `MovePosition` | 抖动 / 穿模 / 重力失真 —— 等于**抢走物理引擎的积分**，位置与速度互相打架 |

⭐ **为什么玩家代码里没有 `Time.fixedDeltaTime`**：**交位移要乘步长**（"这一步到哪里"= 距离）；**交速度不用乘**（"每秒走多快"= 速率）；乘了反而变成"每秒²"。

### 三、`y` 那一半必须原样保留

```csharp
_rb.linearVelocity = new Vector2(_axis * moveSpeed, _rb.linearVelocity.y);
```

- 竖直方向**归重力管**：`linearVelocity.y` 正是重力累积出的当前下落速度；写死 `0` → 重力白算 → **角色悬空不落**
- 10-02 的跳跃会顺着这条走下去：**跳跃 = 给 `y` 一次初速度**（`new Vector2(x, jumpSpeed)`），之后由重力负责减速与下落 —— 同样是"交速度"，不是"自己加位移"

### 四、`Update` 读 / `FixedUpdate` 交（承第 3 章的"Update 写、FixedUpdate 读"）

| 阶段 | 干什么 | 为什么 |
|---|---|---|
| `Update` | `_axis = _move.ReadValue<Vector2>().x` | 输入是"**每帧的意图**"，在帧时钟里读 |
| `FixedUpdate` | 把 `_axis` 换算成速度提交 | 物理在**固定步长**里跑，提交必须与它同拍 |
| `Awake` | `GetComponent` + `InputSystem.actions.FindActionMap("Player").FindAction("Move")` | 只做**一次**（每帧查找是白花的；第 3 章 `Camera.main` 同理） |

### 五、组件清单（谁静态、谁被物理驱动）

| 工程 | 物体 | SpriteRenderer | Collider2D | Rigidbody2D |
|---|---|---|---|---|
| Platformer | `Player` | ✓ | `CapsuleCollider2D` | ✓ **Dynamic** |
| Platformer | `Ground` | ✓ | `BoxCollider2D` | ✗ **没有 = 静态** |
| Breakout（实测计数） | 球 | ✓ | `CircleCollider2D` ×1 | ✓ Dynamic ← **全场刚体只有 2 个**（球 + 挡板） |

### 六、`Rigidbody2D` 五个面值（场景 YAML 核过的实际值）

| `m_CollisionDetection` | `1`（Continuous） | 防高速下落"一步跨过地面" |

## 15. 多输入源汇合 + UI"按住"按钮（10-01 · Breakout 追加）

> 需求：给 Breakout 加"屏幕左 / 右按钮"，**按住持续移动**；且**不能破坏**原有的键盘 / 摇杆输入。

### 一、⭐ 核心判据：输入源可以有多个，但"轴值"只能有一个汇合点

```csharp
// PaddleController.Update
float axis = _move.ReadValue<Vector2>().x;                     // 输入源①：键位 / 摇杆
if (leftButton  != null && leftButton.IsHeld)  axis -= 1f;      // 输入源②：屏幕左按钮
if (rightButton != null && rightButton.IsHeld) axis += 1f;      // 输入源③：屏幕右按钮
_axis = Mathf.Clamp(axis, -1f, 1f);                             // ⭐ 唯一的汇合点
```

- **`FixedUpdate` 一行都没改**（它只认 `_axis`）→ 这就是判据的**现场证据**：**汇合点的作用，是让下游"对输入源的数量一无所知"**
- 左右同时按 → `-1 + 1 = 0` → 挡板不动（`Clamp` 天然处理，不需要写特判）
- ❌ 反例（别这么做）：按钮脚本里直接 `rb.MovePosition(...)` 或直接改位置 → 与轴输入**互相覆盖**（谁后写谁赢），且绕过单向数据流

### 二、"按住"必须用**两个时点**，`OnClick` 做不到

| 通路 | 触发时机 | 能表达"按住"吗 |
|---|---|---|
| `Button.OnClick`（`UnityEvent`，检查器里拖方法） | 按下**且**抬起都在同一对象时，**触发一次** | ❌ 不能 |
| `IPointerDownHandler` / `IPointerUpHandler`（**接口**） | 按下时一次、抬起时一次 | ✅ `Down` 置真、`Up` 置假 → 中间**持续为真** |

### 三、⭐ 框架是**按接口**来找你的（不是按方法名）

```csharp
public class HoldButton : MonoBehaviour, IPointerDownHandler, IPointerUpHandler
{
    [SerializeField] private float value = -1f;      // 左按钮 -1，右按钮 +1
    public bool IsHeld { get; private set; }

    public void OnPointerDown(PointerEventData e) => IsHeld = true;
    public void OnPointerUp(PointerEventData e)   => IsHeld = false;
}
```

- 接口源码（UGUI 包 `Runtime/UGUI/EventSystem/EventInterfaces.cs`）只承诺一件事：
  ```csharp
  public interface IPointerDownHandler : IEventSystemHandler { void OnPointerDown(PointerEventData eventData); }
  ```
- 流程：指针按下 → `EventSystem` 从屏幕坐标发**射线** → 命中的 UI 元素上**找实现了该接口的组件** → 调它的方法
- ⚠️ **方法名不能改、签名必须一致**（形参名随便，类型不行）→ "写了方法却永远不被调用"，九成是**没实现对应接口**
- `IEventSystemHandler` 是个**空接口**，只当"我是 EventSystem 家族成员"的**标记**

**同一个形状你已经见过好几次**：Unity 的回调 = **"事件名 + 一个数据包参数"**

| 回调 | 数据包 | 里面装什么 |
|---|---|---|
| `OnCollisionEnter2D(Collision2D collision)` | `collision` | 碰撞点 / 法线 / 相对速度（09-22 用过 `GetContact(0).point`） |
| `OnTriggerEnter2D(Collider2D other)` | `other` | 撞进来的那个碰撞体 |
| `OnPointerDown(PointerEventData e)` | `e` | `pointerId` / `position` / `delta` / `button` / `clickCount` … |
| `Action<int> OnScoreChanged` | 那个 `int` | 只有一个**值**（不是对象） |

### 四、两套"谁来找你"的对照（控制反转的两个版本）

| 谁调用你 | 靠什么约定找到你 | 拼错 / 写漏的后果 |
|---|---|---|
| Unity 生命周期（`Awake` / `Update` / `OnDestroy`） | **方法名** | **静默失效**（不报错、不执行 → 所以一律用 IDE 补全） |
| EventSystem 事件（`OnPointerDown` 等） | **接口** | **编译报错**（`CS0535` 未实现接口成员 → 编译器替你兜住） |

### 五、三个配套条件（缺任何一个 → "按了没反应，也不报错"）

1. `using UnityEngine.EventSystems;`（漏了 = `CS0246`，找不到 `IPointerDownHandler` / `PointerEventData`）
2. 组件挂在**能被射线命中**的东西上：Canvas 上有 `GraphicRaycaster`，且该图形的 `Raycast Target` = ✅
3. 场景里有 **`EventSystem`**（Breakout 一直都有 —— 证据：`RESTART` 按钮能点）

### 六、面值的默认值也是判据

`[SerializeField] private float value = 0f;` —— 实际值靠检查器填（左 `-1` / 右 `+1`）。
⚠️ 但**默认值 `0f` 有隐患**：将来新建按钮忘记填 → `axis += 0` → **"按了没反应、也不报错"**（最难查的那类）。
⭐ 判据：**面值默认值要么是有意义的值，要么明确留 0 当"必须填"的信号**（并写进注释）。

## 16. 层与掩码 + 脚点探针 + 边沿/电平（10-02 · 闸门①：能跑能跳）

> 需求：把 Platformer 的玩家从"能左右跑"推到"**能跑能跳**"，并让"手感"变成**可调的**而不是碰运气。

### 一、层（Layer）：它是"**物理引擎的世界**"，标签不是

| | 层（Layer） | 标签（Tag） |
|---|---|---|
| 谁认识它 | ⭐ **物理引擎认识**：参与**碰撞矩阵**（谁能撞谁）/ **查询过滤**（`layerMask` 参数）/ `Physics2D.IgnoreLayerCollision` | ❌ 物理完全不看，**只有你的代码认识** |
| 拼错 / 未定义的后果 | `LayerMask.GetMask("X")` → **静默返回 0**（永远查不到） | `CompareTag("X")` → **抛 `UnityException`**（响亮） |
| 住哪 | **都在同一个文件**：`ProjectSettings/TagManager.asset` | 同上（它就是"标签和层"那个窗口） |

- ⚠️ **别拿性能当理由**（Tag 判断与 Layer 判断的开销差异可忽略）。真正的差别是 **"物理想不想认识它"**。
- 👍 界面里的名额：只有 **5 个 `Builtin Layer`**（`Default`=0 / `TransparentFX`=1 / `Ignore Raycast`=2 / `Water`=4 / `UI`=5），其余（3、6、7、**8~31**）**全部标 `User Layer`** → 自定义位比想象中多，**唯一硬约束 = 别动那 5 个 Builtin**。
- ⚠️ 层名**前后不能有空格**（`Ground` ≠ `Ground `）—— 复制粘贴最容易带上尾空格，而它**不报错**。
- ⚠️ **层号是按位置分配的** → 上面清空一行再填新层，下面全体**错位**。所以：
  ```csharp
  LayerMask.GetMask("Ground")     // ✅ 用层名
  int mask = 1 << 8;              // ❌ 硬编码层号：插一行就悄悄指向别的层
  ```

### 二、掩码：位运算的来历（层号 / 层位 / 掩码，三行口诀）

引擎内部把"层"存成**一张 32 位的开关表**（每一位 = 一个层号）：

| 层 | `1 << 层` | 二进制（低 8 位） | 十进制 |
|---|---|---|---|
| 0 Default | `1 << 0` | `0000 0001` | 1 |
| 4 Water | `1 << 4` | `0001 0000` | 16 |
| 5 UI | `1 << 5` | `0010 0000` | 32 |
| **6 Ground** | `1 << 6` | `0100 0000` | **64** |
| **7 Player** | `1 << 7` | `1000 0000` | **128** |

| 说法 | 例子 | 用途 |
|---|---|---|
| **层号**（位置） | `6`、`gameObject.layer` | 用来**指** |
| **层的位**（单个开关） | `1 << 6`（=64） | 用来**算** |
| **掩码**（一堆开关） | `groundLayer.value`、`LayerMask.GetMask(...)` | 用来**筛** |

- `&`（**与**）= **取交集 / 筛选**；`|`（**或**）= **合并集合**（`groundLayer.value | (1 << 7)`）。
- ⭐ 判据：**数值才用 `==` 比；掩码表达的是"集合"，只能用 `&` / `|` 比**（多勾一层就判不出"包含"了）。
- ⭐ **"勾选 → YAML"的现场证据**：场景文件里 `groundLayer: m_Bits: **64**` 就是 `0100 0000` = `1 << 6`（只勾 Ground）；再勾上 Player 会变成 `192` = `1100 0000`（`64 | 128`）→ **勾选 = 或运算的累加**。
- 对照本册第 15 章的 `Action<int>` / C# 侧的 `^`（异或 = 成对抵消，136 用过）：`&` / `|` / `^` 是"位"世界的同一套工具。

### 三、⭐ 探针（我主动问） vs 接触回调（等引擎说）

| 问法 | API | 时机 | 给不给"方向" |
|---|---|---|---|
| 圆的探针 | `Physics2D.OverlapCircle(点, 半径, 掩码)` | ⭐ **现问现答、无延迟** | 不给 |
| 盒子 / 胶囊探针 | `OverlapBox` / `OverlapCapsule` | 同上 | 不给 |
| 细线 | `Physics2D.Raycast(起点, 方向, 距离, 掩码)` | 同上 | 不给 |
| "我碰到了谁" | `Collider2D.IsTouchingLayers(掩码)` | ⚠️ 读引擎**已记录**的接触数据 → **慢一拍** | 不给 |
| 碰撞回调 | `OnCollisionStay2D` + `contact.normal` | ⚠️ 物理**求解之后**才调 → `FixedUpdate` 里读到的**是上一步的结果** | ✅ 给 |

⭐ 判据：**"问什么形状、问哪个点、问哪一层"都在你手里** —— 这就是"手感可调"的来源；回调则是"引擎喂什么你吃什么，还慢一拍"。

**返回值：单位是"有没有"** —— `OverlapCircle` 返回 `Collider2D` 或 **`null`**：
- ⚠️ 用 `!= null`，**别用 `is not null`** —— Unity 重载了 `==`/`!=` 能识别"已销毁物体"；`is null` 走纯 C# 引用语义，**绕过**这层保护
- ⚠️ 第 3 个参数是**掩码不是层号**：`0` = 谁都不问（**永远不接地**）；`-1`（Everything）= 全都问（**包括你自己**）
- 只要一个 bool → 用**单数版**（`OverlapCircle`），别为它分配数组（`OverlapCircleAll`）

### 四、⭐⭐ 探针会命中**玩家自己** → 掩码不是可选项

```csharp
// 圆心就摆在自己碰撞体的【底边】上 → 圆往上探的那部分【压在胶囊里】
bool isGrounded = Physics2D.OverlapCircle(groundCheck.position, checkRadius, groundLayer) != null;
//                                                                      ↑ 靠它排除自己
```

- **不加层过滤的后果**：永远返回非空 → **永远算接地** → 症状是"跳不高 / 空中乱跳"，而且**控制台一声不响**（最难查的那类）
- ⭐ **通用判据**：**"查询类" API（Overlap / Cast）必须配层掩码，因为它们连你自己都会撞**；而 `OnCollisionEnter2D` 回调**天然不会**把自己的碰撞体报给自己 —— 这就是两条路的机制差别。
- ⭐ 记录：`Transform.position` 是**世界坐标**（检查器「位置」框显示的是**本地坐标**，见第 2 章的实验）；探针 `GroundCheck` 的 `localPosition = (0, -0.5, 0)` 是相对父物体的语义，但**查询在世界空间做** → 参数要取 `position`。

### 五、边沿 vs 电平（输入 API 两族）

| API | 类型 | 按住空格 3 秒 |
|---|---|---|
| `IsPressed()` / `ReadValue<float>()` / `.phase` | **电平**（"现在是什么状态"） | **刷屏 `true`** |
| **`WasPressedThisFrame()`** | **边沿**（"变化刚发生那一瞬"） | ❗**只出现一次** |
| `WasReleasedThisFrame()` / `WasPerformedThisFrame()` | 边沿 | 同上 |
| `triggered`（**老写法**，老教程遍地都是） | 边沿 | 基本等价于 `WasPerformedThisFrame` |

- ⭐ 判据：**要"跳一次"用边沿；要"持续施力"用电平** —— 挡板的 `_move.ReadValue<Vector2>().x` 是**电平**（要的是"你**正推着**"），同一个类里两种语义并存是需求不同，不是矛盾。
- 写用 `WasPressedThisFrame()`（新版优先），但要**读得懂** `triggered`。

### 六、⭐ 意图标志位：两种时钟之间的**桥**

```csharp
void Update()      { if (_jump.WasPressedThisFrame()) _jumpRequested = true; }   // 帧级事件 → 存成意图
void FixedUpdate() { /* … 用 _jumpRequested … */ _jumpRequested = false; }       // 物理步消费并清零
```

- **为什么必须过一道桥**：`WasPressedThisFrame()` 是"**帧级**"语义 —— 只有在**动作被更新的那一帧**为真（项目级 Actions 默认在 `Update` 更新）。若直接在 `FixedUpdate` 里读：一个渲染帧有 **0~N 个**物理步 → 要么**漏读**、要么**把同一按键读成多次**。
- ⭐ 判据：**它不是多余的中间变量，而是"帧时钟"与"物理时钟"之间唯一的桥**（承第 3 章的双时钟）。
- ⭐ **"消费"的位置也是判据**：`_jumpRequested = false;` 放在 `if` **外面** = 跳不了就**即时作废**（不缓冲）；放里面 = 意图"憋着"，等落地回满那一刻**自动释放** → 症状是"**落地自己弹一下**"（意外的输入缓冲）。

### 七、一个物理步只提交一次速度

```csharp
float y = _rb.linearVelocity.y;            // ① 先取出"那一份"，三处判断都用它
if (grounded && y <= 0f) _jumpsLeft = maxJumps;
if (_jumpRequested && _jumpsLeft > 0) { y = jumpSpeed; _jumpsLeft--; }   // 起跳 = 【覆盖】不是累加
else if (grounded && y < 0f)          { y = 0f; }                       // 落地归零
_rb.linearVelocity = new Vector2(_axis * moveSpeed, y);                 // ② 全场唯一一次提交
```

- ⭐ 判据：**分两次赋值 = 后写的覆盖先写的**（谁后写谁赢）→ 先把 `y` 的三个去处合成一个，再统一上交。
- **起跳为什么是"覆盖"不是"累加"**：覆盖才能让高度**只由 `jumpSpeed` 决定**（可预期、可调）。
- **落地归零为什么能省掉不写**：站住时求解器会残留一点负值 → 不归零，起跳高度每次都略有不同；归零后 `jumpSpeed` 是**唯一**变量。
- 承第 14 章：Kinematic 交**位置**（`MovePosition`）／ Dynamic 交**速度**（`linearVelocity`）—— 这里 `y` 归重力管，所以**只覆盖 `x`、原样保留 `y`**。

### 八、⭐⭐ 传感器的"跟不上那一瞬"（本日最值钱的一条）

- **现象**：起跳后头一两步，**探针还压在地里**（圆心才抬升约 0.14 = `jumpSpeed × fixedDeltaTime`）
- **后果**：若回满次数写成 `if (isGrounded) _jumpsLeft = maxJumps;` → 次数被**非法回满** → 空中连点**白送跳次**
- **正解**：**加一个"状态方向"的条件** —— `if (isGrounded && y <= 0f)`（**停住或下落**时才回满）。刚起跳时 `y = +jumpSpeed > 0`（正在上升）→ 不回满。
- ⭐ 通用判据：**"用传感器判断状态"时，必须考虑"状态刚改变的那一瞬间传感器还没跟上"** —— 后面做"要不要播放脚步声""是否贴墙""土狼时间"都是同一个坑。
- **半径的代价**：`checkRadius` 调大 → "离地后仍判接地"的窗口 ≈ **一整个半径**（`半径 ÷ (jumpSpeed × fixedDeltaTime) ≈ 还判接地的步数`）→ 更"黏"，但更容易白送跳次。

### 九、响亮地失败：探针接线的**三条**检查

```csharp
bool wiringOk = true;                                          // ⭐ 收集全部问题，再统一停手（修一轮 vs 修三轮）
if (groundCheck == null)                      { /* LogError */ wiringOk = false; }
if (groundLayer.value == 0)                   { /* LogError */ wiringOk = false; }   // 忘了勾
if ((groundLayer.value & (1 << gameObject.layer)) != 0) { /* LogError */ wiringOk = false; }  // ⭐ 勾到了自己
if (!wiringOk) { enabled = false; return; }                    // ⭐ 停手
```

- ⭐ 判据：**`value == 0` 只抓"忘了勾"，抓不了"勾错了"** → 两个检查都要有（"零"和"全/含自己"是两种不同的坏）。
- ⭐ 停手的理由：**不停手的话，真正的病因（槽位没接）会被下游每物理步刷屏的 `NullReferenceException` 埋掉** → 报错指向错误的地方。
- ⭐ 判据：**用 `LogError` 而不是 `LogWarning`** —— 红的 + 能配「Error Pause」把 Play 停住；"响亮"的含义是"**红色 + 打断**"。
- ⚠️ **校验必须放在使用之前**（"日志放在会抛异常的行之后 = 等于没放"，见第 11 章）。

### 十、Gizmo：把"看不见的旋钮"变成看得见

```csharp
void OnDrawGizmosSelected()          // ⭐ Selected 版：只在【选中该物体】时画（OnDrawGizmos 会一直画、场景会乱）
{
    if (groundCheck == null) return; // 编辑器里可能还没接线

```

- **它一次验三件事**：① 改半径 → 圈**立刻胀缩**（旋钮"活"了）② 圈**在不在脚底**（验证子物体坐标算错没有）③ **Play 时亲眼看 `isGrounded` 的真身**（圈贴地 = 接地；圈离地 = 不接地）
- ⭐ 判据：**旋钮的价值体现在"临界形状"上**（平台边缘 / 坑 / 斜坡）—— 在一片又宽又平的地面上调半径，**看不出任何差别**，那不代表它没生效。
- ⚠️ Gizmo **只用于看**，不参与物理。

### 十一、手感公式（把"手感"变成可算的）

```
跳跃高度  h = v² / (2g)        g = 9.81 × gravityScale
保持高度不变时换重力：  v ≈ 7 × √(gravityScale)
```

| 想要的感觉 | `gravityScale` | 同步的 `jumpSpeed` | 高度 |
|---|---|---|---|
| 月球感（飘） | 1 | 7 | 2.5 |
| **本工程当前** | **2** | **10** | **≈ 2.55** |
| 更实、落更快 | 3 | 12.1 | 2.5 |
| 很重 | 4 | 14 | 2.5 |

- ⭐ 顺序不能反：**先用 `gravityScale` 定"重量感"，再用 `jumpSpeed` 定高度**。
- ⭐ **高度对 `v` 是平方关系**：想跳高一倍，`v` 要 **×1.414**（所以凭直觉"加一倍速度"会变成四倍高度）。
- ⚠️ 参考尺寸：相机 `orthographic size = 5` → 竖直可视 **y ∈ [-5, +5]**；本场景地面高度 -2.5 → 玩家站住时 `y ≈ -2.0`。**先算一次，再决定数值**，别让角色跳出屏幕。
- ⚠️ **调参工作流**：**在 Play 模式里实时调**最快（"播放模式改动不保存"这次是**正面用法** —— 拿它当试衣间）→ 满意后**记下数字** → **退出 Play**（改动回滚）→ 在非播放模式下**重填一遍** → **场景 `Ctrl+S`**。

### 补节（10-04）：接地判定从"探针"升级为「**真接触 + 法线朝上**」

**病因**：脚底中心那个 `r = 0.15` 的圆，在 1.0 宽的脚底下**只覆盖中间 30%** → 站在平台边缘时"**物理上站得住、判定上却说离地**" → 回满门被关 → **跳不起来**（详见 `错题本.md` 错误 26）。

**新写法**：

```csharp
private Collider2D _col;
private readonly ContactPoint2D[] _contacts = new ContactPoint2D[8];   // ⭐ 复用缓冲

private bool IsStandingOnGround()
{
    int count = _col.GetContacts(_contacts);
    for (int i = 0; i < count; i++)
        if (_contacts[i].normal.y > 0.7f) return true;   // 法线朝上 = 脚下有地
    return false;
}
```

- **必须在 `FixedUpdate` 里读**：接触每个物理步更新（放 `Update` 里读到的是滞后值）。
- **必须过滤法线**：`IsTouchingLayers` 只答"有没有接触"，**贴墙也算** → 空中贴墙会**白送跳次**。
- ⭐ 判据：**层（掩码）管"允许不允许接触"；法线管"从哪个方向接触"**。
- **为什么用缓冲数组**：这个方法每物理步都调 → 在里面 `new` 就是每步扔一块垃圾（09-25 的 GC 教训）。
- 阈值 `0.7 ≈ cos(45°)` → "接触面偏水平 45° 以内才算脚下"（台阶 / 斜面的宽容度，实测可调）。

**代价与遗留**：

| 项 | 说明 |
|---|---|
| 语义 | 从"近似"变成"**与物理一致**"（能站 ⇔ 能跳） |
| 遗留 1 | `y <= 0f` 那道回满门是**代理量**（用竖直速度符号近似"刚起跳"）→ 若出现"边缘次数不回满"，换成**显式的起跳免疫计时器** |
| 遗留 2 | 光靠"接触"不区分方向时，会把"踩到敌人头顶"也算接地（现在敌人法线通常水平，暂不影响） |

**回访清单销账**：10-02 登记的"脚下三探针 / `OverlapBox`"**不再需要** —— 真接触天然覆盖整个碰撞体宽度。

## 17. Tilemap 全链路：瓦片、网格、合成碰撞体与"接触皮肤"（10-03 · 关卡 1 地形成型）

### 一、为什么上 Tilemap

一条 `Ground`（一个 `BoxCollider2D`）手搭还行；**关卡**有几十上百个格子 → 手摆就是灾难。Tilemap = **网格 + 图层 + 可刷瓦片 + 自动合并的碰撞**。

### 二、装配链（九样东西，缺一样都跑不起来）

```
精灵（PNG：256 px ÷ PPU 256 → 世界 1×1，轴心居中）
  └─ 瓦片 Tile（.asset）—— 关键三字段：
       ① 精灵  ② ⭐ 碰撞体类型 = 网格 (Grid)  ③ 颜色
       ⚠️ 碰撞体类型默认是 Sprite（按精灵形状生成 → 格子间可能留缝、边缘不好踩）
  └─ 调色板（窗口 → 2D → 瓦片调色板 + 一个调色板资产）
  └─ Grid（单元格 1×1）+ Tilemap（子物体，自带 TilemapRenderer）
       ├─ ⭐ 层 = Ground（脚点探针只看这一层；放错层 = 跳不起来且控制台一声不响）
       ├─ Tilemap Collider 2D     ← 生成器
       ├─ Composite Collider 2D   ← 合并器（+ 它自带的 Rigidbody 2D：**主体类型 = 静态**）
       ├─ Tilemap Collider 的「合成操作 = 合并 (Merge)」 ← 把前两者接上
       └─ 摩擦 0 材质（玩家侧 + 地形侧都挂）
```

### 三、两块碰撞体的分工（"砖" 与 "砌墙的人"）

| 组件 | 负责什么 | 懂什么 |
|---|---|---|
| **`Tilemap Collider 2D`** | **按瓦片生成碰撞形状** | 懂瓦片数据 → 铺出来是**一格一个方框** |
| **`Composite Collider 2D`** | **把一堆形状做几何布尔运算，合成轮廓** | ⚠️ **完全不懂瓦片**，只收"别人交给它的形状" |

- **接线**：`Tilemap Collider 2D` 的「合成操作」不是"无" → 它就被 Composite 收走（官方原文：`When any Collider2D is using any composite operation other than None then it is used by this CompositeCollider2D`）
- ⭐ **判据（肉眼可验）**：勾对之后，场景视图里的绿线框**从"每格一个方框"变成"整块一个轮廓"**
- **不合并的代价**：① 性能（内部边全在）② **手感**（走过格子接缝会"卡边"）
- **为什么 Composite 要带静态刚体**：它本质是**静态几何体**，物理引擎要求它挂在刚体上 → **主体类型必须 = 静态**（留 Dynamic → 地面被重力拽走）

### 四、那个下拉框是**几何的布尔运算**（官方定义）

| 面板项 | 官方原文 | 布尔运算 |
|---|---|---|
| 无 | 不启用 Composite | — |
| **Merge** | `...composes geometry using a Boolean OR operation` | **并集** |
| Intersect | `...AND operation` | 交集 |
| Difference | `...NOT operation` | 差集 |
| （"翻转"） | `...XOR operation` | **异或** |

⭐ 与 `136` 的"全场异或"**同一族思想**，只是作用在**形状**上。平台地形要的是**并集（Merge）**。

### 六、⭐ 硬事实一：单元格 `(x, y)` 占据世界 `[x, x+1] × [y, y+1]`

**原点在格子的左下角**（`m_TileAnchor = (0.5, 0.5)` 表示"精灵轴心放在格中心"，格中心 = `(x+0.5, y+0.5)`）。

- **自证方法（最可靠）**：读场景里 `CompositeCollider2D` 的 `m_CompositePaths` —— 那是**合并后轮廓的真实世界坐标**
  - 实测：`(10, −4) → (−10, −4)` 这条水平边 = **地面顶面 = −4**（对应格 `y = −5`）
  - 推论：格 `y = −2` → 顶面 **−1**；格 `y = 0` → 顶面 **1**；格 `y = 3` → 顶面 **4**
- ⚠️ 我一度按"格中心 = 世界坐标"推算，**整张对照表错了 0.5** → 记牢这条，别再重算错

### 七、⭐ 硬事实二：静止时"悬空 0.02"是**接触皮肤**，不是 bug

- `项目设置 → 物理 2D → 默认接触偏移 (Default Contact Offset) = 0.01`（+ 求解器余量）
- 刚体静止时**允许**留在碰撞面上方约 `0.01~0.02` —— 这是 2D 物理的固有"皮肤"
- **换算判据**：相机正交 6 → 屏幕高 12 世界单位 ÷ 1080 px → **1 单位 = 90 px** → **0.02 ≈ 2 像素** ← 白色角色与白色地形之间那条反复出现的细蓝线
- 三个选择：① 把默认接触偏移调到 `0.005`（≈1px）或 `0.001`（亚像素，但接触更"紧"、易微抖）② 上 **Pixel Perfect Camera**（把渲染对齐像素网格，亚像素缝隙被"吸掉"，代价是它接管相机正交大小）③ **接受它**（商业 2D 游戏也常见）
- ⭐ **先分清"物理缝"还是"渲染线"再动手**：判据 = Play 里站住不动，读 `Transform` 的 **Y** —— 站地面（格 `y=−5`，顶面 −4）时 **Y 应为 −3.5**（±0.02 就是无缝）

### 八、⭐ 硬事实三：通道净空必须留余量（零净空时"圆能擦过去、方一定过不去"）

| 净空 − 碰撞体尺寸 | 圆（含 1×1 胶囊=整圆） | 方框 |
|---|---|---|
| ≥ 0.2（20%） | 轻松 | 轻松（而且更稳） |
| 0.05 ~ 0.2 | 能过 | 勉强 |
| **0（正好一样大）** | **切点接触、法线唯一 → 能"擦"过去** | ❌ **一定过不去** |
| < 0 | 过不去 | 过不去 |

- **机制**：圆与上下壁是**切点**接触（圆心稍偏仍能滑过去）；方框的上下边**与通道等长** → 进入瞬间前后两角必须**同时**对齐，而存在 0.01 接触偏移 → 求解器为解穿透把角色**顶在门口**
- ⭐ 判据：**"能不能过"只看「净空 − 尺寸」，与形状无关**；形状只决定"余量小时谁更宽容"
- ⭐ **关卡尺寸必须与碰撞体尺寸配套**：**通道 ≥ 角色高 × 1.5**；搭地形别用"和角色一样大"的格子
- ⚠️ **缩碰撞体换通过性 = 拿视觉穿模换手感**（精灵 1.0、碰撞体 0.8 → 贴墙陷进墙里 0.1）→ 不划算，正确顺序是**先给通道留余量**
- ⚠️ `CapsuleCollider2D` 的**退化情形**：竖直胶囊的中间矩形高 = `size.y − size.x` → **`(1, 1)` 就是一个直径 1 的整圆**（不是"有平直段的胶囊"）；底部是**点接触** → 站不稳、易被墙角顶起

### 九、摩擦：2D 物理材质（与 09-22 那条同源，今天补齐 2D 部分）

- **贴墙按住方向键会浮空/爬墙** = 摩擦托住身体：碰撞体「材质」槽为空 → **默认摩擦 0.4**；贴墙持续给正压力 → `μN` 足够大就能托住体重
- **修法**：新建 **2D** 物理材质（摩擦 0 / 弹性 0）→ 挂到碰撞体；**玩家侧与地形侧都挂** → 对"合并方式"**免疫**（平均/最小/相乘/最大，`(0,0)` 全是 0）
- ⚠️ **换碰撞体会清空材质槽** → "挂回材质"是换碰撞体流程的一步（漏了会误以为"改了没用"）

## 18. 敌人巡逻：三种"到头"信号与合并碰撞体的陷阱（10-04 · 第 7 号成品）

### 一、敌人怎么动：Dynamic 交速度（与玩家同一套）

```csharp
_rb.linearVelocityX = _dir * moveSpeed;      // ⭐ 只碰 x，y 归重力（Unity 6 的分量属性）
```

- ⚠️ `new Vector2(_dir * moveSpeed, 0)` 是**写整条向量** = 把重力对 y 的累积**清零** → 敌人不下落（每步被抹掉，只会以约 `g·dt²` 的速度"慢慢渗"）。判据：**覆盖一条向量前先问"哪些分量不归我管"**。
- ⚠️ 不能用 `MovePosition`（那是 Kinematic 交位置的方式）；也不能 `transform.position +=`（会穿墙、绕开物理）。

### 二、为什么巡逻敌人**要**受重力（今天的设计选择）

- 红利 1：**自动贴地** —— 省掉手动对齐 Y 的活（10-03 的"接触皮肤 0.02"照旧存在，**别拿眼睛当判据**）
- 红利 2：能"贴地走"（马里奥式）
- 代价：会被玩家**顶走**（靠**每步覆盖 x**压住）+ 必须**冻结旋转 Z**（否则方块被撞翻、滚下平台）
- 对照：Kinematic 悬空巡逻也成立（路线绝对可控、不会被顶），但失去"自动贴地" —— 两个方案的分界是 **"我要的是可预测，还是想要意外的乐趣"**

### 三、⭐ 三种"到头"信号（今天的核心）

| 信号 | 传感器 | 提前量 | 覆盖 |
|---|---|---|---|
| 前方无地 | `OverlapCircle`（脚前方，`Ground` 掩码） | 提前 | 平台边缘、坑 |
| **前方有墙** | `Raycast`（**身体中心高度**向前） | 提前 | 墙、台阶 |
| 撞到别的物体 | `OnCollisionEnter2D` | 晚一拍 | 敌人、玩家 |

- ⭐ 三者的差异其实是**传感器口径**：**圆**答"这一片有没有东西"、**线**答"这个方向有没有东西"、**回调**答"和谁刚开始接触"。
- ⭐ **墙 = 免费的折返点** → **关卡可以先不设计**（今天只用"地面 + 一块现成平台"就验完了机制）。

### 四、⭐ 为什么"撞墙"必须靠射线：`Enter` 的粒度

- `OnCollisionEnter2D` 的粒度是 **"两个碰撞体开始接触"**，不是"多了一条接触点"
- 地形是**一个** `CompositeCollider2D`（地面 + 墙 + 平台**合并成一块**）→ 脚踩地面时**已经在接触** → 走到墙边只是"同一对多了条接触点" → **不触发**
- 旁证：撞敌人 / 撞玩家会触发 —— 那是**新的碰撞体对**
- ⇒ 判据：**"是不是同一对碰撞体"决定 `Enter` 会不会触发**

### 五、探针分不出"墙"和"地"

- 墙与地面**同在 `Ground` 层** → `OverlapCircle` 只答"那一层有没有东西"，不答"**是什么**"
- ⇒ 平台左端紧贴墙时，探针一直报"有地" → 敌人**顶墙不动**（射线版治好）
- ⭐ 判据：**要区分的两个东西"类别相同"时，只能靠方向 / 位置 / 形状**

### 六、射线从"身体中心"发的道理

- 地面在**脚下**，不在身体高度的**水平路径**上 → 天然只探到"墙 / 台阶"，不会把地面误判成墙
- 掩码只勾 `Ground` → 敌人自己（`Enemy` 层）不会被命中（**顺便防自伤**）
- **自带闸门**：转身后射线指向反方向 → 条件自动消失 → 不会每物理步乱翻
- ⚠️ Gizmos 里画这条射线时，`_dir` 要给**字段初值**（编辑模式下 `Awake` 不跑 → 不加初值射线长度是 0）

### 七、物理回调怎么读、怎么用

- 回调是**引擎调你**（好莱坞原则："别找我们，我们会找你"），靠**方法名 + 签名**匹配 → ⚠️ **名字 / 签名写错 = 静默失效、不报错**（"响亮地失败"的例外，只能靠 `Debug.Log` 证明）
- `collision.contacts` 是**接触点数组**；每个点一条 **法线**（`normal`，方向：**从对方表面指向我**）
- ⭐ 判据：**法线水平 ⟺ 面竖直（墙）；法线竖直 ⟺ 面水平（地）** —— 因为 `normal = (cos θ, sin θ)`，比 `|normal.x|` 就是比"与水平的夹角"（`0.7 ≈ cos45°`）
- `Enter` 只在"开始接触"那一帧触发 → **不会每步翻转**（对照组：`Stay` 每物理步都调，要在里面加"**方向闸门**"才不抖）
- ⚠️ 回调里**只改状态**（`_dir` 翻符号），动作留给 `FixedUpdate` → 转身在**下一个物理步**才生效（回调发生在物理步之后）

### 八、预制体：时机与验收

- **时机**：机制跑通**之后**再做（"配置复杂 + 会有多个"→ 值得做；"还在调它"→ 别做，免得把 bug 冻进模具）
- ⭐ **验收手法**：**删掉场景实例 → 从 `Prefabs/` 重新拖一个** → 检查器逐项核对（层 / 标签 / 刚体约束 / 碰撞体 / 子物体 / 脚本槽位**全部自带**）—— 不删就验不出来
- ⚠️ 改实例 ≠ 改模具（`Apply` / `Revert`）；别用"复制粘贴场景对象"来加新敌人
- ⚠️ 新文件夹的 `.meta` 躺在**父目录**（`Assets/Prefabs.meta`）→ 提交时别漏

## 19. 物理与表现分离 + `Order` 分层 + 单例 + Animator 动画纪律（10-05 · 第 7 号成品）

> 今天三件事一次做完：**转身**（翻视觉子树）、**金币 + TMP 计分**（触发器 + 单例）、**角色 Animator**（Idle / Run / Jump）。共同主线是**分层**：物理 / 表现分开、两个时钟分开、两个写入者分开。

### 一、物理与表现分离：为什么拆 `Visual` 子物体

```
Player（物理根：Rigidbody2D / BoxCollider2D / PlayerController）
├── Visual            ← 看得见的（SpriteRenderer / Eye / Animator）
│   └── Body          ← Animator 动画的是它自己的 localScale
└── GroundCheck       ← 被代码 / 物理读的（探针）
```

⭐ **判据**：**看得见的进 `Visual`；被代码 / 物理读的留在物理根。**

| 理由 | 现象 |
|---|---|
| **镜像会带上整棵子树** | 翻 `Visual` → 里面的 `Eye` 跟着翻 ✓；若把 `GroundCheck` 放进 `Visual`，**探针会被镜像到身后** → 接地判定失效 |
| **负缩放对碰撞体不可靠** | `localScale.x = -1` 的**碰撞体**形状 / 接触法线会出问题 → 所以要翻"**没有碰撞体**"的那一层 |
| **缩放动画很贵** | 动画驱动**带碰撞体**的物体缩放 = 物理引擎**每帧重建碰撞体形状**（还容易穿模） |

### 二、转身：翻 `Visual.localScale.x`

- ⭐ **负缩放 = 镜像**（不是"变窄"）；世界缩放 = 父级链**连乘** → 翻一层，整棵视觉子树一起镜像
- ⚠️ **`localScale` 是属性 + 返回 struct** → 不能写 `visual.localScale.x = …`（**CS1612**）→ **取出 → 改 → 整体写回**（与本册第 4 章 `linearVelocity.y` 同一条规则）
- ⭐ **脏检查**：**记"上次提交出去的那个值"**（`_appliedFacing` 是 int），别从浮点里反推 —— 与 `ScoreManager._lastDestroyed` 同一模式

**`flipX` vs 翻 `localScale`（选型表）**：

| 做法 | 影响范围 | 适合 |
|---|---|---|
| `SpriteRenderer.flipX` | **只有这一个 renderer**（子物体**不跟着翻**） | 单张整图 |
| 翻**物理根**的 `localScale.x` | **整棵子树**（含探针 / 碰撞体） | ❌ 会坏物理 |
| 翻 **`Visual`** 的 `localScale.x` | 只镜像视觉子树 | ✅ **推荐** |

⚠️ **两者别同时用**（翻两次 = 翻回来）。

### 三、转身写在哪个时钟？"谁产生，谁消费"

| | 朝向由谁产生 | 转身写在哪 | 为什么 |
|---|---|---|---|
| **玩家** | `_axis` ← **`Update`**（读输入） | **`Update`** | 数据在 Update 产生 → **当帧就翻**，跟手 |
| **敌人** | `_dir` ← **`FixedUpdate`**（看地 / 看墙 / 撞墙决策） | **`FixedUpdate`** | 数据在 FixedUpdate 产生 → 就近消费 |

⭐ 补充：60fps 渲染 + 50Hz 物理 → 每秒约 10 帧**没有**物理步；转身只写 `FixedUpdate` 的话，那 10 帧里画面会"晚一拍"。
**铁律不变**：`rb.linearVelocity` 这类**物理提交**只在 `FixedUpdate`、且一个物理步一次。

### 四、`Order in Layer`：平局 = 未定义

```
① 排序图层 (Sorting Layer) → ② 图层内顺序 (Order in Layer) → ③ 距相机的距离（z）
```

**三级全相等 = 平局 → 结果没有承诺**。同一天里测到两组：

| 平局 | 结果 |
|---|---|
| `Player`(0) vs `Tilemap`(0) | 玩家**赢**（一直可见） |
| `Eye`(0) vs `Visual`(0) | 眼睛**输**（被身体盖住） |

⚠️ "**层级里越靠下越后画**"只是**社区观察**，不是规则 → **要用 `Order in Layer` 明说**。

| Order | 谁 |
|---|---|
| `0` | Tilemap 地形 |
| `1` | Coin |
| `2` / `3` | Enemy 的身体 / 眼睛 |
| `3` / `4` | Player 的身体 / 眼睛 |

- **`Order in Layer` 是静态的**：排序关系全局固定、不随位置变（"按 y 动态排序"是俯视 2D 的做法，横版不需要）
- **一个 `Tilemap` = 一个渲染器 = 一个排序键** → 想"地形内部分前后"就**再开一个 Tilemap**
- ⚠️ **排序图层（Sorting Layer）暂不加**：它存在 `ProjectSettings/TagManager.asset` → 加它就等于**动项目设置**（要走"保存项目 + 隐私自查 + 提交设置"）；等出现"背景 / 前景 / 粒子"时**一次性加齐**
- ⚠️ **UI 不需要它**（`Canvas` 用**屏幕空间-叠加**时**不参与**这套排序）

### 五、金币：触发器 + 层门卫（承 Breakout 的"自治"）

- **自治**：`OnTriggerEnter2D` 里自己判断、自己消失 —— 全场 1 个玩家、N 个金币，**玩家代码不需要认识任何金币**
- ⚠️ **勾「是触发器」**：只报"碰到了"，**不产生物理阻挡**（玩家不会被弹开 / 减速）
- ⚠️ **两个碰撞体里至少一个带刚体**消息才会发出（玩家是 Dynamic → 够了；金币**不需要**刚体）
- ⭐ **用层判定，不用标签**：`Player` 层 10-02 就建好了，而 `Player` **标签不存在**
  - 判据：**层管"物理上允许不允许接触"（碰撞矩阵 / 射线掩码），标签管"这是什么"（业务身份）**
- ⭐ **触发器不参与物理求解** → **"实心碰撞体要精确，触发器够用就行"**（宽容度大反而更好吃）
- ⚠️「项目设置 → 物理 2D → 层碰撞矩阵」里 `Pickup × Player` 要打勾，否则**回调根本不发**
- 消失用 `SetActive(false)` 而不是 `Destroy`（销毁贵、禁用便宜 —— 承第 6 章对象池）

### 六、单例：`public static X Instance { get; private set; }`

```csharp
public static ScoreManager Instance { get; private set; }        // 类型级静态槽位
void Awake()   { /* 重复挂载 → LogError + enabled = false + return */  Instance = this; }
void OnDestroy(){ if (Instance == this) Instance = null; }       // 必须还的账
```

| 部分 | 给的能力 |
|---|---|
| `static` | ① 不需要实例就能访问 ② 全进程**只有一份** |
| `public` | 跨类可读 |
| `{ get; private set; }` | **自动属性**（编译器开隐藏字段）+ **读公开、写私有** → **唯一性靠访问级别守门** |

- ⭐ **与 `event` 同一种思想**：`event` = "带门禁的委托字段"（外部只能 `+=`/`-=`，赋值 **CS0070**，第 13 章）；`{ get; private set; }` = "**带门禁的静态字段**"
- ⭐ **同一机制你早用过**：`InputSystem.actions` 也是**静态属性** —— 写在代码里就能拿到，**不需要在场景里找任何物体**
- **两笔账**：① `Instance` 可能为 `null` → `?.`；② 静态字段**不随场景卸载自动清** → `OnDestroy` 清入口（编辑器有域重载会重置，**构建后不会**）
- ⭐ **判据（单例 vs 事件）**：**"我要找的是一个唯一的服务，还是广播一条消息？"** → 唯一的**服务**（计分员 / 游戏裁判 / 音源管理）用**单例**；一条**消息**（漏球 / 砖块清空）用**事件**
- ⚠️ **`Awake` 顺序不确定** → static 入口的"读"要放在初始化之后（事件回调 / `Update`），别在自己的 `Awake` 里读别人 `Awake` 的产物
- 进阶：懒加载 `_instance ??= FindFirstObjectByType<ScoreManager>()`（⚠️ Unity 6 里 `FindObjectOfType` 已**过时**）

### 七、Animator：FSM 的落地 + 五条动画纪律

**FSM 三角**（第 12 章那套）：

| 要素 | Animator 里 |
|---|---|
| 状态 State | `Idle` / `Run` / `Jump` 三个方块 |
| 条件 Parameter | `Speed`(float) / `IsGrounded`(bool) |
| 转移 Transition | 方块之间的箭头（带条件） |

⭐ **脚本只"报事实"，播哪个由状态机决定**：

```csharp
animator.SetFloat(SpeedHash, Mathf.Abs(_axis));
animator.SetBool(GroundedHash, isGrounded);
```

`SpeedHash` / `GroundedHash` 用 `Animator.StringToHash` 缓存成 **`static readonly`**（与 `_move` / `Camera.main` 同族：**查一次就缓存**）。

**⭐ 五条动画纪律**：

1. **只动画"纯视觉、没有碰撞体"的那一层**（今天为此把 `SpriteRenderer` 从 `Visual` 再挪到 `Body`）
2. **同一个属性只能有一个写入者** —— 脚本翻 `Visual.scale.x`（离散），Animator 动画 `Body.scale`（连续）→ **两个不同的 transform**
3. **一个 clip 动过的属性，每个 clip 都要动、且首帧写基准值** —— 否则切状态时**上一个状态的值会残留**
4. **`有退出时间 (Has Exit Time)` 全部取消勾选** —— 否则"当前动画播完才切"，动作**迟滞**（最常见的手感杀手）
5. **转移条件默认是 AND**（列表全部满足）→ 要 OR 就**建两条**转移

**其它要点**：

- ⭐ **`Any State` 只给"任何状态都可能触发的打断"**（死亡 / 受击 / 眩晕）；`Idle ⇄ Run ⇄ Jump` 是**明确的有限转移** → 画明确箭头（⚠️ `Any State → Jump` 不能指向当前已在的状态，会自打断）
- 三个特殊节点：**`入口 Entry`**（箭头指向的就是**默认状态**，**橙色** = 默认）、`Any State`、`出口 Exit`
- 右键菜单**只对状态框生效**（空白处右键没有菜单）；画布平移 = **中键拖** 或 `Alt` + 左键；选中后按 **`F`** 聚焦
- **clip 别留 0 秒长度**（1 帧恒定值也要给一个正的时间跨度）
- `Animator` 的 `Update Mode`：本册第 10 章那条（`timeScale = 0` 要用 `Unscaled Time`）—— **本工程没有 `timeScale = 0`，保持 `Normal`**
- ⚠️ `.anim` / `.controller` 都是**资产层**：改完必须 **`文件 → 保存项目`**（不是场景 `Ctrl+S`）
- ⚠️ **动画参数名是字符串 → 拼错 / 大小写不对 = 静默失效**（与"回调名字写错"同族，第 18 章）

## 20. 死亡与重开 + 敌人伤害与追逐：哨兵 / 裁判 / 唯一出口（10-06 · 第 7 号成品）

### 一、三层结构：致命源 → 裁判 → 订阅者（每层只有一个"家"）

| 层 | 角色 | 职责 | 写法 |
|---|---|---|---|
| **哨兵** | `FailZone` / 敌人 | 只判「是不是玩家」+ 喊一声 | 触发器 / 碰撞回调 + **层门卫** → `GameManager.Instance?.NotifyPlayerLost()` |
| **裁判** | `GameManager`（**单例**） | **唯一出口**：上锁 → 改状态 → 广播 | `if (_isGameOver) return;` → `Time.timeScale = 0` → `OnGameOver?.Invoke()` |
| **订阅者** | `DeathPanel` / `PlayerController` | 各干各的 | `OnEnable` 订阅 / `OnDisable` 退订（谁订阅谁退订）|

⭐ **为什么哨兵走"单例直接调用"，而不是"发事件让裁判订阅"**：
- 敌人是**预制体**（N 个实例）→ 裁判拖不了它的引用；`Instance` 让任何预制体**一行就能上报**
- ⭐ 判据分层：**唯一的"服务"用单例**（听众只有 1 个）；**一条"消息"用事件**（听众未知 / 会变）→ 所以"裁判 → UI"那一段用事件

⭐ **幂等门卫必须放裁判**（`_isGameOver`）：玩家可能**同时压中两块** `FailZone` 盒子（底部 + 左/右），也可能"被敌人撞的同时掉下去" → 上报两次 → 没门卫就是"面板淡入两次 + `LoadScene` 两次"

⭐ **选"事件"的回报**：`OnGameOver` 今天有**两个**订阅者（面板淡入 / 玩家停手），裁判**完全不认识**它们 → 以后加"死亡音效 / 统计 / 成就"只是**多一个订阅者**，`GameManager` 一行不用改

⚠️ **订阅位置**：用 **Inspector 引用**，不要在 `OnEnable` 里取 `GameManager.Instance` —— **不同对象的 `Awake` 顺序不确定**，`Instance` 可能还是 `null` → **静默订阅失败**

### 二、`timeScale = 0` 只冻"世界"，不冻"你"（今天最实用的一张表）

| 还在跑（要自己决定关不关） | 为什么 | 今天的选择 |
|---|---|---|
| `Update` / `LateUpdate` | 不吃 `timeScale` | 玩家**转身 / 读输入** → 必须自己关（`enabled = false`）|
| 改**渲染属性**（`localScale` / `color` / `SetActive`）| 纯渲染 | 同上 |
| UGUI 点击 + `Unscaled Time` 的动画 | 不吃 `timeScale` | **留**（`RESTART` + 面板淡入）|
| 音频播放 | 有自己的时钟 | **留**（死亡音效要能播完）|
| **自动停**：`FixedUpdate` / 物理 / 触发器 | 吃 `timeScale` | 不用管 |
| **自动停**：`Animator`（`Update Mode = Normal`）| 吃 `timeScale` | 不用管（角色定格在最后姿势）|

⚠️ **实测踩坑**：先做完"掉下去 → 世界冻结"，结果**角色死后照样转身**（转身在 `Update` 里、改的是渲染属性 `visual.localScale`）→ 修法：`PlayerController` **订阅** `OnGameOver` → `enabled = false`（`Update` / `FixedUpdate` 一起停手）

⭐ 判据：**"冻结世界" ≠ "停手"** —— `timeScale` 是停世界；"我自己别再动"要用 `enabled` 表达
📎 反向印证：正因为 `Animator` 默认模式**吃** `timeScale`，面板的 Animator **才必须**改成 `Unscaled Time`（见第 10 章）—— 一张表把两次踩坑串起来了

### 三、伤害判定：碰撞 vs 触发器（今天选碰撞）

- 敌人**碰撞体在根、刚体也在根** → `OnCollisionEnter2D` 的回调**一定**到得了根（零不确定性）
  · 若改用子物体上的触发器（hurtbox），要额外确认"回调归属"（触发器回调发给"挂碰撞体的物体"与"挂刚体的物体"）
- ⚠️ **同一个回调里"一个筛层、一个不筛"是故意的**：
  - **伤害上报** → **筛** Player 层（敌人还会撞到别的敌人 / 墙 → 那些绝不能算死亡）
  - **转身** → **不筛**（"前面有东西挡路"对谁都成立）
- ⭐ 判据：**"筛选"（谁能喊）与"去重"（喊几次只算一次）是两种不同职责**，各自只需要一处；只有"同一职责叠第二层"才叫重复防御（哨兵自己再加"只喊一次"就属于可选的第二层 —— 裁判已幂等，加了只是少一行日志）

### 四、敌人追逐：视线 + **覆盖式**速度

```csharp
_seesPlayer = Physics2D.Raycast(transform.position, new Vector2(_dir, 0f), sightDistance, playerLayer);
float speed = _seesPlayer ? moveSpeed * chaseMultiplier : moveSpeed;   // ⭐ 覆盖式重算
_rb.linearVelocityX = _dir * speed;
```
- 与"看墙"**同一个 API 家族**（`Physics2D.Raycast`），只换**掩码** + 独立**距离**
- 掩码只勾 Player → 射线**不会命中自己**（不像脚点探针那样需要专门的防线）
- ⚠️ **必须覆盖式（不累加）**：累加式的症状 = "**离开视野后不减速**"（速度只会涨，没人减回去）
- ⭐ 数值判据（玩法层）：**冲刺速度必须 < 玩家速度**（4 < 6），否则追逐从"躲避"变成"必死"
- ✅ 昨天登记的"冲刺撞到玩家不回头"**今天自动消失**：撞到 = 玩家死 → 世界冻结 → 来不及"扑 → 弹回 → 再扑"
- ⚠️ 已知局限（回访清单）：射线只探**一条水平线** → 玩家跳高就"看不见"
- ⚠️ "会不会冲出平台"：今天靠原有的 `edgeCheck` 仍然管住（**会回头**）→ 做"聪明的敌人"时再区分

### 五、修 bug：用"连续量"判"离散状态"（今天最值钱的一课）

**症状**：移动中落地**立刻**跳 → 跳不起来（站着落地却正常）

**排查三步（可复用）**：
1. **先排配置**：扒刚体 YAML → `m_Constraints: 4` = **冻结旋转 Z** ✓ → 排除"移动时箱体微倾 → 单角接触 → 法线变斜"
2. **一行插桩分开两道门**：回满 = 门 A（`isGrounded`）&& 门 B（`y <= 0f`）→ 打印 `isGrounded / y / _jumpsLeft / 接触数 + 各条法线`
3. ⚠️ **打印本身会骗你**：`F4` 把 `y = +0.0000349` 打印成 `0.0000` → **要看符号就打布尔**（`gateB={y <= 0f}`）或 `y:R`

**实测铁证**：
```
g=True  y=3.489852E-05  gateB=False  left=0  n=3  [0.00,1.00]×3   ← 落地那一步（门 B 关着）
g=False y=-1.96196413   gateB=True   left=0  n=0                  ← 空中（次数仍是 0 → 二段跳也没了）
Player Lost                                                       ← 一次丢跳 → 掉下平台 → 死
```
**病因**：静止接触的求解**残差**是 `+3.5e-05`（微正），而 `y <= 0f` 是**零容差** → 门被关 → 不回满 → `_jumpsLeft > 0` 不成立 → 跳被拒；而 `_jumpRequested` 又按设计"**即时作废**" → 按键被吃掉且**控制台一声不响**

**修法（治本）**：回满改判"**接地的上升沿**"
```csharp
if (isGrounded && !_wasGrounded) _jumpsLeft = maxJumps;   // 完全不看速度
// ⚠️ 末尾必须【每步】更新：_wasGrounded = isGrounded;（否则永远 false = 每步都当上升沿）
```
- 天然满足原意图：起跳后那一两步是 `true → true`（**不是上升沿**）→ 不回满 → **不会白送次数**

⭐⭐ **判据（本册最有价值之一）**：
> **不要用【连续量】（速度）判【离散状态】（有没有落地）。**
> 想表达"我刚起跳 / 我落地了"，就用**离散量**（标志位 / 上升沿）记 —— 连续量只配当辅助。

⚠️ **收尾踩坑**：新判据**插在旧判据上面**（没有替换）→ 文件里同时存在两行 `_jumpsLeft = maxJumps`、意图还相反 → **死代码 + 自相矛盾 = 下一个 bug 的温床**，必须删

### 六、重开链路的收尾
- `Restart()`：**先还 `timeScale = 1`** 再 `LoadScene`（否则新场景一开场就是冻结的）
- 场景重载 = 一切重来 → 静态单例要在 `OnDestroy` 里清入口（`if (Instance == this) Instance = null;`）

## 21. 实心台地 / 1 格禁令 + 相机跟随 + 层的"兼职"（10-07 · 闸门②：关卡 1 可完整通关）

> 今天的起点不是代码，是用户一句设计判断：**"角色掉不下去的地方没有存在的意义"**。
> 它一路推到了整张地图重做（40 宽）、相机跟随、以及两个"共用一条线"的架构坑。

### 一、⭐⭐ 实心台地 vs 1 格厚的悬空薄板（今天最大的一条设计判据）

| 做法 | 后果 |
|---|---|
| ❌ **1 格厚的悬空薄板**（`cellY` 只有 1 行） | ① 板下方全空 → 角色从板边走出去**一路掉到判定区**（不是"踩在一块地上"）② 板与板之间的**竖直净空只有 1 格** → 角色（1×1）**进不去** ⇒ 那段空间**毫无意义** |
| ✅ **实心台地**（顶面一直堆到地形底 `cellY = −8`） | 落差变成**实心竖直侧壁** → 角色撞上去**必须跳** ⇒ **每一格都产生了意义** |

- 三种落差写法对照：**悬空板**（旁边是没意义的 1 格空当）／**实心侧壁**（撞上去必须跳 ✅）／**深渊**（挖穿到底 ⇒ 掉下去即死）
- ⭐ 判据：**写完一段地形，逐格问一句"这一格对角色意味着什么"** —— 答不出（进不去 / 掉不进去 / 站不上）就是废格
- 配套："地形底 `cellY = −8` + 相机视野下界 `−7`" ⇒ **玩家永远看不到地形底下**（画面里地形是"厚实的一块"，不是"漂浮的板"）

### 二、⛔ 1 格禁令（由角色尺寸直接推出）

| 角色尺寸 | 直接推论 |
|---|---|
| **1×1 格**（碰撞体 `1×1`、`offset 0`） | **1 格宽的洞** → 掉不进去 ⇒ 没意义 |
| | **1 格高的缝**（竖直净空 = 1） → 进不去 ⇒ 没意义 |
| | **1 格宽的平台** → 站不住 ⇒ 没意义（平台宽 ≥ 3~4 格） |

- ⚠️ **连带的一条**：**抬升 2 的台阶，上层不能压在下层正上方** —— 上层底面与下层顶面之间正好 1 格净空，角色**头顶顶死、跳不上去** ⇒ 台阶必须**水平错开**（上层从下层右边界之外开始）
  - 若真想上下堆叠，竖直净空必须 **≥ 2**，且**起跳点要落在上层水平范围之外**（跳起越过上层底面高度后再水平移入）
- ✅ **例外（不算废格）**：**1 格宽的墙** —— 角色会**撞到**它，那就是有意义的（"边界挡住"）

### 三、相机跟随：`LateUpdate` 与"出屏即死"

- ⭐ **"跟"必须排在"动"之后** ⇒ 放在 **`LateUpdate`**：
  - 一帧内的顺序是 `Update`（读输入）→ `FixedUpdate`（写速度，可能 0~n 次）→ **物理步（真正移动位置）** → `LateUpdate`
  - 若写在 `Update`，**`Update` 之间谁先谁后是「未定义」的**（相机与玩家说不准）→ 相机会读到玩家**移动前**的位置 → **抖动**
- 写回 `transform.position` 必须"**取出 → 改 → 整体写回**"（承第 2 章的 **CS1612**：属性返回 struct，`transform.position.x = ...` 编译不过）
- ⭐⭐ **"出屏即死"为什么成立**（今天最漂亮的一条设计链）：
  - 相机 x = `Clamp(玩家x, minX, maxX)`，而 **`minX` / `maxX` 是按"关卡边界对齐屏幕边界"算的**（`minX = 关卡左界 + halfWidth`）
  - ⇒ **相机被夹住处，正好是关卡两端**；相机在中间时玩家**永远在屏内**
  - ⇒ **"出屏"只可能发生在关卡两端** ⇒ **出屏 = 出关卡**自动成立，**不需要额外的世界坐标死亡线**
  - ⚠️ **上和下不设这条线**（`fixedY` 固定，垂直方向玩家永远不该"出界"）
- ⚠️ **隐患**：`minX` / `maxX` 是**屏幕宽度的函数**（`halfWidth = orthographicSize × aspect`）。**写死数字 → 分辨率一变就崩**（变成"在关卡里就死"或"出了关卡还不死"）⇒ 正确做法是**运行时算**（`Camera.aspect`）
- 📌 **Y 跟随**：只有在"关卡高到一屏装不下"时才加，且**必须配死区（dead zone）** —— 否则跳跃时相机会跟着上下抽动

### 四、⭐ 层的"兼职"问题：一个掩码不兼职两件事

- 症状：`EnemyPatrol` 的"**脚前探针**"（`OverlapCircle`）和"**撞墙射线**"（`Raycast`）**共用同一个 `groundLayer`**
- 为什么一直没出事：**过去"地"和"墙"恰好都是 Ground** ⇒ 兼职**从没被暴露**
- 什么时候崩：出现"**只挡人、不站人**"的东西（终点 / 尖刺 / 门）——
  - 把 `Goal` 塞进 `Ground` 层 → ① 脚前探针会以为"前方有地" ⇒ 敌人**走上 Goal** ② 还会污染**玩家的接地判定**（`PlayerController.groundLayer` 也是 Ground）⇒ 贴着 Goal 能"空中跳"
- ✅ 正解：**拆出独立掩码** `obstacleLayer`（勾 `Ground + Hazard`），撞墙射线改用它的掩码
- ⭐ 判据：**字段名要写"它回答哪个问题"，而不是"它顺便包含谁"** —— `groundLayer`（脚下有没有地）／`obstacleLayer`（前面有没有挡我的东西）
- 📌 **借层要先看语义**：`Goal` 现在放在 **`Hazard`（10）** 层，只是因为它**正好空着**；`Hazard` 的语义是"危险物"，终点其实是好事 ⇒ 等真要加尖刺/陷阱时**统一规划层**（已登记回访清单）
- 💡 **附带好处**：`Goal` 的碰撞体是**触发器** ⇒ 不参与物理阻挡、**层碰撞矩阵不用改**；而 `Physics2D.queriesHitTriggers` 默认开 ⇒ 敌人的**射线能命中**它（正是我们要的）

### 五、⭐ 订阅端该订「语义」，不是某个具体原因

- 症状：10-06 修好了"**死后**还能转身"（`PlayerController` 订阅 `OnGameOver` → `enabled = false`），今天加了"通关"，**通关后又开始能转身**
- 根因：`PlayerController` 只订了 `OnGameOver`（**死**），**没订** `OnGameWin`（赢）⇒ 通关时**没有任何人来把它关掉**
- ⭐ 判据：**"停手"是【游戏已结束】这件事，不是【死了】这件事**
  - 昨天只有"死"一种结束 ⇒ 订 `OnGameOver` **恰好等价**
  - 今天多了"赢" ⇒ 那个订阅**从"对"变成"漏"**
- ✅ 正解：`GameManager` 加第三条事件 **`OnGameEnded`**（不管怎么结束都广播），**不关心原因的订阅者只订它**；`OnGameOver` / `OnGameWin` 留给**需要区分**的订阅者（结算面板要写不同文本）
- ⭐ 判据：**要区分的订两条，不需要区分的订一条** —— 一个语义一个家
- ⚠️ 落地提醒：**两处 `Invoke` 缺一不可**（"死"那条和"赢"那条），只写一处 = bug 只修了一半
- 🔧 副产品：`CS0067: 事件从未被使用` 这个 warning，**正好是"还没接上"的天然指示灯**

### 六、工程实测三条（编辑器 / MCP 协作）

1. ⭐ **派生数据要隔一帧再读**：瓦片换完之后，`CompositeCollider2D` 的几何体还是**上一批的旧值**（同一次调用里读到的是 stale）→ 隔一次调用再读就是对的。**"刚写完就读"不可靠**
2. ⚠️ **模态对话框会阻塞编辑器主线程**：MCP 桥 ping 不应答、`execute_code` 返回空 —— 但**进程仍然 `Responding = True`**（Windows 消息循环在伺候对话框）⇒ 判据：**进程活着 ≠ 编辑器在干活**
3. ⚠️ **`BoxCollider2D.size` 是本地尺寸，会被 `localScale` 再乘一遍**：`scale (1,2)` × `size (1,2)` = 世界 **1×4**（不是 1×2）⇒ 想改大小**只动其中一个**

## 22. UI 交互事件的两条路：`UnityEvent` vs `EventSystems` 接口（10-08 · 多关卡）

### 一、地图：两条完全不同的路

| | **路①：`UnityEvent`（组件上的 `onXxx`）** | **路②：`EventSystems` 接口** |
|---|---|---|
| 长相 | 组件上的**字段**（`Button.onClick`） | 你要**实现**的接口（`IPointerDownHandler`） |
| 怎么接 | **从外面挂**：`AddListener` / Inspector 拖 | **自己实现**：写在自己的组件上 |
| 你在扩展谁 | **按钮**（它不动，你加监听者） | **你自己**（写一个新组件） |
| Inspector 可见 | ✅ | ❌（纯代码） |
| 多播 | ✅ 多个监听者 | ❌ 一个组件一份实现 |
| 适合 | "点一下 → 做件事" | "**我要定义整个交互过程**"（按住 / 拖动 / 悬停） |

⭐ **判据：看"谁在做主"**
> **别人通知我 → 我去【挂】它**（`UnityEvent`）；**我要参与交互 → 我【实现】它**（接口）

💡 生活模型：`onClick` = **门铃**（别人按、我响应）；`IPointerDownHandler` = **我自己就是门**（我定义"被敲时怎么办"）

### 二、路① 全家福（常用组件的 `onXxx`）

| 组件 | 事件 | 参数 |
|---|---|---|
| `Button` | `onClick` | **无参** |
| `Toggle` | `onValueChanged` | `bool` |
| `Slider` | `onValueChanged` | `float` |
| `TMP_InputField` | `onValueChanged` / `onEndEdit` / `onSubmit` | `string` |
| `TMP_Dropdown` | `onValueChanged` | `int` |
| `ScrollRect` | `onValueChanged` | `Vector2` |

⭐ 它们全是 **`UnityEvent` 家族**（`UnityEvent` / `UnityEvent<T0>` …）⇒ `onClick` 就是**最基础的无参版**
⭐ 推论：**`onClick` 只能挂「无参 `void`」的方法**（方法组直接能传，如 `gameManager.LoadNextLevel`）；要带参数就得上别的 `UnityEvent<T>`

### 三、⭐ 为什么 UGUI 不用标准 C# `event`，而自造 `UnityEvent`？

| 动机 | 说明 |
|---|---|
| **能在 Inspector 里配置** | 策划 / 美术不改代码也能接线（`RestartButton` 就是这么接的） |
| 代价 | 性能与类型安全**都不如**标准事件；接线**藏在场景里** ⇒ **方法一改名就静默失联**（Inspector 显示 `Missing`） |

⭐ 判据：**"接线"越靠近代码，越不容易静默失联** —— 代码里 `AddListener` 改名会**编译报错**；Inspector 拖的只会悄悄变 `Missing`

⭐ 两者 API 对照（**干的是同一件事**）：

| 标准 C# 事件 | UGUI 的 `UnityEvent` |
|---|---|
| `x.Event += 方法` | `button.onClick.`**`AddListener`**`(方法)` |
| `x.Event -= 方法` | `button.onClick.`**`RemoveListener`**`(方法)` |

⇒ 「**谁挂谁摘**」这条规矩**一字不改地适用**

### 四、路② 全家福（指针 / 拖拽接口）

| 接口 | 什么时候被调 |
|---|---|
| `IPointerClickHandler` | 点击 |
| `IPointerEnterHandler` / `IPointerExitHandler` | 悬停进 / 出 |
| **`IPointerDownHandler` / `IPointerUpHandler`** | 按下 / 抬起 |
| `IBeginDragHandler` / `IDragHandler` / `IEndDragHandler` | 拖拽三段 |
| `IDropHandler` | 放下 |
| `IScrollHandler` | 滚轮 |
| `ISubmitHandler` / `ICancelHandler` | 键盘 / 手柄 |

### 五、⭐ 回链：`HoldButton` 就是路②

Breakout 的触屏「按住」按钮（**第 15 章**）实现的是 `IPointerDownHandler` / `IPointerUpHandler`，自己维护 `IsHeld`。

⇒ 当时要的是【**按住**】而不是【点一下】—— **`onClick` 根本做不到**（它只报"点完了"，不报"还按着"）⇒ 必须走接口 ✓

### 六、桥：`EventTrigger` 组件（了解级）

它让你**不写接口**也能在 Inspector 里给"指针事件"挂方法 ⇒ 相当于「**用路①的方式使用路②**」。

### 七、别混淆：Input System 是**另一层**

| 路 | 例子 | 属于哪一层 |
|---|---|---|
| **Input System 的回调** | `InputAction.performed` / `.canceled` | **输入设备层**（不是 UI） |

（Breakout 用新输入系统时见过它 —— 和 UI 事件是**两层东西**。）

### 八、一句话判据（带走）

> **"点一下就完事" → 挂 `onClick`；"我要定义整个交互过程（按住 / 拖动 / 悬停）" → 实现 `EventSystems` 接口。**
