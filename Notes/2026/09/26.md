## 今日沉淀

### 一、`49` 的"键 → 筐"升级：哈希分组

前两周的 `Dictionary` 都是"**键 → 一个值**"（计数 / 存在性 / 映射 / 库存取货），今天第一次是"**键 → 一个筐**"：

```csharp
Dictionary<string, List<string>> dict;   // 键 = 规范形式，值 = 一组词
```

**核心问题只有一个：拿什么当 key？** 两条硬要求（缺一不可）：

| 要求 | 含义 | 谁来保证 |
|---|---|---|
| ① **同类同键** | 异位词必须算出同一个 key | 加/异或/排序/计数**都满足**（都可交换可结合） |
| ② **异类异键** | 非异位词**绝不能**撞 key | ⚠️ **只有"无损编码"满足** —— 这条才是命门 |

**今天一次性看清了"有损编码"全家桶**（都是只满足 ①、栽在 ②）：

| 编码 | 丢掉了什么 | 反例 |
|---|---|---|
| **ASCII 和** | 丢"分布"（只留总量） | `ad` = 97+100 = **197** = `bc` = 98+99（长度还一样，看不出破绽） |
| **异或** | 丢"次数"（成对抵消，只留奇偶） | `aa` = 97^97 = **0** = `bb` = 98^98 |
| **计数表无分隔符拼接** | 丢"位数边界"（编码有歧义） | `[1,11]` → `"111"` = `[11,1]` |

**最后用的是"计数表 + 分隔符"**（`string.Join(",", judge)`）：26 个格子**无损**记下"哪些字母、各几次"，
所以整体复杂度是 **O(n·k)** —— 比排序版 O(n·k log k) 更优，等于**直接做了进阶①**。

**⭐ 两层"碰撞"必须分清**（今天新学的一条尺子）：

| 层 | 谁负责 | 能不能撞 |
|---|---|---|
| **语义层**：你的 key 代表哪个等价类 | **你自己** | ❌ **绝对不能撞**（撞了就是分组语义错了） |
| **哈希层**：`Dictionary` 内部把 key 算成桶下标 | `Dictionary` 自己 | ✅ 允许撞 → 它用 `Equals` 兜底（09-20 学的"冲突解决"） |

> 所以"哈希函数允许碰撞"这句话**不适用于你的 key** —— `Dictionary` 只保证"key 相等 → 同一个筐"，
> 它**不会**替你检查"这个 key 是不是真能代表这组词"。

### 二、⭐ 今天真正的主角：**锁必须罩住副作用**

```csharp
// ❌ 出事的版本：副作用在锁【外面】
private void Win() { audioSource.PlayOneShot(Sfx.GameWin()); End("YOU WIN"); }
                     //  ↑ 没被保护
// 而 Update 每帧调 Win()（缺 if (_isGameOver) return;）→ 每秒 60 次 PlayOneShot

// ✅ 修好之后：锁 → 状态 → 副作用，全在同一方法里，顺序由它自己保证
private void Win()  { End("YOU WIN",   Sfx.GameWin()); }
private void End(string message, AudioClip sound)
{
    if (_isGameOver) return;      // ① 先上锁
    _isGameOver = true;           // ② 再改状态
    ...
    audioSource.PlayOneShot(sound);  // ③ 最后才是副作用
}
```

**为什么只有通关炸、失败没事？**

| 出口 | 调用源 | 触发次数 |
|---|---|---|
| `Lose()` ← `FailZone.OnTriggerEnter2D` | **事件** | 天然**只一次** ✅ |
| `Win()` ← `Update()` | **每帧轮询** | **每帧一次** ❌ |

> ⭐ 这是 09-24「**入口上锁 ≠ 全局上锁**」的升级版：
> 上次是"只锁了入口"，这次是"**锁上在入口，副作用却留在入口外面**"。
> **判据**：**锁必须把副作用整个罩住，否则等于没锁。**

### 三、同相位叠加的"极端版"（接 09-25 那条线）

| 叠加密度 | 听感 |
|---|---|
| 2 声完全同时（撞两块砖） | "一声更响"（`sin + sin = 2sin`） |
| **60 声/秒（每帧一次）** | **持续的嗡嗡 / 电流声，永不结束** |
| 振幅超过 `[-1, 1]` | **削波（clipping）→ 波形方波化 → 大量高次谐波 → 刺耳** |

> ⭐ 一条延伸：**密集的短音会融合成持续音**（颗粒合成原理）。
> 所以"叠加"不只是音量问题 —— **密度够高时它会变成一种全新声音**。

### 四、声音设计：上行 = 胜利，下滑 = 失落 + **段尾淡出**

```csharp
float[] notes = { 523.25f, 659.25f, 783.99f };   // C5-E5-G5 上行大三和弦
float envelope = Mathf.Exp(-8f * t);              // 段内衰减（老配方）
float tail = Mathf.Min(1f, (perNote - i) / tailLen);   // ★ 段尾 20ms 强制收到 0
```

> ⚠️ **`decay × duration ≥ 3` 管不了段与段拼接** —— 那条口诀管的是"**一个音自己收干净**"；
> 拼接处"前一段末尾振幅突然归零、后一段从 0 重新起跳" = **突变 → 额外频率成分 → "咔"声**。
> 修法就是**段尾 20ms 线性淡出**。**和"动画要淡入淡出"是同一条物理规律。**

### 五、C# 类型线：接口 / 抽象类 / 具体类 + **泛型变型**（沉淀进第 30 章）

- **型变判据**：能不能"换个 T 用"，看 **T 出现在什么位置**
  - `IEnumerable<out T>`（**只出不进**）→ **协变** ✅
  - `IList<T>`（**既进 `Add(T)` 又出 `this[int]`**）→ **不变** ❌
- **实测**：`List<List<string>>` → `IList<IList<string>>` **报 CS0266**；但 `List<string>` → `IList<string>` ✅（**直接实现**，T 没变）
- **层数不是判据**：双层 `List<List<string>>` → `IList<List<string>>` 一样通（T 没变）
- **工程尺子**：**对外收窄（接口）、对内放开（具体类）**

### 六、`Debug.LogError(msg, context)` 的 `context`

```csharp
Debug.LogError("GameManager 引用缺失：…", this);   // 第二个参数 = 上下文对象
```

- **作用**：让这条日志**可点可定位** —— 双击控制台里的红字，直接在「层级」里选中这个物体并在检查器高亮该组件
- `this` 就是"当前这个组件实例"（`MonoBehaviour` 继承链上就是 `UnityEngine.Object`）
- **静态方法里没有 `this`** → 只能不传或传 `null`
- ⚠️ **它只影响"日志怎么被定位/展示"，不影响内容与行为** —— 消息告诉你"发生了什么"，`context` 告诉你"在哪儿"

### 七、`CompareTag` 遇到**没建的标签**会直接抛异常

| 写法 | 标签没建 / 拼错时 |
|---|---|
| `.tag == "Wall"` | **静默**返回 false（怎么都不响，还不报错） |
| **`CompareTag("Wall")`** | **当场抛 `UnityException: Tag: Wall is not defined.`** |

> ⭐ 这是 09-22「**静默失效四连**」的**反面** —— 也是"必须用 `CompareTag`"那条规则附带的隐藏好处：
> **它让错误变响亮**。（配合第 11 章"响亮地失败"，是同一个原则的两种表现。）

### 八、面板上的值属于**场景文件**，不属于脚本

```csharp
// BrickSpawner.cs
[SerializeField] private int cols = 8;    // ← 把这里改回 8 【无效】！
[SerializeField] private int rows = 4;    // ← 同上
```

- `= 8` 只是"**组件第一次挂上时的默认值**"；一旦在检查器里改过，**场景文件里就存下了覆盖值**
- 所以"临时调小砖块数 → 录完改回 8×4"**必须去检查器改**，改完 **场景窗口 `Ctrl+S`**（第 2 层保存）
- **判据**：**凡是面板上能改的东西，落盘都归"场景"这一层管**

### 九、⚠️ 隐私事故：`organizationId` 含手机号（09-18 就已推上公开仓库）

```
ProjectSettings/ProjectSettings.asset:728
  organizationId: q13077396039mtu1fngg     ← 中间那串 11 位数字是手机号
```

- **它是什么**：Unity 登录账号后创建项目，会自动把 `organizationId` 写进**必须入库**的 `ProjectSettings.asset`
- **为什么危险**：仓库是 **public**，提交历史里也留着 → **任何人都能搜到**
- **怎么处理的**：`git filter-repo --replace-text`（把该串替换为 `REDACTED`）→ **空提交留标记** → **强推**（远端全部 hash 改写，远程 master 与本地一致已验证）
- **⚠️ 如实的边界**：GitHub 对旧的 commit 对象**不会立刻物理删除**（等它自己 GC），所以**拿到过旧 hash 直链的人短期内仍可能打开**；但"可被搜索到"这条路已经断了
- **长期防复发**：新建 Unity 项目、第一次提交前自查 ——
  ```powershell
  git diff --cached | Select-String "organizationId"        # 期望：无输出
  git diff --cached | Select-String "\b1[3-9]\d{9}\b"       # 期望：无输出（手机号形态扫描）
  ```

## 工程习惯（今天最"贵"的）

> **今天所有排查都是"读磁盘 + 拿证据"，一次都没靠"我觉得"。**

- **异常消息本身就是证据**：`KeyNotFoundException` 把 **key 的值原样打出来** —— `10001000000000000001000000` 这串正好是 `"eat"` 的计数表（1 个 a / 1 个 e / 1 个 t），一眼就能反推出"key 是怎么造的、歧义在哪"
- **一个症状两处线索**：通关音的"刺耳 + 不结束"两条症状，分别指向**削波**和**重复触发**，对着代码一读就定位
- **`git branch -r --contains` / `git merge-base --is-ancestor` 判断"到底推没推"** —— 比"我记得推过"可靠
- **`git ls-remote` 实时查远程** —— 强推后用"远程 refs 的 sha 是否等于本地 HEAD"来验证，比刷新网页靠谱
