## 今日沉淀

### 哈希线 205：双射（bijection）
- **两条规则其实分属两个方向**：①"同一字符始终映射到同一字符"= **s→t 方向**；②"不同字符不能映射到同一字符"= **t→s 方向**
- **一个 Dictionary 只能守一个方向的门** → 规则②本质是"反向有没有冲突"，只有以 `t` 为 key 再建一张表才能查到
- 反例 `"badc"/"baba"`：`b→b, a→a, d→b, c→a` 单方向全部"首次出现、无冲突" → 误判 True；实际 `b` 和 `d` 都映射到 `b`，违反规则②
- **副产品**：`for` 循环解决"两个集合按下标配对"；`foreach` 做不到（它不提供下标）
- **另一条思路（思考题）**：把字符串"归一化"成"每个字符首次出现的位置编号"（`"egg"→"011"`、`"add"→"011"`）再比较——**把不同的东西映射到同一标准形态再比较**，这是 hash/规范化类问题的通用思维

### Unity 三件套
```
GameObject  = 一个空容器（本身什么都不会）
Component   = 装在容器里的功能件
Transform   = 唯一【强制】自带的组件（删不掉，每个物体必须有）
```
- **Unity 里没有"物体的行为"，只有"组件的行为"**：想移动 → 加脚本组件；想被碰撞 → 加 Collider；想被看见 → 加渲染组件
- **`transform` 不是全局变量**，是**从 `Component` 继承来的属性**（≡ `this.transform`）——`: MonoBehaviour` 的真正价值：白送一批快捷访问 + 生命周期方法的"报名资格"
- **Scene 窗口 = 上帝视角（可自由飞）｜Game 窗口 = 相机视角（玩家看到的）**

### ⭐ 运动的母公式（所有移动代码的内核）
```csharp
transform.position += new Vector3(speed * Time.deltaTime, 0f, 0f);
//                              └── 这一帧应该走的距离 ──┘
```
- **`Update` 是"每帧一次"，不是"每秒一次"** → 所以必须 `× Time.deltaTime` 把"每帧的量"换算成"每秒的量"
- **去掉 `deltaTime` = 把"每秒移动"变成"每帧移动"** → 实测 `Update` 一秒上千帧 → **速度放大约 1000 倍**（3 秒飞出约 3000 单位，正交相机视野只有十几个单位）
- **帧率无关性铁律**：凡是"每秒多少"的（移动 / 旋转 / 冷却 / 计时）一律 × `deltaTime`；凡是"每帧一次"的（读输入、判按键）不乘
- 数学本质：`位置 += 速度 × dt` 是**数值积分（欧拉法）** —— 把时间切片，每片当匀速累加
- 实测"10 秒后是 ~10 而不是精确 10"的两个原因：①**`deltaTime` 每帧本身在波动**（主因）②浮点累加误差（次因）
- **两条互斥的移动路线**：直接改 `transform.position`（运动学，自己算，会穿墙）｜操作 `Rigidbody`（物理引擎算，有碰撞重力）—— 打砖块的分工：**挡板走运动学、球走物理**

### CS1612：属性返回 struct → 只能"整体读写"
```csharp
transform.position += v;        // ✅ 编译器展开成 transform.position = transform.position + v（整体赋值）
transform.position.x = 5f;      // ❌ CS1612：无法修改"Transform.position"的返回值，因为它不是变量
```
- **三步对照**：`+=` 是"读 → 算新的 → **整体写回**"；`.x = 5f` 是"读 → 改拷贝 → **丢掉**"（没有写回那一步）
- **根因**：`position` 是**属性**（执行代码后**返回一份拷贝**），不是字段；返回值没有名字、没有稳定存储位置 → **不是变量** → 不能出现在赋值号左边
- **正解**：①`Vector3 p = transform.position; p.x = 5f; transform.position = p;` ②`new Vector3(...)` 整体赋值 ③**优先用 Unity 封装好的方法**（`transform.Translate(...)` / `transform.Rotate(...)`）——**Unity 提供这类方法，本质就是在帮你做"读-改-写回"**
- **类推**：`List<T>` 的下标是**索引器（属性）**→ `list[0].x = 5f` ❌；而**数组**的下标是语言内建的**变量** → `arr[0].x = 5f` ✅（同一个 `[]`，一个是变量一个是属性）
- **为什么编译器要拦**：它能确定这个操作毫无意义。**宁可编译报错，也不要静默 bug** —— 与 Unity 生命周期"按名字点名 → 拼错静默失效"形成对照：**编译器能管的错，绝不留到运行时**

### 字段 vs 属性（判定三步法）
| 长相 | 是什么 |
|---|---|
| 类型 + 名字 + `;` | **字段** |
| 有 `{ get; set; }` 或 `=> 表达式` | **属性** |
| `this[int] { get; set; }` | **索引器**（本质是属性） |

- 惯例：字段 `_camelCase`、属性 `PascalCase` —— **只能用来猜，不能用来定**
- **权威判定：鼠标悬停 + `F12` 转到定义**
- **四个实际后果**：①能否"只改一个分量"（CS1612）②能否当 `out`/`ref` 参数（属性不行，CS0206）③读取代价（属性要执行代码，`transform.position` 要跨到引擎内部取数 → **读一次缓存到局部变量**）④结果是否稳定（计算属性每次现算）
- 记忆锚点：**字段 = 抽屉**（直接拿/放）；**属性 = 前台**（跑一套流程再给你，没法隔着前台动抽屉里的某一格）

### ⚠️ 世界坐标 vs 本地坐标（今天的认知纠偏，见下方专节）
- **`transform.position`（代码）= 世界坐标**｜**`transform.localPosition`（代码）= 本地坐标**
- **Inspector 的「位置」字段 = 本地坐标**（有父物体时）—— **不是世界坐标！**
- **世界坐标在 Inspector 里根本看不到**，两个模式（Normal / Debug）显示的都是本地值，只能用脚本取
- **父子关系**：世界坐标 = 父的世界坐标 + 自己的本地坐标（无旋转缩放时）
- 在面板里改「位置」等价于 `transform.localPosition = ...`，**不是** `transform.position = ...`
- **Unity 这样设计的原因**：调子物体时关心的是"相对父物体的偏移"（父动子动是常态）

### C# 数值精度与浮点数
- **小数默认是 `double`**，不是 `float` → 写 `float` 必须加后缀 `1f` / `0.5f`
- **隐式转换只允许"升级"（不丢数据），不允许"降级"**：`double y = 1f;` ✅｜`float x = 1.0;` ❌ CS0664
- **Unity 的数学类型全是 `float`**（`Vector3.x/y/z` 都是 float）→ 所以 Unity 社区习惯"数字全写 `f`"
- **后缀表**：`f`=float(32)｜无=double(64，小数默认)｜`m`=decimal(128，**算钱专用**)｜`u`=uint｜`L`=long
- **⚠️ 整数除法坑**：`float half = 1 / 2;` → **0**（两个 int 相除再赋给 float）；`1f / 2` → 0.5。**表达式里有一个 float，整个表达式就按 float 算**（进度条/百分比必踩）
- **⚠️ 永远不要用 `==` 比较浮点数**：`0.1f + 0.2f == 0.3f` 得到 `false` → 用 `Mathf.Abs(a - b) < 0.0001f`

### 计基随行：堆与栈
| | **栈 Stack** | **堆 Heap** |
|---|---|---|
| 管谁 | 编译器/运行时**自动** | **GC** 垃圾回收器 |
| 装什么 | 局部变量、参数、返回值、返回地址 | `new` 出来的**对象**、数组、字符串、装箱盒 |
| 速度 | **极快**（分配 = 挪指针） | 慢（找空间 + 记账 + GC 扫描） |
| 大小 | 小（约 1MB）→ 递归太深会 **StackOverflow（不可捕获）** | 大（GB 级）→ 满了只是 OutOfMemoryException（可捕获） |
| 生命周期 | **跟方法同生共死** | **只要有引用就一直活着** |

- **分成两块的根本原因是"生命周期"**：局部变量方法一返回就该消失（栈最合适）；`new` 的对象要活得比方法久（必须堆）
- **三个误区**：①不是"值类型在栈、引用类型在堆"——**存储位置取决于"变量住在哪"**（`class` 的 `int` 字段在堆上，`Transform` 里的 `Vector3 position` 也在堆上，**内嵌**在对象里）②**`new` ≠ 上堆**（`new Vector3(...)` 仍在栈上）③对象里的值类型字段是**内嵌**，不是"指向"
- **`transform.position` 的本质**：从堆上的 Transform 对象里**把那 12 字节拷到栈上**给你 —— 这就是 CS1612 的物理原因
- **两条 Unity 铁律的来源**：①**不要在 `Update` 里频繁 `new`**（GC 尖峰掉帧）②**对象池**（09-22 打砖块要学）—— 都是为了**减少堆分配**
- `string` 是不可变引用类型：每次 `+` 都在堆上新建一个字符串（循环拼接 = 一堆垃圾）

## ⚠️ 特别记录：一次"权威说法 vs 亲手实验"的认知纠偏

**事件**：我给了一张"Transform Inspector 字段空间"的表格，声称 Normal 模式的「位置」是**世界坐标**、Debug 模式才是本地坐标。用户**没有接受**，反复做实验后坚持"两个模式显示的都是相对位置"。

**结果：用户完全正确，我错了。** 查 Unity 官方手册（4.3 中文版 与 Unity 6.0 英文版，两版说法一致）：

> *"The Transform values for any child GameObject are displayed relative to the parent GameObject's Transform values. **These values are called local coordinates.**"*
> *"Unity measures the Position, Rotation and Scale values of a Transform **relative to the Transform's parent**. If the Transform has no parent, Unity measures the properties in world space."*

**我错在哪**：把**两套不同的规则**混为一谈——
| | 值是什么 |
|---|---|
| **代码 API** `transform.position` | **世界坐标**（手册确实这么说） |
| **代码 API** `transform.localPosition` | **本地坐标** |
| **Inspector 的「位置」字段** | **本地坐标**（与 `transform.position` 相反！） |

我拿"API 属性是 world space"这条，**错误地类推**到了"编辑器的显示规则"上。

**更值得记的是**：证据其实**早就在用户给的截图里**——Debug 截图「局部位置 X=1.33 Y=-1.4」与 Normal 截图「位置 X=1.33 Y=-1.47」**数字基本相同**。我当时没有去比对这两个数，而是凭记忆下了结论。

**教训（三条）**：
1. **文档 / 记忆 / AI 都可能错，可复现的实验才是唯一锚点** —— 用户"坚持自己亲眼看到的现象并反复验证"的做法是完全正确的
2. **不要用"看起来权威的说法"去覆盖一手观察**（我那张编得很整齐的表格，反而是最有欺骗性的）
3. **观察数据摆在面前时，要先比对数字**（两张截图数字一样 = 决定性证据，我却放过了）

**这个错误的代价**：如果当时说服了用户，他会带着错误的坐标模型继续做所有 Transform 操作，问题会在打砖块时以"物体莫名跑到奇怪位置"的形式爆发，且根因难查。**今天的半小时追问省下了未来的两小时。**
