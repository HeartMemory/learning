## 今日沉淀

### 一、事件的三条硬知识（都是今天实测出来的）

| 问题 | 结论 | 怎么证的 |
|---|---|---|
| 外部能对事件做什么 | 只能 `+=` / `-=`；**赋值或调用 = CS0070** | 实测报错原文："事件只能出现在 `+=` 或 `-=` 的左边（**从类型 ScoreBoard 中使用时除外**）"——括号那半句就是"内部才能 raise" |
| 多播的**执行顺序** | **订阅顺序**（FIFO）；`GetInvocationList()` 就是那条有序列表 | 订阅 A→B→C，打印出 A、B、C |
| 退订的**顺序与条件** | **顺序随意**（`-=` 不是"撤销上一步"，事件**不是栈**）；但必须**同一方法实例**（方法 + 目标对象都相同） | 乱序退订后只剩 B；lambda 存进变量能退掉、现写两遍退不掉；**同一方法订阅两次、退一次还剩一次** |

### 二、Unity：方向反转（今天的主体）

| | 改前 | 改后 |
|---|---|---|
| 谁是发布者 | 无（`FailZone` 直接调 `gameManager.OnBallLost()`） | **`FailZone`**：`public event Action BallLost;` + `BallLost?.Invoke();` |
| 依赖方向 | `FailZone ─→ GameManager` | **`GameManager ─→ FailZone`**（订阅）；`FailZone ─→ 谁都不认识` |
| 谁需要防线 | FailZone（"我必须认识裁判"） | **只有 GameManager**（它引用了别人）；FailZone 由 `?.` 兜"没人订阅" |

### 三、⭐ 订阅/退订的**配对判据**

| 订阅写在哪 | 退订就该写在哪 | 为什么 |
|---|---|---|
| `Start()` | `OnDestroy()` | 两者**都只执行一次**，天生配对 |
| `OnEnable()` | `OnDisable()` | 两者会**反复成对触发**（物体被反复启停），必须成对 |
| ❌ `OnEnable()` + `OnDestroy()` | —— | **数量不匹配**：多次启用 = 多次订阅 → 退一次退不掉 → **回调被调多次**（今天实测过：同方法订阅两次就执行两次） |

**为什么退订不能省**：`+=` 让**发布者的订阅链持有订阅者对象** → GC 不会回收它（控制台练习 ③ 段：主流程早就丢掉 `temp` 了，它却还能收到通知）。在 Unity 里更狠：被销毁的对象仍挂在链上 → 下次通知抛 `MissingReferenceException`，而 **`?.` 防不住**它（`?.` 只检查字段本身是不是 null）。

### 四、今天踩的**两个编译坑**（都值得记）

1. **CS8632：`Action?` 在 Unity 里不合法**
   - `Assembly-CSharp.csproj` 里**没有** `<Nullable>` 设置 → nullable 上下文关闭 → `?` 注解报警告
   - 对照：控制台练习的 csproj 写了 `<Nullable>enable</Nullable>` → `?` 合法，且**真的参与空分析**（昨天那条 CS8602 就是它给的）
   - ⭐ 判据：**注解（`?`）只是给编译器的提示，`?.` 是运行时检查** —— 前者可省，后者不能省
2. **日志尾巴 ≠ 最新错误**：修复后 `Editor.log` 里仍留着上一次失败的 `CS0103`
   - 判据：比对 `Library/ScriptAssemblies/Assembly-CSharp.dll` 时间戳 vs 源码时间戳（DLL 更新 = 编译过了）

### 五、工程纪律（今天新增两条）

1. **提交前跑一次 `dotnet build` / `dotnet run`**：今天把"实验中间态"（解开注释看报错后忘了还原）提交了一次，做出了一个**编译不过的提交**（错题本 20 的附件）；用 `git reset --soft HEAD~2` 把两个同名提交合并重提修好。**未推送的提交可以自由整理本地历史**（`reset --soft` 只挪指针，改动一点不丢）。
2. **改方向时，旧防线 + 旧注释一起清**：注释写着 `gameManager.OnBallLost()` 而代码早已不认它，会误导下一个读它的人。
