## 今日沉淀

### 一、对象池：四个设计决策（每个都是真问题，不是走过场）

| 决策 | 选择 | 理由 |
|---|---|---|
| **库房用什么容器** | **`Queue<GameObject>`**（FIFO） | 池的语义是"只在一端进出"，`Queue` 把这条约束**焊进类型**。`List` 也能做到 O(1)（取出与归还**都用尾部**），但它允许你写 `RemoveAt(0)` → **O(n)** 且编译器不拦。**接口越窄，误用越不可能**——和 09-08 `IReadOnlyList`"只读眼镜"同一个思想 |
| **池空了怎么办** | **`LogError` + `return null`** | 预分配数（32）= 总需求（32）→ 池空只可能意味着**逻辑 bug** → 应当**响亮地失败** |
| **归还时重置什么** | **位置/旋转不重置**（借出时统一设置）；父子关系用"归属检查"兜住 | 单一保证点：谁发出去谁负责初始状态；状态清空等将来有"砖块血量/颜色"时再补 |
| **⚠️ 双重归还防线** | **`if (!brick.activeSelf) return;`** | 池里的砖**一定失活** → 免费、O(1) 的标志。没它就"一块砖入池两次 → 借出同一个对象两次 → 分身"（对象池最经典的幽灵 bug） |

### 二、依赖注入：Prefab 不能引用场景对象

- **现象**：给 Prefab 上的 `Brick` 加 `[SerializeField] BrickSpawner _pool`，**拖不进去**
- **原因**：Prefab 是**资产**（要能被多个场景共用），`Board` 是**场景里的具体物件**——资产不能绑定某个场景实例
- **解法**：**运行时注入** —— 池在预分配时 `brick.Init(this)`；**"这块砖属于这个池"是永久关系 → 建立一次就够**
- **概念对照**：`[SerializeField]` = **编辑器期装配**；`Init(this)` = **运行期装配**（依赖注入雏形，Block 3 委托/事件的前身）

### 三、⚠️ 量级最大的一条：材质是"成对计算"的，而**球自己漏挂材质**

- **现场**：5 个碰撞体的材质归属 —— 右/左/上墙 ✅、挡板 ✅、**球 ❌（两个槽都是空的）**
- **后果**：球默认材质摩擦 ≈0.4 → 每次碰撞 `Mean(0.4, 对方 0) = 0.2` → **每次接触都被"搓"：掉速 + 变向**；弹性走"最大" `max(0, 1) = 1`，所以**照弹不误**——现象是"弹得挺好但越来越歪"
- **认知纠偏**：**"现象最明显的地方"≠"根因所在"**。撞挡板变化最大（挡板在动，摩擦 + 速度传递叠加），但根因在**球**——它是**每一对碰撞里共用的那一方**。找根因要问"谁参与了每一次碰撞"

### 四、Tag vs 组件：今天选了 Tag，但知道取舍在哪

| | Tag 路线 | 组件路线 |
|---|---|---|
| 强项 | 引擎侧生态（Layer 碰撞矩阵 / 相机 / Animator / `FindWithTag`）+ `CompareTag` **无堆分配** | 类型安全 + 重构友好 + **可叠加多重身份** |
| 软肋 | 字符串弱类型：拼错/改名 → **静默失效** | 忘挂脚本 → **同样静默失效** |
| 硬上限 | 一个物体**只有一个** Tag | 可以有**多个**组件 |

**关键判断**：**同处串联两个判定 ≠ 双保险**（`CompareTag(...) && TryGetComponent(...)` 只是把两处故障串成一条串联网）。真正合理的"两个都用"是**分工**：**Tag 粗筛 → 组件取引用**（判定只做一次）。

**Tag 路线的使用要点**：`CompareTag("Paddle")` 而不是 `tag == "Paddle"`（后者每次调用新建 string → 堆分配）；标签必须在 `项目设置 → 标签和层` 里**真实存在**，否则恒为 false。

### 五、位运算：异或（新开的一条线）

- **三条性质**：`a ^ a = 0`、`a ^ 0 = a`、满足**交换律 + 结合律**（"谁先谁后"不影响结果）
- **用途**：全场异或累加 → 成对元素自己抵消 → 剩下的就是落单的（136）；初始值取 `0` 让"单元素"**免特判**
- **对照**：哈希两条路（计数表 / "遇到就加、再见就删"）都对，但都是 O(n) 空间
- **旧坑**：`^` 是**位异或**不是乘方（错题本 08 的 Python 迁移坑）

### 六、击打点改角度（手感的核心技巧）

- **为什么必须自己接管**：球撞**水平挡板**，接触法线竖直 → 反射角与击打位置**无关**（物理给的是"几何正确"，玩法要的是"好玩"）。这就是**"物理给结果、玩法给手感"**的分界线
- **四步**：判定是不是挡板 → 取击打点偏移 → 归一化成 `t ∈ [-1, 1]` → 用 `t` 造新方向并**锁速率**覆盖速度
- **两种数据源**：

| 数据源 | 范围 | 代价 |
|---|---|---|
| **球心**：`transform.position.x - other.transform.position.x` | ±(半宽 + 球半径) = ±1.8 | 简单、不会空；但含球半径，边缘会提前饱和 |
| **接触点**：`other.GetContact(0).point.x - other.transform.position.x` | ±半宽 = ±1.5 | 更精确；**必须判 `contactCount > 0`** |

- **`GetContact(0)` 的写法**：单行与两行**完全等价**（调用次数相同）；两行胜在**调试可见**、**类型自解释**、**好扩展**（要用 `normal` 时不用改结构）。`ContactPoint2D` 是 **struct** → 多一行不产生堆分配
- **覆盖速度的三条纪律**：`dir.normalized` 后**再乘速率**；**保证 y 分量 > 0**（否则球水平平推、永远不落下来 → 卡死）；在**碰撞回调里改**（物理求解已完成），**不要每帧覆盖**
- **抽象时机（今天特意没抽）**：`GetHitOffset` 只有一个调用方 → 留在 `BallController` 内、**`private`**（`public` 要能点出调用方是谁）。等**第二个真实调用方出现**再抽成**静态工具类**（⚠️ **不是 MonoBehaviour**：纯计算没有生命周期/状态，做成组件只会多一个"忘挂就静默失效"的坑）
- **魔法数字待清理**：`0.25f`（其实是"四分之一宽"，不是半宽）、`Clamp(-2, 2)` —— 待做"角度线性映射"时一并参数化（`maxBounceAngle` 用 `sin/cos`，比 `(t,1).normalized` 的 `atan` 在边缘更均匀）

### 八、`contacts` 数组：什么时候真的会"空"（不变量 vs 通常成立）

- **理论上**：`OnCollisionEnter2D` 里接触流形刚刚建立 → `contacts` **至少 1 个点**，这是引擎语义保证的
- **但它是"通常成立"，不是"契约保证"**（所以判空是**对准真实脆弱点**的廉价保险，不是 219 那种凭感觉的保险丝）：
  1. `Collision2D` 是**复用包装对象**，只在回调期间有效——**存起来下次读就是空的**（"存值不存包裹"）
  2. 同一物理步里更早的回调把碰撞体禁用 → 后续数据可能不完整
  3. 版本 / 后端实现差异、位置修正
- **0 个 / 多个的根源是几何**：圆↔圆 1 点、圆↔面 1 点、**方↔方面贴面最多 2 点**；并且**顺序无保证**，不要做位置假设
- **卡顿与"漏事件"**：卡顿**不**影响回调期间读数据；但**极端卡顿触发 `最大允许时间步长`（默认 0.333s）丢步**时，被丢掉的那几步物理（含事件）**真的不会发生**。另有：高速 → 隧道效应（靠连续检测）；接触中被 `SetActive(false)` → 可能收不到 `Exit`
- **由此得到的架构原则（明天计分要用）**：**事件为主 + 状态兜底** —— 事件负责"精确一次"的动作，**状态查询**负责"持久正确"的信息（分数要能从"剩余砖块数"重算）

### 九、C# 可见性：同一个项目 ≠ 同一个文件夹

- **决定"别人能不能读到"的三个开关**：**程序集**（最外层边界）→ **命名空间**（要不 `using`）→ **访问修饰符**（顶层类型默认 `internal` = 同程序集可见）
- **文件夹不影响可见性**（除两种例外）：`.asmdef` 所在的文件夹独立成程序集（默认看不到外面）；`Editor/` 编译成编辑器程序集（**能读运行时，运行时代码读不到它**）
- **活证据**：`Brick.cs` 用了 `BrickSpawner` 却**不需要 using**（同一个 `Assembly-CSharp`、同一个全局命名空间）；`PaddleController.cs` 用 `InputSystem` **必须 using**（那是**另一个程序集**：Package）
- **验证三招**：写一行调用看是否 `CS0246` / IDE 里 `F12` 能否跳转 / 删掉 `using` 再编译看哪儿报红

## 工程习惯与 git 自修（今天收获最密集的一块）

1. **文件级 `git add <具体文件>` 不会带上 `.meta`** —— 那次提交只进了 `Brick.cs`，`Brick.cs.meta` 落单（后来补提交）。Unity 项目里更稳的是**按目录 add**；自查：`git status --short | Select-String '\?\?.*\.meta'`（空输出才算干净）
2. **`.meta` 不受代码改动影响**：它只存 guid + 导入设置 → **事后补交 = 当时就该交的那份**（用 guid 三重比对验证：HEAD 的 meta = 工作区 meta = `Brick.prefab` 里的引用）。历史里那一帧仍"不自洽"（checkout 会 Missing Script），但**不改写已 push 的历史**，用追加提交修正
3. **三层状态要分清**：工作区 / 暂存区 / HEAD。① `git log --all --oneline -- <路径>` ② `git log --diff-filter=A -- <路径>` ③ `git ls-tree -r HEAD --name-only -- <目录>`
4. **`git add` 的粒度随时可调**（"部分提交"）：忘记"改动前先 commit"不是问题，挑文件补提交即可；纪律：**中间提交最好能编译、能跑**
5. **大改动前先 commit 存档**（今天动 `BrickSpawner` 之前用上了）
