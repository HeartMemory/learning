## 二、算法：`704` 二分查找

| 项 | 内容 |
|---|---|
| 题眼 | **练的不是"找"，是【区间不变量】**：一句话 —— "搜索区间 `[lo, hi]`、target 若存在必在区间内"，代码只是它的翻译 |
| 递归版 | 闭区间 + 终止条件 `lo > hi` = **空区间**，一行盖住"没找到"与"递归到底"（承 104 的一行盖三入口） |
| 迭代版首版 | **13 / 22** ❌ |
| 失败指纹 | **9 组红全是"答案落在最后剩下的那个元素上"**（`[5]` 查 5 / `[1,3]` 查 3 / 值域上界查 9999 / n=10000 查首末位） |
| 病灶 | `hi = Length − 1`（闭区间）却配 `while (lo < hi)` ⇒ **区间剩 1 个元素时循环已退出，那元素从未被比较** |

### ⭐ 三条判据

1. **"我 `lo/hi` 的初值，和我 `while` 的条件，说的是同一个区间吗？"** 闭区间 `[0, Length−1]` 非空 ⇔ `lo <= hi`。初值与循环条件**必须一起写**，它们是同一句话的两半。
2. **这题不会整数溢出**：`n ≤ 10^4` ⇒ `lo + hi ≤ 20,000`。`(lo+hi)/2` 溢出是 69 那类题的药方，**别把别处的药背到这里吃**。
3. **"递归携带的状态能装进几个局部变量吗？"** 能装（二分只有 `lo/hi`）⇒ 递归是**伪装的循环**，空间多花 O(log n) 调用栈（⚠️ C# **不保证尾调用优化**）；装不进（145 后序的 `stage`）⇒ 才非递归不可。

### ⭐⭐ 判题器自身的教训：**"判题器要能失败"**

写完迭代版时，整套用例**仍然 22/22 全绿** —— 因为判题器只调 `Search`，**新写的 `Search1` 一次都没被跑到**。

修法 = **版本登记表**：每版都判、任错即红；Bench 分版计时。改完立刻照出 9 组红。

> 判据：**新增一个实现必须登记，不登记等于没写**；"全绿"只有在"每一版都被调用过"时才有意义。

互证强度也升级了一档：两版 **`sink` 累加值完全相同**（`49980000`）= 对 4 万次查询**返回同一个下标**，比"各自都用例过了"更硬。

### 复杂度

| 版本 | 时间 | 空间 |
|---|---|---|
| 递归 | O(log n) | **O(log n)**（调用栈） |
| 迭代 | O(log n) | **O(1)** |

## 四、Unity 第 2 关：三态 → Blend Tree → 仿原版四状态

### 4.1 Blend Tree 1D 取代「Idle + Run 两状态 + 一条过渡」

| | 普通过渡 | **Blend Tree** |
|---|---|---|
| 本质 | **离散跳变 + 交叉淡化** | **连续插值**（多段动画**按权重同时播**） |
| 中间速度 | 没有对应姿势，只能硬切再淡 | 任意速度都有对应姿势 |

**阈值来自脚本的真实取值**（不是拍的）：

```
MoveSpeed   = 2.0      → threshold 2
SprintSpeed = 5.335    → 原版取 6（不是 5.335）
Speed 参数  = Lerp 向目标值 ⇒ 会经过 0 → 2 → 6 之间所有中间值
```

⭐ **`Automate Thresholds` 必须关**：它会把 N 个 clip 在 **0–1** 均分（0 / 0.5 / 1）；而 `Speed` 是真实速度，到不了 0.5 以下的"走"区。

⭐ 原版用 **6 而不是 5.335** 的含义：冲刺时 `Speed = 5.335` 落在 2→6 的 **89%** 位置 ⇒ `Run_N` 权重 ~0.89、`Walk_N` 还有 0.11 ⇒ **冲刺时仍留一点"走"的成分**。

> ⭐ 判据：**阈值是"权重分配的设计"，不是"速度的精确映射"。**

### 4.2 原版四状态 + 五条过渡（照抄）

| # | 源 → 目标 | 条件 | 退出时间 | Exit Time | 时长 | 中断源 |
|---|---|---|---|---|---|---|
| 1 | `Locomotion → InAir` | `FreeFall == true` | 关 | — | 0.038 | 无 |
| 2 | `Locomotion → JumpStart` | `Jump == true` | 关 | — | 0.070 | 无 |
| 3 | `JumpStart → InAir` | **无条件** | **开** | **0.664** | 0.470 | 无 |
| 4 | `InAir → JumpLand` | `Grounded == true` | 关 | — | 0.098 | 无 |
| 5 | `JumpLand → Locomotion` | **无条件** | **开** | **0.399** | 0.434 | **Destination** |

### ⭐⭐ 五条设计思路

1. **起跳拆两段**：`JumpStart`（一次性）→ `InAir`（空中循环），**靠 exit time 0.664 自动推进**，不靠参数。
2. **两种离地**（最漂亮的一手）：
   - 主动按空格 ⇒ `Jump == true` ⇒ 走 **`JumpStart`**（有起跳动作）
   - 走下坡 / 掉边缘 ⇒ `FreeFall == true` ⇒ 直接走 **`InAir`**（没有起跳动作）
3. **落地也拆两段**：`InAir → JumpLand`（缓冲）→ `Locomotion`；`JumpLand → Locomotion` 的 exit time 0.399 + **中断源 `Destination`** ⇒ 落地缓冲**能被玩家操作打断**，不会僵一下才起步。
4. **`Grounded` 只做"落地了"这一件事**，绝不用来触发"起跳"：它的**默认值是 false**，用它当触发条件 ⇒ 游戏第一帧就会误触发（症状 = 开局莫名蹦一下）。
5. **参数驱动关 Exit Time、动作驱动开 Exit Time** —— 原版五条线逐条都是实证。

### ★ 今日三个坑（都有现象 + 修法）

| 坑 | 现象 | 根因 | 修法 |
|---|---|---|---|
| **`Can Transition To Self` 没关** | 跳跃动画**原地抽搐** | 条件 `Grounded == false` 在整段滞空持续为真 ⇒ 每帧重进该状态 ⇒ 每帧都被拽回第 0 帧（类比"循环里每轮把 i 重置成 0"） | 关掉「可以过渡到自身」 |
| 过渡时长留默认值 | 起跳"软绵绵"、按空格像愣一下 | 新建过渡默认 **0.25 秒** | 参数驱动的那几条改到 **< 0.1** |
| `Animator.Controller` 槽没换 | 改了半天"没变化" | 槽里还挂着**包内自带的** controller ⇒ 一直是别人的状态机在跑 | 换成自己的 `.controller` |

### ★ 术语对照：中断源

| 英文文档 | 中文界面 | 含义 |
|---|---|---|
| None | 无 | 不允许被打断 |
| Current State | Current State | 允许**当前**状态的出边打断 |
| **Destination** | **`Next State`** | 允许**目标状态**的出边打断 |
| Current State Then Next State | … | 先当前、再目标 |
| Next State Then Current State | … | 先目标、再当前 |

> 判据：**中文界面里"没翻译的英文选项"多半是 Unity 的技术标识符**（同 `Scripting` / `TextMeshPro`），去查英文文档就能对上。

### ★ 素材与工程纪律（今天的"钱包"教训）

| 事项 | 结论 |
|---|---|
| 包内大素材进不进 git | **进**。官方 Unity `.gitignore` 模板**不排除** `Assets/` 下贴图 / FBX / `.meta`；`.meta` 存 GUID，缺一个就是**静默丢引用**（不报错、只变空槽） |
| Git LFS | 对 ~100 MB 仓库**无收益**（社区阈值 20–30 GB 才开始痛苦） |
| **"排除" ≠ "删除"** | `.gitignore` 只挡**未跟踪**文件，挡不住工程里还躺着的文件 ⇒ "工程里有、git 里没有"= 本地与远端状态分裂 |
| 跨工程拷材质 | **连 `.meta` 一起拷**（贴图引用存的是 guid，`.meta` 就是 guid 的载体）；只拷 `.png` 不拷 `.meta` ⇒ 材质里贴图变 `None` |
| 地面参照 | 复用 Runner 的 `GroundGrid`（tiling **50×50**）+ 50×50 的地面 ⇒ **1 米一格**，一眼看出走了多远 |
