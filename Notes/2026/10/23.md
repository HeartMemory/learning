## 三句话复盘

1. **今天最大的收获**：**`35` 的"边界"是单数，`34` 要的是复数 —— 而解法只差一个 `+1`。**
   左边界 = `lowerBound(target)`，右边界 = `lowerBound(target + 1) − 1`。第二遍传 `target + 1` 这一步把「上界」整体翻译成了「下界」问题，于是整题退化成"同一个函数调两遍"。判据是它自己的措辞：**`lowerBound` 问的是「位置」，不是「值」** —— 所以 `target + 1` 在不在数组里根本无所谓。
2. **今天最大的教训**：**「命中」只是"存在"，不是"边界"。**
   三次弯路全栽在同一句上：命中就以为找到了答案。真正要问的是「如果还有更优的答案，它在左边还是右边」—— 命中那一支必须**记下 + 继续收**，而且左边界和右边界要往**相反**方向收。
3. **明天第一步**：进**动画事件**（脚触地帧 → 脚步声），顺手销掉"步频与速度脱钩"那笔债 —— 先确认 `Walk_N` / `Run_N` 里已有的两条 `OnFootstep` 位置，再决定"步频反比于速度"的算法落在事件里还是落在播放速率上。

## 一、算法：`34` 在排序数组中查找第一个和最后一个位置

### 1.1 与 `35` 的映射表

| | `35` | `34` |
|---|---|---|
| 问什么 | 该插在哪（**一条边界**） | target 段的**两端**（两条边界） |
| 答案 | `lowerBound(target)` | `lowerBound(target)` / `lowerBound(target + 1) − 1` |
| 循环体 | 命中就 `return` 也行 | **命中绝对不能 `return`** |

⭐ 一句话：**`upper_bound(value) == lower_bound(value + 1)`**（整数域上）⇒ 不必再写第二个函数。

### 1.2 三轮真实弯路（都是判题器照出来的）

| 版本 | 写法 | 症状 | 照妖镜 |
|---|---|---|---|
| ① | 命中就 `return mid`，往 `List` 里收命中 | `[5,7,7,8,8,10]` 查 8 得 `[4,4]`；找不到返回 `[]`（形状都不对） | 返回值长度随数据变 ⇒ 收的就不是答案 |
| ② | 命中后从 `lo` / `hi` 向两边扫 | **正确性 24/24 全绿**，但探针 C **118 ms vs 0.4 ms** | 探针 C（左半全 1、右半全 2） |
| ③ | 先二分命中，再在 `[lo,mid]` / `[mid,hi]` 里找 | `[8,8,8,8]` 查 8 得 `[0,2]`；全相同 10⁵ 得 `[24999,74999]`；**12/27** | 长连续段用例 |

⭐ 弯路 ② 里的两半命运完全不同，值得记住：

- `while (nums[lo] <= target)` 找左边界：**靠不变量白送 O(1)** —— `lo` 只会跳到"确认 `< target`"的位置 ⇒ `nums[lo] ≥ target`，而 `nums[lo] ≤ nums[mid] == target` ⇒ **第一轮必然相等、立刻 break**
- `while (nums[hi] >= target) hi--` 找右边界：**真线性** —— `hi` 只在「`nums[mid] > target`」时下移，命中那一刻它可能还停在"更大的一片"里，得一步步退回来

### 1.3 收口后的三条判据

1. **命中分支 = 记录 + 收缩**，缺一不可（只记不收 ⇒ 原地打转；只收不记 ⇒ 答案丢了）。
2. **一条 `else` 收掉「太大」和「正好等于」**：`if (nums[mid] < value) lo = mid + 1; else hi = mid - 1;` —— 两者都说明"左边界在 mid 左边，或就是 mid"。
3. **「找不到」不写 `if`**：`a` / `b` 初值 `-1`，`break` 只在命中时发生 ⇒ **初值即失败值**。

### 1.4 判题器与探针

| 设计 | 内容 |
|---|---|
| 用例 | **27 项**：官方示例 / 空数组 / 单元素 / 全相同 / 长连续段专项 / 规模 10⁵ |
| 期望值 | **双来源**：官方示例与边界硬编码 + 线性扫 `NaiveRange` 现算（不进 `versions`，否则 Bench 变成自己跟自己比） |
| 探针 | **A 随机升序 / B 全相同 / C 左半全 1**，三组 `sink` 必须两两相同 |
| 实测 | **0.3 / 0.2 / 0.2 ms** vs 线性基线 **521 / 290 / 244 ms** |

⚠️ **探针设计教训（今天最值钱的一条方法论）**：**探针 B「全相同」照不出「往回扫」的代价** —— `lo` 和 `hi` 一伸手就撞上 target，每步都立刻 break，所以完美通过。真正的对手是"目标段在左、更大的值在右"（`[1]×50000 + [2]×50000` 查 1：第一次 `mid` 就命中，`hi` 在 99999 得退 50000 步）⇒ 为此**后补探针 C**。

⭐ 判据：**性能探针要按"我的实现在哪种形状下最费"来造，而不是按"最典型的输入"来造**。

### 2.2 ⚠️ 输入资产的陷阱（改错文件不报错，永远不生效）

| 文件 | 实情 |
|---|---|
| `Starter Assets/…/StarterAssets.inputactions` | **`PlayerInput` 真正引用的就是它** |
| `Assets/InputSystem_Actions.inputactions` | 项目级存在，但**没有任何组件引用** |

⇒ 想加动作 / 改键，必须改**前者**。判据：**「资产存在」≠「资产被引用」** —— 检查器里那根引用才是唯一事实。

### 2.3 死值写入：写了没人读

| 层次 | 事实 |
|---|---|
| 脚本 | `Animator.SetFloat(_animIDMotionSpeed, inputMagnitude)` 一直在跑 |
| 控制器 | 状态的乘数**未勾**（`m_SpeedParameterActive: 0`）⇒ 这个参数从不被读取 |
| 之后 | 参数 `MotionSpeed` 被直接从控制器删除 ⇒ `SetFloat` 指向**不存在的参数** |

⇒ 三处引用（字段 / `StringToHash` / `SetFloat`）一并删掉，删后编译 **0 error 0 warning**。

⭐ 判据：**「代码在写」和「系统在读」是两件事** —— 判断一个参数是否活着，要去看**消费端有没有勾上它**，不能只看写入端在不在。

### 2.4 资产层的落盘（检查器 ≠ 磁盘）

改 `UpperBody` 层默认权重（1 → 0）后，磁盘上的 `.controller` **仍是 1** —— 因为改的只是内存。要在 Animator 窗口 `Ctrl+S` / 文件 → 保存项目 才写盘。

⭐ 自查判据：`git status --short` 里必须出现那个 `.controller` 的 `M`，否则就是**没落盘**。

### 2.5 阈值的可达性（今天唯一保持现状的一条）

| 量 | 值 |
|---|---|
| 混合树阈值 | 0 / 2 / 6 |
| `MoveSpeed` | 2.0 ✓ 与 Walk 阈值对上 |
| `SprintSpeed` | **5.335** ✗ ≠ 6 |
| `Speed` 参数实际上限 | ≈ 5.335 |

全力冲刺时 `t = (5.335 − 2) / (6 − 2) = 0.834` ⇒ **Run 权重 0.834、Walk 0.166**，即冲刺时仍混进 16.6% 的走路动作。

⭐ 判据：**混合树阈值必须落在"角色实际能到达的速度"上**，否则最高档永远只有部分权重。
