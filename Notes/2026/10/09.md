## 今日沉淀

### 一、算法：`700` 二叉搜索树中的搜索（BST 第 2 题）

- ⭐ **题眼**：站在 `cur` 上把 `val` 与 `cur.val` 一比，就知道 `val`（若存在）一定在哪半边 ⇒ **只走一条根到叶的路**，长度 = **树高 h**，别的节点一眼都不看。O(h) 时间 / O(1) 空间。
- ⭐⭐ **判据（今天最硬）**：**「该走哪边」只由【比较】决定；「那边有没有人」由游标变 `null` 表达。**
  - 把两者焊进一个条件（`temp > val && cur.left != null`，后面还跟 `else if`）⇒ 在"该走左但左边是空的"时**掉头往右**；
  - 为什么还能全绿：错的支路里**永远不含答案**（右子树的值全 `> temp > val`）⇒ **只白跑、不跑错**；
  - ⇒ **28 项用例 + 两种实现互证 + 性能裁判全部抓不出来** —— 路线错要靠"拿张图自己走一遍"或"造一个能暴露成本的形状"。
- **判题设计两条**：① **前提自检**（用例树必须真是合法 BST —— 中序严格递增，否则是在错误的题目上练手）② **独立裁判 = 题目定义逐字直译**（**故意不用 BST 性质**、整棵树都翻：定义里一个字都没提"比较大小"）⇒ 它顺便就是"**不用前提的下下策**"的化身。
- **性能裁判两种形状**：**满树 18 层 n = 262,143** → 裁判被调用 **524,285** 次（含空孩子槽）/ 1 ms，正解 **0 ms**（走 19 步）⇒ "砍一支"是真的在省；**左斜链 2,000 节点** → 裁判 2,000 次，**正解也得走 h = n 步** ⇒ ⭐ **O(h) 里的 h 是【树高】不是节点数**：树歪成链，BST 查找就退化成线性 —— **这就是"平衡树"存在的理由**。

### 二、C#：LINQ（五块一次收口）

- ⭐ **底层模型**：LINQ 返回的不是"结果"是"**配方**"，真正的计算发生在**伸手要数据那一刻**（`foreach` / `ToList` / `Count`）—— **拉模型**：调用方每要一个，生产方才算一个。
- ⭐ **"编译器生成隐藏类"的第二次相遇**：`yield return` 所在的方法被编译器整段改写成**状态机类** —— 与 09-30 闭包的 `<>c__DisplayClass` 是**同一个手法**（前者装"执行进度"，后者装"被捕获的变量"）。
- **操作符两族（+一族）**：
  | 族 | 性格 | 例子 |
  |---|---|---|
  | **节流阀** | 够了就收手 | `Take` `TakeWhile` `First` `FirstOrDefault` `Any` `All` `Contains` |
  | **闸门** | 必须吃干才敢继续 | `OrderBy` `ThenBy` `Reverse` `GroupBy` `Join` `GroupJoin` |
  | **一滴一滴** | 来一个处理一个，但不主动收手 | `Where` `Select` `Distinct` `Concat` |
  ⇒ ⭐ **闸门站在前面还是后面，决定它到底"吃进去几个"**（`Take(2).OrderBy` 只吃 2 个；`OrderBy.Take(2)` 先吃全部）。
- ⭐ **分组器不能提前收手（实测）**：`GroupBy(...).Take(1)` 仍然把 keySelector 调用了 **6/6 次** —— 想知道"第一组里都有谁"，就得**看完全部**。
- ⭐ **`GroupBy` vs `ToLookup`**：前者**延迟**（不枚举就不付钱、枚举一次算一次）；后者**立即结算**（调用那一刻就建好，之后白读）⇒ 判据不是"遍历几次"，而是"**这个结果一定会被用到吗？**"（可能压根不用 ⇒ `GroupBy`）。
- **按 key 取的两个设计**：`Lookup` 索引器给**空序列**（安静）；`Dictionary` 索引器**抛 `KeyNotFoundException`**（当场炸）—— 两种都合理，但**你得知道自己在用哪一种**。
- ⭐ **`IGrouping` 就是一条带标签的序列**（`.Key` + 自己就是 `IEnumerable`）⇒ 所以 `GroupBy` 之后**任何操作符都能接**（`Where` / `OrderBy` / `Select`…）。`into` 不是"过滤组"的语法，它是"**命名 + 接着写**"—— **≈ 方法语法里那个"点"**。
- ⭐ **`Where` 放在哪儿就换了"筛什么"**：`group` **之前** ⇒ 筛**元素**；`into` **之后** ⇒ 筛**组**；作用在 `grp` 上 ⇒ 筛**组内元素**（实测三种结果各不相同）。
- ⭐ **`Join` 是哈希连接**（`O(n+m)`，不是 `O(n×m)`）：把**内序列**建成哈希表，再扫**外序列**逐条查表。实测：嵌套循环 **20,010,000 次比较 / 24 ms** vs `Join` **6 ms**（配对都 20,000 条）⇒ ⭐ **次数差 ~900 倍、墙钟只差 4 倍**：**复杂度看操作次数，快慢看秒表，两个都要看**。
- ⭐ **为什么 `join` 写的是 `equals` 不是 `==`**：① 它内部要靠**哈希 + `Equals`**，而 `==` 是**可能被重载的运算符**，行为任意 ② `==` 可交换、说不出"谁属于外、谁属于内"（`equals` 两边变量**归属强制**）③ 想用 `==` 只能退回"笛卡尔积 + 过滤" —— 那正是 `Join` 要替掉的东西。
- ⭐⭐ **`Join` = 「`GroupJoin` 之后把空筐丢掉」**（实测：`GroupJoin + SelectMany` 不补空 ⇒ 输出与内连接**一模一样**）。
  - `into 筐` ⇒ `GroupJoin`（每个外元素**一行**，附带它配上的**所有**内元素）；配不上 ⇒ **空筐**（不是缺行、不是 `null`）。
  - **左连接三步配方**：`GroupJoin` → `SelectMany` → `DefaultIfEmpty`。
  - ⭐ **`GroupJoin` 的输出行数 = 外序列的元素个数**（恒等）；`Join` 做不到（丢行 / 内序列有重复键还会翻倍）。
- ⭐ **`DefaultIfEmpty`** 管的是「**整个序列空**」→ 塞一个 `default`；**不管**「元素是 null」（实测 `["aa", null, "bb"].DefaultIfEmpty()` 原封不动）。
- **聚合**：方法是**长在序列身上的**（不是"操作符"），参数是**选择器**（`Func<T, 数字>`）。
  - 不带参数版本只对"**序列本身就是数字**"成立 ⇒ 组的元素是**记录**时写 `g.Average()` **编译不过**（"组的聚合里永远有两层人"：组 `g` 与组里的元素 `x`）。
  - `Average` **永远返回 `double`**（且 `double.ToString()` 省略末尾无效零 ⇒ `55.0` 打印成 `"55"`）；**空集上 `Average` 抛 `InvalidOperationException`**，而 `Sum`/`Count` 给 0、`All` 给 **`true`（空真）**。
- ⭐ **查询语法 vs 方法语法**：查询语法只是**部分**操作符的糖（`Take`/`Skip`/`Distinct`/`ToLookup`/`ThenBy` 全都没有关键字）⇒ **方法语法是"全集"**，生产代码以它为主。⚠️ 两者**不完全等价**：查询语法的**范围变量**作用域是整个查询、**不能和同块的局部变量重名**（**CS1931**，今天连撞两次），方法语法的 lambda 参数没这个问题。

### 三、Unity：第 3 关「爬塔」落地（纵向关卡第一次实战）

- **关卡形态**：横向关卡的"地形顶"约等于"内容顶"；**纵向关卡的内容一直长到地形顶**（终点就在塔顶）⇒ 两者对"视野边界"的需求**根本不同**（这就是"边界按要装的东西定"那条）。
- **程序化生成**：`ClearAllTiles()` + 「平台区间表 `{起x, 止x, 格y}`」`SetTile` ⇒ 关卡设计变成**一张可读的表**；塔：2 面墙 + 11 层平台，共 **116 块瓦片**。改设计 = 改数字重刷（**幂等**）。
- ⭐⭐ **相邻两层的平台必须【在 x 上投影不重叠】** —— 这才是"交错"的硬定义（不是"左右轮流"）。
  - 为什么：净空 = 层间距 − 瓦片帽；相邻层一旦重叠，"往上跳"的**头顶**就被上一层占掉 ⇒ 平台在眼前却**跳不上去**，而且**不报错**。
  - 正确做法：把塔分成"左带 / 右带"，相邻层**换带**（中间只留 1 格缝），跳跃难度交给"层间距 2 / 4 交替"（2 格单跳够、4 格必须二段跳）。
- ⭐ **坐标账（今天实测钉死）**：**台面世界 y = 格 y + 0.8**。
  - 推演：瓦片锚点 `(0.5, 0.5)` ⇒ 格 `y` 中心 = 局部 `y + 0.5`；`Tilemap.localPosition.y = −0.2` ⇒ 世界中心 = `格y + 0.3`；顶面再加半格 ⇒ **`格y + 0.8`**。
  - 自证（两种，都在今天用过）：`GetCellCenterWorld(new Vector3Int(3,−4,0)) = (3.5, **−3.70**)`；**射线打点** `(3.5, −3.0) 向下 → 命中 −3.199983`。
  - ⚠️ 历史账：10-03 记的"格 y 顶面 = 格 y + 1"是在 **Tilemap 还没有 −0.2 偏移**时成立；10-08 加了偏移后**全部下移 0.2** ⇒ 以后一律按 `+0.8` 算，或**直接射线打点**（最省心）。
- ⭐⭐ **`CompositeCollider2D` 刷完必须显式 `GenerateGeometry()`** —— 否则**物理世界里的几何体还是上一批（甚至上一关）的**。
  - 实测铁证：刷完 116 块瓦片后立刻读，`composite.bounds = Center(6, −3.2) Extents(20, 5)` —— **那是 Level1 的 40×10 地形**；射线全部打空/打到旧地面。调 `GenerateGeometry()` 后变成 `Center(7.5, 10.8) Extents(7.5, 17)`（= 新塔），射线立刻全对。
  - ⭐ 判据：**渲染层（`SetTile`）与物理层（合成几何体）是两份数据** —— 眼睛看到的已经是新的，物理还在旧的。**"看不见的派生数据"必须显式刷新**。
  - 手法：`tilemapCollider.enabled = false → true` 再 `compositeCollider.GenerateGeometry()`（配合 `EditorApplication.QueuePlayerLoopUpdate()` + `Physics2D.SyncTransforms()`）。
- **视野参数反过来约束关卡设计**：本工程 `orthographicSize = 8` ⇒ 视野 **16 高 × 28.44 宽**（aspect 1.777）。塔宽取 **15 格**（< 28.44 ⇒ **水平居中**）、塔高 34 格（> 16 ⇒ **纵向跟随 + 夹取**）—— 正好把 10-08 写的那两条分支都走了一遍。
