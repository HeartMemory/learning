## 一、算法：`112` 路径总和

| 项 | 内容 |
|---|---|
| 题眼 | **「存在性递归」首题**：返回值第一次是 `bool`（问"有没有"而不是"是多少"）。与 104（返回数值）/ 110（返回元组）的分水岭 = **答案要不要从孩子那儿带回来** |
| 路线 | **油表**：入口就减 `remain − val`，到叶子判 `remain == val`（`targetSum` 不进递归） |
| 对照 | **里程表**：`acc + val`，叶子判 `acc == target` —— 每条路径都要多带一个参数 |
| 坑 ① | **"到叶子" ≠ "到空节点"**：空节点直接 `false`；写成 `remain == 0` 的话，"**空树 + target 0**"会误判成 `true` |
| 坑 ② | **remain 归零 ≠ 找到路**：中途归零但**还有孩子**的节点不是终点（`[1,2,null,3]` target 3 就是这种形状） |
| 复杂度 | 时间 **O(n)**（结果为 `false` 必须走遍；为 `true` 可能很早就短路停）；空间 **O(h)**，最坏 **O(n)**（斜链退化） |

### ⭐ 三条跨题可用的判据

1. **返回值的类型决定递归形状**：返回 `bool` = 存在性（用 `||` 短路）；返回 `int` = 计数/最值；返回元组 = 复合信息；返回集合 = 要把东西带回来。
2. **`||` 短路是"存在性"的自然表达**：换按位 `|`，**结果一样、代价不一样**（左边为真也不再探右边）。
3. **剪枝的合法性依赖数据范围**：值域含负数时，"和超过 target 就砍"是错的 —— 这条以后在回溯题里天天用。

### 用例设计判据

**期望值只能从"根到叶子的全部路径和"枚举得来，不能凭印象填。**

满树 `[1,2,3,4,5,6,7]` 只有 4 条根到叶子的路径：

| 路径 | 和 |
|---|---|
| 1 → 2 → 4 | 7 |
| 1 → 2 → 5 | 8 |
| 1 → 3 → 6 | 10 |
| 1 → 3 → **7** | **11** |

⇒ 要造"哪条都不通"的靶子，必须**避开 7 / 8 / 10 / 11 这四个数**（取 9 才对）。
⭐ 这条判据的价值不在本题：**凡是"路径 / 子集 / 组合"类题，期望值都该由枚举产生，而不是由直觉产生。**

## 二、Unity：Runner 第 5 步（音效 + 掉落判定）

### 一、复用清单（哪些原样搬、哪些必须改）

| 资产 / 配方 | 处理 |
|---|---|
| `PlayerAudio`（跳 / 落地 / 走路节拍） | **判据全复用**，只换数据源（2D 是 `MoveAxis` 标量 → 3D 是 `MoveInput` 向量，判据用 `sqrMagnitude`） |
| `SceneAudio`（BGM + 结算音） | 判据全复用（`timeScale = 0` 只冻物理、不冻音频）；Runner 没有"赢"⇒ 三个事件合并成一个 |
| `RunnerMixer`（Music / Sfx 两组） | 从已有工程的 Mixer 复制过来用（分组名一致，AudioSource 直接指过去） |
| 7 个音频素材 | 直接导入（跳跃 3 个随机 / 落地 / 走路 / 失败 / BGM） |
| **程序化 `Sfx.cs`** | 素材库没有金币音 ⇒ 用它造（1568 Hz、0.1 s、快速衰减） |

### 二、三处"照搬会出事"的 3D 改造

| # | 问题 | 做法 |
|---|---|---|
| ① | Runner 的 `PlayerController` **一个事件都没有** | 新增 `OnJumped` / `OnLanded` + `IsGrounded` / `MoveInput` 两个**只读出口**（数据只有本类能改，外面只能读或订） |
| ② | 3D 里没有"落地"这个事实 | 用**边沿**造：`_groundInitialized && _isGrounded && !_wasGrounded` ⇒ 触发。**首帧闸必须有**（原因见三句话复盘第 2 条） |
| ③ | 金币音不能挂在金币身上 | 改由 `ScoreManager`（常驻单例）代播 + **50 ms 节流**（成串吃金币时 `PlayOneShot` 会叠加削波） |

⭐ **判据（跨项目通用）**：**声音的生命周期不能依附于"即将被停用"的物体。**
同族反例：09-26 那次是"锁没罩住副作用"（每帧播 → 削波），这次是"宿主活不过一瞬间"（被禁用 → 掐断）。**两种病，同一个根**：没人管"这个音要活多久"。

### 三、`FailZone`：2D → 3D 要改三处

| # | 2D 原版 | 3D 版 | 不改会怎样 |
|---|---|---|---|
| 1 | `OnTriggerEnter2D(Collider2D)` | `OnTriggerEnter(Collider)` | 回调**永远不进来**，控制台一声不响 |
| 2 | `LayerMask playerLayer` 按层认人 | `other.GetComponent<PlayerController>()` | 本工程**没有 Player 层** ⇒ 永远吃不到 |
| 3 | 自检查"层有没有勾" | 改查 **`Is Trigger`** | 忘勾 = 触发器退化成实体挡板，玩家卡在空气上 |

### 四、碰撞检测四种模式（今日查证 · 官方 Manual）

| 模式 | 算法 | 适合 | 官方明确「不适合」 |
|---|---|---|---|
| 离散 Discrete | 每步只测"当前位置是否重叠" | 缓慢移动 | **快速移动**（会穿过去） |
| 持续 Continuous | 扫描式 CCD（把这一步的路径扫一遍） | 高精度的快速移动**线性**碰撞 | 因**刚体旋转**导致的碰撞 |
| 连续动态 Continuous Dynamic | 扫描式 CCD | 还要**与移动碰撞体**相撞的场景 | 因**刚体旋转**导致的碰撞 |
| 连续推测 Continuous Speculative | 推测式 CCD（预测下一位置） | 快速移动、且想省开销 | **需要很高精度**的某些快速碰撞 |

⭐ 三条判据：

1. **开销从低到高**：离散 < 连续推测 < 持续 < 连续动态（官方建议"从最小开始，不够再升"）。
2. **"持续"与"连续动态"的差别只有一处：对方会不会动。**
3. **三种 CCD 都救不了"转得太快"** —— 那要靠减小物理步长或提高角速度上限。

**本项目结论**：玩家保持「持续」。因为对手（地面 / 障碍 / 判定区）**全是静态碰撞体**，"连续动态"没有额外收益、只是更贵。

### 五、安全判据：触发器会不会被"穿过去"

$$v_{\max} \times \Delta t < \text{触发器厚度}$$

实测：掉落 5.5 米 ⇒ $v = \sqrt{2 \times 9.81 \times 5.5} \approx 10.4$ m/s，每物理步位移 $10.4 \times 0.02 = 0.21$ m，判定区厚度 1 m ⇒ **差 5 倍余量**。
⭐ 以后若加了加速下落 / 重力倍率，用这条式子重算（$v_{\max} < 50$ m/s 才安全）。

## 六、环境插曲（一句话备查）

`dotnet build` 全仓报 `MSB4018 / 找不到回退包文件夹` —— 根因不是代码，而是**机器级 NuGet 配置的残留**：装过两遍开发工具后，旧安装生成的 `fallbackPackageFolders` 仍指向已被删除的路径，卸载不会清理它。处置 = 移除那份残留配置（建空目录是等效的官方绕过法）。**判断依据**：错误出现在 `ResolvePackageAssets` 任务里、且与具体题目无关 —— 所有项目一起炸。
