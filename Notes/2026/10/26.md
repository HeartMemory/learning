## 一、算法：`367` 有效的完全平方数（二分线第 4 题）

**与 69 的分水岭**：69 找「最后一个 `k` 使 `k² ≤ x`」（边界问题），367 问「**有没有** `k` 使 `k² = x`」（存在性问题）。同一套二分，判定式换了。

### 1. 三版走的弯路与各自的病

| 版本 | 写法 | 病 |
|---|---|---|
| 初版 | `num / mid > mid` / `num / mid < mid` / 兜底 | 兜底把「`num/mid == mid` 但有余数」也当中了 ⇒ **多 1 全红** |
| 修正版 | 补 `num % mid == 0` 才算命中，兜底仍写 `hi = mid − 1` | 全绿，但**方向与事实相反**，只靠"夹缝里不可能有平方数"的数学巧合兜住 |
| 定稿版 | `q == mid && 余 0` / `q < mid → hi` / 兜底 `→ lo` | **三分支各对一条不等式**，可独立证明 |

### 2. 今天最值钱的一条判据

> **取整只往一个方向丢精度 ⇒ 误差窗口也只向一侧张开。**

`num = mid² − 1`（少 1）→ `⌊num/mid⌋ = mid − 1` ⇒ 走"太大"分支，**正确**；
`num = mid² + 1`（多 1）→ `⌊num/mid⌋ = mid` ⇒ 被当成命中，**误判**。

⇒ 症状指纹：**「一侧全红、另一侧全绿」= 取整窗口问题**，不必逐个用例调试。

### 3. 溢出这一关（比 704 凶）

| 事实 | 数值 |
|---|---|
| `46340²` | `2,147,395,600` ← int 内最大的完全平方数 |
| `46341²` | `2,147,488,281` > `int.MaxValue` ⇒ **回绕成负数** |
| `hi = num` 时首轮 `lo + hi` | `1 + 2,147,483,647 = 2³¹` ⇒ 回绕 ⇒ `mid = −1,073,741,824` |

**修法对照**：`hi = num/2+1`（把和压到 ~1.07e9，安全）｜ `lo + (hi − lo)/2`（**自足**，不依赖 `hi` 取值）｜ `(long)mid * mid`（精确比较，但不管 `mid` 的计算）。

⚠️ **"运气绿"的实证**：`mid` 为负时 `2147483647 → false` 仍然碰巧正确 —— 换分支方向后才发现原来一直在负区间里打转。

## 二、主线：Root Motion 判据（原排 10-27，今天提前）

### 1. 查证（先读官方，再动手）

Unity 6.3 LTS 三页：**Animator 组件页**（`Apply Root Motion` = "位置与旋转由动画控制还是由脚本控制"）、**How Root Motion works**（Body Transform = 质心 / Root Transform = 它在 Y 平面的运行时投影；三通道 `Bake Into Pose`；`gravityWeight` 由 Position Y 的 bake 驱动）、**OnAnimatorMove**（时机 = 状态机求值后、`OnAnimatorIK` 前；实现它 ⇒ 属性显示 `Handled by Script`；`deltaRotation` 是**累乘**）。

### 2. 证据（扒文件，不靠眼睛）

| 项 | 实测 |
|---|---|
| `PlayerArmature` | `applyRootMotion = False` · `MyThreeState` · `isHuman = True` · **CharacterController 有 / Rigidbody 无** |
| 在用 8 个剪辑 | 三通道 `rot = 1 / Y = 1 / XZ = 1` ⇒ **全部原地** |
| 唯一带位移的剪辑 | **`Run_S`（`rot = 0 / XZ = 0`）—— 且控制器没引用它** |

⇒ `Apply Root Motion = False` **本来就对**，当天不改任何文件。

🔍 查法：`.fbx.meta` 里的 `keepOriginalOrientation` / `keepOriginalPositionY` / `keepOriginalPositionXZ`，`1` = 烘焙 = 没有位移。**别信预览窗**（那演的是 body transform，任何剪辑都会动）。

### 3. A 实验：勾上之后四个现象，一条链

| 现象 | 解释 |
|---|---|
| 移动几乎不动 | 代码 `Move()` 写位移 → 同帧 Animator 把 `rootPosition`（≈ 起点）写回 ⇒ **每帧拽回** |
| 跳不高 | 跳跃的 Y 也是代码算的位移，同一条规则 |
| **走跑动画根本没播** | 位移被夺 ⇒ `CharacterController.velocity ≈ 0` ⇒ `_speed` 每帧从 0 重新起跳 ⇒ `Speed ≈ 0` ⇒ Blend Tree 停在阈值 0 的 `Idle` |
| 跳跃动画正常 | 驱动量是 **`bool`**（`Grounded` / `Jump` / `FreeFall`），与位移测量无关 |

### 4. 两条判据（写进 Unity 笔记第 38 章）

> ① **"姿势"与"位移"是两条独立通道，Root Motion 只夺位移、不夺姿势。**
> ② **但参数能把两条通道焊死** —— `float` 参数挂「实测位移」⇒ 位移的死顺着参数传导成动作的死；挂「意图」⇒ 只滑步。

**这是同一个决策的两面，不是两个 bug**：10-22 那笔「`_animationBlend` 改跟 `_speed`」消掉了"动作档位与实际速度脱钩"，代价就是今天看到的强耦合。
