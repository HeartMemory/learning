## 三句话复盘

1. **今天最大的收获**：**`lo` 是"缝的左岸"**。二分维护的从来不是"某个元素"，而是"左边全部小于 target、右边全部大于 target"的那条**边界**。证据是它自己的取值范围：`lo` 的合法值是 `0..n`（共 `n+1` 个），而"元素下标"只有 `n` 个 —— 多出来的那个位置上**没有元素**，所以它描述的必然是**空隙**。
2. **今天最大的教训**：**"位移对上"和"看起来不滑"是两件事**。先把数学那一半算清（阈值 = 设计速度时，"加权设计速度 ≡ `Speed` 参数"是**恒等式**）⇒ 位移速率其实零误差；排掉这一层之后，才看得见滑步真正来自**资产那一半**：姿势混合 ≠ 速度混合、两段动画的相位漂移。
3. **明天第一步**：把今天的三条"两个旋钮"判据讲一遍给自己听 —— **① 权重 vs 速率 ② 姿势 vs 位置 ③ 层 `Weight` vs 状态过渡**。讲不清的回去读笔记，再进 `34`（双边下界/上界）。

## 一、算法：`35` 搜索插入位置

### 1.1 与 `704` 的分水岭只有一行

| | `704` | `35` |
|---|---|---|
| 问什么 | 在不在 | **要是它在，该站哪** |
| 找不到时 | `return -1` | `return lo`（插入位置） |
| 循环体 | **一字不差** | **一字不差**（算 mid → 命中返回 → 砍掉含 mid 的一半） |

⭐ 题眼是一句**改写**：

> **答案 = 第一个 `>= target` 的下标**（下界 `lower_bound`）。

改写成这句之后，"命中"与"不命中"变成**同一种情况** ⇒ `-1` 那条分支根本不必写。

### 1.2 为什么一定是 `lo`（三层含义）

| 视角 | `lo` 是什么 |
|---|---|
| 数值上 | 一个下标，合法范围 **`0..n`**（是 `n`，不是 `n−1`） |
| 循环中 | "**已确认全部 `< target` 的那一截**的右边界 + 1" |
| **退出后**（必有 `lo = hi + 1`） | **第一个 `>= target` 的下标** |

**证明（不变量法）**：始终维持

> `nums[0 .. lo-1]` 全部 `< target`，且 `nums[hi+1 .. n-1]` 全部 `> target`。

- 初始：两个区间都是**空集** ⇒ 恒成立
- `nums[mid] < target` ⇒ 因**有序**，`nums[0..mid]` 全小 ⇒ `lo = mid + 1`
- `nums[mid] > target` ⇒ 同理 `nums[mid..n-1]` 全大 ⇒ `hi = mid - 1`
- 退出时 `hi + 1 = lo`，代回不变量 ⇒ **`nums[lo..n-1]` 全 `> target`**

两侧一夹：**lo 左边全小、lo 本身及右边全大** ⇒ target 若存在只能在下标 `lo` 上；既然前面命中就 `return` 了，走到这里说明它不存在 —— 但它"该在的位置"仍然是 `lo`。

### 1.3 三条硬判据

1. **`lo` 的合法值是 `0..n`（`n+1` 个），元素下标只有 `n` 个** ⇒ 它描述的是空隙，不可能是元素。
2. **两端不用任何特判**：比全体都小 ⇒ `lo` 原地不动 = `0`（左区恒空）；比全体都大 ⇒ `lo` 一路推到 `n`（右区恒空）。这是"**空区间也满足不变量**"的直接后果，与 `704` 里"空区间一行盖住没找到与递归到底"同源。
3. ⚠️ **不是 `hi`，不是 `mid`**：
   - `hi = lo − 1` 指向"**最后一个** `< target` 的元素"，插入位置在它**后面一格**
   - `mid` 是被判过侧别、**已经划掉**的点，只有命中那一刻它才是答案

### 1.4 自查尺子（证明"真懂了"）

把 `return mid` 删掉，只留两条分支：

```csharp
while (lo <= hi) { mid = ...; if (nums[mid] < target) lo = mid + 1; else hi = mid - 1; }
return lo;
```

| 问题 | 答案 |
|---|---|
| 查**存在**的元素（如 `[1,3,5,6]` 查 5）还返回 2 吗 | **是**。`==` 走 `else` 分支 ⇒ `hi = mid - 1` ⇒ `lo` 照样收敛到 2 |
| 为什么 `return mid` 只是"抄近路" | 因为 **`lo` 本来就是答案**，早返回只是少跑几轮 |

⭐ 顺带钉死：**`upper_bound`（第一个 `> target`）只需把 `<` 换成 `<=`**，其余一个字不动。

### 1.5 判题器（承 `704` 的教训继续加固）

| 设计 | 内容 |
|---|---|
| 期望值**双来源** | 官方示例与关键边界**硬编码**；规模用例由**独立线性下界** `NaiveLowerBound` 现算（它 O(n)、只算期望值、**不进版本表**，否则 Bench 变成自己跟自己比） |
| 反例区 | 四种错法各自点名：`return -1` / `return mid` / `while (lo<hi)` 混闭区间 / 线性扫描 |
| Bench 对账 | **两条 sink 必须相同**（实测 `100000000 vs 100000000`）= 对 4 万次查询返回**同一个下标**，比"各自都用例过了"更硬；本机二分 ≈ 0 ms vs 线性 **96 ms** |

## 二、Unity

### 2.1 动画事件：官方怎么说（查证结论）

| 结论 | 出处 |
|---|---|
| `AnimationEvent` 类似 **`SendMessage`**，按**函数名字符串**查找并调用 | Scripting API |
| 回调**只能 0 或 1 个参数**，类型限 `float` / `int` / `string` / 对象引用 / `AnimationEvent` | Scripting API |
| `animatorClipInfo` / `animatorStateInfo` 是**只读上下文**，运行时由引擎填充 | Scripting API |
| 事件在 clip 的 `time` 处触发；两种添加方式：**动画窗口** / `clip.AddEvent()` | Scripting API + Manual |

⭐ 由此得到一条判据：**函数名拼错不会在编译期报错**，只会在运行时**静默不触发** —— 这是"数据层错误"的典型形态。

### 2.2 侦察结果：脚步声其实早就配好了

| 项 | 实测 |
|---|---|
| 事件 | `Walk_N` 两条 `OnFootstep`@**0.31 / 0.77**；`Run_N` 两条@**0.21 / 0.54**；`JumpLand` 一条 `OnLand`@0.10 |
| 素材 | `Player_Footstep_01~10.wav` **10 个已填进数组**，`Player_Land` 已填 |
| 接收端 | `ThirdPersonController` 里两个 `private void OnFootstep/OnLand(AnimationEvent)` |
| 判据 | `animationEvent.animatorClipInfo.weight > 0.5f` |

⇒ **这套是 Starter Assets 自带的 demo，不是技术债**。两个副作用值得记：

1. **Blend Tree 里多个 clip 同时播 ⇒ 每个 clip 的事件都会触发** ⇒ 必须按 `weight` 过滤，否则走跑交叉区步点密度翻倍。
2. `> 0.5` 是**硬阈值**：权重恰为 0.5 那一瞬两边都不通过 ⇒ **该步静音**（时间极短，几乎听不出）；真正能听出的是交叉区两个 clip 各响一遍。

### 2.3 手写状态机 vs Animator（数据层 vs 代码层）

| 维度 | 手写（`Dictionary<Type, StateBase>`） | Animator（`.controller`） |
|---|---|---|
| 状态的载体 | C# 类 | **资产文件**（YAML 序列化） |
| 谁能改 | 只有程序员 | 策划 / 美术也能改 |
| **错误暴露时机** | **编译期** | **运行时（静默）** |
| 能否混合 | ❌ 只能 A→B 跳变 | ✅ Blend Tree |
| 查"当前状态" | `O(1)` 读字段 | 字符串匹配 + 滞后一帧 |

⭐ 两条对照发现：

- 那份手写草稿里 `StateBase.Destroy()` 与 `StateMachine.Stop()` 的 `Destory()` **拼写不一致** ⇒ **它从未编译通过**；而 Animator 配错了只在运行时表现为"动画抽搐"。
- `if (currentState.GetType() == typeof(T)) return;` 正是 `Can Transition To Self` 的**代码版** —— 差别是：手写时你必须自己想到写它，Animator 里它是个**默认开着的开关**。

⭐ 收口判据：**代码状态机 = 一个 `currentState` 变量（互斥）；Animator = 一个权重向量（可并存）**。前者表达力强，后者能混合、可视化、非程序员可改 —— 所以"半走半跑"只有后者能表达。

### 2.4 手柄模拟幅度与 `MotionSpeed`

| 现象 | 根因 |
|---|---|
| 摇杆轻推 / 推满**只有两档** | `StarterAssetsInputs.analogMovement` 默认 `false` ⇒ `inputMagnitude` **恒为 1** |
| 打开后仍看不出变化（键盘） | 键盘的 `move` 恒为 `(±1, 0)` 等 ⇒ `|move| = 1` ⇒ 乘 1 等于没乘 |

⚠️ 打开 `analogMovement` 有个副作用：**键盘斜向（`(1,1)`）的 `|move| = 1.414` ⇒ 斜着走快 41%**。所以它是"为摇杆准备的开关"，纯键盘方案下反而是错的。

### 2.5 ⭐ 自己发现并修复的 bug：动作档位与真实速度脱钩

**症状**：手柄轻推 + 按住冲刺 ⇒ 播**跑步动画**，但人走得比普通走还慢。

**根因**（两行的目标不同源）：

```csharp
_speed          = Lerp(current, targetSpeed * inputMagnitude, ...);   // 乘了幅度 ✅
_animationBlend = Lerp(current, targetSpeed,                ...);   // 没乘幅度 ❌
```

| 量 | 值 |
|---|---|
| 实际速度 | `5.335 × 0.5` = **2.67** |
| `Speed` 权重参数 | **5.335** ⇒ `Run_N` 权重 0.89（选了跑步动作） |
| `MotionSpeed` 速率 | 0.5 ⇒ 动画位移速率 = 2.67（**不滑步**） |

⇒ **不滑步，但"走的速度配跑步的动作"**。修法：`_animationBlend` 的目标改成 **`_speed`**（真实水平速度）。

⭐ 修完之后的一个**预期行为**：**对着墙推 W 时 `_speed ≈ 0` ⇒ 播 `Idle`（站着）** —— 旧实现会一直播跑步动画（腿在墙边空蹬）。

### 2.6 滑步三层根因（登记技术债，本次未修）

权重侧其实**零误差**：阈值 = 设计速度时，`加权设计速度 = 2 + 4t = Speed` 是**恒等式**。所以真根因在别处：

| # | 根因 | 表现 |
|---|---|---|
| ① | **姿势混合 ≠ 速度混合** | 混的是**骨骼姿势**；`Idle` 权重 0.9 = 90% 骨骼原地站着，人却在移动 ⇒ **轻推像平移**（最痛） |
| ② | **相位漂移** | `Walk_N` **0.97 s** / `Run_N` **0.67 s** 各自循环 ⇒ 权重 0.5 时一段迈左脚、另一段可能在迈右脚 ⇒ 互相抵消 ⇒ 中间速度打滑 |
| ③ | **`Lerp` 滞后** | `_animationBlend` 追 `_speed` 有 **0.1 s** 延迟 ⇒ 起停瞬间不同步 |

治本方向（三条，等触发）：**加密采样点**（`Walk 2 → Jog 3~4 → Run 6`，线性插值误差 ∝ 采样间隔² ⇒ 区间减半误差降到 1/4）/ 相位对齐（相邻档位循环长度成整数比）/ `Idle` 移出混合树 + 低速按 `_speed / MoveSpeed` 缩速率。

### 2.7 🆕 今天的主菜：`Layer` + `Avatar Mask` + 层权重

#### ① 官方语义（两条独立来源一致）

| 结论 | 出处 |
|---|---|
| **Layer = 一层独立的状态机**；`Mask` 划定"这层对哪些部位有**写入权**" | Manual「Animation Layers」 |
| 官方给的例子就是 **下半身走 + 上半身射击/投掷** | Manual「Animation Layers」 |
| Humanoid 用**人体图**勾选（绿=包含、红=排除）；`Transform` 方式需 Avatar 引用 + `Import Skeleton` | Manual「Avatar Mask」 |
| 遮罩还能**省内存与 CPU**（未激活部位的曲线不算） | 同上 |

#### ② 遮罩的目标状态（唯一的判据）

| 图上的位置 | 枚举名 | 目标 |
|---|---|---|
| 脚下阴影 | `Root` | 🔴 红 |
| **胸腹（躯干）** | **`Body`** | 🟢 绿 |
| 头 | `Head` | 🟢 绿 |
| 左/右臂 | `LeftArm` / `RightArm` | 🟢 绿 |
| 左/右手 | `LeftFingers` / `RightFingers` | 🟢 绿 |
| 左/右腿 | `LeftLeg` / `RightLeg` | 🔴 红 |
| 手腕 IK | `LeftHandIK` / `RightHandIK` | 🟢 绿 |
| 脚踝 IK | `LeftFootIK` / `RightFootIK` | 🔴 红 |

⭐ **躯干（`Body`）必须勾绿**：不勾的话射击动作只有手臂在动、躯干不转，看起来像"胳膊自己举起来"。而 `Body` **不含腿**，所以勾它安全。

#### ③ 三个配置陷阱（都实测撞到）

| 陷阱 | 后果 | 正确做法 |
|---|---|---|
| `Animation Type = Humanoid` 时 **`No Avatar` 不可选**（灰掉） | 不是 bug —— Humanoid 的一切能力（重定向 / 人体图遮罩 / IK）都建立在 Avatar 上 | 选 `Create From This Model` |
| **两套不同骨架不能用 `Copy From Other Avatar`** | 那个选项只适用"同一 rig 换 mesh" | 用 `Create From This Model` 让它自己建 |
| **`Override` 层是空状态机** | 遮罩区被写成**默认姿势（T-Pose）** | 层里**必须有状态** |

#### ④ 骨骼自动映射结果（可核验的判据）

导入设置：`Animation Type = Humanoid` + `Create From This Model` ⇒

| 判据 | 实测 |
|---|---|
| `Avatar.isHuman` | `True` |
| 52 个 `human` 槽位里空 `boneName` 数 | **0** ⇒ **没有任何红叉** |

#### ⑤ ⭐ 核心判据：`Weight` 管"这层存不存在"，过渡管"层内播哪一段"

| 你要控制 | 用什么 |
|---|---|
| 举枪 / 不举枪（**这层要不要生效**） | **层权重 `Weight`**（0 ↔ 1 平滑过渡） |
| 举枪 ↔ 开火（**层内换动作**） | 状态过渡 |

⚠️ 用状态过渡做"不举枪"是错的：那个 `Lower` 状态会**持续写上半身姿势**（Idle 的上半身）⇒ 跑动时不摆臂，反而不自然。`Weight = 0` 则这层彻底不参与，Base 层正常摆臂。

#### ⑥ 上身会晃是正常的（姿势 vs 位置）

| 东西 | 由谁决定 | 第 2 层能改吗 |
|---|---|---|
| **姿势**（脊柱、手臂的旋转曲线） | 第 2 层 | ✅ |
| **位置**（骨盆起伏、左右微摆） | **Base 层的 `Run_N`** | ❌ **改不了** |

⇒ 上半身姿势钉住了，但它挂在还按跑步动画起伏的**骨盆**上 ⇒ 整个人被"抬着晃"。

⭐ 判据：**Layer 叠加的是「姿势」，不是「物理」；位置与根运动永远来自 Base 层。** 想更稳只能：瞄准降速 / `Additive` 偏移层（Aim Offset）/ Spine IK。业界主流是前两条。

### 2.8 `UpperBodyAim`（自己写的第一个"分层控制"脚本）

```csharp
bool isHolding = Mouse.current != null && Mouse.current.rightButton.isPressed;
float targetWeight = isHolding ? 1f : 0f;
_currentWeight = Mathf.MoveTowards(_currentWeight, targetWeight,
                                   Time.deltaTime * (isHolding ? _fadeInSpeed : _fadeOutSpeed));
_animator.SetLayerWeight(_upperBodyLayer, _currentWeight);
```

三条判据：

| # | 判据 |
|---|---|
| ① | `MoveTowards` + **`deltaTime × 速度`** = **帧率无关的匀速**推进；换 `Lerp(a, b, dt*k)` 会**永远逼近不到**目标 |
| ② | `Mouse.current` **必须判空**（设备可能不存在），且官方要求 |
| ③ | 输入走**新输入系统设备层**（`Mouse.current`），旧 `Input.GetMouseButton` 会抛 `InvalidOperationException` |

### 2.9 两条输入 API 的分工
