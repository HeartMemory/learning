### 一、算法：`108` 将有序数组转换为二叉搜索树（BST 第 3 题）

- **BST 一条线的第三站**：`98` **查**（这棵树合不合法）→ `700` **找**（在里面搜一个值）→ `108` **造**（按规则长出一棵）。前两题在"读"，本题在"写"。
- ⭐ **题眼**：有序数组的**中点天生是分界线**（比它小的全在左、比它大的全在右）⇒ 放在根上 **BST 不用算就成立**；而"取中点"还顺手把**高度**顶到最优（每层对半分 ⇒ `⌈log2(n+1)⌉`）—— **一个选择同时满足两个要求**。
- ⭐⭐ **与之前 11 题的根本区别：答案不唯一** ⇒ 判题器**不能**照抄 `700` 的"期望序列化比对"（会把正确答案判成 ❌）
  - 本题改用**性质裁判**：① 中序 == 输入数组 ② 每个节点 `|左高 − 右高| ≤ 1` ③ 合法 BST ④ 节点数 == 数组长度
  - 收口一条元认知：**「判题器长什么样」由「答案唯不唯一」决定**（唯一 ⇒ 比对；多解 ⇒ 比性质）
- **结构承 `101`**：主签名 `(int[] nums)` 装不下 `(lo, hi)` ⇒ **必须开 helper**（wrapper + 内核）
- **终止条件 = 空区间** `lo > hi` ⇒ 一行盖住"空数组 / 空孩子"两个入口 ⇒ wrapper 里的 `nums.Length == 0` 特判**因此可以删掉**（承 `104`）
- ⭐⭐ **今天最贵的一笔（三轮栈溢出换来）**：
  - 错法 `mid = (hi − lo) / 2` ⇒ 右孩子 `(mid + 1, hi)` 在 `lo=0, hi=1` 时算成 `(1, 1)`…而 `mid = 0` ⇒ 右孩子退回 **父区间本身** ⇒ 永不落地
  - 为什么三轮才发现：**第一层永远 `lo = 0`**，那时两个公式**结果相同**
  - ✅ 判据：**单元素区间 `[x, x]` 的中点必须就是 `x`**（只有它能让左右孩子双双为空）
- ★ **第二个洞**：**根吃掉的 `mid` 孩子一口不能碰** ⇒ 左右区间必须**跨过**它（左 `(lo, mid−1)` / 右 `(mid+1, hi)`）；两个孩子都用 `mid` ⇒ 区间重叠 + 右孩子可能**等于父区间**
- **形状实测**：n = 4,095 → 树高 **12** ＝ 最优；n = 262,143（2^18−1）→ 树高 **18** ＝ 最优、**6 ms**
- **退化对照**：同一批 262,143 个元素，若"每次取端点当根" ⇒ 建出 **262,143 层**的右斜链（差 26 万倍）⇒ ⭐ **BST 的 O(log n) 全靠「高度」这一件事撑着**（`700` 结尾"平衡树存在的理由"，今天从「查」换到「造」）
- ★ 判题器③顺带钉死：**「高度平衡」（`|左高−右高| ≤ 1`）不要求「节点数平衡」** —— 取中点两样都白拿
- ⚠️ 复杂度：时间 O(n) / 空间 O(h)；若用 `Array.Copy` 切数组会多付 O(n log n) 拷贝

**② 导入设置：判据 = 音频有两种读法**
| 读法 | 特点 | 谁用 |
|---|---|---|
| 进内存（`Decompress On Load`） | 播放**零延迟**、吃内存 | **音效**（短、一秒可能响好几次） |
| 边播边读（`Streaming`） | **省内存**、有解码开销 | **BGM**（3.4 MB、播几分钟、只 1 个实例） |

**③ `AudioMixer` 两条分组（`Music` / `Sfx`）**
- ⭐ 判据：**"音量"这个属性只能有一个写入者** ⇒ 音量交给 Mixer 管，`AudioSource.Volume` 一律保持 `1`
- 层结构：`AudioMixer`（调音台）→ `AudioMixerGroup`（几路推子）→ 每个 `AudioSource` 的 **`输出`** 槽（线插哪路）
- 顺带：Mixer 的改动**是写进 `.mixer` 资产的**，读盘确认后**不必**点「文件 → 保存项目」

**④ 播放策略三分法**
| 音 | 怎么做 | 为什么 |
|---|---|---|
| **BGM** | `loop` + `PlayOnAwake` —— **免脚本** | 场景一加载它自己就播 |
| **跳 / 落地** | 挂在 `PlayerController` **已有的两个分支**上（起跳分支 / 接地上升沿） | ⭐ **天然每件事只响一次**，不需要计时器、不需要去重 |
| **走路** | **节拍式**：计时器把"持续在走"切成"每隔 `stepInterval` 踩一次" | ⭐ 判据 **"踩地是事件，不是状态"** |

- ⛔ **走路音的反面**：`if (在走) PlayOneShot(step)` = 每物理步播一次 = 一秒 50 次叠加 → **削波刺耳**（09-26 "锁必须罩住副作用"的直系亲属）
- ⭐ 两个细节判据：**不在走要归零**（下次起步第一声**立刻**响，而不是等完上一轮剩的间隔）；**到点重置为满**（`+=` 会把误差累积成漂移）
- ⚠️ 用 `Time.fixedDeltaTime`（本方法跑在物理时钟里），不是 `deltaTime`
- `Random.Range(int, int)` 是**左闭右开** ⇒ 上限传 `Length`（传 `Length - 1` 则最后一个永远抽不到）；⚠️ 同名重载 `Range(float, float)` 却是**闭区间**

**⑤ `timeScale` 的影响力半径 · 另一面**
- `GameManager` 结束游戏时 `Time.timeScale = 0f` —— 那**只冻物理**
- ⭐ **`AudioSource` 跑在实时时钟上，根本不吃 `timeScale`**（与 `Animator` 默认**吃**正好相反）⇒ 世界冻结时 **BGM 会一直播下去**
- ⇒ 判据：**"世界冻结"这个动作，不会替你把声音停了** —— 每个想跟着停的东西都得**自己订阅"结束"**

**⑥ 订阅的判据（`SceneAudio`）**
- **"停 BGM"订 `OnGameEnded`**（与**怎么结束**无关）；**"播哪个结算音"订 `OnGameOver` / `OnGameWin`**（这里**必须**区分具体原因）—— 同一份代码里两种订阅并存，正好把 10-07 那条判据的两面各演一遍
- ⭐ **预制体不能引用场景对象** ⇒ BGM 拿不到场景里的 `GameManager` ⇒ **只能用单例**（与 10-06 敌人**完全同构**）
- ⭐ 而 `Awake` / `OnEnable` 的跨对象顺序**不确定** ⇒ **订阅要放 `Start`**（所有 `Awake` 跑完之后）
- 退订用 **`OnDestroy`**（场景物体是"被销毁"，不是"被禁用"）

**⑦ ⚠️ 同一物体上两个同类组件 = 一个陷阱**
- `GetComponent<AudioSource>()` 返回哪一个**是未定义的**
- 而且 Inspector 的组件引用标签是 **`<物体名> (<类型名>)`** ⇒ 两个都显示 `BGM (Audio Source)`，**肉眼分不出**
- ⇒ **两个都靠拖引用**，且要**从「检查器」拖组件标题条**、**不要从「层级」拖物体**（拖物体时选哪个同类组件是未定义的）
- ⭐ 判据：**"平局不可靠"**（承 10-05 `Order in Layer`）；根治手法 = **让它们各有各的家**（把结算音那个 `AudioSource` 挪到子物体上 ⇒ 标签立刻可辨）

**⑧ ⭐⭐ "换关没声"的根因（今天最后抓到的）**
- 实测：`PlayerAudio` 脚本在 **Level1 = 0 / Level2 = 0 / Level3 = 1** 处引用
- 根因：**`BGM` 是 Prefab（三关一致）；`PlayerAudio` 不是** —— `Player` 是三关各一个的**独立物体**
- ⇒ 判据：**"三个场景要一模一样的东西，就该是 Prefab"**（不是 Prefab 的，每加一处改动就得重复三次，漏一次就出现"换关掉音"）
- 当晚处置：先用**最简单无风险**的办法补齐两关；**把 `Player` 提成 Prefab 记入待办**（⚠️ `PlayerController.gameManager` 是**场景引用**，Prefab 存不了 ⇒ 三关各要**重拖一次**）
