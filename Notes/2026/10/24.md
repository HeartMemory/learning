## 一、算法：`69` x 的平方根

### 1.1 与 `34` / `35` 的映射

| | `35` | `34` | `69` |
|---|---|---|---|
| 有序数据哪来的 | 别人给的 `nums` | 别人给的 `nums` | **自己造的**（`k` 天生升序） |
| 元素的值 | `nums[i]` | `nums[i]` | **`k * k`** |
| 找什么 | 第一个 `≥ target` | 两条边界 | **最后一个 `k` 使 `k² ≤ x`** |

⭐ 一句话：**`upper_bound(x) − 1`** —— 与 `35` 的"下界"同一个模板，只差一个比较符。

### 1.2 唯一的新东西：判定式的**定义域**

| 写法 | 数学上 | 实际 | 崩在哪 |
|---|---|---|---|
| `mid * mid <= x` | 对 | ✗ **静默错** | `mid = 46341` ⇒ `2147488281` 溢出成负数 ⇒ `负数 <= x` 恒真 ⇒ 越收越远，**不报错** |
| `mid <= x / mid` ✅ | 等价（整数除法下 `floor(x/mid) < mid ⟺ x < mid²`） | ✓ | `mid = 0` ⇒ **除零** |
| 压 `hi = x/2 + 1` | 缓解 | 部分 | 压不干净（`x = 2` 还要特判） |

### 1.3 两种收缩风格（初版四个病的根都在这张表上）

| | 风格 α「闭区间、排除 mid」 | 风格 β「半开、只缩不排」 |
|---|---|---|
| 条件 | `while (lo <= hi)` | `while (lo < hi)` |
| `mid` | `(lo + hi) / 2`（下取整） | `(lo + hi + 1) / 2`（**必须**上取整） |
| 循环体 | 合格 `lo = mid + 1` ／ 不合格 `hi = mid - 1` | 合格 `lo = mid` ／ 不合格 `hi = mid - 1` |
| 退出后 | `hi` = 最后满足，`lo` = 第一个不满足 | `lo == hi` = 答案 |

⭐ 判据：**哪条分支写了 `lo = mid` / `hi = mid`，取整方向就必须让 `mid` 不等于那一端** —— 否则区间一格没缩 = 死循环。

### 1.4 初版四个独立病（`dotnet run` 一次只暴露一个）

| # | 病 | 症状 |
|---|---|---|
| ① | `if` 当 `while` | 只问一次问题（`x = 10⁶` 要 20 轮） |
| ② | `lo = mid` / `hi = mid` 不排除 `mid` | `x = 8` 走到 `lo=2, hi=3` 原地打转 |
| ③ | `mid = 0` 时 `x / mid` | **除零崩**（`x = 1` 直接抛异常，崩在判题器防线） |
| ④ | `return lo` 配"命中即返回" | 差一（`x = 8` 给 3，答案 2） |

### 1.5 判题器：这次**故意不做性能探针**

判据可算，不是"我觉得"：`x ≤ 2³¹` ⇒ 答案上界 **46340** ⇒ 就算线性枚举也是微秒级，**硬比只会得到一个假差距**（`34` 的探针教训刚好相反：那题必须靠探针才照得出线性段）。

改用的两件：

| 探针 | 内容 | 结果 |
|---|---|---|
| A 全量对账 | `0 ~ 300000` 逐 x 与独立来源（浮点开方 + 双侧校正）比对 | **0 错**，两条 `sink` 均 `109395077`，10.8 ms |
| B 端点区 | `46340² ± 1`、`int.MaxValue` | `46339 / 46340 / 46340 / 46340` 全对 |

19 项 **19/19 全绿**。一个反直觉但**合法**的写法留档：`mid == x / mid` 时直接 `return mid` —— 它覆盖 `mid² ≤ x < mid² + mid` 的**一整段**（如 `mid = 2` 覆盖 `x ∈ [4,5]`），不只完全平方数；但**不可移植到 `34`**。

## 二、Unity：动画事件实测

### 2.1 先纠一条误判

"本会话看不到 `unityMCP` 工具" —— 这是**没实测就下的结论**。实际调 `manage_scene(get_build_settings)` 直接返回了场景列表 = 桥一直通。⇒ 判据：**"看不到"要和"连不上"分开验**，先调一次只读动作再下结论。

### 2.2 侦察：这关的三层**早就通了**

| 层 | 实情 |
|---|---|
| 事件 | 写在 **FBX 的 `.meta`** 里（不在 `.anim` 里）：`Walk_N` / `Run_N` / `Run_S` 各 **2 条 `OnFootstep`**；`JumpLand` / `Walk_N_Land` / `Run_N_Land` 各 1 条 `OnLand` |
| 处理函数 | `ThirdPersonController.cs` 里已有 `OnFootstep` / `OnLand` |
| 音频槽 | `LandingAudioClip` + **10 个** `FootstepAudioClips` + `FootstepAudioVolume = 0.3` 全部接好 |

⇒ **本关不是"做出来"，而是"量出来"**：新建 `FootstepProbe`（只打日志、不碰 `AudioSource` ⇒ 不双声），把混进混合树的事件全部打出来。

### 2.3 实测数据（两轮一致）

| 状态 | 主导剪辑 | 权重 | 间隔/步 |
|---|---|---|---|
| 走 | `Walk_N` | 0.93 – 1.00 | **0.48 – 0.51 s** |
| 加速起步 | `Walk_N` 权重渐升 | 0.14 → 0.48 | 3.85 → 0.86 s（渐密） |
| 稳态跑 | `Run_N` + `Walk_N` | **0.83 / 0.17** | **0.34 – 0.38 s**（配对仅差 **0.002 – 0.008 s**） |
| 减速回走 | `Walk_N` | 0.42 – 0.99 | 0.53 – 1.17 s |

### 2.4 三条判据（都有数字撑着）

1. **混合树同步相位** ⇒ 同一拍上多个剪辑各喊一次 ⇒ 配对间隔 0.002–0.008 s。
2. **`weight > 0.5` 是去重器，不是优化**：跑着落地**一次**收到两条 `OnLand` ——

   | 时刻 | 剪辑 | 权重 |
   |---|---|---|
   | 25.67 s | `Walk_N_Land` | **0.17** |
   | 25.67 s | `Run_N_Land` | **0.83** |
   | 26.79 s | `JumpLand` | **1.00**（原地落地） |

   去掉门卫 ⇒ **落地音播两遍**，还两种音色。
3. **步频挂钩"混合后的剪辑周期"，不挂钩角色速度**：走 0.48 s/步 → 跑 0.34 s/步 只快 **1.4×**，而速度 `2.0 → 5.335` 是 **2.67×** ⇒ 缺口只能由**步幅**补，补不上就是滑步（正好接明天的 Root Motion 判据）。

### 2.5 顺带查清：`JumpLand` 是一棵按 `Speed` 混合的子树

| 阈值 | 剪辑 | 什么时候用 |
|---|---|---|
| 0 | `JumpLand`（`Jump--Jump.anim.fbx` 内，与该 FBX 里的 `JumpStart` 是**两个剪辑**） | 原地落地 |
| 2 | `Walk_N_Land` | 走着落地 |
| 6 | `Run_N_Land` | 跑着落地 |

⭐ **落地播哪条由"落地瞬间的速度"决定** ⇒ `OnLand` 天生"一名多源"。

### 2.6 「16.6% Walk 混权」升级为实测事实

| | 理论（10-23 手算） | 实测（今天） |
|---|---|---|
| Run 权重 | `(5.335 − 2) / (6 − 2)` = **0.834** | **0.83** |
| Walk 权重 | **0.166** | **0.17** |

跑步时 `Walk_N` 的脚印事件**每拍都在发**，只是被门卫挡住 ⇒ **听觉无损**，但"来源"确实混着。⇒ 这条降级为 **"可用已知偏差，不急着修"**，等手感打磨时连同阈值一起调。
